## この章で学ぶこと

博士：ノード君、第7章では「つながらない」を、下の層から順に確かめる方法を学んだな。`ip addr` でアドレスを見て、`ping` で届くかを試し、`ss` で待ち受けを見て、`curl -v` で最後まで確かめる。

ノード：はい！ あれで、だいぶ切り分けられるようになりました。

博士：では、こんな相談が来たらどうする？「ping は通る。サーバーで `ss` を見ると、443番で待ち受けている。なのに `curl https://www.example.com/` は、しばらく待たされた末に失敗する」。

ノード：え〜っと……どれも「大丈夫なはず」に見えますね。どこを見ればいいんだろう。

博士：そこなのだ。設定や状態を見るコマンドが教えてくれるのは、「こう動くはず」という予定だ。この章では、その一歩先へ進む。ケーブルの上を **実際に流れたもの** を記録して、読むのだ。

ノード：実際に流れたもの……。パケットそのものを見る、ってことですか？

博士：うむ。そうして記録したものを **キャプチャ** と呼ぶ。キャプチャを読めるようになれば、「接続の申し込み（SYN）はサーバーに届いているのに、サーバーが返事を出していない」のように、推測ではなく事実で話せるようになる。

### この章が答える問い

- 「つながらない」とき、実際には何が流れ、何が流れなかったのか。それをどうやって確かめ、どう人に伝えるのか。

### 読み終えるとできること

- どこで記録を取るか（この章では **観測点** と呼ぶ）を選び、そこで何が見えて何が見えないかを説明できる。
- 記録したフレームを、一覧 → 層ごとの表示 → 生のバイト列 の順に、外側の層から読める。
- TCPのフラグと Seq / Ack から接続の始まり・データ・終わりを追い、DNS・HTTP・TLS で何が読めて何が読めないかを説明できる。
- 必要な通信だけに絞り込み、RST・SYNの再送・NXDOMAIN・ICMPのエラーから、失敗した場所を絞り込める。
- 観測した事実と、そこから考えた仮説を分けて報告できる。

### 前提

この章は、これまでの章で学んだことを「記録の上で確かめる」章です。次の言葉は、出てきたところで短く思い出してもらいます。

- 第1章: カプセル化、TCPとUDP、ポート番号、3-way handshake、TCPのフラグ（SYN・ACK・FIN・RST）
- 第3章: Default Gateway、TTL
- 第4章: MACアドレス、スイッチの転送、ARP、VLAN
- 第5章: DNSの問い合わせと応答、NXDOMAIN
- 第6・7章: Firewall の DROP と REJECT、`curl`・`dig`・`ss`・`systemctl` などのコマンド

### この章の例のネットワーク

博士：この章では、ずっと次のネットワークを使う。PCが1台、LANのDNSサーバーが1台、ルータの向こうにWebサーバーが1台だ。

```text
          LAN1  192.168.1.0/24                          LAN2  192.168.2.0/24

  PC1   192.168.1.10 ───┐
                        SW1 ──── g0/0 [ R1 ] g0/1 ──────── WEB  192.168.2.80
  DNS1  192.168.1.53 ───┘     192.168.1.1   192.168.2.1         nginx（80番・443番）
```

| 機器 | 役割 | IPアドレス | MACアドレス |
| --- | --- | --- | --- |
| PC1 | 調べる側のPC。Default Gateway は 192.168.1.1、DNSサーバーは 192.168.1.53 | 192.168.1.10/24 | 02:00:00:01:00:01 |
| DNS1 | LANのDNSサーバー。`example.com` の名前を管理する | 192.168.1.53/24 | 02:00:00:02:00:01 |
| SW1 | L2スイッチ | なし | （中継するだけ） |
| R1 | LAN1とLAN2をつなぐルータ | g0/0 192.168.1.1/24、g0/1 192.168.2.1/24 | g0/0 02:00:00:04:00:01、g0/1 02:00:00:04:00:02 |
| WEB | Webサーバー `www.example.com`（nginx） | 192.168.2.80/24 | 02:00:00:05:00:01 |

博士：PC1 で `curl http://www.example.com/` を実行すると、PC1 はまず DNS1 に名前を問い合わせ、それから R1 を通って WEB に接続する。この1回の curl の中に、ARP・DNS・TCP・HTTP がすべて入っている。この章では、このやり取りを1つずつ、最後はバイト単位まで読んでいく。

ノード：1回の curl に、そんなに入ってるんですね。

博士：Simulation でも同じネットワークを使う。ただし、最初は「`www.example.com` が開けない」状態にしてある。キャプチャで失敗の形を読み、原因を1つずつ直して、直ったこともキャプチャで確かめるのだ。

> **シミュレータ**
> MACアドレスは、このシミュレータが機器に割り当てる値（`02:00:00:…`）です。この章に出てくるキャプチャの数値（ポート番号やSeqなど）は、シミュレータで実際に生成したフレームから取っています。自分で実行すると、実行した順番によってポート番号やSeqの値は変わります。

## キャプチャは「実際に流れたもの」の記録

### 「はず」と「実際」

博士：第7章の切り分けを思い出してほしい。`ip route` は経路表を、`ss` は待ち受けているポートを見せてくれた。これらは、機器が「こうするつもりだ」という設定や状態だ。

ノード：はい。でも、設定が正しく見えても動かないことって、ありますよね……。

博士：ある。経路表は正しいのに途中の誰かが捨てている。サーバーは待ち受けているのに、手前の Firewall が落としている。設定をいくら眺めても、「実際にどうなったか」はどこにも書いていない。

ノード：じゃあ、「実際」を見るにはどうすれば？

博士：ケーブルを流れたものを、そのまま記録すればいい。それが **パケットキャプチャ** だ。

> **用語：パケットキャプチャ**（packet capture）
> ネットワークを流れたフレームを、流れた時刻とバイト列ごと記録すること。単に「キャプチャ」とも言い、記録したデータそのものもキャプチャと呼ぶ。

ノード：「パケット」キャプチャなのに、記録するのはフレームなんですか？

博士：いいところに気づいたな。第1章で、Ethernetの層で運ぶ単位を **フレーム**、IPの層で運ぶ単位を **パケット** と呼び分けたのを覚えているかね。キャプチャは、NIC（ネットワークの差し込み口）を通った単位、つまりEthernetのフレームを丸ごと記録する。その中にIPパケットも、TCPも、HTTPも入っている。名前は慣用で「パケット」キャプチャと言うのだ。

ノード：外側の箱ごと記録するから、中身も全部そろってる、と。

博士：そういうことだ。だから、キャプチャ1つから、MACアドレスからHTTPのヘッダまで、すべての層を調べられる。

### 記録する道具：tcpdump と Wireshark

博士：記録には道具を使う。サーバーでよく使うのが **tcpdump** だ。

> **用語：tcpdump**
> LinuxなどのOSで使う、コマンドラインのキャプチャツール。指定したインターフェースを通るフレームを記録し、1行ずつ要約して表示したり、ファイルに保存したりする。

博士：PC1 で `curl http://www.example.com/` を実行したとき、PC1 の eth0 を tcpdump で見ると、こう表示される（途中を省いた）。

```text
user@PC1:~$ sudo tcpdump -n -i eth0
tcpdump: listening on eth0
0.000000 eth0 ARP 192.168.1.10 > 192.168.1.53: ARP Who has 192.168.1.53? Tell 192.168.1.10
0.003000 eth0 ARP 192.168.1.53 > 192.168.1.10: ARP 192.168.1.53 is at 02:00:00:02:00:01
0.004000 eth0 IP 192.168.1.10.49152 > 192.168.1.53.53: DNS Standard query 0xaadc A www.example.com
0.007000 eth0 IP 192.168.1.53.53 > 192.168.1.10.49152: DNS Standard query response 0xaadc A www.example.com A 192.168.2.80
（中略）
0.012000 eth0 IP 192.168.1.10.49153 > 192.168.2.80.80: TCP 49153 → 80 [SYN] Seq=3310558080 Win=64240 Len=0
0.019000 eth0 IP 192.168.2.80.80 > 192.168.1.10.49153: TCP 80 → 49153 [SYN, ACK] Seq=1222621274 Ack=3310558081 Win=64240 Len=0
（中略）
15 packets captured
```

ノード：1行が1つのフレームですね。左の数字が時刻で、`>` の左が送り主、右が宛先……。

博士：うむ。`192.168.1.10.49152` のように、IPアドレスの後ろに `.` でポート番号を続けて書くのが tcpdump の流儀だ。細かい読み方はこの後じっくりやる。今は「1回の curl で、15個のフレームが流れたことが記録に残る」とわかればいい。

ノード：コマンドの頭に `sudo` が付いてるのは、なぜですか？

博士：キャプチャすると、自分のプログラム以外の通信まで見えてしまうからだ。ほかの人のパスワードや個人情報が流れているかもしれない。だから、管理者の権限がないと取れないようになっている。

ノード：見えすぎるから、鍵がかかってるんですね。

博士：そうだ。この話は章の後半でもう一度する。さて、もう一つ、画面で読むための道具が **Wireshark** だ。

> **用語：Wireshark**
> キャプチャを取ったり、ファイルから読み込んだりして、プロトコルごとに読み解いて表示するGUIのツール。一覧・層ごとの表示・バイト列の3つの枠で、1つのフレームを細かく調べられる。

ノード：tcpdump で取って、Wireshark で読む、っていう使い分けですか？

博士：現場ではよくある組み合わせだ。画面のないサーバーでは tcpdump でファイルに保存し、それを手元のPCに持ってきて Wireshark で開く。保存のしかたは後のページで扱う。

### たとえるなら、防犯カメラの録画

ノード：キャプチャって、何かにたとえるとどんなものですか？

博士：防犯カメラの録画が近い。カメラの前を「いつ」「誰が」「何を持って」通ったかが残る。「通るつもりだった人」は映らない。

ノード：設定は「通るつもり」で、キャプチャは「実際に通った」……なるほど！

博士：ただし、たとえには限界もある。カメラ1台では建物全部を映せない。それから、持っている箱に鍵がかかっていれば、箱が通ったことはわかっても中身は見えない。この2つはキャプチャにもそのまま当てはまる。

ノード：鍵付きの箱って、暗号化された通信のことですね。

博士：その通り。「どこで取るか」と「何が読めて何が読めないか」。この2つが、この章を通しての大事なテーマになる。

> **注意**
> キャプチャは「ネットワークで起きたことすべて」の記録ではありません。記録した場所を通ったものだけです。また、暗号化された中身は、記録はできても読めません。

> **まとめ**
>
> - 設定や状態のコマンドは「どう動くはずか」を、キャプチャは「実際に何が流れたか」を示す。
> - キャプチャはフレームを時刻とバイト列ごと記録する。tcpdump はコマンドラインで、Wireshark は画面で読み解く道具。
> - キャプチャには他人の通信も入りうるので、取るには管理者の権限が要る。

## どこで取るか：観測点で見えるものが変わる

### PC1で取っても、全部は見えない

博士：さっきの tcpdump は、PC1 の eth0 で取った。では質問だ。同じ時刻に DNS1 と R1 がやり取りしていたら、それは PC1 のキャプチャに映ると思うかね？

ノード：同じスイッチにつながってるから、映りそうですけど……。

博士：映らない。第4章を思い出したまえ。スイッチは、MACアドレステーブル（どのMACアドレスが、どのポートの先にいるかの表）を見て、宛先のポートにだけフレームを出すのだったな。

ノード：あっ、そうでした。DNS1 から R1 宛てのフレームは R1 のポートにしか出ないから、PC1 のケーブルには流れてこないんですね。

博士：その通り。だからキャプチャでは、「どこで取ったか」が決定的に大事になる。その場所を **観測点** と呼ぶ。

> **用語：観測点**
> キャプチャを取る場所。どの機器の、どのインターフェース（ケーブルの差し込み口）で取ったかで表す。例: 「PC1 の eth0」「R1 の g0/1」

ノード：PC1 の eth0 で取ると、映るのはどれなんですか？

博士：スイッチの先にいるPCで取ると、基本的にこの3種類だ。

- PC1 自身が送ったフレームと、PC1 宛てのフレーム
- ブロードキャスト（同じLANの全員宛て。宛先MACが `ff:ff:ff:ff:ff:ff`）のフレーム。ARP要求がその代表
- スイッチが宛先のポートをまだ知らないために、全ポートへ出したフレーム（第4章のフラッディング）

ノード：ARP要求はブロードキャストだから、DNS1 のケーブルにも届くんですよね。

博士：うむ。実際、PC1 が「192.168.1.1 は誰？」と尋ねたARP要求は、DNS1 の eth0 でも記録される。だが、その後に PC1 と WEB が交わす TCP のやり取りは、DNS1 の eth0 には1つも流れない。curl を1回実行したときに、観測点ごとに何が見えるかを整理するとこうなる。

| 観測点 | PC1のARP要求（全員宛て） | DNS（PC1 ⇔ DNS1） | TCP・HTTP（PC1 ⇔ WEB） |
| --- | --- | --- | --- |
| PC1 の eth0 | 見える | 見える | 見える |
| DNS1 の eth0 | 見える | 見える | 見えない |
| WEB の eth0 | 見えない | 見えない | 見える |

ノード：WEB の eth0 では、ARP要求は見えないんですか？ ブロードキャストなのに。

博士：ブロードキャストが届くのは、同じLANの中だけだ。ルータはブロードキャストを向こう側へ転送しない。だから LAN2 にいる WEB には届かないのだ。

### ほかの機器どうしの通信を見たいとき

ノード：じゃあ、DNS1 と R1 のやり取りを見たいときは、どうすればいいんですか？

博士：方法は2つある。1つめは、当事者の機器そのもので取ることだ。DNS1 が Linux なら、DNS1 にログインして tcpdump を動かせばいい。

ノード：ログインできない機器だったら？

博士：そこで2つめ。スイッチに、通信の「コピー」を出させる。**ミラーポート** という機能だ。

> **用語：ミラーポート**（port mirroring / SPAN）
> スイッチの設定で、指定したポートを流れるフレームのコピーを、別のポートにも出す機能。コピーが出るポートにキャプチャ用のPCをつなぐと、ほかの機器どうしの通信を記録できる。Cisco では SPAN と呼ぶ。

博士：たとえば SW1 で「R1 につながる g0/8 を流れるものを、g0/5 にコピーする」と設定し、g0/5 にキャプチャ用のPCをつなぐ。すると、LAN1 と R1 の間を通るフレームがすべて手に入る。

ノード：スイッチの設定だけでできるなら、手軽ですね。

博士：手軽だが、弱点もある。コピーを出すポートの速さには限りがあるから、コピー元の通信量の合計がそれを超えると、コピーが取りこぼされるのだ。確実に取りたいときは **ネットワークTAP** を使う。

> **用語：ネットワークTAP**（network TAP）
> ケーブルの途中に挟んで、流れる信号をそのままコピーして取り出す専用の機器。スイッチの設定や負荷に左右されずに記録できる。

ノード：ケーブルの途中に挟む……なんだか盗聴器みたいッスね。

博士：仕組みとしては似ている。だからこそ、許可なく挟んではいかん。それも後のページで話そう。

```theory-visual
capture-mirror
```

> **発展**
> NICは普段、自分宛てでないフレームを受け取っても捨てています。キャプチャツールは、NICを「宛先に関係なく全部受け取る」モード（プロミスキャスモード）に切り替えて記録します。ただし、スイッチはそもそも他人宛てのフレームを送ってこないので、スイッチにつながったPCをこのモードにしても、ほかの機器どうしの通信は見えるようになりません。

### 同じパケットでも、観測点で見え方が変わる

博士：観測点が大事な理由は、もう一つある。PC1 から WEB へ ping を送り、その Echo Request（pingの問いかけ）を、PC1 の eth0 と WEB の eth0 の2か所で取ったとしよう。

ノード：同じパケットなんだから、どこで取っても同じに見えるんじゃないですか？

博士：それが違うのだ。2つの観測点で見えた値を並べると、こうなる。

| 項目 | PC1 の eth0 で見たもの | WEB の eth0 で見たもの |
| --- | --- | --- |
| 送信元MAC | 02:00:00:01:00:01（PC1） | 02:00:00:04:00:02（R1 の g0/1） |
| 宛先MAC | 02:00:00:04:00:01（R1 の g0/0） | 02:00:00:05:00:01（WEB） |
| 送信元IP → 宛先IP | 192.168.1.10 → 192.168.2.80 | 192.168.1.10 → 192.168.2.80 |
| TTL | 64 | 63 |

ノード：あれ、MACアドレスが全然違う。IPアドレスは同じなのに。

博士：第3章と第4章の復習だ。MACアドレスは「このリンクの中で、次に渡す相手」を表すから、ルータを通るたびに付け替えられる。IPアドレスは最初の送り主と最後の届け先だから、NAT（アドレスを書き換える仕組み。第6章）がなければ変わらない。

ノード：TTLが 64 から 63 に減ってるのは、R1 を1台通ったからですね。第3章でやった、ルータが1ずつ減らす値。

博士：うむ。スイッチの SW1 は IP ヘッダを書き換えないから、TTLは減らさない。つまり、キャプチャで見るTTLは「ここまでにルータをいくつ通ってきたか」の手がかりになる。

ノード：手がかり、ですか。答えじゃなくて？

博士：送り主が最初に入れるTTLは、OSによって違う。Linux は 64、Windows は 128 が多い。最初の値がわからなければ、いくつ減ったかも断定できないのだ。

ノード：ほかにも、観測点で変わるものってありますか？

博士：第4章のVLANを思い出したまえ。スイッチどうしをつなぐトランク（複数のVLANを1本で運ぶリンク）では、フレームに 802.1Q タグ（VLAN番号を書いた4バイト）が付いている。だが、PCにつながるアクセスポートでは、スイッチがタグを外して渡す。同じフレームでも、トランクで取ればタグが見え、PCで取れば見えない。

> **ポイント**
> キャプチャを読む前に、まず「どの観測点で取ったものか」を確かめます。MACアドレス・TTL・VLANタグは、観測点ごとに違って見えるのが正常です。

> **現場では**
> 障害が起きてから「どこで取れるか」を調べると、それだけで時間がかかります。どのスイッチのどのポートをミラーできるか、TAPを入れられる区間はどこかを、構成図と一緒に事前に決めておきます。クラウドや仮想環境では、物理的なケーブルの代わりに、クラウドや仮想マシンの土台のソフトウェア（ハイパーバイザ）が用意する、通信をコピーする機能（トラフィックミラーリング）を使います。

> **シミュレータ**
> このシミュレータは、すべてのリンクを通ったフレームを自動で記録します（ミラーポートやTAPを用意する必要はありません）。機器のTerminalで実行する `tcpdump` は、その機器につながるリンクで記録済みのフレームを表示するもので、実機のように「今から取り始める」ものではありません。

> **まとめ**
>
> - キャプチャに残るのは、その観測点を通ったフレームだけ。スイッチの先のPCで取ると、自分の通信とブロードキャストなどしか見えない。
> - ほかの機器どうしの通信は、当事者の機器で取るか、ミラーポートやネットワークTAPでコピーを取る。
> - ルータの前後では MAC と TTL が変わり、トランクでは VLAN タグが見える。キャプチャには観測点を必ず書き添える。

## パケット一覧を読む

### 1行が1フレーム

博士：では、いよいよ中身を読んでいこう。PC1 の eth0 で、`curl http://www.example.com/` の1回分を記録したものを、Wireshark と同じ形の表で並べるとこうなる。


博士：焦るでない。これは **パケット一覧** と呼ばれる表で、どの列も意味は単純だ。左から順に見ていこう。

> **用語：パケット一覧**（packet list）
> キャプチャしたフレームを、1行に1つずつ、時刻順に並べた表。番号・時刻・送信元・宛先・プロトコル・長さ・要約の列で、全体の流れをつかむのに使う。

### 左の列：No. と Time

ノード：いちばん左の No. は、ただの通し番号ですか？

博士：そうだ。だが、ただの番号と侮ってはいかん。人に説明するとき「No.8 の SYN, ACK を見てください」と言えば、相手も同じフレームを開ける。報告の根拠を指さすための番号なのだ。

ノード：Time は、時刻ですよね。0.000 から始まってます。

博士：既定では、キャプチャの最初のフレームからの経過秒だ。大事なのは値そのものより、行と行の **差** だ。No.3 の問い合わせから No.4 の応答までは 0.007 − 0.004 で 3ミリ秒。DNS1 が3ミリ秒で答えた、とわかる。

ノード：じゃあ、No.7 の SYN から No.8 の SYN, ACK までは、0.019 − 0.012 で7ミリ秒。WEB までの往復に7ミリ秒かかった、ってことですか。

博士：その通り。応答が遅いと言われたとき、どこで時間がかかっているかを、この差で切り分けられるのだ。

### Source・Destination・Protocol・Length

ノード：Source と Destination は、送信元と宛先のIPアドレスですね。

博士：IPパケットならな。ARP の行はIPヘッダを持たないので、表示のしかたが道具によって違う。Wireshark では送信元・宛先のMACアドレスが出るが、この表（とこのシミュレータ）では、ARPの中に書かれた「尋ねた人のIP」と「尋ねられたIP」を出している。

ノード：Protocol の列は、どうやって決まるんですか？ No.7 は TCP なのに、No.10 は HTTP になってます。

博士：その行を読み解けた中で、いちばん上の層の名前が出る。No.7 はTCPのヘッダだけでデータがないから TCP、No.10 はTCPの中にHTTPのデータが入っているから HTTP だ。

ノード：Length は？

博士：フレーム全体のバイト数だ。No.7 の 60 という数字には、実は少し秘密がある。これは、フレームのバイトを1つずつ並べて読む「Hexダンプ」のページで種明かししよう。

### Info：中身の要約

博士：最後の Info は、上の層の要約だ。TCPならポート番号とフラグとSeq/Ack、DNSなら問い合わせた名前と答え、HTTPならリクエストの1行目が出る。

ノード：`49153 → 80 [SYN]` の 49153 って、何の番号ですか？ 80 はHTTPのポートですよね。

博士：送り主の PC1 が、この接続のために一時的に選んだポート番号だ。**エフェメラルポート** と呼ぶ。

> **用語：エフェメラルポート**（ephemeral port）
> クライアントが接続のたびに、一時的に選んで使う送信元ポート番号。接続が終われば手放す。範囲はOSによって違い、たとえば 49152〜65535 や 32768〜60999 が使われる。

ノード：No.3 の DNS では 49152、No.7 の TCP では 49153。通信ごとに別の番号を使ってるんですね。

博士：うむ。サーバー側の番号（53 や 80）は「何のサービスか」を表し、クライアント側の番号は「どの通信か」を区別する。返事は、この番号を宛先にして戻ってくるのだ。

### 一覧から、話の筋を読む

博士：では、15行を通して、何が起きたかを話してみたまえ。

ノード：え〜っと……。No.1〜2 で、PC1 が DNS1 のMACアドレスをARPで調べてます。No.3〜4 で、DNS1 に `www.example.com` を問い合わせて、`192.168.2.80` という答えをもらった。

博士：いいぞ。続けて。

ノード：No.5〜6 でまたARP……あれ？ PC1 が尋ねてるのは `192.168.1.1` ですね。接続したいのは WEB の `192.168.2.80` なのに、どうして？

博士：第3章を思い出したまえ。宛先が別のネットワークにいるとき、PCはどこにフレームを渡すのだった？

ノード：あっ、Default Gateway です！ `192.168.2.80` は LAN2 にいるから、PC1 はまず R1（192.168.1.1）に渡す。だから R1 のMACアドレスを調べてるんだ。

博士：その通り。キャプチャは、教科書に書いた手順が本当にその順で起きたことを見せてくれるのだ。残りも頼む。

ノード：No.7〜9 が、第1章の3-way handshake ですね。SYN、SYN, ACK、ACK。No.10 で GET を送って、No.11 で `200 OK` が返ってきた。No.12 は「受け取りました」の ACK で、No.13〜15 が FIN で接続を閉じるところ。

博士：完璧だ。一覧を上から読むだけで、「名前解決 → 隣のMAC調べ → 接続 → 要求と応答 → 切断」という筋が見えた。どこかで失敗していれば、この筋のどこで途切れたかが一目でわかる。

> **ポイント**
> 一覧は、まず上から「話の筋」として読みます。名前解決・ARP・接続・データ・切断のどこまで進み、どこで途切れたかをつかんでから、気になる行を詳しく見ます。

> **シミュレータ**
> ネットワーク画面の「Packet Capture」タブは、すべてのリンクで記録したフレームを1つの一覧に並べます。そのため、同じフレームが、通ったリンクの数だけ（PC1 → WEB なら3回）ほぼ同じ時刻に並びます。再送ではありません。1つの観測点だけを見たいときは、その機器のTerminalで `tcpdump` を使うか、行を選んで送信元・宛先のMACアドレスを確かめます。No. は記録した順の通し番号で、コマンドを実行するたびに続きから増えていきます。

> **まとめ**
>
> - パケット一覧は1行が1フレーム。No. は根拠を指すための番号、Time は行どうしの差で応答時間を見る。
> - Protocol は読み解けたいちばん上の層、Info はその要約。クライアント側のポートは、通信ごとに選ぶエフェメラルポート。
> - 一覧は上から「話の筋」として読み、どこで途切れたかをつかむ。

ノード：一覧の1行って、もっと細かく見られないんですか？ Info だけだと、TTL とかはわからないですよね。

博士：見られる。行を1つ選ぶと、そのフレームを外側の層から順に読み解いた結果が表示される。No.7 の SYN を選ぶと、こうだ。

ノード：Ethernet、IPv4、TCP……。第1章の「カプセル化」ですね。データにTCPのヘッダを付けて、さらにIPのヘッダ、Ethernetのヘッダで包む、っていう。

博士：うむ。この表示は、その包みを外側から1枚ずつ開けていったものだ。バイト列を「ここは宛先MAC、ここはTTL」と意味のある項目に読み解くことを、**デコード** と呼ぶ。

> **用語：デコード**（decode）
> キャプチャしたバイト列を、プロトコルの決まりに従って「ここは宛先MAC、ここはTTL」と項目ごとに読み解くこと。Wireshark ではこの役目をする部品を dissector と呼ぶ。

博士：そして、デコードした結果を層ごとに折りたたんで見せるのが **階層表示** だ。

> **用語：階層表示**（packet details）
> 1つのフレームのデコード結果を、Ethernet・IP・TCP…と層ごとに入れ子にして見せる表示。外側の層が上、内側の層が下に並ぶ。

ノード：Ethernet の Destination が `02:00:00:04:00:01` になってます。これって R1 の g0/0 のMACアドレスですよね。

博士：よく見ているな。さっき No.5〜6 のARPで調べた、まさにその値だ。IPの宛先は WEB、Ethernet の宛先は R1。前のページで話した「MACは次に渡す相手、IPは最後の届け先」が、1つのフレームの中に並んでいる。

### 次の箱の中身を、どうやって知るのか

ノード：でも、不思議なんですけど。Ethernet の箱を開けたとき、中に入っているのが IPv4 なのか ARP なのか、どうやってわかるんですか？

博士：いい質問だ。各ヘッダには、「中に何が入っているか」を書いた欄があるのだ。Ethernet ヘッダでは、それが **EtherType** だ。

> **用語：EtherType**
> Ethernet ヘッダの最後の2バイトで、中に入っているプロトコルの種類を表す番号。例: `0x0800` は IPv4、`0x0806` は ARP、`0x86DD` は IPv6、`0x8100` は 802.1Q の VLAN タグ。

ノード：No.7 の Type は `0x0800 (IPv4)` ですね。だから次は IPv4 として読む、と。ARP の行なら `0x0806` になってるはずですか？

博士：その通り。そして IPv4 のヘッダにも、同じ役目の欄がある。**プロトコル番号** だ。

> **用語：プロトコル番号**（protocol number）
> IPv4 ヘッダの Protocol 欄に入る番号で、IPパケットの中身の種類を表す。例: 1 は ICMP、6 は TCP、17 は UDP。

ノード：No.7 は `TCP (6)` だから、次は TCP として読む。No.3 の DNS なら 17 で UDP……。箱の外側に、中身を書いた荷札が貼ってあるんですね。

博士：うまいことを言う。受け取った側が迷わず開けられるように、そう設計されているのだ。ほかに、47（GRE）や 50（ESP）といった番号もある。これは第11章で扱うトンネルの中身だ。

### TCP・UDPの上には、荷札がない

ノード：じゃあ、TCP の中身が HTTP だっていうのも、TCP ヘッダのどこかに書いてあるんですか？

博士：そこが落とし穴だ。TCP と UDP のヘッダには、「中身はHTTPです」と書く欄はない。道具は、主にポート番号（80 なら HTTP、53 なら DNS、443 なら TLS）と、中身の並び方のパターンから **推測** しているのだ。

ノード：推測なんですか！ じゃあ、8080番で動いてる Web サーバーは？

博士：道具がそのポートを知らなければ、HTTP ではなくただの「TCP のデータ」と表示されることがある。逆に、443番を別のプロトコルが使っていれば、TLS と誤って読まれることもある。

> **注意**
> ポート番号は中身の手がかりであって、保証ではありません。「443番だから HTTPS」と決めつけず、階層表示で実際に TLS として読み解けているかを確かめます。Wireshark では、行を右クリックして「Decode As…」から、そのポートを何として読むかを指定し直せます。

> **まとめ**
>
> - 行を選ぶと、フレームを外側の層から順にデコードした階層表示が見られる。
> - Ethernet の EtherType、IPv4 のプロトコル番号が「次の箱の中身」を示す。
> - TCP・UDP の上（HTTP・DNS・TLSなど）は、ポート番号と中身のパターンからの推測。ポート番号は手がかりにすぎない。

## Hexダンプを読む（1）EthernetとIPv4

### なぜ、生のバイトまで見るのか

ノード：階層表示があれば、もう十分な気がするんですけど……。その下のバイト列まで見る必要って、あるんですか？

博士：デコードは、あくまで道具の「解釈」だ。道具が知らないプロトコルや、途中で切れた壊れたフレームは、うまく読み解けない。それに、プロトコルの決まりを定めた文書（RFC）は、「先頭から何バイト目に何がある」というバイトの位置で書かれている。最後に頼れるのは、生のバイトなのだ。

ノード：道具の解釈が合っているかを、自分で確かめられるようにする、ってことですね。

博士：そうだ。そのための第一歩が、**16進数** に慣れることだ。

> **用語：16進数**（hexadecimal）
> 0〜9 と a〜f の16個の記号で数を表す書き方。a が10、f が15にあたる。2桁で 00〜ff（10進数の 0〜255）を表せるので、1バイト（8ビット）をちょうど2桁で書ける。`0x` を付けて `0x28` のように書くことが多い。

ノード：`0x28` は、10進数だといくつですか？

博士：上の桁が16の位、下の桁が1の位だ。2×16 ＋ 8 で 40 になる。`0xc0` なら c が12だから、12×16 ＋ 0 で 192 だ。

ノード：192……。あ、`192.168` の 192 ですね！

### Hexダンプの形

博士：では、No.7 の SYN を、1バイトずつ16進数で並べたものを見せよう。これを **Hexダンプ** と呼ぶ。

> **用語：Hexダンプ**（hex dump）
> フレームのバイト列を、1バイトを16進数2桁で表し、1行に16バイトずつ並べた表示。右側には、同じバイトを文字として読んだもの（読めない値は `.`）を添えることが多い。

```text
0000  02 00 00 04 00 01 02 00 00 01 00 01 08 00 45 00   ..............E.
0010  00 28 00 04 00 00 40 06 f6 21 c0 a8 01 0a c0 a8   .(....@..!......
0020  02 50 c0 01 00 50 c5 53 1b 80 00 00 00 00 50 02   .P...P.S......P.
0030  fa f0 8f 21 00 00 00 00 00 00 00 00               ...!........
```

ノード：うっ、暗号みたいッス。左端の `0000`、`0010` は何ですか？

博士：その行の最初のバイトが、フレームの先頭から何バイト目かを16進数で書いたものだ。これを **オフセット** と呼ぶ。

> **用語：オフセット**（offset）
> データの先頭から数えた位置。先頭のバイトを 0 番目として数え、16進数で書くことが多い。例: オフセット `0x16` は、先頭から22バイト目（0から数えて）。

ノード：`0010` の行は、0x10、つまり16バイト目から始まる……。じゃあ、オフセット `0x16` のバイトはどれですか？

博士：`0x16` から行の頭の `0x10` を引くと 6。だから `0010` の行の、0から数えて6番目のバイトだ。

ノード：0、1、2、3、4、5、6……`40` ですね。

博士：うむ。その `40` が何なのかを、先頭から順に解いていこう。

### Ethernet ヘッダ（オフセット 0x00〜0x0d）

博士：先頭の14バイトが Ethernet ヘッダだ。最初の6バイトが宛先MAC、次の6バイトが送信元MAC、最後の2バイトが EtherType と決まっている。

ノード：最初の6バイトは `02 00 00 04 00 01`。宛先MACが R1 の `02:00:00:04:00:01`。次の6バイト `02 00 00 01 00 01` が送信元の PC1。そしてオフセット `0x0c`〜`0x0d` の `08 00` が EtherType で、IPv4！

博士：見事だ。階層表示の Ethernet II の3項目と、ぴったり同じだろう。

### IPv4 ヘッダ（オフセット 0x0e〜0x21）

博士：EtherType の直後、オフセット `0x0e` から IPv4 ヘッダが始まる。最初のバイト `45` は、1バイトに2つの値が詰めてある。上の桁（上位4ビット）の 4 がバージョンで IPv4、下の桁の 5 がヘッダの長さだ。

ノード：ヘッダの長さが5バイト？ 短すぎませんか？

博士：単位が4バイトなのだ。5×4 で20バイト。オプションのない IPv4 ヘッダは20バイトだから、ここからオフセット `0x21` までが IPv4 ヘッダになる。

ノード：なるほど。続きの `00 28` は？

博士：`0x0f` の `00` は通信の優先度などを表す印で、今回は使っていない。その次、オフセット `0x10`〜`0x11` の `00 28` が全長（Total length）だ。IPヘッダとその中身を合わせたバイト数で、0x28 は？

ノード：さっきやりました、40です！ IPヘッダの20バイトと、TCPヘッダの20バイトで40。データはゼロってことですね。

博士：その通り。残りも一気に見よう。

ノード：`0x12`〜`0x13` の `00 04` が Identification……これは何ですか？

博士：パケットが途中で分割されたときに、「元は同じパケットだ」と見分けるための番号だ。続く `0x14`〜`0x15` の `00 00` は、分割に関する印と位置で、今回は分割されていない。

ノード：その次、`0x16` の `40` が……TTL！ 0x40 は 4×16 で 64。階層表示の Time to live と同じだ。

博士：そして `0x17` の `06` がプロトコル番号だ。

ノード：6 だから TCP。さっきの「中身の荷札」がここにあるんですね。`0x18`〜`0x19` の `f6 21` は？

博士：ヘッダチェックサムだ。ヘッダのバイトから計算した確認用の値で、受け取った側が同じ計算をして、途中でヘッダが壊れていないかを確かめる。

ノード：じゃあ、`0x1a` からの4バイト `c0 a8 01 0a` が送信元IP……。c0 が192、a8 が 10×16＋8 で168、01 が1、0a が10。`192.168.1.10` だ！

博士：最後の `c0 a8 02 50` は？

ノード：192.168.2.…… 0x50 は 5×16 で 80。`192.168.2.80`、WEB です。

博士：これで IPv4 ヘッダを全部読んだ。整理しておこう。

| オフセット | バイト | 項目 | 値 |
| --- | --- | --- | --- |
| 0x00〜0x05 | `02 00 00 04 00 01` | 宛先MAC | R1 の g0/0 |
| 0x06〜0x0b | `02 00 00 01 00 01` | 送信元MAC | PC1 |
| 0x0c〜0x0d | `08 00` | EtherType | IPv4 |
| 0x0e | `45` | バージョン / ヘッダ長 | 4 / 5×4＝20バイト |
| 0x10〜0x11 | `00 28` | 全長 | 40バイト |
| 0x12〜0x13 | `00 04` | Identification | 0x0004 |
| 0x14〜0x15 | `00 00` | 分割の印 / 位置 | 分割なし |
| 0x16 | `40` | TTL | 64 |
| 0x17 | `06` | プロトコル番号 | TCP |
| 0x18〜0x19 | `f6 21` | ヘッダチェックサム | 0xf621 |
| 0x1a〜0x1d | `c0 a8 01 0a` | 送信元IP | 192.168.1.10 |
| 0x1e〜0x21 | `c0 a8 02 50` | 宛先IP | 192.168.2.80 |

### Length が 60 の種明かし

ノード：あれ？ Ethernet ヘッダが14バイトで、IPの全長が40バイト。足すと54バイトですよね。でも一覧の Length は 60 でした。

博士：前のページで予告した秘密だ。Hexダンプの最後の行を見たまえ。オフセット `0x36` から先に、`00` が6つ並んでいるだろう。

ノード：ほんとだ。これは何ですか？

博士：Ethernet には「フレームは最低この長さ」という決まりがある。中身が短すぎるときは、後ろにゼロを詰めて長さをそろえるのだ。これを **パディング** と呼ぶ。

> **用語：パディング**（padding）
> 決められた最小の長さに満たないとき、足りない分を埋めるために付け足す、意味のないバイト（ふつうは `00`）。Ethernet のフレームは、末尾の誤り検出用の4バイト（FCS）を含めて最低64バイト、キャプチャに残る部分では最低60バイトになるように埋める。

ノード：中身は54バイトしかないから、60バイトになるまで6バイトのゼロを足した、と。じゃあ、このゼロは IP や TCP の一部じゃないんですね。

博士：そうだ。IPの全長が40と書いてあるから、受け取った側は、IPヘッダの先頭から40バイトより後ろを中身として扱わない。全長の欄がちゃんと役に立っているわけだ。

> **注意**
> VLAN のトランクで取ったフレームには、送信元MACの直後に 802.1Q タグの4バイト（`81 00` と、VLAN番号を含む2バイト）が入ります。その分、EtherType も IPv4 ヘッダも4バイト後ろにずれます。オフセットで読むときは、まずタグの有無を確かめます。

> **発展**
> 送信側のホストで取ったキャプチャでは、チェックサムが「誤り」と表示されることがあります。チェックサムの計算をNICに任せる機能（チェックサムオフロード）があると、OSがキャプチャに渡す時点ではまだ計算されていないためです。それだけで壊れたパケットと判断しないようにします。

> **シミュレータ**
> 実機のLinuxが送るTCPのパケットでは、オフセット `0x14` が `40 00`（「分割しないでほしい」というDFフラグ）になっていることがよくあります。このシミュレータは `00 00` で生成します。FCSとプリアンブル（フレームの前に付く同期用の信号）は記録しません。

> **まとめ**
>
> - Hexダンプは1バイトを16進数2桁で並べた表示。左端は行の先頭のオフセット（先頭から何バイト目か）。
> - Ethernet ヘッダは先頭14バイト（宛先MAC・送信元MAC・EtherType）、続く IPv4 ヘッダは20バイトで、TTL は 0x16、プロトコル番号は 0x17、IPアドレスは 0x1a からにある。
> - 短いフレームは、最低の長さまでパディング（`00`）で埋められる。VLANタグがあると、それ以降が4バイトずれる。

## Hexダンプを読む（2）TCPヘッダとフラグ

### ポート番号は「大きい桁から」並ぶ

博士：IPv4 ヘッダはオフセット `0x21` で終わり、`0x22` から TCP ヘッダが始まる。もう一度、同じ SYN のHexダンプを見よう。

```text
0020  02 50 c0 01 00 50 c5 53 1b 80 00 00 00 00 50 02   .P...P.S......P.
0030  fa f0 8f 21 00 00 00 00 00 00 00 00               ...!........
```

博士：TCP ヘッダの最初の2バイトが送信元ポート、次の2バイトが宛先ポートだ。

ノード：送信元ポートは `0x22`〜`0x23` の `c0 01` ……。2バイトの数って、どう計算するんですか？

博士：左のバイトが大きい桁だ。`c0` に256を掛けて、`01` を足す。192×256 ＋ 1 で？

ノード：49152 ＋ 1 で 49153。一覧に出ていた、PC1 のエフェメラルポートですね！ 宛先は `00 50` で、0×256 ＋ 80 で 80番。

博士：うむ。このように、2バイト以上の数を「大きい桁のバイトから先に」並べる決まりを **ネットワークバイトオーダー** と呼ぶ。

> **用語：ネットワークバイトオーダー**（network byte order）
> 複数バイトの数を、大きい桁のバイトから順に並べる決まり（ビッグエンディアン）。IP・TCP・UDPのヘッダの数値は、すべてこの順で書かれる。例: ポート番号 80 は `00 50`。

ノード：わざわざ決まりにするってことは、逆の順で並べるコンピュータもあるんですか？

博士：ある。今のPCのCPUの多くは、メモリの中では小さい桁から並べている。だから、ネットワークに出すときの順番を1つに決めておかないと、機器どうしで数を読み違えるのだ。

### SeqとAck、そしてヘッダの長さ

博士：次の4バイト、`0x26`〜`0x29` の `c5 53 1b 80` がシーケンス番号だ。4バイトの数は、256を掛ける段が4つになる。

ノード：うわ、計算が大変そう……。

博士：一度だけ手で確かめてみよう。

```text
c5 × 16,777,216 = 197 × 16,777,216 = 3,305,111,552
53 ×     65,536 =  83 ×     65,536 =     5,439,488
1b ×        256 =  27 ×        256 =         6,912
80 ×          1 = 128 ×          1 =           128
                                     ─────────────
                                     3,310,558,080
```

ノード：3310558080！ 一覧の `Seq=3310558080` と同じだ。普段は電卓の16進モードに任せればいいですね。

博士：それでいい。大事なのは「この4バイトがSeqだ」とわかることだ。その次の4バイト `00 00 00 00` は確認応答番号（Ack）だが、最初の SYN はまだ相手から何も受け取っていないので、0 になっている。Seq と Ack の意味は、次のページで詳しく追うぞ。

ノード：その次の `0x2e` の `50` は？

博士：IPv4 の `45` と同じく、上の桁に意味がある。上の 5 が TCP ヘッダの長さで、これも4バイト単位。5×4 で20バイトだ。

### フラグは「ビットの足し算」

博士：そして、オフセット `0x2f` の `02`。これが **TCPフラグ** だ。

> **用語：TCPフラグ**（TCP flags）
> TCP ヘッダの1バイトの中で、1ビットずつ「この印が立っているか」を表す欄。SYN（接続の申し込み）・ACK（確認応答が有効）・FIN（送信の終わり）・RST（接続の打ち切り）などがあり、1つのパケットに複数立つこともある。

ノード：1ビットずつ、ってどういうことですか？

博士：1バイトは8ビットだ。そのビット1つ1つに、別々の印が割り当てられている。大きい桁のビットから順に、値と印を並べるとこうなる。

```text
ビットの値   0x80  0x40  0x20  0x10  0x08  0x04  0x02  0x01
印           CWR   ECE   URG   ACK   PSH   RST   SYN   FIN
```

博士：上の3つ（CWR・ECE・URG）は、混雑の通知や緊急のデータのための印で、普段の通信ではほとんど見かけない。下の5つを覚えておけば十分だ。

ノード：`02` は SYN のビットだけが立ってる、だから [SYN] なんですね。

博士：では、No.8 の SYN, ACK なら、この1バイトはいくつになる？

ノード：SYN が 0x02 で、ACK が 0x10 だから……足して `12` ですか？

博士：正解だ。実際、No.8 のオフセット `0x2f` は `12` になっている。同じ考え方で、FIN, ACK は 0x01 ＋ 0x10 で `11`、RST, ACK は 0x04 ＋ 0x10 で `14` だ。

ノード：No.10 の GET のフレームには `[PSH, ACK]` って出てました。PSH は初めて見ます。

博士：0x08 のビットだ。データを運ぶパケットによく立っている印だな。

> **用語：PSH**（push）
> TCPフラグの1つ。受け取った側に「ためておかずに、すぐアプリケーションへ渡してほしい」と伝える印。データを運ぶパケットに ACK と一緒に立つことが多い（`0x18`）。

ノード：`18` は 0x08 ＋ 0x10 で PSH と ACK……。数字の意味がわかると、Hexダンプも読めてくる気がします！

### 残りの欄と、うしろのゼロ

博士：残りは3つだ。`0x30`〜`0x31` の `fa f0` が **ウィンドウサイズ**、`0x32`〜`0x33` の `8f 21` がチェックサム、`0x34`〜`0x35` の `00 00` は緊急時のデータの位置を表す欄で、今はほとんど使われない。

> **用語：ウィンドウサイズ**（window size）
> TCP ヘッダの欄で、「確認応答を待たずに、あとこれだけのバイト数なら続けて送ってよい」と受け取る側が相手に伝える値。受け取る側の余裕の大きさを表す。

ノード：`fa f0` は 250×256 ＋ 240 で……64240。Info の `Win=64240` ですね。そのうしろの `00` が6つは、さっきのパディングだ。

博士：その通り。これで SYN のフレームを、先頭から最後の1バイトまで読み切った。TCP の部分をまとめておこう。

| オフセット | バイト | 項目 | 値 |
| --- | --- | --- | --- |
| 0x22〜0x23 | `c0 01` | 送信元ポート | 49153 |
| 0x24〜0x25 | `00 50` | 宛先ポート | 80 |
| 0x26〜0x29 | `c5 53 1b 80` | シーケンス番号 | 3310558080 |
| 0x2a〜0x2d | `00 00 00 00` | 確認応答番号 | 0（SYNなので未使用） |
| 0x2e | `50` | ヘッダ長 | 5×4＝20バイト |
| 0x2f | `02` | フラグ | SYN |
| 0x30〜0x31 | `fa f0` | ウィンドウサイズ | 64240 |
| 0x32〜0x33 | `8f 21` | チェックサム | 0x8f21 |
| 0x36〜0x3b | `00` ×6 | パディング | （TCPの一部ではない） |

> **シミュレータ**
> 実機のOSが送る SYN には、TCPオプション（一度に送れる最大の大きさ MSS や、ウィンドウの拡大率など）が付いています。そのため実機では、ヘッダ長の欄が `a0`（10×4＝40バイト）、フレームの長さが74バイト前後になるのが普通です。このシミュレータはオプションを付けないので、ヘッダ長は常に20バイトです。

> **まとめ**
>
> - IP・TCPの数値は、大きい桁のバイトから並ぶ（ネットワークバイトオーダー）。ポート番号は2バイト、Seq・Ackは4バイト。
> - TCPフラグは1バイトの中のビットの組み合わせ。SYN＝`02`、SYN, ACK＝`12`、PSH, ACK＝`18`、FIN, ACK＝`11`、RST, ACK＝`14`。
> - ヘッダ長の欄（IPv4 の `45`、TCP の `50`）は4バイト単位。ここを読めば、次の層がどこから始まるかがわかる。

## SeqとAckで、TCPの会話を追う

```theory-visual
tcp-sequence
```

### 2つの番号の役目

博士：Hexダンプで読んだ Seq と Ack は、TCP の会話を追うためのいちばん大事な手がかりだ。第1章で少し触れたが、改めて確かめておこう。

ノード：えっと、送ったデータに付ける番号、でしたっけ。

博士：うむ。TCP は、送るデータの1バイト1バイトに通し番号を付けている。そのパケットが運ぶデータの先頭の番号が **シーケンス番号** だ。

> **用語：シーケンス番号**（sequence number / Seq）
> TCPで、送るデータの各バイトに付ける通し番号のうち、そのパケットが運ぶデータの先頭の番号。最初の値（初期シーケンス番号）は接続ごとにランダムに選ぶ。受け取った側は、この番号でデータを正しい順に並べ直し、抜けを見つける。

博士：そして、受け取った側が「ここまで受け取った。次はこの番号から送ってくれ」と返す番号が **確認応答番号** だ。

> **用語：確認応答番号**（acknowledgment number / Ack）
> TCPで、受け取った側が相手に返す「次に受け取りたいバイトの番号」。言いかえると「この番号の手前までは、すべて受け取った」という知らせ。ACKフラグが立っているときだけ意味を持つ。

ノード：最初の値がランダムなのは、どうしてですか？ 0 から始めればわかりやすいのに。

博士：毎回 0 から始めると、前の接続の遅れて届いたパケットと区別しにくい。それに、番号を推測されると、第三者が偽のパケットを割り込ませやすくなる。だから接続ごとに、予想しにくい値から始めるのだ。

### 3-way handshake の番号を追う

博士：では、No.7〜9 の3つの番号を並べてみよう。

```text
No.   向き           フラグ      Seq           Ack
 7   PC1 → WEB      SYN        3310558080    （なし）
 8   WEB → PC1      SYN, ACK   1222621274    3310558081
 9   PC1 → WEB      ACK        3310558081    1222621275
```

ノード：No.8 の Ack は 3310558081。No.7 の Seq より、ちょうど1大きいです。

博士：それが3-way handshake の決まりだ。SYN にはデータが入っていないが、SYN そのものが番号を1つ使う、と決められている。だから WEB は「あなたの SYN を受け取った。次は 3310558081 番から」と返している。

ノード：No.9 の Ack が 1222621275 なのも、WEB の SYN（Seq=1222621274）に対して、1つ足して返してるんですね。お互いに相手の最初の番号を確認し合ってる。

博士：その通り。キャプチャで「SYN, ACK の Ack が、SYN の Seq ＋1 になっているか」を見れば、その SYN, ACK が本当にその SYN への返事かを確かめられる。

### データの量で、番号が進む

博士：次は、データのやり取りだ。No.10 の GET は Seq=3310558081 で、データの長さ（Len）は 91 バイトだった。

ノード：Len って、どこからわかるんですか？

博士：IPヘッダに書かれた全長から、IPヘッダとTCPヘッダの長さを引けばいい。No.10 の IP の全長は 131 だから、131 − 20 − 20 で 91 だ。

ノード：じゃあ、WEB からの No.11 の Ack は……。

博士：一覧を見てみたまえ。

ノード：Ack=3310558172 です。3310558081 ＋ 91 ＝ 3310558172。GET の91バイトを全部受け取った、っていう意味ですね！

博士：そうだ。No.11 の `200 OK` は Len=140 だった。では、それに対する PC1 の No.12 の Ack は？

ノード：WEB の Seq 1222621275 ＋ 140 で、1222621415。……一覧の No.12 と一致しました。

博士：会話全体を図にするとこうなる。

```text
PC1 192.168.1.10:49153                                   WEB 192.168.2.80:80
 No.7   SYN       Seq=3310558080                     ──▶
 No.8                 ◀── SYN, ACK  Seq=1222621274  Ack=3310558081
 No.9   ACK       Seq=3310558081  Ack=1222621275     ──▶
 No.10  PSH, ACK  Seq=3310558081  Len=91（GET）       ──▶
 No.11                 ◀── PSH, ACK  Seq=1222621275  Ack=3310558172  Len=140（200 OK）
 No.12  ACK       Seq=3310558172  Ack=1222621415     ──▶
 No.13  FIN, ACK  Seq=3310558172                     ──▶
 No.14                 ◀── FIN, ACK  Seq=1222621415  Ack=3310558173
 No.15  ACK       Seq=3310558173  Ack=1222621416     ──▶
```

ノード：最後の FIN も、SYN と同じで番号を1つ使うんですね。No.14 の Ack が 3310558173 で、No.13 の Seq ＋1 になってます。

博士：よく気づいた。FIN も「送信の終わり」という印として、番号を1つ使うのだ。

### 番号が読めると、何がわかるのか

ノード：でも、番号が合っているのを確かめて、何の役に立つんですか？

博士：番号が合わないところが、問題の場所だからだ。たとえば、同じ Seq のパケットがもう一度送られていれば（送り直しのことを再送と呼ぶ。後のページで詳しく見る）、最初のものが相手に届かなかった（か、届いたという知らせが戻らなかった）ことを示す。Ack がいつまでも増えなければ、データが向こうに届いていない。

ノード：ほかには？

博士：どちらが先に FIN を送ったかで、「どちらが接続を閉じたか」がわかる。今回は No.13 で PC1 が先に閉じている。curl がページを受け取り終えて、自分から切ったわけだ。途中で RST が来ていれば、どちらが会話を打ち切ったかも番号と向きでわかる。

> **ポイント**
> SYN と FIN は番号を1つ使い、データは長さの分だけ番号を進めます。「相手の Ack ＝ 自分の Seq ＋ 送った量」になっているかを見れば、データが届いたかどうかを確かめられます。

### Wireshark では「0」から始まって見える

ノード：さっきから大きな数で計算してきましたけど、Wireshark でもこんな大きな数が出るんですか？

博士：いや。Wireshark は既定で、最初の Seq を 0 とみなして引き算した値を表示する。これを **相対シーケンス番号** と呼ぶ。

> **用語：相対シーケンス番号**（relative sequence number）
> 接続の最初の Seq を 0 とみなして表した番号。Wireshark の既定の表示で、実際にヘッダに入っている値（raw）とは違う。設定で raw の表示に切り替えられる。

ノード：じゃあ Wireshark だと、No.7 の SYN は Seq=0 で、No.8 は Seq=0 Ack=1……。No.11 の Ack は 92 になるわけですね。

博士：そうだ。読みやすいが、「SYN の Seq が 0 だ」と言うと誤りになる。ヘッダに入っているのは、さっき Hexダンプで計算した 3310558080 だ。

> **注意**
> Wireshark の Seq=0 は表示上の値で、実際のヘッダの値ではありません。ほかの観測点のキャプチャや、別のツールの出力と突き合わせるときは、raw の値で比べます。

> **シミュレータ**
> このシミュレータのパケット一覧は、Seq と Ack を raw（ヘッダに入っている実際の値）で表示します。また、接続を閉じるやり取りを「FIN, ACK → FIN, ACK → ACK」の3つで行います。実機では、相手の ACK と FIN が別々のパケットになり、4つになることもあります。

> **まとめ**
>
> - Seq は運ぶデータの先頭の番号、Ack は「次に受け取りたい番号」。SYN と FIN は番号を1つ使う。
> - 相手の Ack が「自分の Seq ＋ 送った量」になっていれば、データは届いている。同じ Seq の再送や、増えない Ack は問題の手がかり。
> - Wireshark の既定は相対シーケンス番号（最初が 0）。実際のヘッダの値とは別物。

## 絞り込む：キャプチャフィルタと表示フィルタ

```theory-visual
capture-filters
```

### 本番のサーバーは、1秒に何千ものフレームが流れる

博士：さっきの例は、curl 1回分の15フレームだった。だが本番のWebサーバーで取れば、1秒に何千、何万というフレームが流れる。

ノード：その中から、見たい通信だけを探すのは大変ですね……。

博士：だから絞り込む。絞り込むタイミングは2つある。1つは「記録するとき」、もう1つは「記録した後、表示するとき」だ。まず、記録するときに絞るものを **キャプチャフィルタ** と呼ぶ。

> **用語：キャプチャフィルタ**（capture filter）
> キャプチャを取るときに指定する条件。条件に合わないフレームは、そもそも記録されない。tcpdump ではコマンドの最後に書く。

博士：tcpdump では、条件をコマンドの最後に書く。PC1 で DNS だけを取るなら、こうだ。

```text
user@PC1:~$ sudo tcpdump -n -i eth0 udp port 53
0.004000 eth0 IP 192.168.1.10.49152 > 192.168.1.53.53: DNS Standard query 0xaadc A www.example.com
0.007000 eth0 IP 192.168.1.53.53 > 192.168.1.10.49152: DNS Standard query response 0xaadc A www.example.com A 192.168.2.80
2 packets captured
```

ノード：`udp port 53` だけで、DNS の2行だけになった！ 前に付いてる `-n` と `-i eth0` は何ですか？

博士：`-i` は、どのインターフェースで取るかの指定だ。`-i any` なら全部のインターフェースになる。`-n` は、表示のときにIPアドレスを名前に変換しない、という指定だ。

ノード：名前に変換されたほうが、読みやすそうですけど。

博士：変換するために、tcpdump 自身が DNS に問い合わせを出してしまうのだ。それが表示を遅らせたり、自分の記録に混ざったりする。だから `-n` を付けるのが定番だ。ほかに、MACアドレスも表示する `-e`、N個で止める `-c N` もよく使う。

### 条件の書き方：BPF

ノード：`udp port 53` って、決まった書き方があるんですか？

博士：ある。tcpdump のキャプチャフィルタは、**BPF** という仕組みの書き方を使う。Wireshark でキャプチャを始めるときに指定するフィルタも、同じ書き方だ。

> **用語：BPF**（Berkeley Packet Filter）
> キャプチャフィルタの書き方と、それをOSの中で高速に判定する仕組み。`host`・`net`・`port` などの条件を `and`・`or`・`not` で組み合わせて書く。書き方の正式な説明は pcap-filter という文書にまとまっている。

博士：例のネットワークで使いそうなものを並べてみよう。

```text
host 192.168.2.80            送信元か宛先が 192.168.2.80
src host 192.168.1.10        送信元が 192.168.1.10
dst port 443                 宛先ポートが 443
net 192.168.1.0/24           送信元か宛先が 192.168.1.0/24 の中
udp port 53                  UDP で、どちらかのポートが 53
tcp and host 192.168.2.80    TCP で、かつ 192.168.2.80 との通信
arp or icmp                  ARP か ICMP
vlan 10                      VLAN 10 のタグが付いたフレーム（トランクで取るとき）
not port 22                  22番（SSH）を使う通信以外
```

ノード：`host` は送信元でも宛先でもよくて、`src` や `dst` を付けると向きを決められるんですね。

博士：うむ。`and`・`or`・`not` は、`&&`・`||`・`!` と書いてもいい。組み合わせるときは、括弧も使える。ただし BPF では、`and` と `or` は同じ強さで、左から順に組み合わされる。迷ったら括弧で囲むことだ。

```text
sudo tcpdump -n -i eth0 'host 192.168.2.80 and (port 80 or port 443)'
```

ノード：条件全体を `'` で囲んでるのは？

博士：括弧は、シェル（コマンドを解釈するプログラム）にとって特別な記号だからだ。囲まないと、tcpdump に届く前にシェルが別の意味に解釈してしまう。

> **現場では**
> サーバーに SSH でログインして tcpdump を動かすと、自分の SSH の通信（22番）が大量に記録され、しかもその表示がまた SSH で流れる、という循環が起きます。`not port 22` を付けて、自分の操作を除くのが定番です。

### 記録した後に絞る：表示フィルタ

博士：もう1つの絞り方が、記録した後に表示だけを絞る **表示フィルタ** だ。

> **用語：表示フィルタ**（display filter）
> 記録したキャプチャのうち、条件に合うものだけを画面に表示する Wireshark の機能。隠れたフレームは消えていないので、条件を消せば元に戻る。書き方は BPF とは別。

ノード：書き方が別なんですか？ ややこしい……。

博士：Wireshark の表示フィルタは、デコードした項目の名前で書くのだ。たとえばこうなる。

```text
ip.addr == 192.168.2.80                  送信元か宛先が 192.168.2.80
tcp.port == 80                           TCP で、どちらかのポートが 80
dns                                      DNS として読み解けたもの
dns.flags.rcode == 3                     DNS の結果が NXDOMAIN のもの
tcp.flags.syn == 1 && tcp.flags.ack == 0 SYN だけが立ったもの（接続の申し込み）
tcp.analysis.retransmission              Wireshark が再送と判断したもの
```

ノード：`dns.flags.rcode == 3` みたいに、中身の細かい値で絞れるんですね。BPF だと、そこまではできない？

博士：BPF はOSの中で、フレームの数を減らすために高速に判定する仕組みだから、表せるのは主にヘッダの値だ。表示フィルタは、記録した後にじっくり読み解けるので、細かい条件を書ける。整理するとこうだ。

| | キャプチャフィルタ | 表示フィルタ |
| --- | --- | --- |
| 効くとき | 記録するとき | 記録した後、表示するとき |
| 合わないフレーム | 記録されない（後から見られない） | 隠れるだけ（条件を消せば戻る） |
| 書き方 | BPF（tcpdump と共通） | Wireshark 独自 |
| 例 | `tcp port 80` | `tcp.port == 80` |

### 絞りすぎると、証拠まで捨てる

ノード：じゃあ、最初からキャプチャフィルタでぎゅっと絞って取れば、楽ですね。

博士：そこが落とし穴だ。たとえば、443番の接続が失敗する原因を調べようとして、`tcp port 443` で取ったとする。もし原因が DNS の失敗だったら、どうなる？

ノード：DNS は UDP の53番だから……記録されない。SYN が1つも出ていない、という不思議なキャプチャだけが残りますね。

博士：それだけではない。ルータが「届けられない」と知らせる ICMP のエラーにも、ポート番号はない。だから `tcp port 443` には合わず、捨てられてしまう。

ノード：原因を示すパケットほど、条件から外れちゃうんですね……。

博士：うむ。調べ始めは `host 192.168.2.80` のように相手だけで広めに取り、細かい絞り込みは表示フィルタでやる。これが基本だ。

> **注意**
> キャプチャフィルタで捨てたフレームは、二度と取り戻せません。原因がまだわからないうちは広めに取り、表示フィルタで絞ります。ただし、広く取るほど関係のない人の通信まで残るので、取る範囲と保存の扱いには気をつけます（後のページで扱います）。

> **シミュレータ**
> 「Packet Capture」タブの入力欄と、機器のTerminalの `tcpdump` は、どちらも BPF に近い書き方（`host`・`src`・`dst`・`net`・`port`・`tcp`・`udp`・`icmp`・`arp`・`vlan`・`and`・`or`・`not`・括弧）に対応しています。`dns`・`http`・`tls` は、このシミュレータ独自の拡張です（実機の tcpdump では `port 53` などで書きます）。Wireshark の表示フィルタの書き方（`==` など）には対応していません。tcpdump のオプションは `-i`・`-e`・`-c` に対応し（`-c N` は記録済みの最後のN件を表示します）、`-w` などのファイル保存は使えません（保存は「PCAP」ボタンで行います）。

> **まとめ**
>
> - キャプチャフィルタは記録するときに絞り、合わないものは残らない。表示フィルタは表示を絞るだけで、消せば戻る。
> - tcpdump のフィルタは BPF の書き方（`host`・`port`・`and`・`or`・`not`）。Wireshark の表示フィルタは項目名で書く別の書き方。
> - 絞りすぎると、DNS や ICMP のような原因を示すフレームまで捨てる。調べ始めは広めに取る。

## DNSをキャプチャで読む

### 問い合わせと応答を、ひと組で見る

博士：ここからは、上の層のプロトコルがキャプチャでどう見えるかを読んでいく。まずは DNS だ。第5章で学んだとおり、PC1 は名前を引くとき、DNSサーバーに UDP の53番で問い合わせる。一覧の No.3 と No.4 がそれだった。

```text
 3  0.004  192.168.1.10  192.168.1.53  DNS   75  Standard query 0xaadc A www.example.com
 4  0.007  192.168.1.53  192.168.1.10  DNS  106  Standard query response 0xaadc A www.example.com A 192.168.2.80
```

ノード：No.3 は PC1 の 49152番から DNS1 の 53番へ。No.4 はその逆で、53番から 49152番へ返ってきてますね。

博士：うむ。どちらの行にも `0xaadc` という同じ値が出ているだろう。これが **トランザクションID** だ。

> **用語：トランザクションID**（transaction ID）
> DNSの問い合わせに付ける2バイトの番号。応答には同じ番号が入るので、問い合わせた側はどの質問への答えかを対応付けられる。キャプチャでは、問い合わせと応答の組を探す手がかりになる。

ノード：UDP には、TCP みたいな Seq や Ack はないんですよね。だから DNS 自身が番号を付けて、質問と答えを結びつけてる、と。

博士：その通りだ。ちなみに `dig` の画面では、同じ番号が10進数で `id: 43740` と出る。0xaadc を10進数にすると 43740 だ。表記が違うだけで同じ番号だから、突き合わせるときは気をつけたまえ。

### 問い合わせのバイト列

博士：No.3 の問い合わせを、UDP ヘッダからバイト単位で読んでみよう。IPv4 ヘッダまではこれまでと同じなので、オフセット `0x22` から見る。

```text
0020  01 35 c0 00 00 35 00 29 c6 9d aa dc 01 00 00 01   .5...5.)........
0030  00 00 00 00 00 00 03 77 77 77 07 65 78 61 6d 70   .......www.examp
0040  6c 65 03 63 6f 6d 00 00 01 00 01                  le.com.....
```

ノード：`0x22` の `c0 00` が送信元ポートで 49152、`00 35` が宛先ポートで 53。UDP ヘッダは TCP より短いんですね。

博士：UDP ヘッダは8バイトしかない。ポートが2つ、長さ（`00 29`＝41バイト）、チェックサムで終わりだ。だから `0x2a` からはもう DNS のメッセージになる。

ノード：`0x2a` の `aa dc` がトランザクションID。その次の `01 00` は？

博士：フラグだ。TCPと同じく、ビットごとに印が決まっている。問い合わせの `01 00` は、「再帰的に最後まで調べてほしい」という RD の印だけが立っている。続く `00 01` が「質問が1つ」、その後の `00 00` が3つ並んでいるのは、答え・権威・追加の各欄が0件、という意味だ。

ノード：オフセット `0x36` の `03 77 77 77` は……右の文字の欄に `www` って出てます。

博士：DNSのメッセージの中では、名前をドットで区切り、区切った部分ごとに「文字数（1バイト）＋ 文字」で書く決まりになっている。最後に `00` を置いて、名前の終わりを示す。

ノード：`03` で3文字の `www`、`07` で7文字の `example`、`03` で `com`、最後の `00` で終わり。ドットそのものは入ってないんですね。

博士：そうだ。名前の後ろの `00 01` が「Aレコード（IPv4アドレス）を知りたい」、最後の `00 01` が「インターネットの名前（IN）」という意味だ。

### 応答のフラグと、結果の番号

博士：次は No.4 の応答だ。

```text
0020  01 0a 00 35 c0 00 00 48 22 6c aa dc 85 80 00 01   ...5...H"l......
0030  00 01 00 00 00 00 03 77 77 77 07 65 78 61 6d 70   .......www.examp
0040  6c 65 03 63 6f 6d 00 00 01 00 01 03 77 77 77 07   le.com......www.
0050  65 78 61 6d 70 6c 65 03 63 6f 6d 00 00 01 00 01   example.com.....
0060  00 00 01 2c 00 04 c0 a8 02 50                     ...,.....P
```

ノード：フラグが `85 80` になってます。これも、ビットの足し算ですか？

博士：その通り。1バイト目の `85` は 0x80 ＋ 0x04 ＋ 0x01 だ。0x80 は「これは応答です」（QR）、0x04 は「私はこの名前を管理する権威サーバーです」（AA）、0x01 は問い合わせから引き継いだ RD だ。2バイト目の `80` は「再帰的な問い合わせに対応できます」（RA）。そして2バイト目の下4ビットが、結果を表す **RCODE** だ。

> **用語：RCODE**（response code）
> DNSの応答のフラグの下4ビットに入る、結果を表す番号。0 は NOERROR（成功）、2 は SERVFAIL（サーバー側で解決に失敗）、3 は NXDOMAIN（その名前は存在しない）、5 は REFUSED（問い合わせを拒否）。

ノード：`80` の下4ビットは 0 だから、NOERROR。成功ですね。

博士：うむ。そのあと、質問がそのまま繰り返され、オフセット `0x4b` から答えが始まる。名前、`00 01`（A）、`00 01`（IN）、そして `00 00 01 2c` が TTL、`00 04` がデータの長さ、最後の `c0 a8 02 50` が答えのIPアドレスだ。

ノード：`c0 a8 02 50` は 192.168.2.80！ `00 00 01 2c` は 1×256 ＋ 44 で 300。

> **注意**
> DNSの答えに入っている TTL（キャッシュしてよい秒数。第5章）と、IPヘッダの TTL（通れるルータの数の上限。第3章）は、名前が同じでも別のものです。DNSの TTL 300 は「300秒は覚えておいてよい」、IPの TTL 64 は「あと64台のルータを通れる」という意味です。

### 名前が存在しないとき

ノード：もし `www.example.com` が DNS1 に登録されていなかったら、キャプチャではどう見えるんですか？

博士：実は、Simulation の最初の状態がそれだ。PC1 で `curl http://www.example.com/` を実行すると、PC1 の eth0 ではこう見える。

```text
0.004000 eth0 IP 192.168.1.10.49152 > 192.168.1.53.53: DNS Standard query 0xaadc A www.example.com
0.007000 eth0 IP 192.168.1.53.53 > 192.168.1.10.49152: DNS Standard query response 0xaadc A www.example.com No such name
```

ノード：`No such name` ……。フラグは？

博士：`85 83` だ。下4ビットが 3、つまり RCODE＝3 の **NXDOMAIN** になる。

> **用語：NXDOMAIN**（Non-Existent Domain）
> DNSの応答で RCODE が 3 のもの。「問い合わせた名前は存在しない」という意味で、Wireshark では「No such name」と表示される。名前の打ち間違いや、レコードの登録漏れで起きる。

ノード：その後に、TCP の SYN は続かないんですか？

博士：1つもない。接続先のIPアドレスがわからないのだから、curl は SYN を出しようがないのだ。curl はここで「Could not resolve host」と言って終わる。

ノード：住所がわからないと、手紙を出せないのと同じですね。じゃあ「SYN が1つもない」こと自体が、DNS で止まった手がかりになるんだ。

博士：いいところに気づいたな。それから、もう1つ区別しておきたまえ。名前はあるが、問い合わせた種類のレコードがない場合は、RCODE は 0（NOERROR）で、答えが0件になる。これを NODATA と呼ぶ。NXDOMAIN とは原因が違うのだ。

> **シミュレータ**
> 実際のDNSサーバーの応答では、答えの欄の名前は、メッセージの中で前に出てきた名前を指す2バイト（たいていは `c0 0c`）に縮められています（名前の圧縮）。このシミュレータは圧縮をせず、名前をそのまま書くので、応答が少し長くなります。

> **まとめ**
>
> - DNS は UDP の53番。問い合わせと応答は、同じトランザクションIDで対応付ける（`dig` では10進数で表示）。
> - 名前はドットで区切った部分ごとに「文字数＋文字」で書かれる。応答のフラグの下4ビットが RCODE で、0 は成功、3 は NXDOMAIN。
> - NXDOMAIN のあとには SYN が続かない。「SYN が1つもない」ことも、名前解決で止まった手がかりになる。

## HTTPとTLS：読める中身と、読めない中身

### HTTPは、そのまま文字で読める

博士：次は、No.10 の GET を Hexダンプで見てみよう。TCP ヘッダが終わるオフセット `0x36` から先が、HTTP のデータだ。

```text
0030  fa f0 7a ca 00 00 47 45 54 20 2f 20 48 54 54 50   ..z...GET / HTTP
0040  2f 31 2e 31 0d 0a 48 6f 73 74 3a 20 77 77 77 2e   /1.1..Host: www.
0050  65 78 61 6d 70 6c 65 2e 63 6f 6d 0d 0a 55 73 65   example.com..Use
0060  72 2d 41 67 65 6e 74 3a 20 63 75 72 6c 2f 38 20   r-Agent: curl/8 
0070  28 50 41 54 48 20 73 69 6d 75 6c 61 74 6f 72 29   (PATH simulator)
0080  0d 0a 41 63 63 65 70 74 3a 20 2a 2f 2a 0d 0a 0d   ..Accept: */*...
0090  0a                                                .
```

ノード：右側に、`GET / HTTP/1.1` とか `Host: www.example.com` とか、そのまま出てます！

博士：HTTP は、リクエストもレスポンスも文字で書くプロトコルだ。`47` が G、`45` が E、`54` が T、`20` が空白。そして `0d 0a` が行の終わり（改行）を表す。このように、暗号化されずにそのまま読める状態を **平文** と呼ぶ。

> **用語：平文**（plaintext）
> 暗号化されていない、そのまま読めるデータ。HTTP は平文で送られるので、通り道でキャプチャすれば、URL・ヘッダ・本文がすべて読める。

ノード：No.11 の `200 OK` のほうも、きっと本文の `<h1>www.example.com</h1>` まで読めるんですよね。

博士：読める。調べる側には便利だが、裏を返せば、通り道にいる誰でも読めるということだ。ログインのパスワードや、ログインした状態を表す Cookie が平文で流れていたら、どうなる？

ノード：キャプチャした人に、まる見えです……。だから HTTPS を使うんですね。

### TLS の始まりを読む

博士：そうだ。第1章で学んだ TLS（通信を暗号化し、相手が本物かを証明書で確かめる仕組み）を使うのが HTTPS だ。では、PC1 で `curl https://www.example.com/` を実行したときのキャプチャを見よう。3-way handshake の後は、こうなる。

```text
TLS  141  Client Hello (SNI=www.example.com)            PC1 → WEB
TLS  226  Server Hello, Change Cipher Spec, Application Data   WEB → PC1
TCP   60  49155 → 443 [ACK] ...                          PC1 → WEB
TLS  166  Application Data                               PC1 → WEB
TLS  221  Application Data                               WEB → PC1
```

ノード：Client Hello、Server Hello……。これは何のやり取りですか？

博士：暗号化を始める前の打ち合わせだ。どの暗号の方式を使うか、どの鍵で暗号化するかを決め、サーバーが証明書を見せる。これを **TLSハンドシェイク** と呼ぶ。

> **用語：TLSハンドシェイク**（TLS handshake）
> TLSで暗号化を始める前に、クライアントとサーバーが使う暗号の方式や鍵を決め、サーバーが証明書で身元を示すやり取り。TCPの3-way handshake が終わった後に行う。

博士：その最初の一言が **Client Hello** だ。

> **用語：Client Hello**
> TLSハンドシェイクで、クライアントが最初に送るメッセージ。使える暗号の方式の一覧や、接続したいサーバーの名前などを伝える。暗号化される前に送るので、キャプチャで中身を読める。

ノード：暗号化される前……。じゃあ、Client Hello は中身が読めるんですか？

博士：読める。Hexダンプのうしろのほうを見たまえ。

```text
0030  fa f0 20 6c 00 00 16 03 01 00 52 01 00 00 4e 03   .. l......R...N.
（中略）
0070  00 14 00 12 00 00 0f 77 77 77 2e 65 78 61 6d 70   .......www.examp
0080  6c 65 2e 63 6f 6d 00 2b 00 03 02 03 04            le.com.+.....
```

ノード：`www.example.com` が、そのまま見えてます！

博士：これが **SNI** だ。

> **用語：SNI**（Server Name Indication）
> Client Hello に入れる「接続したいサーバーの名前」。1つのIPアドレスで複数のサイトを動かすサーバーが、どの証明書を出せばよいかを、暗号化の前に知るために使う。そのため、キャプチャで読める。

ノード：なるほど、証明書を選ぶ前の段階だから、暗号化できないんですね。最初の `16 03 01 00 52 01` は？

博士：TLS のデータは「レコード」という単位で送られ、その頭の5バイトに種類・版・長さが書いてある。`16`（10進数で22）が「ハンドシェイクのメッセージ」、`03 01` が版、`00 52` が長さで82バイト。その次の `01` が「Client Hello です」という印だ。

### Server Hello から先は、読めない

博士：次に、サーバーが返すのが **Server Hello** だ。

> **用語：Server Hello**
> TLSハンドシェイクで、サーバーが Client Hello に答えるメッセージ。使う暗号の方式などを決めて伝える。TLS 1.3 では、これ以降のやり取り（証明書を含む）はすべて暗号化される。

ノード：同じ行に、`Change Cipher Spec, Application Data` も出てますね。

博士：Change Cipher Spec は、古い中継機器を戸惑わせないために残された合図で、中身に意味はない。大事なのはその先だ。TLS 1.3 では、Server Hello のすぐ後から暗号化が始まる。証明書も、その後の HTTP のリクエストもレスポンスも、すべて「Application Data（暗号化されたデータ）」というレコードとして流れる。Hexダンプで見ても、意味のない数字の並びにしか見えない。

ノード：じゃあ、HTTPS のキャプチャから読めるのはどこまでなんですか？

博士：整理するとこうなる。

| キャプチャで読めるもの | キャプチャで読めないもの（TLS 1.3） |
| --- | --- |
| IPアドレス・ポート番号 | 証明書の中身 |
| Client Hello の SNI（接続先の名前） | URL のパス（`/login` など） |
| 各レコードの大きさと、送られた時刻 | HTTP のヘッダ・Cookie・本文 |
| どちらが FIN や RST で接続を閉じたか | サーバーが返したエラーの内容 |

ノード：中身は読めなくても、「いつ、誰と、どのくらいの量を、どこで切ったか」は残るんですね。

博士：その外形だけでも、多くのことがわかる。たとえば、Server Hello の直後にクライアントが短いレコードを1つ送って FIN で切っていたら、「クライアントが証明書を受け入れなかったのでは」と考えられる。ただし、それはあくまで推測だ。確かめるには、クライアント側で `curl -v` を実行して、エラーの文言を読む。

### SNI も隠す技術：ECH

ノード：SNI が読めると、どのサイトを見ているかがわかっちゃいますよね。

博士：うむ。そこで、Client Hello の中身まで暗号化する **ECH** という技術が使われ始めている。

> **用語：ECH**（Encrypted Client Hello）
> Client Hello の大事な部分（SNI など）を暗号化して送る TLS の拡張。ECH を使う通信では、キャプチャから接続先のサイト名が読めなくなる。

> **発展**
> TLS 1.2 以前では、サーバーの証明書は暗号化されずに送られるため、キャプチャで証明書の中身（名前や有効期限）を読めます。また、HTTP/3 は TCP ではなく UDP の443番の上で QUIC というプロトコルを使い、ハンドシェイクのほとんどが暗号化されます。「443番＝TCPのTLS」とは限りません。

> **現場では**
> 検証環境で暗号化された中身を読む必要があるときは、ブラウザや curl が対応している SSLKEYLOGFILE（TLSの鍵をファイルに書き出す仕組み）を使い、Wireshark にその鍵を読ませて復号します。許可された検証環境だけで使い、本番の利用者の通信には使いません。本番では、アプリケーションのログや、プロキシ（利用者の代わりに通信を中継するサーバー）のログと、キャプチャの外形を組み合わせて判断します。

> **シミュレータ**
> このシミュレータは実際の暗号処理を行いません。Server Hello 以降の「暗号化されたデータ」は、意味のないバイト列で埋めたものです。「Packet Capture」タブでTLSの行を選ぶと、学習用に、シミュレータが内部で持っている中身を注記として表示します（実際のキャプチャでは見えません）。

> **まとめ**
>
> - HTTP は平文なので、リクエスト行・Host・Cookie・本文までキャプチャで読める。
> - TLS では、Client Hello（SNI を含む）までは読めるが、TLS 1.3 では Server Hello 以降が暗号化され、証明書も HTTP の中身も読めない。
> - 暗号化されていても、IP・ポート・大きさ・時刻・どちらが切断したかは残る。外形からの推測は、クライアントのログで確かめる。

### 型1：SYN に RST が返る

ノード：SYN のすぐ後に、[RST, ACK] が返ってきてます。RST は第1章で出てきた、接続を打ち切る合図ですよね。

博士：そうだ。まず、誰が返したかを確かめよう。送信元は？

ノード：192.168.2.80、WEB です。Ack が 3310558081 で、SYN の Seq ＋1 だから、確かにこの SYN への返事ですね。

博士：うむ。つまり SYN は WEB まで届いている。経路も、途中の機器も問題ない。WEB の OS が「80番で待ち受けているプログラムがいない」から、即座に断ったのだ。実際、WEB では nginx が止まっている。

ノード：届いた上で断られた、ってことですね。返事が7ミリ秒で来てるから、待たされることもない。

博士：その通り。ただし、実機では Firewall が宛先の代わりに RST を返すこともある。IPヘッダの TTL を見て、WEB から来たにしては値が合わない、といったことから見分ける手がかりにするのだ。

### 型2：同じ SYN が、間隔を広げて繰り返される

博士：次は `curl https://192.168.2.80/` だ。今度はこうなる。

```text
0.020000 eth0 IP 192.168.1.10.49154 > 192.168.2.80.443: TCP 49154 → 443 [SYN] Seq=2326136519 Win=64240 Len=0
1.023000 eth0 IP 192.168.1.10.49154 > 192.168.2.80.443: TCP 49154 → 443 [SYN] Seq=2326136519 Win=64240 Len=0
3.026000 eth0 IP 192.168.1.10.49154 > 192.168.2.80.443: TCP 49154 → 443 [SYN] Seq=2326136519 Win=64240 Len=0
```

ノード：SYN が3回。しかも Seq が全部同じ……。返事は1つもないですね。

博士：返事がないので、PC1 が同じ申し込みを送り直しているのだ。これを **再送** と呼ぶ。

> **用語：再送**（retransmission）
> 送ったデータや SYN に対する確認応答が一定時間内に返ってこないとき、同じものをもう一度送ること。同じ Seq のパケットが繰り返し現れるのが目印で、待つ時間は1秒、2秒、4秒…と倍々に延びていく。

ノード：Time の差が、1.023 − 0.020 で約1秒、3.026 − 1.023 で約2秒。本当に倍になってます。

博士：そして、待たされた末に curl は「Connection timed out」と言って諦める。RST のときとは、時間のかかり方がまるで違うだろう。

ノード：でも、これだけだと、どこで止まったのかわかりませんよね。行きで捨てられたのか、WEB の返事が帰りに捨てられたのか。

博士：いい疑問だ。そこで観測点を増やす。同じ時刻に、WEB の eth0 で tcpdump を見ると、こうなっている。

```text
user@WEB:~$ sudo tcpdump -n -i eth0 tcp port 443
0.022000 eth0 IP 192.168.1.10.49154 > 192.168.2.80.443: TCP 49154 → 443 [SYN] Seq=2326136519 Win=64240 Len=0
1.025000 eth0 IP 192.168.1.10.49154 > 192.168.2.80.443: TCP 49154 → 443 [SYN] Seq=2326136519 Win=64240 Len=0
3.028000 eth0 IP 192.168.1.10.49154 > 192.168.2.80.443: TCP 49154 → 443 [SYN] Seq=2326136519 Win=64240 Len=0
```

ノード：WEB のケーブルまでは、SYN が3回とも届いてる！ なのに、WEB は何も送り返していない。じゃあ、止まっているのは WEB の中ですね。

博士：その可能性が高い。tcpdump は、受け取ったフレームを、OS の Firewall（iptables）が判定するより前に記録する。だから「tcpdump に見えた」ことは「NICまでは届いた」ことを示すが、「アプリまで届いた」ことは示さない。WEB のホストの Firewall が、443番を黙って捨てている（DROP）と考えるのが自然だ。

> **ポイント**
> 返事がないときは、送り手側と受け手側の2か所で取ると、止まった区間を絞り込めます。受け手のNICに届いていれば経路の問題ではなく、受け手の中（Firewall やアプリ）を疑います。

### 型3：ICMP のエラーが返る

ノード：Firewall が DROP じゃなくて REJECT だったら、どう見えるんですか？ 第7章で、REJECT は断りの返事を出すって習いました。

博士：Linux の REJECT は、既定で ICMP の **Destination Unreachable** を返す。

> **用語：Destination Unreachable**（ICMP type 3）
> 「宛先に届けられない」ことを送り主に知らせる ICMP のメッセージ。理由をコード（code）で表す。0 は宛先のネットワークへの経路がない、1 はホストに届かない、3 はそのポートで待ち受けがない（Port Unreachable）、13 は管理上の理由で禁止されている。

博士：同じ形は、UDP で待ち受けのないポートに送ったときにも見られる。TCP なら RST で断るところだが、UDP には RST がないので、ICMP で知らせるのだ。DNS サーバーではない WEB に `dig @192.168.2.80 www.example.com` と問い合わせてみると、WEB から ICMP が返る。そのバイト列が面白い。

```text
0020  01 0a 03 03 83 24 00 00 00 00 45 00 00 3d 00 15   .....$....E..=..
0030  00 00 3f 11 f6 f0 c0 a8 01 0a c0 a8 02 50 c0 04   ..?..........P..
0040  00 35 00 29 b9 75                                 .5.).u
```

ノード：オフセット `0x22` の `03` が type 3、`0x23` の `03` が code 3 で Port Unreachable ですね。その後ろに、また `45` が出てきてます。

博士：それが ICMP エラーの大事な仕組みだ。エラーの原因になった元のパケットの、IPヘッダと、その続きの少なくとも先頭8バイトを、そのまま後ろに付けて返すのだ。この例は20バイト＋8バイトだが、実機のOSはもっと長く引用することも多い。

ノード：元のパケットのコピー付き……。`c0 a8 01 0a`、`c0 a8 02 50` が元の送信元と宛先で、その次の `c0 04 00 35` は……49156 と 53！ 元の UDP のポートまで入ってる。

博士：うむ。続く8バイトは UDP ヘッダそのものだ。だから受け取った PC1 は、「49156番から53番へ送った、あの問い合わせへのエラーだ」と特定できる。キャプチャを読む私たちも同じだ。

ノード：なるほど！ ICMP にはポート番号がないのに、どの通信へのエラーかがわかるのは、この引用のおかげなんですね。

博士：第3章の traceroute で、途中のルータが返していた Time Exceeded（type 11。TTL が尽きたという知らせ）にも、同じように元のヘッダが引用されている。

### 型4：TLS の途中で、クライアントが切る

博士：最後は、証明書の問題だ。TCP の接続も Client Hello も Server Hello もそろっているのに、その直後にクライアントが短い Application Data を1つ送り、FIN で切ってしまう。

ノード：さっきのページで出た形ですね。TLS 1.3 だと中身は読めないから……。

博士：そう、キャプチャからは「暗号化の入口でクライアントが自分から切った」までしか言えない。証明書の名前の不一致や期限切れは、あくまで仮説だ。クライアントで `curl -v` を実行して、エラーの文言で確かめる。

### 見えたものを整理する

博士：4つの型に、前のページの NXDOMAIN を加えて整理しておこう。

| 見えたもの | 言えること | 次に確かめること |
| --- | --- | --- |
| DNS の応答が No such name で、SYN が1つもない | 名前解決で止まった | 名前の綴り、DNS の登録 |
| SYN に、宛先から RST, ACK が返る | 宛先には届いたが、そのポートで待ち受けがない | `ss -tlnp`、サービスの状態 |
| 同じ Seq の SYN が、1秒・2秒…の間隔で繰り返される | どこかで黙って捨てられたか、返事が戻れない | 別の観測点で取る、Firewall のルール |
| ICMP Destination Unreachable が返る | 経路がない、または拒否された（引用部分で通信を特定） | ICMP を返した機器の経路表・ルール |
| Server Hello の後、クライアントが短いデータを送って切る | TLS の入口で、クライアントが切った | `curl -v` で証明書のエラーを読む |

> **注意**
> このシミュレータの「Packet Capture」タブでは、同じ SYN が通ったリンクの数だけ、ほぼ同じ時刻に並びます。それは再送ではありません。再送かどうかは、同じ観測点（同じリンク）の中で、同じ Seq が秒単位の間隔をあけて現れるかで見分けます。

> **シミュレータ**
> 実機の Linux は、SYN の再送を既定で6回（1・2・4・8・16・32秒の間隔）まで行い、2分ほど待ってから諦めます。このシミュレータは、最初の SYN と再送2回（1秒・2秒の間隔）で打ち切ります。

> **まとめ**
>
> - RST は「届いたが断られた」、同じ Seq の SYN の再送は「返事がない」。時間のかかり方も違う。
> - 返事がないときは、送り手と受け手の2つの観測点で取り、止まった区間を絞る。tcpdump に見えても、アプリに届いたとは限らない。
> - ICMP のエラーは元のIPヘッダと先頭8バイトを引用するので、どの通信へのエラーかを特定できる。

## PCAPファイルと、キャプチャの取り扱い

### 記録をファイルに残す

ノード：キャプチャって、画面に出して終わりなんですか？ 後から見直したり、先輩に見てもらったりしたいんですけど。

博士：ファイルに保存できる。tcpdump では `-w` でファイルに書き、`-r` で読み込む。

```text
sudo tcpdump -n -i eth0 -w web.pcap 'host 192.168.2.80'    取って web.pcap に保存する
tcpdump -n -r web.pcap 'tcp port 443'                     保存したファイルから、443番だけを表示する
```

ノード：`-w` のときは画面に何も出ないんですか？

博士：出ない。フレームはすべてファイルに書かれる。そのファイルの形式が **PCAP** だ。

> **用語：PCAP**（pcap）
> キャプチャを保存するための、広く使われているファイル形式。フレームごとに、記録した時刻・長さ・バイト列を並べて保存する。tcpdump が `-w` で書く形式で、Wireshark など多くのツールで読める。拡張子は `.pcap`。

博士：Wireshark が既定で保存するのは、その発展形の **pcapng** だ。

> **用語：pcapng**（PCAP Next Generation）
> PCAPを拡張したファイル形式。1つのファイルに複数のインターフェースの記録や、コメントなどの付加情報を入れられる。Wireshark の既定の保存形式で、拡張子は `.pcapng`。

ノード：ファイルにしておけば、サーバーで取って、手元の Wireshark で読む、ができるわけですね。

### 取りすぎないための工夫

博士：ただし、本番のサーバーで何も考えずに `-w` すると、すぐにディスクがあふれる。そこで工夫が2つある。1つめは、各フレームの先頭だけを保存することだ。保存する長さを **スナップ長** と呼ぶ。

> **用語：スナップ長**（snapshot length / snaplen）
> 1つのフレームにつき、先頭から何バイトまでを保存するかの上限。tcpdump では `-s` で指定する。ヘッダだけ見られれば十分なときに小さくすると、ファイルが小さくなり、中身（個人情報など）も残りにくい。

ノード：ヘッダだけでいいなら、先頭の100バイトくらいで十分ですね。

博士：2つめは、ファイルを決まった数だけ回して使う **リングバッファ** だ。

> **用語：リングバッファ**（ring buffer）
> 決まった数のファイルを順に使い、最後まで行ったら最も古いファイルから上書きしていく記録のしかた。長時間取り続けても、使う容量に上限を設けられる。

```text
sudo tcpdump -n -i eth0 -s 128 -C 100 -W 10 -w cap.pcap
  -s 128   各フレームの先頭128バイトだけ保存する
  -C 100   ファイルが約100MBになったら次のファイルへ
  -W 10    ファイルは10個まで。超えたら古いものから上書きする
```

ノード：これなら、いつ起きるかわからない障害を待ち構えて取れますね。

### キャプチャは「中身ごと」の記録である

博士：さて、第1ページで「キャプチャには他人の通信も入る」と言ったのを覚えているかね。ここで、取り扱いの話をまとめておく。

ノード：平文の HTTP なら、パスワードや Cookie までそのまま入ってるんでしたね。

博士：そうだ。だから次のことを守る。

- 取る前に: 自分に権限のあるネットワークで、管理者の許可を得て、目的に必要な範囲（機器・時間・条件）だけを取る。組織の規程や法令に従う。
- 保存するとき: 置き場所とアクセスできる人を決め、調査が終わったら消す。
- 共有するとき: 必要な通信だけを書き出し、関係のないホストや中身を含めない。Wireshark では「Export Specified Packets」で、表示中のフレームだけを保存できる。IPアドレスを別の値に置き換えて渡すときは、置き換えの対応表を別に安全に保管する。

ノード：ファイルを渡した後で、中身が書き換わってないことって、どう確かめるんですか？

博士：ファイルの **ハッシュ値** を記録しておくのだ。

> **用語：ハッシュ値**（hash value）
> ファイルの中身から計算する、決まった長さの値。中身が1バイトでも変わると、まったく別の値になる。`sha256sum cap.pcap` などで計算し、ファイルの取り違えや書き換えに気づくために使う。

> **現場では**
> 本番のネットワークでミラーポートを設定したり、TAPをつないだりするのは、本番環境への設定変更です。目的・対象・期間・承認者と、終わったときの戻し方を事前に決めます。ミラー設定の消し忘れは、帯域の圧迫や情報漏えいのもとになります。ルータや Firewall の上で直接取るときは、機器のCPUの負荷も確かめます。また、ファイルと一緒に「観測点（機器・ポート・向き）」「開始と終了の時刻」「キャプチャフィルタ」「そのときの症状」を残します。これがないと、後から見た人は、何かが見えない理由が観測点なのかフィルタなのかを判断できません。

> **発展**
> PCAPファイルには、フレームの一番外側が何か（リンク種別）も記録されます。ふつうは Ethernet ですが、Linux で `-i any` を使うと、Ethernet ヘッダの代わりに Linux 独自の短いヘッダ（Linux cooked capture）が付きます。トンネルのインターフェースなどでは、Ethernet ヘッダがなく IP ヘッダから始まる形（raw IP）になることもあります。また、NICが VLAN タグを外してから OS に渡すことがあり、トランクにつながったサーバーで取ってもタグが見えないことがあります。

> **シミュレータ**
> 「Packet Capture」タブの「PCAP」ボタンで、表示中のフレームを PCAP ファイルとして書き出せます（Wireshark で開けます）。メニューの「Packet Analyzer」では、手元の pcap / pcapng ファイルを読み込んで同じ形で読めます（20MB・20,000パケットまで。ファイルはブラウザの外へ送信されません）。

> **まとめ**
>
> - キャプチャは PCAP（tcpdump の `-w`）や pcapng（Wireshark の既定）で保存し、別の場所で読み直せる。
> - 本番ではスナップ長（`-s`）とリングバッファ（`-C`・`-W`）で、取りすぎを防ぐ。
> - キャプチャは中身ごとの記録。許可を得て必要な範囲だけを取り、共有前に絞り込み、ハッシュ値で取り違えを防ぐ。

## 観測と仮説を分けて報告する

### 「Firewall が原因です」は、まだ言えない

博士：キャプチャを読み終えたら、結果を人に伝えることになる。ノード君、さっきの443番の件を、チームに報告するとしたら？

ノード：「WEB の Firewall が 443番を落としているのが原因です！」

博士：相変わらず気が早いな。キャプチャで実際に見えたのは何だった？

ノード：え〜っと……PC1 と WEB の両方で、同じ Seq の SYN が3回見えた。返事はどちらにもなかった。……Firewall そのものは、キャプチャには映ってないですね。

博士：そうだ。キャプチャで見えた事実と、そこから考えた説明は、分けて扱わなければならない。前者を **観測** と呼ぶ。

> **用語：観測**（observation）
> キャプチャやログで、実際に見えた事実。どの観測点で、何番のフレームに、何が見えた（何が見えなかった）かとして書く。ほかの人が同じファイルを開けば、同じものを確かめられる。

博士：そして、観測をもとに「おそらくこうだろう」と考えた説明が **仮説** だ。

> **用語：仮説**（hypothesis）
> 観測した事実を説明するために立てた、まだ確かめていない考え。別の観測点のキャプチャ・設定・ログなどで確かめて、初めて事実になる。

### 報告の型

博士：報告は、観測・仮説・確認の3段に分けて書くといい。さっきの件なら、こうだ。

```text
観測点：PC1 の eth0、WEB の eth0（同じ時間帯）
観測　：PC1 の eth0 で、192.168.2.80:443 宛ての SYN が3回（同じ Seq=2326136519、約1秒・2秒の間隔）。
　　　　WEB の eth0 にも、同じ3つの SYN が届いている。
　　　　SYN, ACK・RST・ICMP は、どちらの観測点にも見えない。
仮説　：WEB の中で SYN が捨てられている（ホストの Firewall の DROP など）。
確認　：WEB で iptables -L INPUT -n を見る。nginx-tls が 443番で待ち受けているかを ss -tlnp で見る。
```

ノード：観測には、観測点とフレームの番号や値が書いてあるから、誰が見ても同じものを確かめられる。仮説は「など」が付いてて、確認の方法がセットになってるんですね。

博士：うむ。仮説を確かめた結果、iptables に `DROP tcp dpt:443` のルールが見つかれば、そこで初めて「原因は WEB の Firewall のルール」と言える。

### 「見えない」は「送られていない」ではない

ノード：観測のところに「見えない」って書くのも、観測なんですね。

博士：大事な観測だ。ただし、注意がいる。キャプチャに無いことは、次のどれでも起こる。

- 本当に送られていない
- その観測点を通らなかった（別の経路を通った、スイッチが別のポートに出した）
- キャプチャフィルタで捨てていた
- 取りこぼした（ミラーポートの帯域不足など）

ノード：だから「見えなかった」と書くときは、どの観測点で、どのフィルタで取ったかも書いておく、と。

博士：その通り。「見えない」を「送られていない」と言い切らないことだ。

### 両側で取るなら、時刻を合わせる

博士：今回のように2か所で取ったキャプチャを並べるとき、機器ごとの時計がずれていると、どちらが先かを読み違える。だから、機器の時計は **NTP** で合わせておく。

> **用語：NTP**（Network Time Protocol）
> ネットワーク上の時刻サーバーから時刻を受け取り、機器の時計を合わせるプロトコル。複数の機器のキャプチャやログを、時刻で突き合わせるための前提になる。

ノード：NAT（第6章）を挟んでいたら、前後でIPアドレスやポートが変わっちゃいますよね。

博士：そうだ。その場合は、時刻や Seq などから「この2つは同じ通信だ」と対応付け、その根拠も報告に書いておく。

> **現場では**
> キャプチャは細かい分、常に全部を取り続けるのは容量の面でも負荷の面でも現実的ではありません。普段の傾向は、フローログ（誰と誰が、いつ、どれだけ通信したかの記録。NetFlow や AWS の VPC Flow Logs など）や、機器のメトリクス（CPU使用率や通信量などの数値の記録）・ログで見ます。異常が起きた区間と時間帯を絞り込んでから、キャプチャで深く調べます。フローログからは通信の量と相手はわかりますが、パケットの順序や再送の様子まではわかりません。

> **まとめ**
>
> - 報告は「観測（観測点・フレーム番号・値）」「仮説」「確認の方法」を分けて書く。
> - 「見えない」は、観測点・フィルタ・取りこぼしでも起きる。「送られていない」と断定しない。
> - 複数の観測点を突き合わせるときは、時刻を NTP で合わせ、NAT の前後は対応付けの根拠を書く。

#### ノード君の今日のポイント

- キャプチャは「実際に流れたもの」の記録。ただし、その観測点を通ったものだけ。どこで取ったかを必ず書く。
- 一覧で話の筋 → 階層表示で層ごと → Hexダンプでバイトとオフセット、の順に外側から読む。ポート番号は手がかりにすぎない。
- TCPフラグはビットの足し算（SYN＝`02`、SYN, ACK＝`12`、RST, ACK＝`14`）。相手の Ack ＝ 自分の Seq ＋ 送った量。
- キャプチャフィルタ（BPF）は記録するときに捨て、表示フィルタは表示を絞るだけ。調べ始めは広めに取る。
- DNS は RCODE（3＝NXDOMAIN）、HTTP は平文で丸見え、TLS 1.3 は Client Hello の SNI まで。
- RST は「断られた」、同じ Seq の SYN の再送は「返事がない」、ICMP エラーは引用部分で通信を特定できる。
- 報告は観測と仮説を分ける。「見えない」を「送られていない」と断定しない。キャプチャは許可を得て、必要な範囲だけ取る。
