## キャプチャは「そのリンクを通ったもの」の記録

博士：ノード君、友だちから「APIにつながらないんだけど」と相談されたら、まず何をする？

ノード：え〜っと、設定を見直します。URLとか、ポートとか。

博士：うむ。だが、設定を見直しても原因がはっきりしないことは、よくあるのだ。

ノード：ありますね…。そうなると、もうお手上げッスよ。

博士：そこで役に立つのが、実際に流れたパケットの記録だ。それを見ると、「SYN（TCPの接続の申し込み）は出ているのに返事がない」「名前解決で失敗している」といったことが、事実としてわかる。

ノード：へぇ、推測じゃなくて事実なんですね。

博士：そうだ。今回はその**パケットキャプチャ**の話だ。まず、キャプチャで何が見えるかは「どこで取るか」で決まる、ということ。それから、パケット一覧・階層表示・Hex dumpの読み方を話すぞ。

ノード：盛りだくさんですね。

博士：まだある。キャプチャフィルタと表示フィルタの違い。そして、TCP・DNS・ICMP・TLSの失敗が、キャプチャ上でどう見えるか、だ。

ノード：失敗の見え方、知りたいです。

博士：最後に、観測した事実と、そこからの仮説を分けて報告すること。ここまでが今回の内容だ。

ノード：事実と仮説、ですか。なんだか探偵みたいッスね。

博士：まさにそうだ。キャプチャは、現場に残った証拠なのだ。

### まず、言葉をそろえる

ノード：キャプチャって、Wiresharkのことですよね？

博士：焦るでない。Wiresharkは道具の名前だ。まず言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| パケットキャプチャ | 流れたフレームを、時刻とバイト列ごと記録すること。単に「キャプチャ」とも言う |
| tcpdump | Linuxなどで使う、コマンドラインのキャプチャツール |
| Wireshark | キャプチャを取り、プロトコルごとに読み解いて表示するGUIツール |
| 観測点 | キャプチャを取る場所。どの機器の、どのインターフェースか |
| デコード | バイト列を「ここは宛先MAC、ここはTTL」と項目に読み解くこと |
| pcap / pcapng | キャプチャを保存するファイル形式 |

博士：パケットキャプチャは、流れたフレームを、時刻とバイト列ごと記録することだ。単に「キャプチャ」とも言う。

ノード：tcpdumpがコマンドラインのツールで、WiresharkがGUIのツールなんですね。

博士：その通り。Wiresharkは、キャプチャを取るだけでなく、プロトコルごとに読み解いて表示してくれる。その読み解きが**デコード**だ。

ノード：バイト列を「ここは宛先MAC、ここはTTL」って項目に分けることですね。

博士：うむ。それから**観測点**。キャプチャを取る場所のことで、どの機器の、どのインターフェースか、ということだ。保存するファイル形式は、pcapやpcapngだな。

ノード：でも、わざわざキャプチャしなくても、設定や経路表を見ればわかりませんか？

博士：設定や経路表が示すのは「どうなるはずか」だ。キャプチャが示すのは「実際に何が流れたか」なのだ。

ノード：「はず」と「実際」…。

博士：そうだ。だから、原因を調べるときの強い証拠になる。

### どこで取るかで、見えるものが変わる

ノード：キャプチャを取れば、ネットワークで起きていることが全部わかるんですよね？

博士：残念ながら違う。キャプチャに残るのは、その観測点を通ったフレームだけだ。

博士：防犯カメラを思い浮かべるといい。カメラには、前を通った人しか映らないだろう？

ノード：たしかに。別の通路を通った人は映らないですね。

博士：うむ。ただし、暗号化された中身は、映っていても読めない。そこは覚えておきたまえ。

ノード：じゃあ、僕のPCで取ると、何が見えるんですか？

博士：スイッチにつながったPCで取ると、見えるのは基本的に次のものだ。

- 自分宛て・自分発のフレーム
- ブロードキャスト（LAN内の全員宛て）のフレーム
- フラッディングされたフレーム（スイッチが宛先ポートを知らず、全ポートに出したもの）

ノード：あれ、ほかのPCどうしの通信は入ってないんですね。

博士：スイッチは、宛先のポートにだけフレームを出すからだ。第4章でやったな。

ノード：あ、そうでした。じゃあ、ほかの機器どうしの通信を見たいときは？

博士：スイッチの**ミラーポート**を使う。SPANとも言って、通信のコピーを別のポートに流す設定だ。

博士：あるいは**ネットワークTAP**だ。ケーブルの途中で信号をコピーする機器だな。

ノード：なるほど。コピーを分けてもらって見るんですね。

博士：それから、同じ通信でも、観測点で見え方が変わる。表にするとこうだ。

| 観測点 | 見え方 |
| --- | --- |
| ルータの手前と先 | 送信元・宛先MACが違う（ルータが付け替える） |
| VLANのトランク（複数のVLANを運ぶリンク）上 | 802.1Qタグ（VLAN番号を示す4バイト）が見える |
| アクセスポート側 | タグは見えない（スイッチが外して渡す） |

ノード：ルータの手前と先で、MACが違うんですか？

博士：そうだ。ルータが送信元・宛先MACを付け替えるからな。

ノード：VLANのトランクって、複数のVLANを運ぶリンクでしたっけ。

博士：その通り。トランク上では、802.1Qタグ（VLAN番号を示す4バイト）が見える。だがアクセスポート側では、スイッチがタグを外して渡すので見えないのだ。

ノード：同じ通信なのに、取る場所でこんなに違うんですね。

博士：だから、**「どのリンクで取ったキャプチャか」を必ず記録する**のだ。

### パケット一覧を読む

博士：では、実際にキャプチャを読んでみよう。これはWebサイトに接続し始めたときの一覧だ。1行が1フレームだな（Infoは一部省略してある）。

```text
No.  Time      Source        Destination   Protocol  Length  Info
1    0.000000  192.168.1.10  192.168.1.53  DNS       75      Standard query 0x1a2b A www.example.com
2    0.001210  192.168.1.53  192.168.1.10  DNS       91      Standard query response 0x1a2b A www.example.com A 203.0.113.80
3    0.001530  192.168.1.10  203.0.113.80  TCP       74      50514 → 443 [SYN] Seq=0 Win=64240 Len=0
4    0.012840  203.0.113.80  192.168.1.10  TCP       74      443 → 50514 [SYN, ACK] Seq=0 Ack=1 Win=65160 Len=0
5    0.012990  192.168.1.10  203.0.113.80  TCP       66      50514 → 443 [ACK] Seq=1 Ack=1 Win=64240 Len=0
```

ノード：うわ、数字だらけッスね…。

博士：焦るでない。No.3の行を、列ごとに読んでみよう。

| 列 | No.3の値 | 意味 |
| --- | --- | --- |
| No. | 3 | キャプチャ内の通し番号。報告で「No.3のSYN」と指すのに使う |
| Time | 0.001530 | 既定では、キャプチャ開始からの経過秒。再送の間隔や応答時間を見る |
| Source / Destination | 192.168.1.10 → 203.0.113.80 | IPパケットなら送信元・宛先IP。ARP（IPからMACを調べるプロトコル）のようにIPを持たないフレームではMACアドレス |
| Protocol | TCP | 解析できた最も上位のプロトコル |
| Length | 74 | フレームのバイト数 |
| Info | 50514 → 443 [SYN] … | 上位プロトコルの要約。TCPならポート、フラグ、Seq/Ack、DNSならクエリ名など |

ノード：No.はキャプチャ内の通し番号ですね。報告で「No.3のSYN」と指すのに使う、と。

博士：うむ。Timeは、既定ではキャプチャ開始からの経過秒だ。再送の間隔や応答時間を見るのに使う。

ノード：Source / Destinationは、IPアドレスですね。

博士：IPパケットならな。ARP（IPからMACを調べるプロトコル）のように、IPを持たないフレームではMACアドレスになる。

ノード：Protocolは「TCP」。これはどう決まるんですか？

博士：解析できた最も上位のプロトコルが表示される。Lengthは、フレームのバイト数だ。

博士：Infoは、上位プロトコルの要約だ。TCPならポート、フラグ、Seq/Ack、DNSならクエリ名などが出る。

ノード：じゃあ、一覧全体では何が起きてるんですか？

博士：No.1〜2でDNSの問い合わせが終わり、No.3〜5で**3-way handshake**をしている。TCP接続を始める、3回のやり取りだ。

ノード：No.4とNo.3のTimeの差は…0.012840から0.001530を引いて、約11ミリ秒ですか。

博士：その通り。応答まで約11ミリ秒とわかる。

ノード：あれ、SYNのSeqが0になってます。始まりの値はランダムじゃなかったでしたっけ？

博士：そこはよくひっかかるところだ。TCPのSeq/Ackは、送ったバイトの通し番号と、確認応答の番号だったな。Wiresharkでは、これが既定で**相対値**、つまり最初の番号を0とした値で表示される。

ノード：ということは、本当は0じゃない？

博士：うむ。最初のSYNはSeq=0に見えるが、実際のヘッダにはランダムな大きな数が入っているのだ。

博士：ただし、このアプリでは少し事情が違う。注意書きを見ておくといい。

> このアプリの注意：パケット一覧のSeq/Ackは、相対値ではなく実際の値（raw）です。「SYN, ACKのAck＝相手のSeq＋1」という関係は同じです。また、ARPの行のSource/Destinationには、ARPの中の送信者IP（Sender）と対象IP（Target）を表示します。

ノード：このアプリだと、相対値じゃなくて実際の値なんですね。でも「SYN, ACKのAck＝相手のSeq＋1」という関係は同じ、と。

博士：そうだ。ARPの行のSource/Destinationに、ARPの中の送信者IP（Sender）と対象IP（Target）が出ることも覚えておきたまえ。

### 階層表示：外側から順に剥がす

ノード：一覧の1行って、もっと細かく見られないんですか？

博士：見られる。1行を選ぶと、そのフレームが外側のヘッダから順に解析されるのだ。

博士：第1章のカプセル化を覚えているか？

ノード：箱の中に箱、ってやつですね。

博士：うむ。階層表示は、その箱を外から開けていく作業だ。図にするとこうなる。

```text
Frame 12: 78 bytes on wire
Ethernet II, Src: 00:11:22:33:44:55, Dst: 00:1a:2b:3c:4d:5e
802.1Q Virtual LAN, PRI: 0, DEI: 0, ID: 10
Internet Protocol Version 4, Src: 192.168.1.10, Dst: 192.168.2.20
Transmission Control Protocol, Src Port: 50000, Dst Port: 80
```

ノード：Ethernet、802.1Q、IPv4、TCP…。上から順に開けていくんですね。でも、次の箱の中身が何かって、どうやってわかるんですか？

博士：各ヘッダに、「中身の種類」を示す欄があるのだ。受け取った側が迷わず読めるよう、そう設計されている。

| 欄 | 値 → 次に入っているもの |
| --- | --- |
| EtherType | 0x0800 → IPv4、0x0806 → ARP、0x86DD → IPv6、0x8100 → 802.1Qタグ |
| IPv4のProtocol | 1 → ICMP（IPの連絡係）、6 → TCP、17 → UDP、47 → GRE（トンネル）、50 → ESP（IPsecの暗号化部分） |

ノード：EtherTypeが0x0800ならIPv4、0x0806ならARP、0x86DDならIPv6、0x8100なら802.1Qタグ…。

博士：そうだ。IPv4のProtocolなら、6がTCP、17がUDPだ。1はICMP、IPの連絡係だな。47はトンネルのGRE、50はIPsecの暗号化部分のESPだ。

ノード：じゃあ、TCPの上のHTTPも、同じように欄で決まるんですか？

博士：いい質問だ。TCP/UDPの上のDNS、HTTP、TLSには、こうした欄がない。

ノード：え、じゃあどうやって判定してるんですか？

博士：主に、ポート番号（53、80、443など）と、中身のパターンからの推測だ。

博士：だから、標準外のポートのHTTPは、そのままではHTTPと表示されないことがある。

ノード：つまり、ポート番号だけで中身を決めつけちゃダメってことですよね。

博士：その通り。**ポート番号は手がかりであって、中身の保証ではない**のだ。

### Hex dump：バイトとフィールドの対応

博士：一覧もデコードも、結局はバイト列の解釈にすぎない。そのバイト列を並べたものがHex dumpだ。次は、802.1Qタグのないフレームの例だ。

```text
0000  00 1a 2b 3c 4d 5e 00 11 22 33 44 55 08 00 45 00
0010  00 3c 1c 46 40 00 40 06 9a 07 c0 a8 01 0a c0 a8
0020  02 14 c3 50 00 50 ...
```

ノード：うっ、暗号みたいッス。

博士：1バイトは16進2桁だ。左端の数字は、先頭（0）からの位置を16進で表した**オフセット**だな。

ノード：じゃあ、2行目の`0010`は、先頭から0x10の位置から始まる、ってことですね。

博士：そうだ。では、バイトとフィールドの対応を表にしよう。

| オフセット | バイト | 意味 |
| --- | --- | --- |
| 0x00〜0x05 / 0x06〜0x0b | `00 1a …` / `00 11 …` | 宛先MAC / 送信元MAC |
| 0x0c〜0x0d | `08 00` | EtherType＝IPv4 |
| 0x0e | `45` | バージョン4、ヘッダ長5×4＝20バイト |
| 0x16 / 0x17 | `40` / `06` | TTL＝64 / Protocol＝TCP |
| 0x1a〜0x1d | `c0 a8 01 0a` | 送信元IP＝192.168.1.10（`c0`＝12×16＋0＝192） |
| 0x22〜0x23 / 0x24〜0x25 | `c3 50` / `00 50` | 送信元ポート＝50000 / 宛先ポート＝80 |

ノード：0x00〜0x05が宛先MAC、0x06〜0x0bが送信元MACですね。

博士：うむ。その次、0x0c〜0x0dの`08 00`がEtherTypeで、IPv4だ。

ノード：0x0eの`45`は？

博士：バージョン4で、ヘッダ長が5×4＝20バイト、という意味だ。

ノード：0x16の`40`がTTL＝64で、0x17の`06`がProtocol＝TCP…。

博士：その通り。0x1a〜0x1dの`c0 a8 01 0a`は、送信元IP＝192.168.1.10だ。`c0`は12×16＋0＝192、という計算になる。

ノード：なるほど、16進を10進に直せばいいんですね。ポートは`c3 50`が送信元の50000、`00 50`が宛先の80、と。

博士：うむ。ここで注意がある。802.1Qタグが付くと、送信元MACの直後に4バイトが入るのだ。

ノード：4バイト…。何が入るんですか？

博士：`81 00`と、VLAN IDを含む2バイトのTCI（タグの制御情報）だ。だから、以降のフィールドは4バイト後ろにずれる。

ノード：タグの有無で、オフセットが変わっちゃうんですね。

### キャプチャフィルタと表示フィルタ

ノード：博士、「DNSだけ見たい」ときはどうすればいいですか？

博士：絞り方は2つある。並べるとこうだ。

```text
tcpdump -i eth0 -n udp port 53    取るときに絞る（キャプチャフィルタ）
udp.port == 53                    取った後に絞る（Wiresharkの表示フィルタ）
```

ノード：上がtcpdumpで、下がWiresharkですね。何が違うんですか？

博士：上は取るときに絞る**キャプチャフィルタ**、下は取った後に絞る**表示フィルタ**だ。比べるとこうなる。

| | キャプチャフィルタ | 表示フィルタ |
| --- | --- | --- |
| 効くとき | 記録するとき | 記録した後、表示するとき |
| 合わないパケット | 記録されない。後から見られない | 隠れるだけ。フィルタを消せば戻る |
| 構文 | BPF（pcap-filter）。tcpdumpとWiresharkで共通 | Wireshark独自 |
| 例 | `tcp port 80` | `tcp.port == 80`、`dns.flags.rcode == 3`、`tcp.analysis.retransmission` |

ノード：キャプチャフィルタは記録するときに効いて、表示フィルタは記録した後、表示するときに効く…。

博士：うむ。一番の違いは、合わないパケットの扱いだ。キャプチャフィルタだと記録されない。後から見られないのだ。

ノード：表示フィルタなら隠れるだけで、フィルタを消せば戻るんですね。

博士：その通り。構文も別だ。キャプチャフィルタはBPF（pcap-filter）で、tcpdumpとWiresharkで共通。表示フィルタはWireshark独自だ。

ノード：`tcp port 80`と`tcp.port == 80`。似てるけど、別物なんですね。

博士：そうだ。表示フィルタなら、`dns.flags.rcode == 3`や`tcp.analysis.retransmission`のような書き方もできる。

ノード：じゃあ、最初から絞って取っておけば楽ですね。

博士：そこは気をつけたまえ。キャプチャフィルタで絞りすぎると、原因を示すパケットまで捨ててしまう。

ノード：あっ、捨てたら戻らないんでしたね。

博士：うむ。取るときに絞るのか、取った後に絞るのかを区別するのだ。

博士：では、BPF（Berkeley Packet Filter）の書き方の例を見ておこう。

```text
host 192.168.1.10          送信元か宛先がこのIP
src net 192.168.1.0/24     送信元がこのネットワーク
dst port 53                宛先ポートが53
udp port 53                UDPで、どちらかのポートが53
tcp port 80                TCPで、どちらかのポートが80
icmp or arp                ICMPまたはARP
vlan 10                    VLAN ID 10のタグ付きフレーム
host 10.0.0.1 and not port 22
```

ノード：`host`は送信元か宛先、`src`は送信元、`dst`は宛先…。向きも指定できるんですね。

博士：うむ。`vlan 10`なら、VLAN ID 10のタグ付きフレームだ。最後の行のように、`and`や`not`で組み合わせることもできる。

ノード：DNSなら、`udp port 53`でいいんですよね？

博士：通常のDNSの問い合わせはUDP 53だからな。`port 53`と書けば、TCP 53も含む。

博士：それから、`and`・`or`・`not`は`&&`・`||`・`!`とも書けて、括弧でまとめられる。

### 接続の失敗は、キャプチャでこう見える

博士：さて、いよいよ本題だ。接続の失敗は、キャプチャではこう見える。

| 見えたもの | 何が起きたか |
| --- | --- |
| 同じSeqのSYNが、間隔を広げて再送される。返事がない | どこかで黙って破棄されたか、SYN, ACKが戻れていない |
| SYNに「RST, ACK」が返る（RSTは接続を打ち切る合図） | 宛先ホスト（またはRSTを代わりに返す機器）には届いたが、そのポートで待ち受けていない |
| DNS応答のRCODE（結果の番号）が3（NXDOMAIN） | その名前は存在しない。Wiresharkでは「No such name」 |
| ICMP Destination Unreachable | 途中の機器か宛先が「届けられない」と知らせた |
| TLSのServer Helloの直後に切断 | 暗号化の入口で止まった（証明書の検証失敗などが仮説） |

ノード：失敗にも、いろいろあるんですね。

博士：うむ。一つずつ見ていこう。まずSYNの再送だ。同じSeqのSYNが、間隔を広げて再送され、返事がない。

ノード：それって、どういう状態なんですか？

博士：どこかで黙って破棄されたか、SYN, ACKが戻れていないかだ。たとえば、次のように見える。

```text
No.  Time      Info
1    0.000000  50514 → 443 [SYN] Seq=0
2    1.001000  [TCP Retransmission] 50514 → 443 [SYN] Seq=0
3    3.005000  [TCP Retransmission] 50514 → 443 [SYN] Seq=0
```

ノード：Timeの間隔が、だんだん広がってますね。Seqはずっと0です。

博士：同じ申し込みを送り直すのだから、Seqは同じなのだ。

ノード：RSTは、どういうときに返るんですか？

博士：RSTは、接続を打ち切る合図だ。SYNに「RST, ACK」が返ったら、宛先ホスト（またはRSTを代わりに返す機器）には届いたが、そのポートで待ち受けていない、ということだ。

ノード：届いてはいるんですね。黙って捨てられるのとは違う、と。

博士：そうだ。次は**DNS**だ。DNS応答のRCODE（結果の番号）が3なら**NXDOMAIN**。その名前は存在しない、という意味だ。Wiresharkでは「No such name」と出る。

ノード：NXDOMAINのときは、TCPのSYNはどうなるんですか？

博士：一度も送られない。接続先のIPがわからないからな。

ノード：あ、そうか。住所がわからないと、手紙も出せないですもんね。

博士：うむ。ちなみに、名前はあるが該当タイプのレコードがない場合は、NOERRORで回答が0件になる。NXDOMAINとは区別されるのだ。

ノード：名前がないのと、レコードがないのは別物、と。

博士：次は**ICMPエラー**だ。途中の機器か宛先が「届けられない」と知らせてきたのが、ICMP Destination Unreachableだな。

ノード：でも、ICMPのエラーが来ても、どの通信へのエラーかわからなくないですか？

博士：心配いらない。Destination Unreachable（type 3）やTime Exceeded（type 11）には、元のIPヘッダと、続く先頭8バイト以上が入っている。

ノード：8バイトで、何がわかるんですか？

博士：8バイトあれば、TCP/UDPのポートまで含む。だから、どの通信へのエラーかを特定できるのだ。

ノード：なるほど。エラーに、元の荷札のコピーが付いてくるんですね。

博士：うまいことを言う。UDPの閉じたポートには、Port Unreachable（code 3）が返るのが典型だ。

博士：LinuxのUDP方式のtracerouteでも、最後の宛先はこれを返す。途中のルータからは、TTLが尽きたときにTime Exceededが返る。

ノード：tracerouteの仕組みも、キャプチャで見えるんですね。

博士：最後は**TLS**だ。暗号化と、証明書による相手の確認の仕組みだな。

ノード：暗号化されてたら、キャプチャしても何も見えないんじゃ…。

博士：全部が見えないわけではない。最初にクライアントが送るClient Helloは、暗号化されていないのだ。

博士：だから、SNI（server_name拡張）で接続先のホスト名が見える。ECH、つまりEncrypted Client Helloを使う場合を除いてな。

ノード：その後はどうなんですか？

博士：TLS 1.3では、Server Hello以降のハンドシェイク（証明書を含む）も、アプリケーションデータも暗号化される。Wiresharkでは、主に「Application Data」と表示される。

ノード：じゃあ、表にあった「Server Helloの直後に切断」は、理由がわからないですね。

博士：うむ。暗号化の入口で止まった、ということまではわかる。証明書の検証失敗などは、あくまで仮説だ。

博士：中身は見えないから、切断の理由はクライアント側のログ（`curl -v`など）で確かめるのだ。

ノード：暗号化されてないHTTPなら、どうですか？

博士：平文のHTTPなら、`GET / HTTP/1.1`やHostヘッダ、`HTTP/1.1 200 OK`がそのまま読める。

### PCAPファイル

ノード：取ったキャプチャは、保存しておけるんですか？

博士：できる。主にpcap形式か、Wiresharkの既定のpcapng形式で保存する。

博士：実機のtcpdumpでは、`-w`でファイルに保存し、`-r`で読む。

ノード：保存と読み込みですね。

博士：それから、`-n`で名前解決を止めるのが定番だ。

ノード：どうして止めるんですか？

博士：逆引きのDNS通信で、表示が遅れたり、記録に混ざったりしないようにだ。まとめると、たとえばこうなる。

```text
sudo tcpdump -i eth0 -n -w web.pcap 'host 203.0.113.80 and tcp port 443'
```

ノード：eth0で、203.0.113.80とのTCP 443番だけを、名前解決なしでweb.pcapに保存するんですね。

### 観測と仮説を分ける

博士：キャプチャで何かを見つけたら、報告することになる。そのとき大事なのが、観測と仮説を分けることだ。例を見てみよう。

```text
観測：PC1のeth0で、10.0.2.80:443宛てのSYNが3回（No.1〜3、同じSeq）。SYN, ACKもRSTもない。
仮説：途中のFirewallが破棄している。
確認：Firewallのログ、サーバー側でのキャプチャ。
```

ノード：観測、仮説、確認、の3段になってるんですね。

博士：うむ。「SYNが3回見え、SYN, ACKは見えない」は観測だ。「Firewallが落としている」は仮説だ。

ノード：え、SYNに返事がないなら、Firewallで決まりじゃないんですか？

博士：相変わらず気が早いな。それはまだ仮説にすぎない。仮説は、別の観測点のキャプチャ、経路表、ログで確かめるのだ。

博士：それと、根拠のパケット番号を添えるといい。そうすれば、ほかの人も検証できる。

ノード：「No.1〜3」って書いてあるのは、そのためなんですね。

博士：もう一つ大事なことがある。キャプチャに無いことは、取りこぼしや、観測点・フィルタの誤りでも起こる。

ノード：あっ、フィルタで絞りすぎたら、映らないですもんね。

博士：その通り。だから、**「見えない」を「送られていない」と断定しない**ことだ。

### 取る前に、許可と範囲を確認する

ノード：よし、さっそく会社のネットワークでキャプチャしてみます！

博士：まあ待て。キャプチャには、通信内容、Cookie、平文の認証情報、個人情報が含まれることがあるのだ。

ノード：えっ、そんなものまで入っちゃうんですか。

博士：うむ。だから、権限のあるネットワークで、許可を得て、必要な範囲だけを取る。

博士：組織の規程や法令に従うこと。保存場所とアクセス権を管理し、共有前には不要な情報を取り除くこと。

ノード：取る前も、取った後も、気をつけないといけないんですね。

### 発展：実機で戸惑いやすい点

博士：ここからは、実機で戸惑いやすい点だ。今は読み飛ばしてもかまわない。

ノード：せっかくなので、聞いておきます。

博士：まず、NICやドライバがVLANタグを外してからOSに渡すことがある。だから観測点によっては、タグが見えない。

ノード：タグが見えなくても、慌てちゃダメってことですね。

博士：次に、送信側ホストで取ると、チェックサム誤りと表示されることがある。NICのチェックサムオフロード、つまり計算をNICに任せる機能のためだ。

ノード：え、それって壊れてるんじゃ…。

博士：それだけで破損と判断してはいかん。

博士：それから、ファイルにはリンク種別が記録される。通常のEthernetのほか、Linuxの`-i any`で使うLinux cooked capture（SLL/SLL2）や、Ethernetヘッダを持たないraw IPなどがある。

ノード：Ethernetじゃない形式もあるんですね。

博士：最後に、TLS 1.2以前では、証明書は暗号化されずに送られる。だから、キャプチャで読めるのだ。

ノード：TLS 1.3だとServer Hello以降は暗号化されてたから、そこが違うんですね。

### このシミュレータで試せること

博士：このシミュレータでは、次のことを試せるぞ。

- 記録されたフレームをPacket CaptureタブやPacket Analyzerで開き、No./Time/Source/Destination/Protocol/Length/Infoの一覧、階層デコード、Hex dumpを確認する。項目にカーソルを合わせると、該当バイトが強調されます。
- フィルタを試す：`tcp port 80`、`udp port 53`、`host 192.168.1.10 and icmp`、`src net 192.168.1.0/24`、`vlan 10`、`not arp`、`(dns || tls) && host 10.0.0.53`、`-i eth0`、`ether host 00:11:22:33:44:55`、`esp`、`gre`。
- 機器のCLIで `tcpdump -i eth0 -e -c 10 icmp` を実行し、MAC付きで直近の10件を表示する。
- 表示中のフレームをPCAPとして書き出し、Wiresharkで開いて比較する。手元のpcap/pcapngを取り込んで読む（ファイルはブラウザ内だけで解析され、送信されません）。
- ラボ「パケットで通信を読む」で、3-way handshake、DNSのポート、tracerouteのTime Exceededを読み取る。
- Capstoneで、SYN再送、RST、DNS NXDOMAIN、Server Hello後のTLS切断、ICMP Unreachableから、接続失敗の理由を説明する。

ノード：手元のpcapも読めるんですね。ブラウザの外に送信されないなら安心ッス。

博士：ただし、シミュレータならではの簡略化もある。

> シミュレータでの簡略化:
> - すべてのリンクのフレームが自動で記録されます。実機ではミラーポートやTAPなどの観測点を用意しない限り、ほかの機器どうしの通信は見えません。
> - `tcpdump` はその機器のリンクで記録済みのフレームを再生するもので、ライブキャプチャではありません。`-c N` は記録済みの最後のN件を表示します（実機では、N件取ったところで終了します）。
> - `dns`・`http`・`tls` はBPFの構文ではなく、表示フィルタ風の拡張です（実機のtcpdumpでは `port 53` などで指定します）。未対応の式は、すべてに一致させずエラーになります。
> - 生成フレームのIPv4/ICMP/TCP/UDPチェックサムは正しく計算されますが、FCSとプリアンブルは省略しています。TLSのServer Hello以降は実際の暗号ではなく、意味を持たない埋め草のバイト列です。取り込めるPCAPは20MB・20,000パケットまでです。

ノード：全部のリンクが自動で記録されるのは便利ですけど、実機ではそうはいかないんですね。

博士：うむ。実機では、観測点を用意するところから始まるのだ。

博士：さて、次回は「ネットワーク構築」だ。これまでの章で学んだことを、1つの構成にまとめていくぞ。

ノード：いよいよ組み立てですか。キャプチャで確かめながら進めたいッスね。

博士：うむ、それがいい。本当にその通りに流れるかを確かめるのが、最後の仕上げなのだ。

ノード：はい、がんばります！

#### 用語メモ

- **パケットキャプチャ**［packet capture］：流れたフレームを、時刻とバイト列ごと記録すること。単に「キャプチャ」とも言う。
- **観測点**：キャプチャを取る場所。どの機器の、どのインターフェースか。
- **ミラーポート**［SPAN］：通信のコピーを別のポートに流すスイッチの設定。
- **ネットワークTAP**［network TAP］：ケーブルの途中で信号をコピーする機器。
- **デコード**［decode］：バイト列を「ここは宛先MAC、ここはTTL」と項目に読み解くこと。
- **キャプチャフィルタ**［capture filter］：記録するときに絞るフィルタ。構文はBPF（pcap-filter）で、合わないパケットは記録されない。
- **表示フィルタ**［display filter］：記録した後、表示を絞るWireshark独自のフィルタ。消せば元に戻る。
- **NXDOMAIN**：DNS応答のRCODEが3。その名前は存在しないことを示す。
- **SNI**：暗号化されないClient Helloのserver_name拡張。接続先のホスト名が見える。
- **pcap / pcapng**：キャプチャを保存するファイル形式。pcapngはWiresharkの既定。

#### ノード君の今日のポイント

- キャプチャは、その観測点を通ったものだけの記録。どこで取ったかを必ず記録する。
- 一覧 → 階層表示 → Hexの順に、外側から読み解く。ポート番号は手がかりにすぎない。
- キャプチャフィルタ（BPF）は記録時に捨て、表示フィルタは表示を絞るだけ。構文も別。
- SYN再送・RST・NXDOMAIN・ICMP Unreachable・TLS切断は、それぞれ違う失敗を示す。
- 報告では、パケット番号付きの観測と、仮説を分けて書く。「見えない」を「送られていない」と断定しない。
- キャプチャには個人情報なども含まれるので、許可を得て、必要な範囲だけを取る。
