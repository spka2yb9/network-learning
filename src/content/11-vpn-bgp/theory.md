## VPNで拠点をつなぎ、BGPで経路を伝える

博士：ノード君、「オフィスのPCから、AWSのVPCにある社内システムへ接続したい」と頼まれたら、どうする？

ノード：え〜っと、専用線を引く…とかですか？

博士：ところが、専用線は引かずに、インターネット越しに安全につなぎたいという依頼なのだ。しかも、回線が1本切れても、自動で切り替わってほしいという。

ノード：注文が多いッスね。

博士：うむ。こうした依頼に応えるのが、**VPN**と**BGP**の組み合わせだ。前半でVPN、後半でBGPを扱い、最後に2つを組み合わせた障害時の動きを追うぞ。

ノード：今回は、どんなことがわかるようになるんですか？

博士：まず、トンネル（パケットを別のパケットで包む仕組み）と、IPsec・GREの違い。それから、VPNで「行きと帰りの両側に経路が必要」な理由だ。

ノード：両側、ですか。片側だけじゃだめなんですね。

博士：そうだ。理由は、あとでじっくりやる。後半は、BGPが経路を伝え合う流れと、セッションが確立する条件。そして、1つの宛先について、BGPが最良の経路（**Best Path**）を選ぶ順番だ。

ノード：最後が、自動で切り替わる話ですね。

博士：その通り。トンネル2本とBGPで、障害時に自動で切り替わる仕組みを話すぞ。

### まず、言葉をそろえる

博士：最初に、言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| VPN（Virtual Private Network） | インターネットのような共有の回線の上に、専用線のように使える仮想の通り道を作る技術 |
| トンネル | 元のパケットを別のパケットで包んで、相手まで運ぶ仕組み |
| アンダーレイ | トンネルを運ぶ、下のネットワーク（例：インターネット） |
| IPsec | IPパケットを暗号化し、改ざんを検知する仕組み |
| BGP（Border Gateway Protocol） | 組織どうしで「どのネットワークがどこにあるか」を伝え合うルーティングプロトコル |
| AS（Autonomous System、自律システム） | 1つの組織が共通の方針で運用するネットワークの単位 |
| プレフィックス | 172.16.2.0/24 のような、宛先ネットワークの範囲。経路表の「宛先」にあたる |
| 経路の広告 | 「このプレフィックスへは、私に送ってください」と隣に伝えること |

ノード：VPNは、共有の回線の上に、専用線みたいな仮想の通り道を作る技術なんですね。

博士：うむ。その通り道を作るのが**トンネル**で、トンネルを運ぶ下のネットワークが**アンダーレイ**だ。例えばインターネットだな。

ノード：IPsecは、暗号化と改ざん検知ですか。

博士：そうだ。そして**BGP**は、組織どうしで「どのネットワークがどこにあるか」を伝え合うルーティングプロトコル。**AS**は、1つの組織が共通の方針で運用するネットワークの単位だ。

ノード：**プレフィックス**は、172.16.2.0/24 みたいな、経路表の「宛先」のことですね。

博士：その通り。そして「このプレフィックスへは、私に送ってください」と隣に伝えることを、**経路の広告**という。

ノード：なるほど。「私に送って」って言うのが広告なんですね。

### トンネル — パケットを別のパケットで包む

博士：では、**トンネル**からだ。元のパケットを別のヘッダで包み、アンダーレイを通して相手まで運ぶ仕組みだ。

ノード：包む…どこかで聞いたような。

博士：01章のカプセル化で、「箱をさらに箱に入れる」話をしたな。トンネルは、IPパケットをまるごと、もう1つのIPパケットに入れるのだ。

ノード：IPの中にIPですか。途中のルータは混乱しないんですか？

博士：しない。途中のルータは、外側のヘッダだけを見て転送する。中身の宛先は気にしないのだ。

ノード：あ、だったら、インターネットのルータが知らない社内のアドレスでも届くってことですよね。

博士：うむ。192.168.10.0/24 などの社内のアドレスでも、相手の拠点まで届けられる。

ノード：VPNって、スマホで会社につなぐのもそうですよね？

博士：そうだ。VPNには、大きく2つの使い方がある。1つは**リモートアクセスVPN**。個々のPCやスマートフォンが、クライアントソフトなどで社内ネットワークに接続する。

ノード：もう1つは？

博士：**サイト間VPN（Site-to-Site VPN）**だ。拠点のゲートウェイどうしがつながり、ネットワークとネットワークを結ぶ。端末側に特別な設定は不要だ。

ノード：端末は何もしなくていいんですね。

博士：この章で扱うのは、こちらのサイト間VPNだ。

### IPsec — IKEで合意し、ESPで守る

ノード：で、暗号化はどうするんですか？

博士：そこで**IPsec**だ。IPsecは、役割の違う2つのプロトコルでできている。

ノード：2つ？

博士：まず**IKE（Internet Key Exchange）**。両端のゲートウェイが「話し合う」ためのプロトコルだ。最初に、互いを認証する。

ノード：認証って、パスワードみたいなものですか？

博士：近いな。方法は、両端に同じ鍵を設定しておく**事前共有鍵（PSK、Pre-Shared Key）**か、証明書だ。

ノード：認証が済んだら？

博士：次に、使う暗号方式の組み合わせと鍵を合意する。この組み合わせを**プロポーザル**という。例えば aes256-sha256 だな。

ノード：IKEは、どのポートを使うんですか？

博士：通常はUDP 500だ。途中にNATがある場合は、UDP 4500を使う。これを**NAT-T**と呼ぶ。

ノード：話し合って決まった内容は、何て呼ぶんですか？

博士：合意した内容を**SA（Security Association）**と呼ぶ。IKEどうしの話し合いを守る**IKE SA**と、データを守る**IPsec SA**がある。

ノード：じゃあ、両端で鍵が違っていたら…

博士：うむ。PSKやプロポーザルが両端で一致しないと、SAができず、トンネルは上がらない。そこは覚えておきたまえ。

ノード：もう1つのプロトコルは？

博士：**ESP（Encapsulating Security Payload）**だ。データの暗号化と改ざん検知を提供する。IPプロトコル番号は50だ。

ノード：プロトコル番号って…

博士：01章で見た、「Protocol」欄の番号だよ。

ノード：あ、そうでした。

博士：サイト間VPNで使う**トンネルモード**では、元のIPパケット全体を暗号化し、ゲートウェイどうしのIPを持つ新しいIPヘッダを付ける。図にするとこうなる。

```text
元のパケット   [IP 192.168.10.10 → 10.0.1.10][TCP][データ]
ESPトンネル    [IP 198.51.100.2 → 203.0.113.2][ESP][暗号化された元のパケット]
```

ノード：外側が 198.51.100.2 → 203.0.113.2 で、192.168.10.10 → 10.0.1.10 の元のパケットは、暗号化されて中に入っちゃうんですね。

博士：その通り。だからキャプチャでは、外側のIPと、ESPの**SPI**（どのSAで守られているかを示す番号）・シーケンス番号は見える。

ノード：内側の宛先やポートは？

博士：見えない。

#### GRE — 包むだけで、暗号化しないトンネル

ノード：トンネルって、IPsecしかないんですか？

博士：いや、**GRE（Generic Routing Encapsulation）**もある。IPパケットを包むトンネルだが、暗号化はしない。IPsecと比べてみよう。

| | GRE | IPsec（ESP、トンネルモード） |
| --- | --- | --- |
| IPプロトコル番号 | 47 | 50 |
| 暗号化・改ざん検知 | しない | する |
| キャプチャで見える内容 | 内側のパケットがそのまま読める | 外側のIPとSPI・シーケンス番号だけ |
| 主な仕様 | RFC 2784 | RFC 4303（ESP） |

ノード：GREはプロトコル番号47で、キャプチャすると内側のパケットがそのまま読めちゃうんですね。

博士：そうだ。IPsecのほうは、外側のIPとSPI・シーケンス番号だけだ。仕様はGREがRFC 2784、ESPがRFC 4303だな。

ノード：GREで、暗号化もしたいときは？

博士：GREをIPsecで保護する構成にするといい。

### ルートベースとポリシーベース — どの通信をトンネルに入れるか

博士：トンネルができたら、次は「どの通信をトンネルに入れるか」を決める。

ノード：全部入れちゃえばいいんじゃないですか？

博士：相変わらず気が早いな。決め方は2種類ある。

| | ポリシーベースVPN | ルートベースVPN |
| --- | --- | --- |
| 決め方 | 「192.168.10.0/24 から 10.0.1.0/24 へ」のような条件（トラフィックセレクタ） | 経路表で、トンネルインターフェースへ向けた通信 |
| BGPなどの動的ルーティング | 向かない | トンネル上で動かせる |

ノード：ポリシーベースは、「192.168.10.0/24 から 10.0.1.0/24 へ」みたいな条件で決めるんですね。

博士：うむ。この条件を**トラフィックセレクタ**という。Cisco機器のポリシーベースVPNでは、この条件をACLで書くため「暗号化ACL」とも呼ぶ。

ノード：ルートベースは、経路表でトンネルインターフェースへ向けた通信…。トンネルインターフェースって何ですか？

博士：**トンネルインターフェース**は、トンネルを1本の仮想のインターフェース（例：tunnel1）として扱うものだ。普通のインターフェースと同じようにIPアドレスを付け、経路の出口に指定できる。

ノード：トンネルにも、IPアドレスを付けるんですか。

博士：そうだ。AWSのSite-to-Site VPNでは、トンネル内側のアドレスに 169.254.0.0/16 の中の /30 を使う。

ノード：表だと、BGPなどの動的ルーティングは、ポリシーベースには向かなくて、ルートベースならトンネル上で動かせるんですね。

博士：ルートベースなら、トンネルはただの「出口の1つ」だからだ。だから、03章の経路表やこの章のBGPを、そのまま使える。

ノード：つまり、トンネルも普通の出口として、経路表で扱えるってことですよね。

博士：その通り。

### 経路は、両側でトンネルに向ける

博士：では、オフィスのPC1（192.168.10.10）から、VPC内のEC2（10.0.1.10）へ接続する例を、1ホップずつ追ってみよう。

```text
Office LAN 192.168.10.0/24 → CGW（拠点ルータ。Customer Gateway）
  → 暗号化トンネル（インターネット上）
  → VGW1（AWS側の終端。例：仮想プライベートゲートウェイ） → VPC側 10.0.1.0/24

行き  192.168.10.10 → 10.0.1.10
  1. PC1：自分のLAN外なので、Default GatewayのCGWへ
  2. CGW：経路表で 10.0.1.0/24 → tunnel1 に一致
  3. CGW：ESPで包む。外側は 198.51.100.2 → 203.0.113.2
  4. インターネット：外側の宛先 203.0.113.2 だけを見て転送
  5. VGW1：外側を外して復号し、元のパケットを 10.0.1.10 へ
帰り  10.0.1.10 → 192.168.10.10
  6. VGW1：経路表で 192.168.10.0/24 → トンネル に一致するか
  7. 包んでCGWへ。CGWが外してPC1へ
```

ノード：CGWが拠点ルータで、VGW1がAWS側の終端ですね。

博士：うむ。行きは、PC1が自分のLAN外なので、Default GatewayのCGWへ送る。CGWは経路表で 10.0.1.0/24 → tunnel1 に一致し、ESPで包む。

ノード：外側は 198.51.100.2 → 203.0.113.2 で、インターネットは外側の宛先 203.0.113.2 だけを見て転送するんですね。

博士：そして、VGW1が外側を外して復号し、元のパケットを 10.0.1.10 へ届ける。

ノード：届いた！ じゃあ、これで完成ですね。

博士：まあ待て。帰りがある。6番を見たまえ。

ノード：「VGW1：経路表で 192.168.10.0/24 → トンネル に一致するか」…。帰りは、VGW1の経路表しだいなんですね。

博士：そうだ。拠点側には「10.0.1.0/24 → トンネル」、クラウド側には「192.168.10.0/24 → トンネル」の経路が必要なのだ。

ノード：6の経路がなかったら、どうなるんですか？

博士：帰りのパケットは、別の経路（例：インターネット向けのDefault Route）に出てしまう。宛先がプライベートアドレスなので、インターネットで捨てられる。

ノード：うわ。トンネルはUpなのに…

博士：そう、トンネルがUpでも、通信は成立しない。

ノード：なるほど。「行きと帰りの両側に経路が必要」って、こういうことですか。

博士：もう1つ、大事な経路がある。トンネルの相手、つまり外側の宛先 203.0.113.2 への経路だ。

ノード：それも、トンネルに向ければいいんですか？

博士：逆だ。その経路は、トンネルの外、つまりインターネット側を向いている必要がある。この経路自体をトンネルに向けると、「トンネルを運ぶためにトンネルを使う」ことになり、トンネルは正しく動かない。

ノード：自分で自分を運ぶ…確かに無理ッスね。

博士：トンネルには、あと2つ注意点がある。トンネルは、内側のパケットにとって1ホップだ。tracerouteでは、トンネル内の途中のルータは見えない。

ノード：インターネットの中をいくつ越えても、1ホップに見えるんですね。

博士：それから、包む分だけヘッダが増える。だから、**MTU**（1回で運べる最大サイズ。01章でやったな）や、**TCP MSS**（1つのTCPセグメントに入れるデータの最大サイズ）の調整が必要になることがある。

### BGP — AS同士が経路を伝え合う

博士：さて、後半はBGPだ。03章のOSPFを覚えているか？

ノード：1つの組織の中で、コストが最小の道を自動で計算するやつですね。

博士：うむ。BGPは、組織どうし（AS間）で経路を伝え合うためのプロトコルだ。どの経路を受け取り、どれを優先するかという、組織の方針を反映できるように作られている。

ノード：ASは、どうやって区別するんですか？

博士：**ASN（AS番号）**で識別する。2バイトASNでは、64512〜65534がプライベート用だ。4バイトASNにも、プライベート範囲がある。

ノード：プライベートASNって、どこで使うんですか？

博士：社内やクラウドとの接続では、プライベートASNがよく使われる。

ノード：BGPで話す相手は、何て呼ぶんですか？

博士：**ネイバー**だ。ピアとも呼ぶ。相手には2種類ある。

| | eBGP | iBGP |
| --- | --- | --- |
| 相手 | 異なるASのルータ | 同じASのルータ |
| 経路を渡すときのAS_PATH | 自分のASNを先頭に加える | 変えない |
| 受け取った経路の再広告 | ほかのピアへ広告する | ほかのiBGPピアへは広告しない |
| 管理距離（Cisco IOS） | 20 | 200 |

ノード：eBGPは異なるASのルータで、iBGPは同じASのルータですね。

博士：そうだ。eBGPでは、経路を渡すときにAS_PATHの先頭へ自分のASNを加える。iBGPでは変えない。管理距離は、Cisco IOSでeBGPが20、iBGPが200だ。

ノード：「受け取った経路の再広告」のところ、iBGPは「ほかのiBGPピアへは広告しない」んですか？

博士：うむ。iBGPで受け取った経路を、ほかのiBGPピアへ広告しないルールを、**スプリットホライズン**と呼ぶ。

ノード：どうしてですか？

博士：AS内ではAS_PATHが変わらず、ループを見分けられないためだ。その代わり、AS内のBGPルータは**フルメッシュ**（全員と全員）でつなぐか、**ルートリフレクタ**（iBGPで受け取った経路を、ほかのiBGPピアへ配り直す役のルータ）などを使う。

#### セッション — まず、相手と話せる状態を作る

ノード：ネイバーは、自動で見つかるんですか？

博士：見つからない。相手のアドレスとASNを手動で指定し、TCP 179でセッションを張るのだ。やりとりするメッセージは、この4つだ。

| メッセージ | 役割 |
| --- | --- |
| OPEN | AS番号やHold Timeなどを伝え合い、セッションを始める |
| KEEPALIVE | 生きていることを定期的に伝える |
| UPDATE | 経路の広告と取り消しを伝える |
| NOTIFICATION | エラーを伝えて、セッションを閉じる |

ノード：OPENでAS番号やHold Timeを伝え合って始めて、KEEPALIVEで生きてることを伝えて、UPDATEで経路の広告と取り消し。NOTIFICATIONは、エラーを伝えて閉じる、ですね。

博士：その通り。

ノード：セッションができたかどうかは、どうやって確かめるんですか？

博士：`show ip bgp summary` のState/PfxRcd欄を見るといい。数字（受け取ったプレフィックスの数）が出ていれば**Established**、つまり経路を交換できる状態だ。IdleやActiveと文字のままなら、まだ確立していない。

ノード：ずっとActiveのままだったら？

博士：主な原因は4つだ。まず、remote-as（相手のASN）の設定が、相手の実際のASNと違う場合。OPENで拒否される。

ノード：ASNの書き間違いですね。

博士：次に、相手のアドレスへの経路がない場合だ。セッションを張るには、まずTCPで相手に届く必要がある。

ノード：経路を交換する前に、まず相手に届かなきゃいけないんですか。

博士：そうだ。通常は、直結、静的経路、OSPFなどで届ける。

ノード：残りの2つは？

博士：相手側に、こちらのアドレスのneighbor設定がない場合。それと、ACLなどで、TCP 179が遮断されている場合だ。

#### 設定例と、network文の落とし穴

博士：設定例を見てみよう。

```text
router bgp 65001
 neighbor 10.0.12.2 remote-as 65002
 neighbor 10.0.13.2 remote-as 65003
 network 192.168.1.0/24
```

> シミュレータでの簡略化: `network` はCIDR表記でもマスク表記でも書けます。実機のCisco IOSでは `network 192.168.1.0 mask 255.255.255.0` のようにマスクで書きます。

ノード：1行目の `router bgp 65001` は…

博士：自分のASN（65001）の宣言だ。2〜3行目で、2つのネイバーとそのASNを指定している。

ノード：10.0.12.2 がAS 65002、10.0.13.2 がAS 65003ですね。4行目の `network 192.168.1.0/24` は？

博士：「192.168.1.0/24を広告する」という意味だ。

ノード：じゃあ、network文を書けば広告されるんですね。

博士：ただし、落とし穴がある。Cisco IOSなどの `network` は、同じプレフィックスが経路表に**完全一致で**存在するときだけ広告される。経路表に192.168.1.0/24がなければ、書いても広告されない。

ノード：えっ、書くだけじゃだめなんですか。

博士：たとえば、経路表に 172.16.2.0/24 しかないのに `network 172.16.0.0/16` と書くと、何も広告されない。

ノード：/16にまとめて広告したいときは、どうするんですか？

博士：まとめた経路を、**集約経路**という。広告したいときは、その経路を経路表に作るか（Null0という「捨てる先」への静的経路など）、`aggregate-address` を使うといい。

### パス属性 — 経路に付いてくる情報

博士：BGPの経路には、**パス属性**という情報が付いてくる。ルータはこれを見て、どの経路を使うかを決めるのだ。

| 属性 | 意味 | 優先されるのは |
| --- | --- | --- |
| AS_PATH | 経路が通ってきたASの並び | 短いほう |
| NEXT_HOP | その宛先へ送るときの、次のIPアドレス | （届くことが前提） |
| LOCAL_PREF | 自AS内だけで共有する優先度。既定値は100（Cisco IOSなど） | 大きいほう |
| MED | 隣のASへ「こちらから入ってほしい」と伝えるヒント。その先のASへは伝わらない | 小さいほう |

ノード：AS_PATHは短いほう、LOCAL_PREFは大きいほう、MEDは小さいほうが優先…。向きがバラバラですね。

博士：そこは覚えておきたまえ。1つずつ見ていこう。まず**AS_PATH**。eBGPで広告するときに、自分のASNを先頭に加える。

ノード：受け取った経路に、自分のASNが入っていたら？

博士：ループとして破棄する。自分から出た経路が、回り回って戻ってきたということだからだ。

ノード：なるほど。AS_PATHが、ループ防止にもなっているんですね。

博士：次に**NEXT_HOP**。eBGPで学んだ経路をiBGPピアへ渡すとき、既定では外部ピアのアドレスのまま渡される。

ノード：外のルータのアドレスのまま…。AS内のルータが、そこに届かなかったら？

博士：その経路は使えない。そこで、`next-hop-self` で自分のアドレスに書き換えるのだ。

ノード：**LOCAL_PREF**は、自AS内だけで共有する優先度で、既定値は100でしたね。

博士：うむ。Cisco IOSなどでの既定値だ。最後に**MED**。既定では、同じ隣接ASから届いた経路どうしでだけ比較される。

#### 経路の向きと、通信の向きは逆

博士：ここが、BGPでいちばん混乱しやすい点だ。

ノード：身構えます。

博士：R2が「172.16.2.0/24はこちら」とR1へ広告したとしよう。R1から172.16.2.0/24への通信は、どちらへ流れる？

ノード：え〜っと、R2へ…ですよね。

博士：そうだ。つまり、**広告はR2 → R1、通信はR1 → R2** と、向きが逆になる。

ノード：あ、広告は「こっちに送って」だから、通信はその逆向きになるんだ。

博士：うむ。このため、制御したい通信の向きで、使う手段が変わる。

| 変えたいもの | 使う手段 | 誰が決めるか |
| --- | --- | --- |
| 自ASから**出ていく**通信の出口 | 受け取る経路のLOCAL_PREFを上げる | 自分 |
| 自ASへ**入ってくる**通信の入口 | MEDを付ける、AS_PATH prepend | 相手（こちらはお願いするだけ） |

ノード：自ASから出ていく通信の出口は、受け取る経路のLOCAL_PREFを上げて、自分で決められるんですね。

博士：その通り。

ノード：入ってくる通信の入口は、MEDを付けるか、AS_PATH prepend…。で、決めるのは相手？

博士：そうだ。こちらはお願いするだけなのだ。**AS_PATH prepend**は、自分のASNを重ねてAS_PATHを長く見せる方法だ。そのリンクから入ってくる通信を減らすよう促す。

ノード：AS_PATHが長いと選ばれにくいから、ですね。じゃあprependすれば、入口は変えられる！

博士：焦るでない。相手がLOCAL_PREFで決めていれば、効かない。最後に決めるのは、通信を送る側だからだ。

### 経路選択 — 1つのプレフィックスで追う

博士：では、受け取った経路がどう処理されるかを見よう。順番はこうだ。

```text
Route Advertisement → Path Attribute → Route Selection → Best Path → Routing Table
```

ノード：広告を受け取って、パス属性を見て、経路を選んで、Best Pathが経路表へ、ですか。

博士：うむ。受け取った経路はフィルタを通って**BGPテーブル**（BGPで受け取った経路をためておく表。経路表とは別だ）に入り、宛先ごとに1つのBest Pathが選ばれる。

ノード：Best Pathは、そのまま経路表に載るんですか？

博士：経路表に登録されるかは、他のプロトコルとの管理距離（03章のAD）で決まる。Cisco IOSでは、eBGP 20、iBGP 200だったな。

ノード：さっきの表の値ですね。

博士：では、R1が172.16.2.0/24を、2つのピアから受け取った例を見よう。

```text
Prefix           Next Hop     AS_PATH        LOCAL_PREF   結果
172.16.2.0/24    10.0.12.2    65002          100          best（AS_PATHが短い）
172.16.2.0/24    10.0.13.2    65003 65002    100
```

ノード：10.0.12.2 経由がbestで、理由は「AS_PATHが短い」ですね。

博士：比べる項目には、決まった順番がある。1番目は、NEXT_HOPに届くか。どちらも届くから、引き分けだ。

ノード：2番目は？

博士：LOCAL_PREF。どちらも100で、引き分け。3番目は、自分で生成した経路か。どちらも違うから、これも引き分けだ。

ノード：4番目がAS_PATHの長さで…1つと2つだから…

博士：**10.0.12.2 経由が勝ち**だ。

ノード：なるほど。

博士：ここでR1が、10.0.13.2から受け取る経路のLOCAL_PREFを200にしたとする。どうなる？

ノード：AS_PATHは10.0.12.2経由のほうが短いままだから…やっぱり10.0.12.2ですか？

博士：違う。2の段階で差がつく。AS_PATHより先にLOCAL_PREFが比較されるため、遠回りに見える10.0.13.2経由がbestになるのだ。

ノード：あ、比べる順番が大事なんですね。

博士：回線コストなどの理由で「わざと遠回りを選ばせる」ときは、このようにLOCAL_PREFを使う。

ノード：比べる項目は、この4つだけなんですか？

博士：いや。実機（Cisco IOS）では、Weight（その機器だけで使うCisco独自の値）やORIGINなど、比べる項目がもっと多くある。あとで、シミュレータの注意書きで確かめよう。

### フィルタと収束

博士：受け取る経路と送る経路は、**prefix-list**で絞る。たとえば、こう書く。

```text
ip prefix-list LAN seq 5 permit 10.0.0.0/8 le 24
```

ノード：`le 24` って何ですか？

博士：「長さ24以下」という意味だ。この行は、10.0.0.0/8の範囲内で、プレフィックス長が/8〜/24の経路に一致する。

ノード：一致しない経路は？

博士：prefix-listの最後には、暗黙の拒否がある。

ノード：フィルタって、なくても動きますよね？

博士：フィルタのないeBGPは、誤った経路を受け取ったり、流したりする原因になる。自社のものではない経路を外へ流してしまうと、他社の通信まで引き寄せてしまうことがあるのだ。

ノード：うわ、それは怖いッスね。

博士：それから、経路が変わってから、すべてのルータの選択が落ち着くまでを**収束**と呼ぶ。

ノード：収束するまでの間は？

博士：一時的に通信が途切れたり、遠回りしたりすることがある。

### 障害時の切り替え — トンネル2本とBGP

博士：いよいよ、最初の「回線が1本切れても、自動で切り替わってほしい」だ。VPNとBGPを組み合わせると、障害に強い接続になる。

ノード：どうやるんですか？

博士：AWSのSite-to-Site VPNでは、1つのVPN接続に2本のトンネルが用意される。それぞれ、AWS側の別のエンドポイントにつながる。

ノード：1本だけ設定しておけば、よくないですか？

博士：メンテナンスで、片方が一時的に落ちることもある。だから、両方のトンネルを設定するのだ。

ノード：BGPは、どこで動かすんですか？

博士：各トンネルの上だ。すると、トンネルが落ちたときに、次のように切り替わる。

```text
平常時  CGWのBGPテーブル: 10.0.1.0/24 via tunnel1（best） / via tunnel2
障害    tunnel1 が Down → tunnel1 上のBGPセッションが切れる
        → tunnel1 経由で学んだ経路が取り消される
切替    残った tunnel2 経由の経路が best になり、経路表が書き換わる
```

ノード：tunnel1がDownになると、その上のBGPセッションが切れて、tunnel1経由で学んだ経路が取り消されて…残ったtunnel2経由がbestになる。

博士：そうだ。BGPでは、セッションが切れると、そのセッションで学んだ経路も取り消される。だから、人が経路を書き換えなくても、残ったトンネルへ切り替わる。

ノード：すごい。落ちたらすぐ切り替わるんですか？

博士：厳密には、セッションが切れたと気づくまでの時間は、Hold Time などで決まる。**Hold Time** は、KEEPALIVEやUPDATEが届かないまま過ぎたら切断と判断する時間だ。

ノード：平常時は、どっちのトンネルを使うんですか？

博士：パス属性で決める。たとえば、片方の広告にAS_PATH prependを付けて、長く見せるといい。

ノード：さっきのprependが、ここで使えるんですね。

### よくある誤解

博士：さて、ここで陥りやすい誤解を確認しておこう。

ノード：トンネルがUpなら、もう通信できますよね？

博士：さっきやったばかりだぞ。両側に、相手のネットワークをトンネルへ向ける経路が必要だ。

ノード：あ、そうでした。じゃあ、IPsecなら、アドレスも含めてすべて隠れますよね？

博士：いや。トンネルモードでも、外側のIPヘッダ（ゲートウェイのアドレス）は見える。

ノード：network文を書けば、広告されますよね？

博士：同じプレフィックスが、経路表に完全一致で存在する必要がある。

ノード：AS_PATH prependで、入口は必ず変えられる！

博士：相手がLOCAL_PREFで決めていれば、効かない。

ノード：全部さっき習ったのに、つい言っちゃいますね。

### このシミュレータで試せること

博士：このシミュレータでは、次のことを試せる。

- `interface tunnel1` で `ip address 169.254.10.1/30`、`tunnel source g0/1`、`tunnel destination 203.0.113.2`、`tunnel mode ipsec`、`tunnel protection psk <鍵>`、`tunnel protection proposal aes256-sha256` を設定し、`show crypto session`、`show interfaces tunnel1`、`show logging` で状態を確かめる。

- `router bgp 65001` で `neighbor ... remote-as`、`network`、`next-hop-self`、`update-source lo0`（セッションの送信元にループバックのアドレスを使う）、`prefix-list NAME in|out`、`shutdown` を設定し、`show ip bgp summary`、`show ip bgp`、`show ip bgp 172.16.2.0/24` でBest Pathの理由を読む。
- `neighbor 10.0.13.2 local-preference 200`、`neighbor 10.0.12.2 med 50`、`neighbor 10.0.12.2 as-path prepend 2` で経路選択を変え、`show ip bgp` でBest Pathの変化を、`show ip bgp summary` で収束までの更新ラウンド数を確認する。セッションが確立しない理由は `show logging` に表示されます。

ノード：片側だけ経路を入れて、わざと失敗させられるんですね。

博士：うむ。ただし、実機と違って簡略化しているところがある。注意書きを読んでおくといい。

>
> シミュレータでの簡略化: BGPはTCP 179、OPEN/KEEPALIVE、タイマーを再現せず、設定が一致しBGP以外の経路で相手に届けばEstablishedになります。TCP 179を遮るACLも考慮しません。eBGPは直結のピアのみです（実機では `ebgp-multihop` などで変更できます）。
>
> シミュレータでの簡略化: `local-preference`、`med`、`as-path prepend` を `neighbor` に直接書くのは教育用の短縮構文で、実機ではroute-mapで設定します。経路選択は NEXT_HOPの到達性 → LOCAL_PREF → 自分が生成した経路 → AS_PATH長 → MED（同じ隣接AS） → eBGP優先 → Router ID → ピアアドレス の順です。実機（Cisco IOS）ではWeight、ORIGIN、NEXT_HOPまでのIGPメトリックなども比較されます。

#### 用語メモ

- **トンネル**［tunnel］：元のパケットを別のパケットで包んで、相手まで運ぶ仕組み。途中のルータは外側のヘッダだけを見る。
- **IPsec**：IPパケットを暗号化し、改ざんを検知する仕組み。IKEで合意し、ESPで守る。
- **ESP**［Encapsulating Security Payload］：データの暗号化と改ざん検知を提供するプロトコル。IPプロトコル番号は50。
- **SA**［Security Association］：IKEで合意した内容。IKE SAとIPsec SAがある。
- **ルートベースVPN**［route-based VPN］：経路表で、トンネルインターフェースへ向けた通信をトンネルに入れる方式。BGPを動かせる。
- **BGP**［Border Gateway Protocol］：組織どうし（AS間）で経路を伝え合うルーティングプロトコル。TCP 179を使う。
- **AS**［Autonomous System］：1つの組織が共通の方針で運用するネットワークの単位。ASNで識別する。
- **パス属性**［path attribute］：BGPの経路に付いてくる情報。AS_PATH、NEXT_HOP、LOCAL_PREF、MEDなど。
- **LOCAL_PREF**：自AS内だけで共有する優先度。大きいほうが優先され、出ていく通信の出口を選ぶのに使う。
- **収束**［convergence］：経路が変わってから、すべてのルータの選択が落ち着くまで。

#### ノード君の今日のポイント

- トンネルは、元のパケットを包んで運ぶ仕組み。IPsec（ESP）は暗号化し、GREは暗号化しない。
- ルートベースVPNでは、経路表でトンネルへ向ける。行きと帰りの両側に経路が必要。
- BGPはAS間で経路を広告し合い、宛先ごとにBest Pathを1つ選ぶ。広告と通信の向きは逆。
- 出ていく通信はLOCAL_PREFで選び、入ってくる通信はMEDやAS_PATH prependで相手に働きかける。
- トンネル2本の上でBGPを動かすと、障害時は経路の取り消しで自動的に切り替わる。
