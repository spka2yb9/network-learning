## 名前から宛先へ — DNSは、世界中で分担して管理する名簿

博士：ノード君、サーバーを新しいIPアドレスへ移したのに、しばらく古いサーバーにつながる人がいる。そんな話を聞いたことはあるかな？

ノード：え〜っと、あります。設定はちゃんと変えたのに、ってやつですよね。

博士：うむ。DNSを扱うと、一度は出会う現象だ。理由を説明するには、「誰が誰に何を聞いているか」と「答えがどこに、どれだけ残るか」を知る必要があるのだ。

ノード：誰が、何を、どこに……ですか。

博士：今回はそれを順に話すぞ。まず、DNSが1台のサーバーではなく、多くの組織の「分担」でできている理由。次に、`www.example.com` を調べるとき、誰が誰に何を聞いているか。

ノード：はい。

博士：それから、よく使うレコード（A、CNAME、MX など）の意味と、置き方の決まり。キャッシュとTTLが、設定変更の反映にどう影響するか。最後に、`dig` の出力で、どこを見ればよいかだ。

ノード：盛りだくさんッスね。よろしくお願いします。

### まず、言葉をそろえる

博士：最初に、この章で使う言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| DNS | Domain Name System。名前からIPアドレスなどを調べる仕組み |
| 名前解決 | 名前をIPアドレスなどに変換すること。「名前を引く」とも言う |
| レコード | DNSに登録された1件の情報。「この名前のIPv4アドレスはこれ」など |
| ゾーン | 1つの管理者が責任を持つ、名前の範囲 |
| 権威DNSサーバー | ゾーンの情報を持ち、正式な答えを返すサーバー |
| 再帰リゾルバ | PCの代わりに、ほかのDNSサーバーへ聞いて回るサーバー |
| キャッシュ | 一度調べた答えを、決まった時間だけ覚えておくこと |
| TTL | キャッシュしてよい時間（秒）。レコードごとに決まっている |

ノード：DNSって、名前からIPアドレスを調べる仕組みのことですよね。

博士：そうだ。正式には Domain Name System。名前からIPアドレス「など」を調べる仕組みだ。名前をIPアドレスなどに変換することを**名前解決**と言い、「名前を引く」とも言う。

ノード：「など」ってことは、IPアドレス以外も出てくるんですね。

博士：うむ。DNSに登録された1件の情報を**レコード**と呼ぶ。「この名前のIPv4アドレスはこれ」のようなものだ。

ノード：ゾーンとか、権威とか、再帰とか、ちょっと難しそうな言葉もありますね。

博士：焦るでない。どれもこの章の中で出てくる。今は「1つの管理者が責任を持つ名前の範囲がゾーン」「ゾーンの情報を持ち、正式な答えを返すのが権威DNSサーバー」「PCの代わりに、ほかのDNSサーバーへ聞いて回るのが再帰リゾルバ」と覚えておけばよい。

ノード：キャッシュとTTLは？

博士：一度調べた答えを、決まった時間だけ覚えておくのが**キャッシュ**。その「キャッシュしてよい時間（秒）」が**TTL**で、レコードごとに決まっている。

ノード：あれ？ TTLって第1章にも出てきましたよね。ルータを通るたびに1減るやつ。

博士：いいところに気づいたな。それは別物なのだ。注意書きにしておくから、そこは覚えておきたまえ。

> 注意：DNSのTTLは「キャッシュしてよい秒数」です。第1章のIPヘッダのTTL（ルータを通るたびに1減る値）とは、名前が同じだけの別物です。

ノード：名前が同じだけ、なんですね。まぎらわしいなぁ。

### なぜ、1台の名簿にしないのか

ノード：世界中の名前とIPアドレスの対応なんて、大きなサーバー1台にまとめて置いておけばいいんじゃないですか？

博士：そう思うだろう。だが、世界中の名前を1か所で管理すると、すべての変更がその1か所の作業待ちになるのだ。

ノード：あ、窓口が1つしかない役所みたいな……。行列ができちゃいますね。

博士：その通り。そこでDNSは、名前を木の形に分け、枝ごとに管理者を決めた。

ノード：枝ごとに、ですか。

博士：たとえば `com` の管理者は、「`example.com` の担当は誰か」だけを知っている。`example.com` の中の名前は、`example.com` の管理者が自分で決めるのだ。

ノード：`com` の管理者は、`example.com` の中身までは知らないんですね。

博士：うむ。このように、下の範囲の管理を別の管理者に任せることを**委任**と呼ぶ。

ノード：委任すると、何がうれしいんですか？

博士：各組織は、ほかの組織を待たずに自分の範囲を変更できる。それに、負荷や障害の影響も、範囲ごとに分散されるのだ。

ノード：なるほど。みんなで分担して、1つの大きな名簿を作ってるってことですね。

### ドメイン名は右から読む

博士：では、その木の形を名前の中で見てみよう。ドメイン名は、ドットで区切られた「ラベル」の並びなのだ。

ノード：`www` とか `example` とか `com` とかが、ラベルですね。

博士：うむ。そして**右に行くほど、大きな範囲**を表す。右端が木の根（Root）で、正式には末尾のドット `.` で表すのだ。図にするとこうなる。

```text
www.example.com.
 │     │     │  └ Root（.）
 │     │     └ TLD（com）
 │     └ example.com（組織が管理する範囲）
 └ ホスト名（www）
```

ノード：え、`www.example.com` の最後にドットなんて付いてましたっけ？

博士：普段は省略しているだけだ。右から、Root、TLD（`com`）、組織が管理する範囲の `example.com`、そしてホスト名の `www` と読む。

ノード：英語の住所みたいに、小さい範囲から書いてあるんですね。

博士：うむ、そんなイメージでいい。**TLD**（Top Level Domain）は、`com` や `jp` のような、いちばん右のラベルのことだ。

ノード：末尾のドットまで含めた名前には、何か呼び名があるんですか？

博士：末尾のドットまで含めた完全な名前を、**FQDN**（Fully Qualified Domain Name、完全修飾ドメイン名）と呼ぶ。`dig` の出力やゾーンの設定では、名前はドット付きで表されるから、見慣れておくといい。

### DNSに登場する役割

博士：次は、名前解決に登場する役者たちだ。このシミュレータの機器と合わせて表にするとこうなる。

| 役割 | 何をするか | このシミュレータの例 |
| --- | --- | --- |
| スタブリゾルバ | OSの中の部品。自分では聞いて回らず、再帰リゾルバに答えを頼む | PC1 |
| 再帰リゾルバ | 頼まれた名前を、Rootから順に聞いて回る。結果をキャッシュする | RESOLVER（192.168.1.53） |
| Rootサーバー | 木の根。TLD（`com` など）の担当サーバーを知っている | ROOT（198.51.100.10） |
| TLDサーバー | `com` などの担当。その下の `example.com` の担当サーバーを知っている | TLD（198.51.100.20） |
| 権威DNSサーバー | ゾーンの情報そのものを持ち、責任を持って答える | AUTH（198.51.100.30） |

ノード：5種類も！ PC1もDNSの役割を持ってるんですか？

博士：そうだ。OSの中には**スタブリゾルバ**という部品がある。これは自分では聞いて回らず、再帰リゾルバに答えを頼むだけなのだ。

ノード：じゃあ、聞いて回るのは再帰リゾルバ……RESOLVER（192.168.1.53）ですね。

博士：その通り。頼まれた名前を、Rootから順に聞いて回り、結果をキャッシュする。再帰リゾルバは、フルサービスリゾルバやキャッシュDNSサーバーとも呼ばれるぞ。

ノード：呼び名がいっぱいありますね。

博士：PCの `/etc/resolv.conf`（Linuxで問い合わせ先を書くファイル）に書くのは、このサーバーなのだ。そこは覚えておきたまえ。

ノード：はい。Rootサーバーは、木の根っこですよね。

博士：うむ。Rootサーバーは、TLD（`com` など）の担当サーバーを知っている。TLDサーバーは `com` などの担当で、その下の `example.com` の担当サーバーを知っている。

ノード：で、権威DNSサーバーが、ゾーンの情報そのものを持っていて、責任を持って答えるんですね。

博士：そうだ。

ノード：Rootサーバーって、世界に1台だけなんですか？ 壊れたら大変そう……。

博士：Rootサーバーには、a〜mの13の名前がある。実際には**anycast**（同じアドレスを複数の拠点から応答させる方法）で、世界中の多数の拠点から応答しているのだ。

ノード：へぇ、名前は13でも、応答している拠点は世界中にたくさんあるんですね。

博士：それから、権威サーバーの応答には、**AA**（Authoritative Answer、権威のある答え）という印（フラグ）が付く。これは後で `dig` を読むときに効いてくるぞ。

ノード：聞き方にも違いがあるんですか？ PCがリゾルバに聞くのと、リゾルバがRootに聞くのとで。

博士：いい質問だ。聞き方は2種類ある。スタブリゾルバは「最後まで調べて、答えだけください」という**再帰問い合わせ**を送る。このとき**RD**（Recursion Desired）フラグを立てるのだ。

ノード：丸投げですね。

博士：うむ。一方、再帰リゾルバは、各サーバーに「知っている範囲で答えて」という**反復問い合わせ**を送る。

ノード：どうして、そんなふうに分けてるんですか？

博士：手間のかかる仕事をリゾルバに集めることで、PCは1回聞くだけで済む。しかも、キャッシュをほかのPCと共有できるのだ。

ノード：なるほど。誰かが一度調べてくれたら、僕もその答えを使えるってことですね。

### 名前解決の流れ：www.example.com を引いてみる

博士：では実際に、PC1が `www.example.com` の**Aレコード**（IPv4アドレス）を調べるところを追ってみよう。リゾルバのキャッシュは空とする。図にするとこうなる。

```text
① PC1      → リゾルバ  「www.example.com の A は？」（再帰を希望）
② リゾルバ → Root      同じ質問 → 「答えは持っていない。com は a.gtld-servers.net（198.51.100.20）へ」
③ リゾルバ → TLD       同じ質問 → 「example.com は ns1.example.com（198.51.100.30）へ」
④ リゾルバ → 権威      同じ質問 → 「www.example.com A 203.0.113.80」（AA付き）
⑤ リゾルバ → PC1       「203.0.113.80」（リゾルバはこの結果をキャッシュする）
```

ノード：え〜っと、②のRootは「答えは持っていない」って言ってますね。

博士：うむ。②と③は答えではなく、「次に聞くべき相手」の案内なのだ。これを**委任の応答**（referral）と呼ぶ。

ノード：Rootは「com はあっちへ」、TLDは「example.com はあっちへ」って、たらい回し……じゃなくて、案内してくれるんですね。

博士：そうだ。リゾルバは案内をたどり、答えを持つ権威サーバーへたどり着く。それが④の、AA付きの答えだ。

ノード：毎回こんなに聞いて回ってたら、時間がかかりそうです。

博士：だからリゾルバは、途中の案内もキャッシュする。`com` の担当サーバーを覚えれば、次に別の `.com` の名前を調べるとき、②を省けるのだ。

ノード：賢いですね。PC1からは、この流れが全部見えてるんですか？

博士：いや。PC1が受け取るのは⑤だけで、②〜④は見えない。途中を見たいときは、`dig +trace` を使うといい。これは後で話そう。

### ゾーンと委任

ノード：博士、「ドメイン」と「ゾーン」って、同じものですか？

博士：同じとは限らないのだ。たとえば `example.com` のゾーンで、`dev.example.com` 以下を別チームに委任したとする。

ノード：はい。

博士：すると、そこから下は別のゾーンになる。`example.com` ドメインの一部ではあるが、`example.com` のゾーンからは外れるのだ。

ノード：名前としては `example.com` の仲間だけど、管理の範囲は別になる、ってことですか。

博士：うむ、その理解でいい。

ノード：委任って、具体的にはどうやるんですか？

博士：**親ゾーンに、子ゾーンのNSレコードを置く**ことで行う。**NSレコード**は、「このゾーンの権威サーバーはこれです」という情報だ。`com` ゾーンの中を覗くと、こんなふうになっている。

```text
; com ゾーン（親）の中
example.com.      172800 IN NS ns1.example.com.
ns1.example.com.  172800 IN A  198.51.100.30   ; glue
```

ノード：1行目がNSレコードですね。`example.com` の権威サーバーは `ns1.example.com` だ、と。2行目の `; glue` っていうのは何ですか？

博士：それが次の話だ。

#### glue：「どちらが先か」の循環を断つ

博士：ノード君、`ns1.example.com` のIPを知るには、どこに聞けばいいと思う？

ノード：え〜っと、`example.com` の中の名前だから、`example.com` の権威サーバーに……あれ？

博士：気づいたな。その権威サーバーが `ns1.example.com` 自身なのだ。このままでは聞きに行けない。

ノード：卵が先か、ニワトリが先か、みたいになっちゃいますね。

博士：そこで親ゾーンは、子ゾーンの中にあるネームサーバーのアドレス（Aレコードや、IPv6用のAAAAレコード）も持っておく。これが**glue**（接着剤）だ。

ノード：上の例の2行目がそれですね。

博士：その通り。さっきの名前解決の流れの③の応答にも、glueが付いて返るのだ。

ノード：glueのアドレスが間違っていたら、どうなるんですか？

博士：リゾルバは権威サーバーにたどり着けない。どの権威サーバーにも届かなければ、そのゾーンの名前はすべて**SERVFAIL**（解決に失敗）になる。

ノード：全部ですか……。ほかのゾーンも巻き込まれます？

博士：いや、ほかのゾーンは問題なく引ける。

### 主なレコードタイプ

博士：さて、ゾーンの中身を見てみよう。これは、このシミュレータの `example.com` ゾーン（AUTHが持つもの）の一部だ。

```text
example.com.       3600  IN SOA   ns1.example.com. hostmaster.example.com. (
                                  2026092801 7200 3600 1209600 300 )
example.com.       86400 IN NS    ns1.example.com.
example.com.       3600  IN MX    10 mail.example.com.
example.com.       3600  IN TXT   "v=spf1 mx -all"
www.example.com.   300   IN A     203.0.113.80
www.example.com.   300   IN AAAA  2001:db8::80
shop.example.com.  300   IN CNAME www.example.com.
```

ノード：うわ、いっぱい並んでますね。どう読めばいいんですか？

博士：左から「名前・TTL・クラス・タイプ・値」の順だ。クラスの `IN` は、インターネットという意味だ。

ノード：じゃあ `www.example.com.` の A の行は、「`www.example.com` のIPv4アドレスは 203.0.113.80 で、300秒キャッシュしていい」ってことですね。

博士：うむ、その通りだ。タイプごとの中身を表にするとこうなる。

| タイプ | 中身 | 使われる場面 |
| --- | --- | --- |
| A / AAAA | IPv4 / IPv6アドレス | Webサーバーなどのアドレス |
| CNAME | 別名。「正式な名前はこちら」 | 1つのサーバーに複数の名前を付ける |
| MX | メールの配送先のホスト名と優先度 | メールの受信サーバー |
| TXT | 任意の文字列 | SPF（このドメインのメールを送ってよいサーバーの宣言）、サービスのドメイン所有確認 |
| NS | そのゾーンの権威サーバー | 委任 |
| SOA | ゾーンの管理情報 | ゾーンの頂点に1つだけ置く |
| PTR | IPアドレスに対応する名前 | 逆引き |

ノード：A と AAAA は、IPv4 と IPv6 のアドレスですね。CNAMEの「別名」ってどういうことですか？

博士：`shop` を聞かれると、権威サーバーは「正式名は `www`」と答える。そしてリゾルバが続けて `www` を解決するのだ。

ノード：1つのサーバーに、`shop` と `www` の2つの名前を付けられるんですね。

博士：そうだ。ただし大事な決まりがある。CNAMEを持つ名前には、**ほかのレコードを置けない**。

ノード：どうしてですか？

博士：「別名です」と言いながら別の情報もあると、どちらを信じるか決められないからだ。

ノード：なるほど。「本名はあっちです、でもこっちの情報もあります」って言われたら、どっちを信じればいいか迷いますね。

博士：うむ。そのため、SOAとNSが必須のゾーンの頂点（`example.com` 自体）は、CNAMEにできないのだ。

ノード：MXの `10` っていう数字は何ですか？

博士：優先度だ。**小さいほど優先**される。

ノード：大きいほうが優先なのかと思ってました。

博士：逆なのだ。それから、MXの値はホスト名で、IPアドレスは書けない。そのホスト名のAレコードを別に用意するのだ。

ノード：この例なら、`mail.example.com` のAレコードが別に必要、ってことですね。TXTは？

博士：任意の文字列だ。SPF（このドメインのメールを送ってよいサーバーの宣言）や、サービスのドメイン所有確認に使われる。

ノード：NSは委任で出てきましたね。SOAは？

博士：SOAはゾーンの管理情報で、ゾーンの頂点に1つだけ置く。値は左から次の順だ。

| 項目 | 意味 |
| --- | --- |
| ns1.example.com. | プライマリ（元データを持つ権威サーバー）の名前 |
| hostmaster.example.com. | 管理者の連絡先。最初の `.` を `@` と読む |
| 2026092801 | シリアル番号（版番号）。変更のたびに増やす |
| 7200 3600 1209600 | refresh / retry / expire。セカンダリ（コピーを持つ予備の権威サーバー）が更新を確認する間隔、失敗時の再試行間隔、確認できないまま応答を続ける期限（秒） |
| 300 | minimum。「ない」という答えのキャッシュ時間に使う（後述） |

ノード：最初の `ns1.example.com.` は、プライマリ、つまり元データを持つ権威サーバーの名前ですね。次の管理者の連絡先が `hostmaster.example.com.` ……メールアドレスっぽくないですね。

博士：最初の `.` を `@` と読むのだ。

ノード：あ、`hostmaster@example.com` になるんですね！

博士：その通り。2026092801 はシリアル番号、つまり版番号で、変更のたびに増やす。

ノード：7200 3600 1209600 は？

博士：refresh / retry / expire だ。セカンダリ（コピーを持つ予備の権威サーバー）が更新を確認する間隔、失敗時の再試行間隔、確認できないまま応答を続ける期限で、単位は秒だ。

ノード：最後の `300` の minimum は？

博士：「ない」という答えのキャッシュ時間に使う。これは後で話すぞ。

ノード：タイプの表の最後にあったPTRは「逆引き」ですか。

博士：うむ。IPアドレスから名前を調べることを**逆引き**と呼ぶ。IPv4アドレスの数字を逆に並べ、`in-addr.arpa` の下の名前として扱うのだ。

```text
192.168.1.10 → 10.1.168.192.in-addr.arpa.  PTR  pc1.corp.example.
```

ノード：192.168.1.10 が 10.1.168.192 になってますね。なんでわざわざ逆にするんですか？

博士：ドメイン名は右ほど大きな範囲だったな。だから数字を逆にすると、アドレスの区切りが委任の木に合うのだ。

ノード：じゃあ、逆引きゾーンは誰が管理するんですか？

博士：そのアドレスブロックを割り当てられた側が管理する。注意したいのは、正引き（名前からIPアドレスを調べる向き）のゾーンを変えても、PTRは自動では変わらないということだ。

ノード：正引きと逆引きは、別々に直さないといけないんですね。

### キャッシュとTTL

博士：さて、いよいよ冒頭の話に近づくぞ。リゾルバは、各レコードのTTL（秒）の間だけ結果をキャッシュする。

ノード：キャッシュしてる間はどうなるんですか？

博士：2回目の問い合わせは権威サーバーへ行かず、キャッシュから返る。このとき返るTTLは、**残り時間**なのだ。

```text
1回目:  www.example.com.  300  IN  A  203.0.113.80   （権威サーバーまで問い合わせ）
60秒後: www.example.com.  240  IN  A  203.0.113.80   （キャッシュから応答）
```

ノード：60秒たったら、300が240になってますね。あと240秒は覚えておく、ってことか。

博士：その通り。

ノード：TTLは長いのと短いの、どっちがいいんですか？

博士：TTLが長いほどキャッシュが効き、応答が速くなり、権威サーバーの負荷も減る。その代わり、変更が行き渡るまで時間がかかるのだ。

ノード：あ！ サーバーを移したのに古いサーバーにつながる人がいるのは、リゾルバがTTLの間、古い答えを返しているからなんですね。

博士：うむ、そういうことだ。

ノード：キャッシュから返ったかどうかは、AAフラグで見分けられますか？

博士：それはできないのだ。リゾルバは権威サーバーではないので、リゾルバ経由の応答には、1回目でもAAフラグが付かない。

ノード：え、1回目でもですか。じゃあどうやって判断するんですか？

博士：TTLが減っていることや、応答時間の短さで判断するといい。

### 「ない」こともキャッシュされる

博士：ノード君、存在しない名前を聞いたらどうなると思う？

ノード：「ありません」って返ってきて……それで終わりですよね？

博士：実は、その「ない」という答えもキャッシュされるのだ。存在しない名前は**NXDOMAIN**という答えになる。

ノード：「ない」をキャッシュするんですか！

博士：うむ。名前はあるが、指定の型のレコードがない状態（**NODATA**）も同じだ。これを**ネガティブキャッシュ**と呼ぶ。

ノード：何のためにそんなことを？

博士：打ち間違いの名前で、毎回権威サーバーまで問い合わせが届くのを防ぐためだ。

ノード：なるほど。どれくらいの時間、覚えておくんですか？

博士：権威サーバーは、否定の応答にSOAレコードを付ける。保持時間は「SOAレコード自体のTTL」と「SOAのminimum」の小さい方だ。

ノード：さっきのゾーンだと、SOAのTTLが3600で、minimumが300だから……。

博士：min(3600, 300) で300秒になる。

ノード：300秒ですね。さっき「後で話す」って言ってたのはこれだったんですね。

### dig の出力を読む

博士：では、道具の話だ。**dig** は、DNSサーバーに問い合わせ、応答をそのまま表示するコマンドだ。典型的な出力（抜粋）を見てみよう。このシミュレータの `dig` も、ほぼ同じ形式で表示するぞ。

```text
$ dig www.example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 4321            ← ① 応答コード
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0  ← ② フラグ

;; ANSWER SECTION:
www.example.com.     300     IN      A       203.0.113.80              ← ③ 答えとTTL

;; SERVER: 192.168.1.53#53(192.168.1.53) (UDP)                         ← ④ 答えたサーバー
```

ノード：うっ、記号がいっぱい……。どこを見ればいいんですか？

博士：焦るでない。見るのは①〜④の4か所だ。①の応答コードは、あとで表を使って読む。

ノード：②のフラグは？

博士：`qr` は応答、`rd` は再帰を希望した、`ra` は再帰に対応、`aa` は権威サーバーの答え、という意味だ。

ノード：この例だと `aa` がないですね。リゾルバが答えたからか。

博士：その通り。よく覚えていたな。③の2列目がTTLだ。④では、意図したリゾルバが答えたかを確認する。

ノード：192.168.1.53 だから、RESOLVERですね。

博士：うむ。では①の応答コードだ。表にするとこうなる。

| 応答コード | 意味 | よくある原因 |
| --- | --- | --- |
| NOERROR | 成功。ただし、ANSWERが空ならNODATA | （NODATAなら）その型のレコードがない |
| NXDOMAIN | その名前は存在しない | 名前の打ち間違い、登録漏れ |
| SERVFAIL | リゾルバが答えを得られなかった | 委任先に届かない、応答が不正 |
| REFUSED | サーバーが問い合わせを断った | 再帰を許可していないクライアントから聞いた |

ノード：NOERRORなら成功……でも「ANSWERが空ならNODATA」って書いてありますね。

博士：そうだ。NOERRORでもANSWERが空なら、その型のレコードがないということだ。NXDOMAINは、その名前が存在しない。名前の打ち間違いや登録漏れが、よくある原因だ。

ノード：SERVFAILは、glueのところで出てきましたね。

博士：うむ。リゾルバが答えを得られなかったということで、委任先に届かない、応答が不正、といった原因が多い。

ノード：REFUSEDは？

博士：サーバーが問い合わせを断った場合だ。再帰を許可していないクライアントから聞いたときに出る。

ノード：応答が全然返ってこないときは？

博士：`no servers could be reached` のように表示される。問い合わせ先の誤り、サーバーの停止、途中での遮断を疑うといい。

ノード：じゃあ、ちゃんと答えが返ってきたら安心ですね。

博士：まあ待て。**答えが返っても安心はできない**のだ。ANSWERのIPが、期待したサーバーのものかまで確認したまえ。

ノード：そうか、返ってきたIPが間違っていることもあるんですね。

博士：そこで役に立つ使い方を2つ教えよう。まず `dig @198.51.100.30 www.example.com` だ。`@` の後のサーバーに直接聞く。

ノード：198.51.100.30 は、AUTH……権威サーバーですね。

博士：うむ。権威サーバーなら flags に `aa` が付き、`ra` はない。`recursion requested but not available` と警告が出ることもある。

ノード：権威サーバーに直接聞くと、何がわかるんですか？

博士：権威サーバーが新しい値で、リゾルバが古い値なら、キャッシュが残っているということだ。

ノード：なるほど！ 比べればいいんですね。もう1つは？

博士：`dig +trace www.example.com` だ。PC自身がRootから順に反復問い合わせをして、委任をたどる。どこで止まるかを見るのに使うといい。

ノード：さっきPC1からは見えなかった②〜④を、自分でたどるわけですね。

### レコードの変更とTTLの計画

ノード：博士、じゃあIPアドレスを切り替えたいときは、どうすればいいんですか？

博士：事前にTTLを下げておくのだ。手順にするとこうなる。

```text
数日前  TTL を 86400 → 300 に下げる（古い 86400 のキャッシュが切れるのを待つ）
当日    A レコードを新しいIPへ変更。権威サーバーとリゾルバの両方で確認
当日〜  旧サーバーは、古いキャッシュが消えるまで止めない
後日    問題がなければTTLを戻す
```

ノード：数日前にTTLを下げる……当日じゃダメなんですか？

博士：ダメなのだ。**TTLを下げる変更も、古いTTLの間は伝わらない**からな。

ノード：あ、そうか。TTLの値ごと、古いレコードがキャッシュされてるのか。

博士：その通り。86400秒（1日）のキャッシュを持つリゾルバは、最大1日、新しいTTLを知らないのだ。

ノード：だから古い86400のキャッシュが切れるのを待つんですね。旧サーバーをすぐ止めないのも、古いキャッシュが残っているから、と。

博士：うむ。ほかにも落とし穴がある。新しい名前を登録前に一度引くと、NXDOMAINがネガティブキャッシュに残る。

ノード：あっ、「追加したのに引けない」ってなるやつですね。

博士：そうだ。また、リゾルバによってはTTLに上限・下限を設けている。OSやブラウザも独自にキャッシュするため、TTLどおりに切り替わるとは限らないのだ。

ノード：TTLどおりにいくとは限らない、って頭に入れておきます。

### 発展：もう少し正確に

博士：ここからは発展だ。今は読み飛ばしてもかまわないぞ。

ノード：せっかくなので聞きたいです。

博士：まず**名前の長さ**。1つのラベルは63オクテットまで、名前全体は255オクテットまでだ。

ノード：いくらでも長くできるわけじゃないんですね。

博士：次に**QNAME minimisation**。上位のサーバーには必要な部分だけを聞くリゾルバもある。Rootには `com` の部分だけ、などだ。

ノード：さっきの図だと、Rootにも「www.example.com の A は？」って同じ質問をしてましたね。

博士：うむ。聞く範囲が変わっても、委任をたどる考え方は同じなのだ。

ノード：SOAの最後の値、minimumにも何かあるんですか？

博士：もとはゾーンのレコードの最小TTLだったが、後にネガティブキャッシュの時間として定義し直されたのだ。

ノード：だから「minimum」って名前なんですね。

博士：**UDPとTCP**の話もしておこう。問い合わせは通常UDPの53番だ。応答が切り詰められた（TCフラグ）ときは、TCPで問い合わせ直す。

ノード：TCPも使うんですね。

博士：うむ。ゾーン転送（セカンダリがプライマリからゾーンのデータをまとめて受け取ること）もTCPを使う。最後に**CNAMEの例外**。厳密には、DNSSEC（署名で応答の正しさを確かめる仕組み）用のレコードは、CNAMEと同じ名前に置けるのだ。

ノード：「CNAMEを持つ名前には、ほかのレコードを置けない」の例外ですね。

博士：もっと詳しく知りたければ、RFCを読むといい。関係するものを表にしておこう。

| RFC | 内容 |
| --- | --- |
| RFC 1034 / 1035 | DNSの基本（考え方と、メッセージ・レコードの形式） |
| RFC 2308 | ネガティブキャッシュ（SOAの最後の値の再定義） |
| RFC 9156 | QNAME minimisation |

ノード：RFC 2308 が、さっきのSOAの最後の値の再定義ですね。

博士：その通り。

### よくある誤解

博士：ここで、よくある誤解を確認しておこう。ノード君、PCは名前をどうやって調べているかな？

ノード：PCがRootから順に聞いて回っているんですよね？

博士：ちがう。聞いて回るのは再帰リゾルバだ。PCはリゾルバに1回聞くだけなのだ。

ノード：あ、そうでした。スタブリゾルバは丸投げでしたね。じゃあ、レコードを変えれば、すぐ全員に反映されますよね？

博士：されない。リゾルバはTTLが切れるまで古い値を返す。だから、切り替え前にTTLを下げるのだ。

ノード：うっ……。でも、`dig` で答えが返れば、DNSは正常ですよね？

博士：では、問題を出すぞ。

2. `dig www.example.com` を2回実行すると、TTLが300から240に減っていました。何が起きていますか？

ノード：1つ目は、再帰リゾルバです。フルサービスリゾルバとも言うんでしたね。

博士：正解だ。

### このシミュレータで試せること

博士：最後に、このシミュレータで試せることを紹介しておこう。

- `cat /etc/resolv.conf` で問い合わせ先を確認し、`echo "nameserver 192.168.1.53" > /etc/resolv.conf` で変更する
- `dig www.example.com`、`dig example.com MX`、`dig +short www.example.com` で、答え・TTL・flagsを読む
- `dig @198.51.100.30 www.example.com` で権威サーバーに直接聞き、リゾルバ経由の答えと比べる
- `dig +trace www.example.com` で、Rootから委任をたどる様子を見る
- `dig -x 192.168.1.10` で逆引きを試す。`nslookup www.example.com 192.168.1.53` も使える
- `dig` → `sleep 60` → `dig` で、キャッシュのTTLが減ることを確かめる
- リゾルバで `rndc dumpdb -cache` を実行してキャッシュを見る。`rndc flush` で消す
- AUTHの機器設定にあるDNSゾーンで、レコードを追加・変更する
- ラボ：「名前解決を、たどる」「サービス追加のDNS設計」、トラブルシューティングラボ3つ

ノード：`dig` → `sleep 60` → `dig` で、さっきの300が240になるのを確かめられるんですね。

博士：そうだ。ただし、シミュレータには実機と違うところがある。まとめておくぞ。

> シミュレータでの簡略化:
> - 時間は仮想時間で、`sleep` で進めます。
> - PC（スタブリゾルバ）はキャッシュを持たず、キャッシュするのは再帰リゾルバです。実機では、OSやブラウザもキャッシュすることがあります。
> - 実際のBIND（広く使われているDNSサーバーのソフト）では、`rndc dumpdb` は画面ではなくファイル（既定では named_dump.db）に書き出します。
> - 実機の `/etc/resolv.conf` はsystemd-resolvedやNetworkManagerなどに管理され、直接書き換えても上書きされることがあります。
> - DNSSEC、ワイルドカード、EDNS、ゾーン転送は実装していません。
> - 問い合わせはUDPだけです。実際のDNSは、応答が切り詰められた（TCフラグ）ときなどにTCPで問い合わせ直します。

ノード：実機だと、`/etc/resolv.conf` を直接書き換えても上書きされることがあるんですね。気をつけます。

博士：さて、次回は「NAT / Firewall」だ。名前から宛先がわかったら、次はその通信が境界をどう通り抜けるかを見ていくぞ。

ノード：名前がわかって、宛先もわかって、次はその先ですね。

博士：うむ。今日の「誰が誰に何を聞いているか」と「答えがどこに、どれだけ残るか」は、忘れないようにな。

ノード：はい！ サーバーを移したのに古いほうにつながる理由も、もう説明できます。

#### 用語メモ

- **委任**［delegation］：下の範囲の管理を別の管理者に任せること。親ゾーンに子ゾーンのNSレコードを置いて行う。
- **ゾーン**［zone］：1つの管理者が責任を持つ、名前の範囲。
- **FQDN**［Fully Qualified Domain Name］：末尾のドットまで含めた完全な名前。完全修飾ドメイン名。
- **再帰リゾルバ**［recursive resolver］：PCの代わりに、Rootから順に聞いて回り、結果をキャッシュするサーバー。フルサービスリゾルバ、キャッシュDNSサーバーとも呼ぶ。
- **権威DNSサーバー**［authoritative DNS server］：ゾーンの情報そのものを持ち、責任を持って答えるサーバー。応答にAAフラグが付く。
- **委任の応答**［referral］：答えではなく、「次に聞くべき相手」を示す案内。
- **glue**：親ゾーンが持つ、子ゾーンの中にあるネームサーバーのアドレス（A/AAAAレコード）。
- **TTL**［Time To Live］：キャッシュしてよい時間（秒）。レコードごとに決まっている。
- **ネガティブキャッシュ**［negative caching］：NXDOMAINやNODATAという「ない」という答えのキャッシュ。

#### ノード君の今日のポイント

- DNSは、委任でつながった分散データベース。各組織は自分のゾーンだけを管理する。
- PCは再帰リゾルバに1回聞くだけ。Root → TLD → 権威サーバーと聞いて回るのはリゾルバ。
- 委任は親ゾーンのNSとglueで表す。glueが誤ると、そのゾーン全体が引けなくなる。
- 答えはTTLの間キャッシュされる。「ない」という答えもキャッシュされる。
- 変更の前にTTLを下げ、`dig` で status・答えのIP・SERVERを確かめる。
