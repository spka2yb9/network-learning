## 境界で「書き換える」NATと、「通すか決める」ファイアウォール

博士：ノード君、会社のPCで、いつも普通にWebサイトを見ているな。

ノード：はい。毎日見てます。

博士：そのPCのアドレスは、たとえば 192.168.1.10 のようなものだ。それなのに、インターネットのサイトを普通に見られる。不思議だと思わんか？

ノード：え〜っと…言われてみれば、そうですね。

博士：逆に「社内のサーバーを外に公開して」と頼まれたら、どうする？

ノード：うーん、どこまで開けていいのか迷っちゃいそうです。

博士：うむ。その両方に関わるのが、ネットワークの境界で働く**NAT**と**ファイアウォール**なのだ。

ノード：今回はその2つの話ですね。

博士：そうだ。まず、プライベートアドレスのままでは、インターネットと通信できない理由。次に、多くのPCが1つのグローバルアドレスを共有できる仕組み、**PAT**だ。

ノード：1つのアドレスを、みんなで使うんですか。

博士：そうだ。それから、ルールは「上から順に、最初に一致したもの」で決まること。ステートフルとステートレスの違いと、戻りの通信が通る理由。最後に、公開サーバーを**DMZ**という別の区画に置く理由を話すぞ。

ノード：盛りだくさんッスね。

### まず、言葉をそろえる

博士：最初に、言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| 境界 | 社内LANとインターネットなどの境目。ルータやファイアウォールが置かれる |
| プライベートアドレス | 組織の中で自由に使えるアドレス（192.168.0.0/16 など）。インターネットでは通用しない |
| グローバルアドレス | インターネットで通用する、世界で重複しないアドレス |
| NAT | Network Address Translation。パケットのアドレス（とポート番号）を書き換える仕組み |
| ファイアウォール | ルールに従って、パケットを通すか止めるかを決める仕組み・機器 |
| ACL | Access Control List。「この条件なら許可／拒否」を上から並べたリスト |
| エフェメラルポート | クライアントのOSが、接続のたびに一時的に選ぶ送信元ポート |

ノード：境界っていうのは、社内LANとインターネットの境目のことなんですね。

博士：そうだ。そこにルータやファイアウォールが置かれる。プライベートアドレスは組織の中で自由に使えるが、インターネットでは通用しない。グローバルアドレスは、世界で重複しないアドレスだ。

ノード：NATとファイアウォールって、同じ機器に入ってることが多いですよね。だいたい同じものですか？

博士：まあ待て。同じ機器で動くことは、よくある。それでも目的は別なのだ。NATは「書き換える」仕組みで、ファイアウォールは「通すか決める」仕組みだ。

ノード：書き換える係と、通すか決める係…。

博士：そうだ。**NATは本来、アクセス制御の仕組みではない。**そこは覚えておきたまえ。

### なぜプライベートアドレスにはNATが必要か

博士：PC1（192.168.1.10）が、インターネット上のサーバー 198.51.100.80 にアクセスするとしよう。

ノード：はい。

博士：送信元が 192.168.1.10 のまま出ていくと、サーバーはどこへ返事を送る？

ノード：送信元の 192.168.1.10 ですよね。

博士：その通り。ところが、192.168.1.10 への経路は、インターネットにないのだ。

ノード：え、どうしてですか？

博士：プライベートアドレスは、多くの組織が同じ範囲を重複して使っている。そのため、インターネットのルータは経路として扱わない。返事は迷子になり、届かないのだ。

ノード：なるほど。あっちこっちに 192.168.1.10 がいたら、どこに返せばいいかわからないですもんね。

博士：うむ。そこで境界のルータが、送信元をグローバルアドレス、たとえば 203.0.113.2 に書き換えて送る。

ノード：返事はどうなるんですか？

博士：戻りのパケットが来たら、記録しておいた対応表を見て、宛先を元の 192.168.1.10 に戻す。

ノード：へぇ。行きで書き換えて、帰りで戻すんですね。

博士：会社の郵便係を思い浮かべるといい。社員の手紙の差出人を、会社の住所に書き換えて出す。返事が届いたら、控えを見て本人に回すのだ。

ノード：わかりやすいです。

博士：ただし、控えにない手紙は、誰に回せばよいかわからない。この点は、あとで説明するNATテーブルでも同じだ。

ノード：控えにない手紙…覚えておきます。

博士：もう1つ。IPv4アドレスは不足している。多くの端末が少数のグローバルアドレスを共有できることも、NATが広く使われる理由なのだ。

### NATの種類

博士：NATは、書き換える場所によって2つに分けられる。

| | SNAT（送信元NAT） | DNAT（宛先NAT） |
| --- | --- | --- |
| 書き換えるもの | 送信元アドレス（とポート） | 宛先アドレス（とポート） |
| 主な場面 | 社内からインターネットへ出る | 外から公開用アドレスに来た通信を、内側のサーバーへ届ける |
| 例 | 192.168.1.10 → 203.0.113.2 | 203.0.113.2:8080 → 192.168.1.20:80 |
| 戻りのパケット | 宛先を元の内側アドレスに戻す | 送信元を公開用アドレスに戻す |

ノード：SNATが送信元で、DNATが宛先ですね。

博士：そうだ。SNATは、社内からインターネットへ出るときに使う。例は 192.168.1.10 → 203.0.113.2 だ。

ノード：DNATは、外から公開用アドレスに来た通信を、内側のサーバーへ届けるんですね。203.0.113.2:8080 が 192.168.1.20:80 に。

博士：その通り。どちらも、戻りのパケットは記録された対応に従って、自動で元に戻される。SNATなら宛先を元の内側アドレスに、DNATなら送信元を公開用アドレスに戻すわけだ。

ノード：SNATとDNATって、どこでも使う呼び方なんですか？

博士：SNAT / DNATは、Linuxのiptables（NATやパケットのフィルタを設定するコマンド）などで使う呼び方だ。Cisco機器では、内側を基準に `ip nat inside source` として設定する。

ノード：機器によって言い方が違うんですね。

博士：うむ。対応のさせ方にも、いくつかの種類がある。

| 呼び方 | 意味 |
| --- | --- |
| 静的NAT | 内側と外側のアドレスを1対1で固定的に対応させる |
| PAT / NAPT | アドレスに加えてポート番号も書き換え、多数の端末で1つのグローバルアドレスを共有する。Cisco機器では overload と呼ぶ |
| ポートフォワード（ポートマッピング） | 「外側アドレスの8080番に来たら、内側サーバーの80番へ」のように、ポート単位でDNATする |

ノード：PATとNAPTは同じもので、Ciscoだと overload って呼ぶんですね。

博士：そうだ。アドレスに加えてポート番号も書き換えるから、多数の端末で1つのグローバルアドレスを共有できる。

ノード：サーバーを公開するなら、静的NATで丸ごと対応させるのがラクそうです。

博士：焦るでない。静的NATでサーバーを丸ごと対応させると、そのサーバーのすべてのポートに、外から届くようになる。

ノード：あ、全部見えちゃうんですか。

博士：そうだ。公開したいのが1つのサービスだけなら、ポートフォワードで必要なポートだけを対応させるといい。

### NATテーブル：行きと帰りを結び付ける

博士：PATでは、書き換えるたびに、その対応を**NATテーブル**に記録する。

ノード：さっきの郵便係の控えですね。

博士：うむ。PC1とPC2が、偶然同じ送信元ポート53000で、同じサーバーに接続した例を見てみよう。図にするとこうなる。

```text
内側（変換前）          外側（変換後）          通信相手
192.168.1.10:53000  ↔  203.0.113.2:53000      198.51.100.80:80   ← PC1（そのまま使えた）
192.168.1.11:53000  ↔  203.0.113.2:40001      198.51.100.80:80   ← PC2（53000は使用中なので別の番号）
```

ノード：PC1は53000のまま、PC2は40001に変わってますね。

博士：よく見ているな。戻りのパケットは、どれも宛先が 203.0.113.2 だ。

ノード：あ…じゃあ、アドレスだけだと、どっちに返せばいいか…。

博士：そう、**アドレスだけでは、PC1宛てかPC2宛てか区別できない。**そこでポート番号で区別するのだ。

```text
帰り  198.51.100.80:80 → 203.0.113.2:40001
      テーブルを見て、宛先を 192.168.1.11:53000 に戻して届ける
```

ノード：40001番宛てに返ってきたら、テーブルを見て 192.168.1.11:53000、つまりPC2に戻すんですね。

博士：その通り。

ノード：でも、PC2はどうしてポートが40001に変わったんですか？

博士：同じ外側アドレスで、53000番がすでに使われていたからだ。そのままでは、戻りの区別がつかない。

ノード：なるほど。かぶったら番号を変えるんですね。…あれ、でもpingって、ポート番号ありませんでしたよね？

博士：いいところに気づいたな。pingのようなICMPには、ポート番号がない。代わりに、ICMPメッセージの識別子（Identifier）で区別するのだ。

ノード：へぇ、ちゃんと代わりがあるんですね。

博士：ところで、Cisco機器では、内側の元のアドレスを **inside local**、変換後のアドレスを **inside global** と呼ぶ。このシミュレータの `show ip nat translations` は、次のように表示される。

```text
Pro  Inside global          Inside local           Outside global
tcp  203.0.113.2:53000      192.168.1.10:53000     198.51.100.80:80
```

ノード：Inside local が元の 192.168.1.10:53000 で、Inside global が変換後の 203.0.113.2:53000 ですね。

博士：そうだ。Outside global は通信相手のアドレスだ。なお、実機のCiscoでは、Outside local の列もある。こちらは、あとの発展で説明しよう。

#### NATがあっても、守られているわけではない

ノード：外から突然パケットが来たら、どうなるんですか？

博士：そのパケットは、NATテーブルに対応がない。だから、内側のどの端末へ届ければよいか決まらず、届かない。

ノード：おお、じゃあNATがあれば、外からの攻撃は防げるってことですよね。

博士：そこが落とし穴だ。それは、書き換えの仕組みから生じた副作用にすぎん。

ノード：副作用、ですか。

博士：そうだ。ポートフォワードや静的NATを設定すれば、そのポートには誰でも届く。何を通してよいかを決めるのは、ファイアウォールの仕事なのだ。

ノード：控えにない手紙が届かないのは、たまたまってことですね。

博士：うむ。そういうことだ。

### CiscoでのNAT設定と処理の順序

博士：では、Cisco機器での設定を見てみよう。インターフェースに内側・外側を指定し、変換のルールを書く。

```text
interface g0/0
 ip nat inside
interface g0/1
 ip nat outside
ip nat inside source 192.168.1.0/24 interface g0/1 overload
ip nat inside source static tcp 192.168.1.20 80 interface g0/1 8080
```

ノード：g0/0 が内側で、g0/1 が外側ですね。下の2行は何ですか？

博士：1つ目のルールは、192.168.1.0/24からの通信を、g0/1のアドレスを使ってPATする。

ノード：2つ目は？

博士：g0/1のアドレスの8080番に来たTCPを、192.168.1.20の80番へ転送する。

ノード：ポートフォワードですね。じゃあ、この変換ルールさえ書けば動くんですね。

博士：相変わらず気が早いな。ルールがあっても、インターフェースの `ip nat inside` / `ip nat outside` が欠けていると、変換されない。

ノード：え、そうなんですか。

博士：通信したあとも `show ip nat translations` が空なら、まずここを疑うといい。

ノード：はい、覚えておきます。

博士：処理の順序も重要だ。内側から外側へは**ルーティングの後に**変換し、外側から内側へは**ルーティングの前に**変換する。

ノード：向きによって逆なんですか？

博士：外から来たパケットは、宛先を内側のアドレスに戻してからでないと、どこへ送るか決められないからだ。

ノード：なるほど。宛先が 203.0.113.2 のままじゃ、内側のどこに送るかわからないですもんね。

博士：その通り。ここで、シミュレータでの注意書きも見ておこう。

> シミュレータでの簡略化: 実機のCisco IOSでは `ip nat inside source list 1 interface g0/1 overload` のように、対象をACLで指定します。ここでは学習用にCIDRで直接書きます。PATは、元の送信元ポートが空いていればそのまま使い、使用中なら別のポートを選びます。

ノード：実機だとACLで対象を指定するけど、ここではCIDRで直接書くんですね。

博士：そうだ。それからPATは、元の送信元ポートが空いていればそのまま使い、使用中なら別のポートを選ぶ。さっきのPC1とPC2の例と同じだな。

### ACLとルールの評価

博士：次は、通すか決める側の話だ。**ACL**は、条件と処理（permit＝許可 / deny＝拒否）の並びなのだ。

ノード：条件に合ったら、許可か拒否か、ってことですね。

博士：うむ。では、ノード君。次の例を見たまえ。

```text
10 deny   ip  any any
20 permit tcp any host 192.168.2.10 eq 80
```

ノード：ルール20で、192.168.2.10 の80番、つまりWebを許可してますね。だからWebは通る…。

博士：ところが、Webは通らないのだ。

ノード：えっ、どうしてですか？

博士：パケットは**上から順に**評価され、**最初に一致したルールで結果が決まる**からだ。どのパケットもルール10に一致する。だから、すべて拒否される。

ノード：ルール20まで、見てもらえないんですね…。

博士：そうだ。後ろにもっと適切なルールがあっても、使われない。そのため、狭い条件のルールを先に、広い条件のルールを後に置くのだ。

ノード：シミュレータのFirewallでも同じですか？

博士：うむ。このシミュレータのFirewallでも、ルールは番号の小さい順に評価される。

ノード：じゃあ、どのルールにも一致しなかったパケットは、どうなるんですか？

博士：その扱いを**既定の動作**と呼ぶ。表にするとこうだ。

| 既定の動作 | 意味 | 特徴 |
| --- | --- | --- |
| default deny | 許可したものだけ通す | 安全側で、ファイアウォールの基本。CiscoのACLは末尾に見えない「すべて拒否」がある |
| default allow | 拒否したもの以外は通す | 書き忘れが、そのまま穴になる |

ノード：default deny は、許可したものだけ通す。default allow は、拒否したもの以外は通す。

博士：そうだ。default deny は安全側で、ファイアウォールの基本だ。CiscoのACLは、末尾に見えない「すべて拒否」がある。

ノード：default allow だと、書き忘れがそのまま穴になっちゃうんですね。

博士：その通り。もう1つ、**inbound / outbound** という言葉がある。

ノード：inboundは社外から社内、outboundは社内から社外ですよね。

博士：まあ待て。これは、そのインターフェースから見た向きなのだ。`in` はそのインターフェースに入ってくるパケット、`out` は出ていくパケットだ。「社外から社内へ」という意味ではない。

ノード：インターフェースが基準なんですね。

### ステートレスとステートフル

博士：戻りの通信をどう扱うかで、フィルタは2種類に分かれる。**ステートレス**と**ステートフル**だ。

| | ステートレス | ステートフル |
| --- | --- | --- |
| 判断の材料 | そのパケットのヘッダだけ | ヘッダ ＋ 接続追跡の記録 |
| 過去の通信 | 覚えていない | 許可した接続を覚えている |
| 戻りの通信 | 戻り用のルールを自分で書く | 記録に一致すれば自動で通す |
| ルールの広さ | 戻りのために、広いポート範囲を開けがち | 「どちらから始まる、どの通信か」だけ書けばよい |

ノード：ステートレスは、そのパケットのヘッダだけで判断して、過去の通信は覚えていない。

博士：そうだ。だから、戻り用のルールを自分で書く。戻りのために、広いポート範囲を開けがちだ。

ノード：ステートフルは、ヘッダと接続追跡の記録で判断するんですね。許可した接続を覚えていて、戻りは記録に一致すれば自動で通す。

博士：うむ。ルールには「どちらから始まる、どの通信か」だけ書けばよい。順に見ていこう。

#### ステートレス：戻りの通信も自分で書く

博士：社内のPC（192.168.1.10）が、外のWebサーバーの80番に接続するとしよう。戻りのパケットは、どうなる？

ノード：え〜っと、送信元ポートが80で…宛先は？

博士：宛先は、PCが選んだ**エフェメラルポート**だ。

ノード：OSが、接続のたびに一時的に選ぶポートでしたね。何番になるんですか？

博士：範囲はOSで異なる。Linuxの既定は32768〜60999、IANA（番号を管理する団体）の推奨は49152〜65535だ。

ノード：広いですね…。

博士：そうだ。戻りを通すには、この広い範囲を許可するルールが必要になる。例を見てみよう。

```text
ip access-list extended WEB-IN
 10 permit tcp any host 192.168.2.10 eq 80
 20 permit tcp any eq 80 192.168.1.0/24 established
interface g0/1
 ip access-group WEB-IN in
```

ノード：10と20は、それぞれ何を許可してるんですか？

博士：10は、192.168.2.10のWeb（80番）への接続を許可する。20は、192.168.1.0/24の端末が外のWebに接続したときの戻りを許可する。

ノード：20の最後の `established` って、何ですか？

博士：Ciscoの `established` は、ACKまたはRSTフラグが立ったTCPに一致する。外から始まる最初のSYNは通さないのだ。

ノード：じゃあ、これで戻りだけ通せて安心ですね。

博士：ところが、状態を追跡しているわけではない。だから、フラグを細工したパケットは通り抜けてしまう。

ノード：あ、フラグしか見てないからか。

博士：そうだ。しかもUDPには、こうしたフラグがない。そのため、さらに広く開けることになる。

ノード：ステートレスって、けっこう苦しいですね。

博士：うむ。ここにも、シミュレータでの簡略化がある。

> シミュレータでの簡略化: 実機のCisco IOSでは、アドレス範囲をワイルドカードマスク（例 `192.168.1.0 0.0.0.255`）で書きます。ここではCIDRで書きます。

ノード：実機はワイルドカードマスクで、ここではCIDRで書くんですね。

#### ステートフル：接続を覚えて、戻りを自動で通す

博士：一方、ステートフルファイアウォールは、許可した通信を**接続追跡**（connection tracking）のテーブルに記録する。

ノード：何を記録するんですか？

博士：送信元・宛先のアドレスとポート、プロトコル、状態の組だ。こんな具合だな。

```text
tcp  10.0.1.10:50000 → 10.0.2.80:443  ESTABLISHED
```

ノード：10.0.1.10の50000番から、10.0.2.80の443番へのTCPで、状態がESTABLISHEDですね。

博士：そうだ。たとえば、社内のPCからDMZのWeb（443番）へのSYNを、ルールで許可したとする。

ノード：はい。

博士：その接続が記録されるので、サーバーから返るSYN-ACKは記録に一致する。戻り用のルールなしで通るのだ。

ノード：おお、便利ですね。ステートレスだと、どうなるんですか？

博士：このSYN-ACKに一致するルールがなければ、捨てられる。行きは通るのに、接続が完成しないのだ。

ノード：うわ、行きだけ通ってもダメなんですね。

博士：Linuxのconntrackなどでは、パケットを次の状態に分ける。

| 状態 | 意味 |
| --- | --- |
| NEW | 新しい接続の最初のパケット |
| ESTABLISHED | すでに記録にある接続に属するパケット |
| RELATED | 既存の接続に関連するパケット（その接続に関するICMPエラーなど） |
| INVALID | どの接続にも当てはまらない、不正なパケット |

ノード：NEWが最初のパケットで、ESTABLISHEDが記録にある接続のパケット…。RELATEDって何ですか？

博士：既存の接続に関連するパケットだ。その接続に関するICMPエラーなどがそうだな。INVALIDは、どの接続にも当てはまらない、不正なパケットだ。

ノード：つまりステートフルだと、ルールには始まりの向きのことだけ書けばいいってことですよね。

博士：うむ。ルールに書くのは「どちらから始まる、どの通信を許すか」だけになる。ステートレスよりずっと狭く、意図に沿ったポリシーにできるのだ。

### 拒否の仕方で、相手の見え方が変わる

博士：拒否するときにも、やり方が2つある。**drop**と**reject**だ。

| | drop（無言で捨てる） | reject（拒否を知らせる） |
| --- | --- | --- |
| 相手に返すもの | 何も返さない | ICMPのエラーなど |
| 相手の見え方 | SYNを再送した末に、タイムアウト | すぐにエラーを受け取る |
| 向いている場面 | 外部に情報を与えたくない | 調査しやすくしたい。相手を待たせたくない |

ノード：drop は無言で捨てて、reject は拒否を知らせるんですね。

博士：そうだ。drop は相手に何も返さない。だから相手は、SYNを再送した末に、タイムアウトする。

ノード：reject だと、ICMPのエラーなどが返ってきて、すぐにエラーを受け取れる、と。

博士：うむ。外部に情報を与えたくないなら drop、調査しやすくしたい・相手を待たせたくないなら reject が向いている。

ノード：reject されたら、どう見えるんですか？

博士：ICMP administratively prohibited（管理上の禁止）が返ると、`traceroute` では `!X` と表示される。

ノード：`!X` ですね。覚えておきます。

博士：CiscoルータのACLの `deny` は、既定でこのICMPを返す。設定で止めることもできるぞ。

ノード：Ciscoの deny は、名前は deny なのに知らせてくれるんですね。

博士：そうだ。一方、このシミュレータのFirewallでは、`deny` が無言の破棄、`reject` がICMPの返送だ。

ノード：結局、どっちを使えばいいんですか？

博士：調査のしやすさと、外部に情報を与えないことのバランスで決めるといい。

### 内側のサーバーを公開する：DNATと許可はセット

ノード：最初の話に戻りますけど、外から社内のWebサーバーを見せるには、どうすればいいんですか？

博士：2つの設定が必要だ。DNAT（ポートフォワード）で内側のサーバーへ届けることと、ファイアウォールで必要なポートだけを許可することだ。

ノード：DNATだけじゃダメなんですか？

博士：DNATは宛先を書き換えるだけで、通してよいかは判断しない。だから、セットなのだ。

ノード：書き換える係と、通すか決める係ですもんね。

博士：その通り。ファイアウォールのルールに書く宛先にも、注意したまえ。

ノード：公開用のアドレスを書けばいいんじゃないですか？

博士：Linuxのnetfilter（iptablesが使う、カーネル内のパケット処理の仕組み）などでは、ルールはDNATの後に評価される。そのため、宛先は変換後の内側アドレスで書くのだ。

ノード：へぇ、書き換わった後の宛先を見てるんですね。シミュレータはどうですか？

博士：このシミュレータのFirewallも同じだ。ただし、製品によっては、変換前のアドレスで書くものもある。

### DMZ：公開サーバーを別の区画に置く

博士：Webやメールのように外部へ公開するサーバーは、社内LANとは別の区画に置く。それが**DMZ**（DeMilitarized Zone、非武装地帯）だ。

ノード：非武装地帯って、ちょっと物騒な名前ですね。

博士：もとは、対立する両側の間に置く緩衝地帯を指す言葉だ。図にするとこうなる。

```text
Internet ─── [Firewall] ─── 社内LAN
                 │
                DMZ（公開Webサーバー）
```

ノード：Firewallの先で、社内LANとDMZが別々に分かれてますね。

博士：うむ。それぞれの間の通信は、こう決める。

- インターネット → DMZ：公開するポートだけ許可
- 社内LAN → DMZ：必要な通信だけ許可
- DMZ → 社内LAN：原則として拒否

ノード：DMZから社内LANは、原則として拒否なんですね。どうしてですか？

博士：公開サーバーは、外から攻撃を受けやすい場所だ。侵害されても、攻撃者はそこから社内LANへ直接は進めない。

ノード：なるほど。やられても、被害が社内まで広がらないようにするんですね。

博士：そうだ。被害の範囲を区画で限定する。それがDMZの考え方なのだ。

### 発展：NATの細かい処理と用語

博士：ここは、今は読み飛ばしてもかまわんぞ。

ノード：いえ、せっかくなので聞きます。

博士：よろしい。まず**チェックサムの再計算**だ。IPアドレスを書き換えると、IPヘッダのチェックサム（ヘッダが壊れていないかを確かめるための値）を計算し直す。

ノード：TCPやUDPは、どうなんですか？

博士：TCP/UDPのチェックサムも、アドレスを計算に含む。だから、同じく計算し直すのだ。

ノード：アドレスを書き換えるだけじゃ、済まないんですね。

博士：次に**ICMPエラーの書き換え**だ。ICMPエラーは、原因になったパケットのヘッダを中に含む。NATは、その中身も書き換えてから内側へ返す。

ノード：中に入ってるヘッダまで直すんですか。細かいですね。

博士：最後に**Ciscoの4つの用語**だ。inside local は内側ホストの元のアドレス、inside global は内側ホストの変換後のアドレス。

ノード：そこまでは、さっき出てきましたね。

博士：うむ。outside local は外側ホストの、内側から見たアドレス。outside global は外側ホストの実際のアドレスだ。

ノード：inside と outside で2つずつ、全部で4つですね。

博士：関係するRFCも挙げておこう。

| RFC | 内容 |
| --- | --- |
| RFC 1918 | プライベートアドレスの範囲 |
| RFC 3022 | 従来型のNATとNAPT |

ノード：RFC 1918がプライベートアドレスの範囲で、RFC 3022が従来型のNATとNAPTですね。

### よくある誤解

### このシミュレータで試せること

博士：このシミュレータで試せることも挙げておこう。

- ルータで `ip nat inside` / `ip nat outside`、`ip nat inside source 192.168.1.0/24 interface g0/1 overload` を設定する。通信後に `show ip nat translations` でテーブルを見て、`clear ip nat translation *` で消す
- `ip nat inside source static 192.168.1.20 203.0.113.2` や、`ip nat inside source static tcp 192.168.1.20 80 interface g0/1 8080` で内側のサーバーを公開する
- `ip access-list extended WEB-IN` でACLを作り、`ip access-group WEB-IN in` で適用する。拒否されたときの `traceroute` の `!X` を観察する
- Firewallで `firewall mode stateful` / `firewall mode stateless` を切り替え、`firewall default deny`、`firewall rule 10 permit tcp 10.0.1.0/24 host 10.0.2.80 eq 443` を設定する。`show firewall` と `show conntrack` で判定と状態を確認する
- Firewallのルールで `reject` と `deny` を入れ替えて、クライアントに見えるエラーの違いを比べる
- ラボ：「プライベートアドレスでインターネットへ」「内側のサーバーを必要な分だけ公開する」「DMZを守るFirewallポリシー」、トラブルシューティングラボ3つ

#### 用語メモ

- **NAT**［Network Address Translation］：パケットのアドレス（とポート番号）を書き換える仕組み。
- **PAT / NAPT**［Port Address Translation］：ポート番号も書き換え、多数の端末で1つのグローバルアドレスを共有する方式。Cisco機器では overload と呼ぶ。
- **ポートフォワード**［port forwarding］：外側アドレスの特定のポートに来た通信を、内側サーバーのポートへDNATすること。
- **NATテーブル**［NAT table］：変換前と変換後の対応を記録した表。戻りのパケットを元の端末へ戻すのに使う。
- **ACL**［Access Control List］：「この条件なら許可／拒否」を上から並べたリスト。最初に一致したルールで結果が決まる。
- **default deny**：どのルールにも一致しなかったパケットを拒否する既定の動作。許可したものだけ通す。
- **エフェメラルポート**［ephemeral port］：クライアントのOSが、接続のたびに一時的に選ぶ送信元ポート。
- **接続追跡**［connection tracking］：許可した通信を記録し、戻りの通信を自動で通すためのテーブル。ステートフルファイアウォールが使う。
- **DMZ**［DeMilitarized Zone］：公開サーバーを置く、社内LANとは別の区画。非武装地帯。

#### ノード君の今日のポイント

- プライベートアドレスはインターネットで経路にならないから、境界でグローバルアドレスに書き換える。
- PATはポート番号も書き換えて、NATテーブルで戻りのパケットを元の端末へ戻す。NATは書き換えの仕組みで、守ってくれるわけじゃない。
- ルールは上から評価され、最初に一致したもので決まる。既定は default deny が基本。
- ステートフルは接続を記録して戻りを自動で通す。ステートレスは戻りのルールも書く。
- 公開はDNATと許可ルールのセットで、必要なポートだけ。公開サーバーはDMZに置く。
