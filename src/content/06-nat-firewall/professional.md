### NATを防御の代わりにしない

**「NATの内側だから安全」は、設計ではなく偶然です。**

PATの内側に外から新しい接続を始めにくいのは、書き換えの仕組みから生じた副作用です。許可ルールとして設計されたものではありません。

ポートフォワードを1行追加すれば、内側のサーバーは外から見えます。IPv6ではNATを使わないことも一般的です。守りたい通信は、ファイアウォールのポリシーとして明示的に書きます。NATの設定を変えたら、公開範囲が変わっていないかも確認します。

### ルールは「理由」と一緒に管理する

ファイアウォールのルールは、追加されるばかりで削除されにくいものです。理由がわからないルールは誰も消せず、やがて不要な穴や、評価順の思わぬ衝突の原因になります。

各ルールに、目的・依頼者・関連するシステム・見直しの期限を記録します。定期的にルールごとの一致回数を確認し、長く使われていないものは削除を検討します。

### 変更は影響の小さい方向から試す

ルールは上から順に評価されるので、順序を1つ間違えるだけで、すべての通信が止まることがあります。

- 変更前に、現在のルールを保存し、戻す手順を決める
- リモートから操作しているなら、自分の管理用の接続が新しいルールで遮断されないかを先に確認する
- 追加は既存のルールより狭い条件から始め、意図した通信だけが通ることを確認してから広げる

### default denyは「必要な通信の一覧」とセットで

default deny（許可したものだけ通す）は安全ですが、必要な通信を洗い出していないと業務が止まります。

送信元・宛先・ポート・向き・用途を一覧にしてから、ポリシーを作ります。DNS、時刻同期（NTP）、監視、更新の配信など、目立たないけれど必要な通信を忘れがちです。許可する送信元は、できるだけ `any` ではなく必要な範囲に絞ります。

### DMZで被害の範囲を区切る

公開サーバーは、いつか侵害される前提で配置を考えます。

- DMZ → 社内LAN：原則拒否。どうしても必要なものだけ、宛先とポートを絞って許可する
- 管理用の接続：特定の管理端末からだけに限定する
- DMZ → インターネット：更新の取得など必要なものに絞る。侵害されたとき、外部へ情報を持ち出されにくくなる

### ログと状態テーブルを監視する

拒否のログは、攻撃や設定ミスの発見に役立ちます。ただし大量になりやすいので、保存先と保存期間を決めておきます。

許可されたはずの通信が失敗したときは、どのルールに一致したか、接続追跡（conntrack）の状態は何かを確認します。NATテーブルや接続追跡のテーブルの使用量も監視し、上限に近づいていないかを見ます。

### 切り分けは「どこで書き換わり、どこで止まったか」

NATとファイアウォールが関わる障害では、境界の内側と外側でパケットのアドレスとポートを比べます。

1. 変換が起きているか（`show ip nat translations` が空でないか）
2. どのルールに一致しているか
3. 戻りのパケットが帰ってきているか

タイムアウトなら、無言の破棄（drop）や戻りの経路を疑います。すぐにエラーが返るなら、rejectのルールや相手のポートを疑います。観測した結果と、そこから立てた仮説は分けて記録します。

### ACLとNATの評価順を確認する

同じ機器でACLとNATを使うとき、ACLが変換前と変換後のどちらのアドレスで評価されるかは、機器や向きによって異なります。

| 例 | ルールに書く宛先 |
| --- | --- |
| Cisco IOSの外側インターフェースの入力ACL（NATより先に評価） | 変換前の公開用アドレス |
| Linuxのnetfilter、このシミュレータのFirewall（DNATの後に評価） | 変換後の内側アドレス |

思い込みでルールを書くと、正しそうに見えて一致しないルールになります。製品のドキュメントで処理の順序を確認し、実際の通信で確かめます。

### まとめ

- NATは防御ではない。守りたい通信はファイアウォールのルールとして書く。
- ルールには理由と見直し期限を付け、使われていないものは削除を検討する。
- 変更は保存・戻し方・自分の接続の確認をしてから、狭い条件で試す。
- default denyの前に、DNSや時刻同期を含む必要な通信を一覧にする。
- ACLが変換前と変換後のどちらのアドレスで評価されるかを、製品ごとに確かめる。
