## この章で学ぶこと

博士：ノード君、第9章では、ルータやスイッチを並べて、ネットワークを一から組み立てたな。今日は、機器を自分では持たずに、Amazonが貸し出している設備の上にネットワークを作る話だ。

ノード：機器を持たないのに、ネットワークを作るんですか？

博士：うむ。こうして設備を借りて使う形を、**クラウド** と呼ぶ。くわしくは次のページで話すが、今日使うのは、Amazonのクラウドだ。

ノード：Amazonのクラウドにも、名前があるんですか？

博士：**AWS** だ。AWSでは、機器の代わりに、画面で「部品」を作って設定する。部品の名前は見慣れないものばかりだが、中身はこれまでに学んだサブネット、経路表、NAT、ファイアウォールなのだ。

ノード：じゃあ、今までの知識がそのまま使えるんですね。

博士：使える。むしろ、使わないと迷子になる。この章では、新しい部品が出てくるたびに「これは第何章の、あれにあたる」と対応づけていくぞ。

### この章が答える問い

博士：この章でずっと考えるのは、次の問いだ。

> **ポイント**
> インターネットから、クラウドに置いたWebサーバーまで、通信は本当に届くのか。届かないなら、どの部品のどの設定で止まっているのか。

ノード：「届くか」だけじゃなくて、「どこで止まるか」まで、ですか。

博士：そうだ。実務で頼まれるのは、たいてい「つながらないので見てほしい」だからな。そのために、1つの通信を **行き** と **帰り** に分けて、通り道にある部品を1つずつ確かめる方法を身につける。

### 読み終えるとできること

- AWSのネットワークの部品が、これまでの章のどの仕組み（サブネット・経路表・NAT・ファイアウォール）にあたるかを説明できる
- サブネットが「インターネットと直接やり取りできるか」を、名前ではなく経路表を見て判断できる
- インターネットからサーバーまでの通信を、行きと帰りに分けて、どの部品のどのルールで通るかをたどれる
- 「通した通信を覚えているフィルタ」と「覚えていないフィルタ」の違いから、帰りの通信に何が必要かを説明できる
- 外に公開しないサーバーが外へ出るときの仕組みと、その部品の置き場所を説明できる

### 前提にする章

博士：これまでの章のうち、特に次のところを使う。忘れていても大丈夫だ。使うときに、その場で短く思い出させる。

| 章 | 使うところ |
| --- | --- |
| 第1章 | ポート番号、接続を始める側が選ぶ一時的なポート番号、NIC |
| 第2章 | CIDR表記、サブネットの分け方、プライベートIPアドレス |
| 第3章 | 経路表、Longest Prefix Match、Default Route、帰りの経路 |
| 第6章 | NAT（1対1のNATとPAT）、ステートフルとステートレスのフィルタ |

### この章でずっと使う例

博士：この章では、最初から最後まで、次の構成を使う。小さな会社のWebサービスだと思ってくれたまえ。

```text
              Internet
  client 198.51.100.77          update server 198.51.100.10
                  |
             [ path-igw ]
                  |
+--- VPC path-vpc 10.0.0.0/16 --- Region ap-northeast-1 (Tokyo) ---+
|    AZ ap-northeast-1a                                            |
|                                                                  |
|  +--- public-a 10.0.1.0/24 ----+    +--- private-a 10.0.2.0/24 -+ |
|  |                             |    |                           | |
|  |  web    10.0.1.10   :80     |--->|  db    10.0.2.10   :5432  | |
|  |         203.0.113.10        |    |                           | |
|  |                             |    |                           | |
|  |  nat-a  203.0.113.20        |<---|  (OS updates go out here) | |
|  +-----------------------------+    +---------------------------+ |
+------------------------------------------------------------------+
```

ノード：英語ばっかりで、まだ何が何だか…。

博士：今はそれでいい。登場人物だけ紹介しておこう。

- **web** は、インターネットに公開するWebサーバー。80番で待ち受け、外から届くアドレス `203.0.113.10` を持つ
- **db** は、webだけが使うデータベースのサーバー。5432番で待ち受け、外からは届かないようにする
- webは左の区画、dbは右の区画に置く。左は「インターネットと直接やり取りできる区画」、右は「できない区画」
- **nat-a** は、右の区画のdbが、OSの更新のために外へ出るときの出口
- 一番上の **path-igw** は、このネットワーク全体とインターネットの出入口

ノード：左と右で何が違うのかが、気になります。

博士：それが、この章の山場の1つだ。先に答えだけ言っておくと、違いは名前ではなく **経路表** で決まる。

ノード：名前じゃないんですか。

博士：うむ。理由は、ページを進めながら確かめていこう。そして、この章の Simulation では、何もない状態からこの構成を自分の手で1つずつ組み立てる。Theory と同じ順に作っていくので、ページを読んだら、Simulation で同じものを作ってみるといい。

> **シミュレータ**
> この章の Simulation は、ブラウザの中だけで動く、AWSのネットワークの教育用モデルです。実際のAWSには接続せず、アカウントも料金も要りません。部品の作り方や画面の表示は、実際のAWSの管理画面とは異なります。

## クラウドの中に、自分のネットワークを作る

### 機器を買わずに、ネットワークを用意したい

博士：ノード君、会社で新しいWebサービスを公開することになったとしよう。第9章のやり方で用意するなら、何が要る？

ノード：え〜っと、サーバーを買って、ルータとスイッチとファイアウォールを買って、ラックに入れて、配線して、設定して…。

博士：機器が届くまでに何週間もかかる。アクセスが増えたら、また買い足しだ。逆に、サービスをやめたら機器が余る。

ノード：思ったより人が来なかったら、高い機器が無駄になりますね。

博士：そこで使われるのが、最初のページで名前だけ出した **クラウド** だ。

> **用語：クラウド**（cloud computing）
> サーバーやネットワークなどの設備を、自分で買わずに、インターネット越しに借りて使う形。必要なときに画面やコマンドで作り、使った分だけ料金を払う。

ノード：借りるんですね。サーバーだけじゃなくて、ネットワークも借りられるんですか？

博士：うむ。そのクラウドのサービスの代表が、この章で使う **AWS** だ。

> **用語：AWS**（Amazon Web Services）
> Amazonが提供するクラウドのサービス。仮想のサーバー、ネットワーク、データの保存場所など、たくさんのサービスを組み合わせて使う。

ノード：第1章から第9章でやってきた、機器を自分で持つやり方には、名前があるんですか？

博士：**オンプレミス** と呼ぶ。クラウドと比べるときによく使う言葉だ。

> **用語：オンプレミス**（on-premises）
> 自社で機器を用意し、自社の建物やデータセンターに置いて管理する形。第1章〜第9章で扱ってきたネットワークは、すべてこの形。

### AWSの設備は、どこにあるのか

ノード：借りるといっても、AWSの機器はどこかに置いてあるんですよね？

博士：もちろんだ。AWSは、世界の各地にデータセンターを持っている。その地域の単位を **リージョン** と呼ぶ。

> **用語：リージョン**（Region）
> AWSのデータセンターが集まっている、地理的な地域。東京（`ap-northeast-1`）、大阪（`ap-northeast-3`）のように、名前とコードが付いている。ネットワークは、どれか1つのリージョンを選んで作る。

ノード：東京リージョンを選べば、日本の利用者から近いってことですね。でも、東京のデータセンターが停電したら、全部止まっちゃいません？

博士：いいところに気づいたな。それに備えて、1つのリージョンの中は、さらにいくつかの **AZ** に分かれている。

> **用語：AZ**（Availability Zone、アベイラビリティゾーン）
> リージョンの中にある、1つ以上のデータセンターのまとまり。AZどうしは電源・冷却・ネットワークが独立していて、1つのAZが止まっても、ほかのAZは動き続ける。例: `ap-northeast-1a`、`ap-northeast-1c`

ノード：`ap-northeast-1a` の最後の `a` が、AZの名前なんですね。

博士：そうだ。東京リージョンには、`1a`、`1c`、`1d` の3つのAZがある。AZどうしは何キロも離れているが、専用の高速な回線で結ばれているので、AZをまたいでも通信はほとんど遅れない。

博士：たとえるなら、リージョンは「都市」、AZは「その都市の、離れた場所に建つ別々のビル」だ。1つのビルが停電しても、別のビルは動いている。ただし、たとえはここまでだ。ビルの間の行き来に時間がかかる、という部分は当てはまらない。

ノード：大事なサーバーは、2つのAZに分けて置けばいい、ってことですね。

博士：その通り。この考え方は、このあと何度も出てくる。

### VPC — 借りた設備の中の、自分専用のネットワーク

博士：さて、AWSのデータセンターでは、ほかの会社のサーバーもたくさん動いている。

ノード：え、同じネットワークにいたら、ほかの会社のサーバーから僕らのサーバーが見えちゃいませんか？

博士：それは困るな。だからAWSでは、まず自分専用のネットワークの「囲い」を作る。それが **VPC** だ。

> **用語：VPC**（Virtual Private Cloud）
> AWSの中に作る、自分専用の仮想ネットワーク。ほかの利用者のネットワークとは切り離されている。1つのリージョンの中に作り、そのリージョンのすべてのAZにまたがる。

ノード：「仮想」ってことは、ケーブルやルータは…？

博士：見えない。AWSの中では、ルータやファイアウォールは箱ではなく、画面で作る「設定の部品」として用意されている。部品の名前は新しいが、役割はこれまでの章で学んだものと同じだ。

ノード：なるほど！ 箱が見えないだけで、中でやっていることは同じなんですね。

### VPCを作るときに、最初に決めること

博士：VPCを作るときに最初に決めるのが、VPC全体で使うアドレスの範囲だ。第2章で学んだ **CIDR** 表記（`10.0.0.0/16` のように、先頭の何ビットがネットワーク部かを `/` の後ろに書く書き方）で指定する。

ノード：`/16` なら、後ろの16ビットが自由に使えるから、2の16乗で65,536個ですね。

博士：そうだ。VPCには、`/16`（65,536個）から `/28`（16個）までの大きさを指定できる。範囲は、第2章で学んだ **プライベートIPアドレス**（`10.0.0.0/8` など、インターネットでは使わないと決められた範囲）から選ぶのが普通だ。この章の例では、東京リージョンに `path-vpc` という名前で、`10.0.0.0/16` のVPCを作る。

ノード：だったら、どのVPCも `10.0.0.0/16` にしておけば、迷わなくて済みますね。

博士：そこが落とし穴だ。後で別のVPCや、会社のネットワークとつなぐことになったとき、アドレスの範囲が重なっていたらどうなる？

ノード：え〜っと…。第3章の経路表で、`10.0.1.10` 宛てが「こっちのVPC」なのか「向こうのVPC」なのか、区別できなくなります。

博士：その通りだ。しかも、VPCを作るときに決めた範囲は、後から変更できない。だから、最初に「ほかと重ならない範囲」を選ぶことが大事なのだ。

> **注意**
> 「VPCはほかの利用者と切り離されているから、アドレスは何でもいい」は誤解です。切り離されているのは今だけで、別のVPCや社内のネットワークとつなぐ日は、たいてい後からやって来ます。そのとき範囲が重なっていると、経路表で宛先を区別できず、つなぐこと自体ができない場合もあります。

> **現場では**
> 会社全体で「どのVPC・どの拠点に、どの範囲を使うか」を一覧表やIPアドレスを管理するツールで管理し、新しいVPCには、そこから重ならない範囲を割り当てます。VPCを作ったときの範囲は変えられませんが、追加の範囲を後から足すことはできます。足す範囲も、ほかと重ならないように選びます。

> **まとめ**
>
> - クラウドは、設備を買わずに借りて使う形。AWSはその代表的なサービス
> - リージョンは地域、AZはその中の独立したデータセンターのまとまり。大事なものは2つのAZに分けて置く
> - VPCは、リージョンの中に作る自分専用の仮想ネットワーク。作るときにCIDRでアドレスの範囲を決める
> - VPCの範囲は後から変えられない。ほかのネットワークと重ならない範囲を選ぶ

## サブネットに分けて、サーバーを置く

### VPCを、役割ごとの区画に分ける

博士：VPC `10.0.0.0/16` ができた。ここに、webとdbを置きたい。

ノード：置き場所は、VPCのどこでもいいんですか？

博士：オンプレミスで、公開用のWebサーバーと、外に見せたくないデータベースを、同じネットワークにそのまま並べるかね？

ノード：並べないです。第6章では、外から入ってくる通信を境界で止めました。公開するところと、隠すところは分けたいです。

博士：うむ。そのために、VPCの範囲を小さく区切る。第2章で学んだ **サブネット**（大きなアドレスの範囲を、小さな範囲に区切ったもの）だ。AWSでも同じ名前で呼ぶ。

ノード：そこは同じなんですね。

博士：ただし、AWSのサブネットには大事な決まりが1つある。**サブネットは、必ず1つのAZに属する** のだ。VPCはリージョンのすべてのAZにまたがるが、サブネットを作るときは「どのAZに置くか」を1つ選ぶ。

```text
Region ap-northeast-1 (Tokyo)
└─ VPC path-vpc 10.0.0.0/16          ← すべてのAZにまたがる
   ├─ AZ ap-northeast-1a
   │   ├─ public-a   10.0.1.0/24     ← web と nat-a を置く
   │   └─ private-a  10.0.2.0/24     ← db を置く
   └─ AZ ap-northeast-1c
       └─ （この章では使わない）
```

ノード：AZを選ぶってことは、サブネットがそのAZのデータセンターの中にある、ってことですか？

博士：そう考えてよい。だから、1つのAZが止まると、そのAZのサブネットにあるサーバーも止まる。サーバーを2つのAZに分けて置くには、AZごとにサブネットを作る必要があるわけだ。

ノード：この例では、両方とも `1a` ですね。

博士：説明を簡単にするためだ。本番では、`1c` にも同じ役割のサブネットをもう1つずつ作る。それは、後のページの「複数のサーバーに振り分ける」話で触れよう。

### サブネットの中で、使えないアドレスが5つある

ノード：public-a は `10.0.1.0/24` だから、第2章の計算で、256 − 2 で254台のサーバーに使えますね。

博士：気が早いな。AWSのサブネットでは、先頭の4つと最後の1つ、合わせて5つのアドレスをAWSが予約していて、サーバーには付けられないのだ。`10.0.1.0/24` なら、こうなる。

```text
10.0.1.0     ネットワークアドレス（第2章と同じ）
10.0.1.1     VPCのルータが使う（次のページで説明）
10.0.1.2     AWSが予約（AWSが用意するDNSサーバー用）
10.0.1.3     AWSが将来のために予約
10.0.1.255   ブロードキャストアドレス（第2章と同じ。ただしVPCでは使えない）
```

ノード：`10.0.1.2` はDNSサーバー用…。第5章の、名前をIPアドレスに変えてくれる仕組みですね。

博士：うむ。AWSは、VPCの中で使えるDNSサーバーを用意している。そのアドレスは、VPCの範囲の先頭に2を足した `10.0.0.2` だ。各サブネットの「先頭+2」も、あわせて予約されている。

ノード：ブロードキャストアドレスは、第4章でやった「同じLANの全員宛て」の宛先ですよね。VPCで使えないのに、予約はされているんですか？

博士：うむ。VPCはブロードキャストを通さないが、アドレスとしては予約されている。だから、数え方はこうなる。

```text
/24 … 256 − 5 = 251個
/26 …  64 − 5 =  59個
/28 …  16 − 5 =  11個
```

ノード：/28だと、たった11台ですか。

博士：だから、サブネットを小さく作りすぎないことだ。AWSで数えるときは、2ではなく5を引く。覚えておきたまえ。

> **発展**
> VPCではブロードキャストが使えないので、第4章のARP（IPアドレスからMACアドレスを調べる、全員宛ての問い合わせ）も、普通のLANと同じ形では届きません。VPCでは、ARPの問い合わせにAWSの仕組みが代わりに答えています。利用者が意識することはほとんどありませんが、「VPCの中は、普通のLANと同じではない」ことは覚えておくとよいでしょう。

### EC2 — サーバーを借りる

博士：区画ができたので、サーバーを置こう。AWSでサーバーを借りるサービスが **EC2** だ。

> **用語：EC2**（Elastic Compute Cloud）
> AWSで仮想のサーバーを借りるサービス。OS（LinuxやWindows）と性能を選ぶと、数分でサーバーが用意される。

ノード：借りたサーバー1台1台は、何と呼ぶんですか？

博士：**インスタンス** と呼ぶ。この章の web と db は、どちらもEC2のインスタンスだ。

> **用語：インスタンス**（instance）
> EC2で作った仮想サーバーの1台1台のこと。「EC2インスタンス」とも呼ぶ。

### インスタンスのアドレスは、ENIに付く

ノード：インスタンスにも、IPアドレスを付けるんですよね？ どこに付くんですか？

博士：第1章で学んだ **NIC**（機器をネットワークにつなぐ差し込み口）を思い出してほしい。インスタンスにも、仮想のNICが付いている。それが **ENI** だ。

> **用語：ENI**（Elastic Network Interface）
> インスタンスに付く、仮想のネットワークの差し込み口（NIC）。IPアドレスや、後で出てくる「通信を通すかどうか」の設定は、インスタンスそのものではなくENIに付く。

博士：そして、ENIに付くアドレスを **プライベートIP** と呼ぶ。インスタンスを置いたサブネットの範囲から選ぶ。

> **用語：プライベートIP**（private IP address）
> 組織の中だけで使うアドレス（第2章のプライベートIPアドレス）。AWSでは、VPCの中でインスタンス（のENI）に付くアドレスを指し、置いたサブネットの範囲から選ぶ。インターネットからは直接届かない。例: web の `10.0.1.10`

ノード：web は public-a に置くから `10.0.1.10`、db は private-a に置くから `10.0.2.10` ですね。`.1` から `.3` は予約済みで使えないし。

博士：その通りだ。web にログインして、第7章で使った `ip addr` を実行すると、こう見える。

```text
$ ip addr show eth0
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP>
    inet 10.0.1.10/24 brd 10.0.1.255 scope global eth0
```

ノード：普通のLinuxと同じですね。ENIは、OSから見ると `eth0` なんだ。

### 届いても、待ち受けていなければつながらない

博士：もう1つ、第1章と第7章の大事な話を思い出しておこう。通信がサーバーまで届いても、OSの上でアプリがそのポートを待ち受けていなければ、接続は成立しない。

ノード：TCPなら「Connection refused」で断られるんでしたね。

博士：うむ。この章の web は80番（HTTP。Webの通信）、db は5432番（PostgreSQLというデータベースのソフトが使う番号）で待ち受けている、とする。web で第7章の `ss` を実行すると、こうだ。

```text
$ ss -lnt
State    Local Address:Port
LISTEN   0.0.0.0:80
```

博士：AWSの設定をどれだけ正しくしても、ここが違えばつながらない。AWSの部品が受け持つのは「届けるところまで」で、待ち受けるのはOSとアプリの仕事だ。

ノード：「つながらない」と言われたら、最後はサーバーの中も見る、ってことですね。

> **シミュレータ**
> このシミュレータのEC2には、OSは入っていません。代わりに「OSが待ち受けるポート」（例: `tcp/80`）を設定すると、`ss` に LISTEN の行があるのと同じ扱いになります。

> **まとめ**
>
> - VPCの範囲をサブネットに区切り、公開する区画と隠す区画を分ける。サブネットは必ず1つのAZに属する
> - 各サブネットでは5つのアドレスをAWSが予約する。/24なら、使えるのは251個
> - EC2で借りたサーバーをインスタンスと呼ぶ。アドレス（プライベートIP）は、仮想のNICであるENIに付く
> - 届いても、OSが待ち受けていなければ接続できない

## ルートテーブル — サブネットごとの経路表

### VPCの中にも、ルータはいる

博士：web（`10.0.1.10`）が、db（`10.0.2.10`）に問い合わせを送るとしよう。2台は別々のサブネットにいる。オンプレミスなら、何が必要だった？

ノード：第3章でやりました。サブネットが違うから、間にルータが要ります。PCはまずDefault Gateway（自分のサブネットの外へ送るときに渡すルータのアドレス）に送って、ルータが経路表を見て転送します。

博士：完璧だ。では、VPCのどこにルータがある？

ノード：…画面のどこにも、ルータの部品がないです。

博士：見えないが、ちゃんといる。VPCには、最初から **VPCルータ** が組み込まれているのだ。

> **用語：VPCルータ**（VPC router）
> VPCに最初から組み込まれている、目に見えないルータ。VPCの中のすべてのサブネットにつながっていて、各サブネットの先頭+1のアドレス（例: `10.0.1.1`）が、そのサブネットのDefault Gatewayになる。

ノード：あ、さっきの予約アドレスの `10.0.1.1` が、これなんですね。

博士：うむ。web のDefault Gatewayは `10.0.1.1`、db のDefault Gatewayは `10.0.2.1` で、どちらもVPCルータだ。web で `ip route` を実行すると、第7章で見たのと同じ形で出てくる。

```text
$ ip route
default via 10.0.1.1 dev eth0
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.10
```

### ルートテーブル — VPCルータの経路表

ノード：ルータがいるなら、経路表もありますよね？

博士：ある。AWSでは、それを **ルートテーブル** と呼ぶ。

> **用語：ルートテーブル**（Route Table）
> VPCルータが使う経路表。「宛先（Destination）」と「送り先（Target）」の組を並べたもので、サブネットから出ていくパケットをどこへ送るかを決める。第3章のルータの経路表にあたる。

博士：VPCを作った直後のルートテーブルは、こうなっている。

```text
Destination     Target
10.0.0.0/16     local
```

ノード：1行だけですね。`local` って何ですか？

博士：VPC全体の範囲宛てを「VPCの中で届ける」という意味の経路だ。これを **local経路** と呼ぶ。

> **用語：local経路**（local route）
> ルートテーブルに必ず入っている、VPC全体の範囲（例: `10.0.0.0/16`）宛ての経路。VPCを作ると自動で入り、削除できない。この経路があるので、VPCの中のサブネットどうしは、何も設定しなくても経路の上ではつながっている。

ノード：じゃあ、web から db（`10.0.2.10`）へのパケットは…。`10.0.2.10` は `10.0.0.0/16` に含まれるから、local経路で届く！

博士：その通り。第3章の Connected（ルータのポートが直接つながっているネットワークへの経路）が、最初から入っていると思えばよい。帰りの `10.0.1.10` 宛ても同じ local経路で届くから、VPCの中なら帰りの経路も自動でそろう。

### 経路の送り先は、部品のIDで書く

博士：では、インターネットへ出るための経路を足したルートテーブルを見てもらおう。

```text
public-rt
Destination     Target
10.0.0.0/16     local
0.0.0.0/0       igw-0a1b2c3d
```

ノード：`0.0.0.0/0` は、第3章のDefault Route（どの宛先にも一致する経路）ですね。でも、送り先が `igw-0a1b2c3d`…？ 第3章では、Next Hop（次に渡すルータのIPアドレス）を書きました。

博士：そこがオンプレミスとの違いだ。ルートテーブルでは、送り先をIPアドレスではなく、**部品のID** で書く。この送り先を **ターゲット** と呼ぶ。

> **用語：ターゲット**（target）
> 通信の送り先として指定する相手。ルートテーブルでは、経路ごとに「どの部品へ送るか」を、部品のID（`local`、`igw-…` など）で書く。

ノード：`igw-0a1b2c3d` は、何の部品なんですか？

博士：インターネットとの出入口の部品だ。次のページで詳しく話す。AWSの部品のIDは、頭の文字で種類がわかるようになっている。`igw-` はその出入口、`nat-` は後で出てくる「外へ出るための出口」、という具合だ。後ろの英数字は、作るときにランダムに決まる。

ノード：経路の選び方は、第3章と同じですか？

博士：同じだ。宛先に一致する経路が複数あれば、いちばん長く一致するものを選ぶ **Longest Prefix Match** だ。public-rt で試してみたまえ。

ノード：宛先が db の `10.0.2.10` なら、`10.0.0.0/16` にも `0.0.0.0/0` にも一致します。長いのは `/16` だから、local。宛先がインターネットのクライアント `198.51.100.77` なら、一致するのは `0.0.0.0/0` だけだから、`igw-0a1b2c3d` へ。

博士：完璧だ。

### ルートテーブルは、サブネットに関連付ける

ノード：でも、ルータは1台なのに、`public-rt` みたいに名前の付いたルートテーブルがいくつもあるんですか？

博士：いいところに気づいたな。AWSでは、ルートテーブルをいくつでも作り、それぞれをサブネットに **関連付け** る。

> **用語：関連付け**（association）
> サブネットに「どのルートテーブル（や、後で出てくるサブネット単位のフィルタ）を使うか」を結びつけること。1つのサブネットに関連付けられるルートテーブルは1つ。1つのルートテーブルは、複数のサブネットで共有できる。

博士：そのサブネットから出ていくパケットは、関連付けたルートテーブルで行き先が決まる。VPCルータは1台で、サブネットごとに違う経路表を使い分けている、と考えるとよい。

ノード：オンプレミスの経路表は「ルータごと」でしたけど、AWSでは「サブネットごと」なんですね。

博士：うむ。サブネットを建物のフロアにたとえるなら、ルートテーブルは各フロアの出口に貼った「行き先の案内板」だ。public-a の出口には「外へはこちら」と書いた案内板を、private-a の出口には別の案内板を貼れる。ただし、案内板が決めるのは「そのフロアから出ていくとき」だけだ。入ってくるパケットの行き先を決めるものではない。

### 関連付けていないサブネットは、メインルートテーブルを使う

ノード：関連付けを忘れたサブネットは、どうなるんですか？ 経路表なし？

博士：いや。VPCを作ると、ルートテーブルが1つ自動で作られる。それが **メインルートテーブル** で、明示的に関連付けていないサブネットは、これを使う。

> **用語：メインルートテーブル**（main route table）
> VPCを作ると自動で作られるルートテーブル。ルートテーブルを明示的に関連付けていないサブネットは、すべてこれを使う。作った直後は local経路だけが入っている。

ノード：既定の経路表があるんですね。じゃあ、メインルートテーブルに `0.0.0.0/0 → igw-…` を入れておけば、毎回関連付けなくて楽ですね。

博士：それをやると、後で誰かが新しいサブネットを作ったとき、関連付けを忘れただけで、そのサブネットがインターネットとつながってしまう。公開するつもりのないサーバーまでな。

ノード：うわ、それは怖いですね。

> **注意**
> メインルートテーブルには、インターネットへの経路を入れないでおきます。公開用の経路は、別に作ったルートテーブル（この章では `public-rt`）に入れ、公開したいサブネットにだけ明示的に関連付けます。こうすると、関連付けを忘れたサブネットは「外へ出られない」安全な側に倒れます。

博士：この章の例では、次のようにする。

```text
メインルートテーブル（関連付けなし → private-a が使う）
  10.0.0.0/16   local

public-rt（public-a に関連付け）
  10.0.0.0/16   local
  0.0.0.0/0     igw-0a1b2c3d
```

```theory-visual
aws-main-route-table
```

> **シミュレータ**
> VPCを作ると、メインルートテーブル（名前は `vpc-1-main` など）が自動でできます。サブネットとの関連付けは、サブネットの設定の「ルートテーブル」欄で選びます。local経路は表の先頭に「自動で作られ、削除できません」と表示されます。

> **まとめ**
>
> - VPCには目に見えないVPCルータがいて、各サブネットの先頭+1がDefault Gatewayになる
> - ルートテーブルはVPCルータの経路表。送り先（ターゲット）は部品のIDで書き、Longest Prefix Matchで選ぶ
> - local経路があるので、VPCの中のサブネットどうしは行きも帰りも経路がそろっている
> - ルートテーブルはサブネットに関連付ける。関連付けていないサブネットはメインルートテーブルを使うので、メインには外への経路を入れない

## Internet Gatewayと「パブリック」の条件

```theory-visual
aws-public
```

### VPCには、インターネットへの出入口がない

博士：さっきの public-rt の `igw-0a1b2c3d` の正体を話そう。VPCは、作っただけではインターネットとつながっていない。外との出入口を、自分で付ける必要があるのだ。

ノード：オンプレミスなら、インターネットの回線をつないだルータが出入口でしたね。

博士：うむ。AWSで、その役割をするのが **IGW** だ。

> **用語：IGW**（Internet Gateway、インターネットゲートウェイ）
> VPCとインターネットをつなぐ出入口の部品。1つのVPCに1つだけ取り付けられる。AWSが壊れても止まらないように運用しているので、利用者が台数や性能を気にする必要はない。

博士：IGWは、作っただけでは使えない。VPCに **アタッチ** して初めて出入口になる。

> **用語：アタッチ**（attach）
> 部品を、VPCなどに取り付けること。IGWは、VPCにアタッチして初めて使える。取り外すことは、デタッチ（detach）と呼ぶ。

ノード：IGWは、サブネットの中に置くんですか？ オンプレミスのルータみたいに。

博士：いや、そこが違う。IGWはサブネットの中ではなく、VPCそのものの縁に付く。サブネットに置く機器ではないので、IGW自身にはプライベートIPもない。ルートテーブルで「この宛先はIGWへ」とターゲットに指定して使うのだ。この章の例では、`path-igw` を作って path-vpc にアタッチし、public-rt の `0.0.0.0/0` のターゲットにする。

### プライベートIPのままでは、インターネットから届かない

ノード：これで、インターネットのクライアントから web（`10.0.1.10`）に届くんですね。

博士：まだだ。クライアントは、どのアドレスに送ればいい？

ノード：`10.0.1.10`…あ、これはプライベートIPアドレスだから、インターネットでは使えないんでした。

博士：そうだ。インターネットから届くには、インターネットで通用するアドレスが要る。それが **パブリックIP** だ。

> **用語：パブリックIP**（public IP address）
> インターネットで通用するアドレス。インスタンスに付けると、インターネットからそのアドレス宛てに通信が届くようになる。この章の web には `203.0.113.10` を付ける。

ノード：パブリックIPも、ENIに付くんですよね。じゃあ、web の `ip addr` に `203.0.113.10` が出てくる？

博士：出てこない。OSから見えるのは、プライベートIPの `10.0.1.10` だけだ。パブリックIPとプライベートIPの変換は、OSの外にあるIGWが、1対1で行う。

ノード：1対1の変換…。第6章の静的NAT（内側の1つのアドレスを、外側の1つのアドレスと決まった組み合わせで変換するNAT）と同じですか？

博士：同じ考え方だ。表にすると、こうなる。

| 向き | IGWに着く前 | IGWを通った後 |
| --- | --- | --- |
| web → インターネット | 送信元 `10.0.1.10` | 送信元 `203.0.113.10` |
| インターネット → web | 宛先 `203.0.113.10` | 宛先 `10.0.1.10` |

ノード：外から見ると web は `203.0.113.10`、VPCの中では `10.0.1.10`。IGWが通訳してるんですね。

博士：たとえるなら、社員1人ずつに直通の外線番号がある「ダイヤルイン」だな。外線番号（パブリックIP）にかけると、決まった内線（プライベートIP）につながる。ただし、IGWは電話の受付と違って、かかってきた電話を選ばない。誰からの通信を通すかは、次のページから話すフィルタで決める。

### 固定のパブリックIP — Elastic IP

ノード：パブリックIPは、どうやって付けるんですか？

博士：インスタンスを作るときに、AWSに自動で付けてもらうことができる。ただし、自動で付いたパブリックIPは、インスタンスを停止して起動し直すと、別のアドレスに変わってしまう。

ノード：Webサーバーのアドレスが変わったら困りますよ。第5章のDNSに登録したアドレスと合わなくなります。

博士：そこで、変わらないアドレスを確保して使う。それが **Elastic IP** だ。

> **用語：Elastic IP**（Elastic IP address、EIP）
> 自分のアカウントに確保しておく、固定のパブリックIP。インスタンスなどに関連付けて使い、解放するまで同じアドレスを使い続けられる。

> **現場では**
> パブリックIPには、使っているかどうかにかかわらず料金がかかります（Elastic IPを確保しただけで使っていない場合も同じです）。本当に外へ公開する必要のある部品だけに付けます。

### 「パブリック」かどうかは、経路で決まる

ノード：最初のページで、左の区画は「インターネットと直接やり取りできる区画」って言ってましたよね。サブネットに `public-a` って名前を付けたから、そうなるんですか？

博士：ならない。名前は、ただのラベルだ。インターネットと直接やり取りできるかどうかを決めるのは、そのサブネットが使うルートテーブルだ。

> **用語：パブリックサブネット**（public subnet）
> 関連付けたルートテーブルに、アタッチ済みのIGWへの経路（例: `0.0.0.0/0 → igw-…`）があるサブネット。中のインスタンスは、パブリックIPがあれば、インターネットと直接やり取りできる。

ノード：じゃあ、IGWへの経路がないサブネットは？

博士：**プライベートサブネット** だ。

> **用語：プライベートサブネット**（private subnet）
> 関連付けたルートテーブルに、IGWへの経路がないサブネット。中のインスタンスは、パブリックIPを付けても、インターネットと直接はやり取りできない。

ノード：じゃあ、public-a に関連付けるルートテーブルを、public-rt からメインルートテーブルに替えたら、プライベートサブネットになる？

博士：その通り。「パブリック」はサブネットの種類ではなく、経路の結果なのだ。この章の例では、public-a は public-rt を使うのでパブリック、private-a はメインルートテーブルを使うのでプライベートだ。

ノード：経路さえあれば、もうインターネットとつながる？

博士：焦るでない。経路があっても、ターゲットのIGWがVPCからデタッチされていたらどうなる？

ノード：送り先がない…。経路に一致したパケットが、どこにも行けずに捨てられます。

博士：うむ。行き先のなくなった経路は「ブラックホール」と呼ばれ、パケットを吸い込んで捨てるだけになる。

### インスタンスが、インターネットと直接やり取りする条件

博士：ここまでをまとめよう。インスタンスがインターネットと直接やり取りするには、次の条件がすべて要る。

| 条件 | 何のためか |
| --- | --- |
| VPCにIGWがアタッチされている | VPCに出入口を作る |
| サブネットのルートテーブルに、そのIGWへの経路がある | パケットをIGWまで運ぶ（パブリックサブネット） |
| インスタンスにパブリックIP（またはElastic IP）がある | IGWで変換するときの、外側のアドレスになる |
| フィルタで許可されている | 次の2ページで説明する |
| OSがそのポートで待ち受けている | 前のページで説明した |

ノード：パブリックサブネットに置いても、パブリックIPがなければダメ。パブリックIPがあっても、プライベートサブネットならダメ。両方そろって初めて、なんですね。

> **注意**
> 「サブネットの名前に public と付ければパブリックサブネットになる」「VPCにIGWを付ければ、サブネットはインターネットとつながる」は、どちらも誤解です。決めるのは、サブネットに関連付けたルートテーブルに、アタッチ済みのIGWへの経路があるかどうかです。

> **シミュレータ**
> サブネットを選ぶと、設定欄の見出しに Public / Private の印と、その理由（どのルートテーブルのどの経路で決まったか）が表示されます。経路を足したり、IGWをデタッチしたりして、印が変わるのを確かめてみましょう。

> **まとめ**
>
> - IGWはVPCとインターネットの出入口。VPCにアタッチして、ルートテーブルのターゲットに指定して使う
> - IGWは、パブリックIPとプライベートIPを1対1で変換する（第6章の静的NAT）。OSから見えるのはプライベートIPだけ
> - パブリックサブネットかどうかは、名前ではなく、ルートテーブルにアタッチ済みのIGWへの経路があるかで決まる
> - インターネットと直接やり取りするには、経路・パブリックIP・フィルタの許可・OSの待ち受けがすべて要る

## Security Group — サーバーごとのステートフルな門番

### 届くようになったら、次は「何を通すか」

博士：経路とパブリックIPがそろって、インターネットから web へ通信が届く道はできた。では、web に届いてほしい通信は何だ？

ノード：Webの通信、80番です。

博士：では、世界中の誰でも、web の22番に接続できたら？ 22番は、第7章で使ったSSH（サーバーにログインして操作するための通信）の番号だ。

ノード：まずいです！ パスワードを総当たりで試されたりしそう。

博士：だから、必要な通信だけを通すフィルタが要る。第6章で学んだファイアウォールのうち、**ステートフル** なもの——通した通信を覚えておき、その返事は自動で通すもの——を思い出してほしい。

ノード：行きの通信を許可すれば、帰りのルールは書かなくていいやつですね。接続ごとに「この通信は通した」と記録を残すから。

博士：うむ。AWSで、それにあたるのが **SG** だ。

> **用語：SG**（Security Group、セキュリティグループ）
> インスタンス（のENI）ごとに付ける、ステートフルなファイアウォール。「通してよい通信」を許可するルールだけを並べ、どれにも一致しない通信は通さない。許可した通信の返事は、自動で通す。

ノード：インスタンスごとに付けるんですか？ 第6章のファイアウォールは、ネットワークの境界に1台置きました。

博士：そこが違うところだ。SGは、サーバー1台1台の部屋の扉に立つ門番のようなものだ。同じサブネットにいる隣のサーバーから来た通信でも、扉のところでSGに止められる。

### インバウンドとアウトバウンド

博士：SGのルールは、通信の向きで2つに分けて書く。まず、外からそのインスタンスに入ってくる向きを **インバウンド** と呼ぶ。

> **用語：インバウンド**（inbound）
> 外からその部品に入ってくる向きの通信。SGのインバウンドのルールには、「どこから（送信元）・どのプロトコルの・何番のポートへ」の通信を許可するかを書く。

ノード：反対向きは何て呼ぶんですか？

博士：インスタンスから外へ出ていく向きを、**アウトバウンド** と呼ぶ。

> **用語：アウトバウンド**（outbound）
> その部品から外へ出ていく向きの通信。SGのアウトバウンドのルールには、「どこへ（宛先）・どのプロトコルの・何番のポートへ」の通信を許可するかを書く。

博士：web に付けるSGを `web-sg` として、ルールはこうする。

```text
web-sg
インバウンド
  TCP  80    送信元 0.0.0.0/0     どこからでも、Webの通信を受ける
アウトバウンド
  All  All   宛先   0.0.0.0/0     作ったときのまま（どこへでも出られる）
```

ノード：送信元の `0.0.0.0/0` は、「どのアドレスからでも」ってことですね。22番のルールはないから、SSHは通らない。

博士：そうだ。SGに書けるのは許可だけで、「拒否」のルールはない。ルールに順番もない。すべてのルールを見て、どれか1つに一致すれば通す。どれにも一致しなければ通さない。

ノード：「アウトバウンドは作ったときのまま」っていうのは？

博士：新しく作ったSGは、インバウンドが空（つまり何も入れない）、アウトバウンドには「どこへでも許可」が1行入った状態で始まる。サーバーから外へ出ていく通信は、たいてい止めなくていいからだ。

### 返事は、アウトバウンドのルールに関係なく通る

ノード：web がWebの返事を返すときは、アウトバウンドのルールで判定されるんですか？

博士：いい質問だ。仮に、web-sg のアウトバウンドを全部消して空にしたとしよう。クライアント `198.51.100.77` からの80番への接続は、どうなる？

ノード：え〜っと、返事は web から外へ出ていく通信だから、アウトバウンドが空なら止まる…？

博士：止まらない。SGはステートフルだ。インバウンドで許可した接続を覚えているので、その返事は、アウトバウンドのルールに関係なく通す。

```text
行き  198.51.100.77:50000 → 10.0.1.10:80   インバウンド「TCP 80 0.0.0.0/0」に一致 → 許可して記録
帰り  10.0.1.10:80 → 198.51.100.77:50000   記録にある接続の返事 → ルールを見ずに許可
```

博士：ちなみに `50000` は、クライアントのOSがこの接続のために一時的に選んだ送信元ポートだ。次のページで、これが大事になる。

ノード：第6章と同じだ。じゃあ、アウトバウンドが空だと、何ができなくなるんですか？

博士：web のほうから新しく始める通信だ。たとえば、web から db への問い合わせや、OSの更新のダウンロードは、web が始める通信なので、アウトバウンドの許可が要る。

ノード：「誰が始めた通信か」で、どちらのルールで判定されるかが決まるんですね。

### 1つのENIに、複数のSG

博士：1つのENIには、SGを複数付けられる。そのときは、付けたすべてのSGのルールを合わせたもののどれかに一致すれば通る。

ノード：「Webサーバー用」と「社内からの管理用」みたいに、役割ごとにSGを分けて組み合わせられるんですね。

> **注意**
> SGには許可のルールしか書けません。「この送信元だけは拒否したい」ということは、SGではできません。SGを複数付けても、許可が足し合わされるだけで、拒否にはなりません。特定の範囲をまとめて拒否したいときは、次のページで説明する、サブネット単位のフィルタを使います。

> **現場では**
> 管理用のSSH（22番）やRDP（3389番。Windowsを遠隔で操作する通信）を `0.0.0.0/0` に開けるのは避けます。送信元を会社のアドレスに絞るか、ポートを開けずにサーバーを操作できるAWSの仕組み（Systems Manager の Session Manager）を使います。また、SGのルールを削除しても、すでに記録されている接続はすぐには切れない場合があります。「ルールを消したのに、まだつながっている」ときは、これを疑います。

> **まとめ**
>
> - SGは、インスタンス（のENI）ごとに付けるステートフルなファイアウォール（第6章）
> - ルールはインバウンドとアウトバウンドに分けて書く。書けるのは許可だけで、順番はなく、どれにも一致しなければ拒否
> - 許可した接続の返事は、反対向きのルールに関係なく通る。アウトバウンドのルールが効くのは、そのインスタンスから始める通信
> - 新しいSGは、インバウンドが空、アウトバウンドがすべて許可の状態で始まる

## Network ACL — サブネットの境界の、ステートレスな関所

```theory-visual
aws-filters
```

### サブネットの単位で、まとめて止めたい

ノード：SGで拒否が書けないなら、「この範囲からの通信は全部お断り」はどうするんですか？

博士：たとえば、`192.0.2.0/24` から、攻撃のような通信が大量に来ているとしよう。サブネットにいるサーバー全部について、まとめて止めたい。

ノード：SGは許可しか書けないから…困りますね。

博士：そこで使うのが、サブネットの境界に置くもう1つのフィルタ、**NACL** だ。第6章で学んだ、ルータのACL（パケットを1つずつ、上のルールから順に見て、通すか捨てるかを決めるリスト）を思い出してほしい。

> **用語：NACL**（Network ACL、ネットワークACL）
> サブネットに関連付ける、ステートレスなフィルタ。サブネットの境界を出入りするパケットを、番号の小さいルールから順に見て、最初に一致したルールの「許可」か「拒否」で決める。どれにも一致しなければ拒否する。

ノード：「ステートレス」は、第6章のACLと同じで、通した通信を覚えていない、ってことですよね。

博士：うむ。行きのパケットも帰りのパケットも、それぞれ別のパケットとしてルールで判定する。これが、この後の大事な話につながる。

### ルールは番号順に、最初に一致したもので決まる

博士：VPCを作ると、NACLも1つ自動で作られる。その中身はこうだ。

```text
インバウンド
  番号   プロトコル  ポート  送信元      許可/拒否
  100    All         All     0.0.0.0/0   ALLOW
  *      All         All     0.0.0.0/0   DENY
アウトバウンド
  番号   プロトコル  ポート  宛先        許可/拒否
  100    All         All     0.0.0.0/0   ALLOW
  *      All         All     0.0.0.0/0   DENY
```

ノード：最後の `*` は何ですか？

博士：どのルールにも一致しなかったパケットを拒否する、最後のルールだ。消すことはできない。第6章のACLの、最後に隠れている「暗黙の拒否」と同じだな。このNACLは100番で全部を許可しているので、実際には何でも通す。

> **用語：デフォルトNACL**（default network ACL）
> VPCを作ると自動で作られるNACL。インバウンドもアウトバウンドも、すべての通信を許可するルールが入っている。ほかのNACLを関連付けていないサブネットは、これを使う。

ノード：全部許可なら、無いのと同じですね。

博士：そうだ。だから、SGだけで守っているVPCも多い。一方、自分で新しく作ったNACLは、ルールが1つもない状態、つまり `*` の拒否だけで始まる。関連付けた瞬間に、そのサブネットは何も通さなくなる。

ノード：SGとは逆に、作ったばかりだと全部止まるんですね。気をつけます。

博士：さっきの攻撃の例なら、こう書く。番号の小さいほうから見るので、拒否を先に置く。

```text
インバウンド
  50    All   All   192.0.2.0/24   DENY     攻撃元をまとめて拒否
  100   All   All   0.0.0.0/0      ALLOW
  *     All   All   0.0.0.0/0      DENY
```

ノード：`192.0.2.5` からのパケットは、50番に一致して拒否。ほかからのパケットは、50番に一致しないから100番で許可。順番が大事なんですね。

### ステートレスだと、帰りの通信でつまずく

博士：では、NACLで最もつまずきやすいところだ。public-a に、こんなNACLを作って関連付けたとしよう。「Webの80番だけ通したい」という気持ちで書いたものだ。

```text
インバウンド
  100   TCP   80    0.0.0.0/0   ALLOW
  *     All   All   0.0.0.0/0   DENY
アウトバウンド
  （ルールなし）
  *     All   All   0.0.0.0/0   DENY
```

ノード：インバウンドで80番を許可したから、Webは見えますよね？

博士：クライアント `198.51.100.77` からの通信で、行きと帰りを見てみたまえ。

```text
行き  198.51.100.77:50000 → 10.0.1.10:80   インバウンド 100 に一致 → 許可
帰り  10.0.1.10:80 → 198.51.100.77:50000   アウトバウンド ルールなし → * で拒否
```

ノード：あっ、帰りが止まってる。NACLは行きを覚えていないから、帰りのパケットを「知らない通信」として、アウトバウンドのルールで判定するんだ。

博士：その通りだ。では、帰りを通すルールを書こう。帰りのパケットの宛先ポートは何番だ？

ノード：`50000` です。…この番号って、第1章で出てきた気がします。

博士：うむ。第1章で学んだ **エフェメラルポート** だ。NACLを書くときに欠かせないので、改めて整理しておこう。

> **用語：エフェメラルポート**（ephemeral port）
> 接続を始める側のOSが、その接続の送信元ポートとして一時的に選ぶ番号。返事はこのポート宛てに戻ってくる。選ばれる範囲はOSによって違う（Linuxは 32768〜60999、Windowsは 49152〜65535 など）。

ノード：じゃあ、アウトバウンドに「TCP 50000 を許可」と書けばいい？

博士：次のクライアントは、別の番号を選んでくる。どのOSのクライアントが来ても返事を通すには、範囲で許可するしかない。AWSは、`1024〜65535` を許可するよう勧めている。

```text
アウトバウンド
  100   TCP   1024-65535   0.0.0.0/0   ALLOW    帰り（エフェメラルポート宛て）
  *     All   All          0.0.0.0/0   DENY
```

ノード：ずいぶん広いですね。SGだったら、こんな行は要らなかったのに。

博士：そうだ。ステートフルかステートレスかで、これだけ手間が違う。そして、この広さがあるので、NACLだけで細かく守るのは難しい。NACLは「まとめて止める」補助、細かい許可はSG、と役割を分けるのが普通だ。

> **注意**
> 「SGで許可したから、NACLは気にしなくてよい」は誤解です。サブネットの外から来る通信は、NACLとSGの両方で許可されて初めて届きます。そしてNACLはステートレスなので、行きを許可しても、帰り（エフェメラルポート宛て）を反対向きのルールで許可していなければ、返事が止まります。

### 同じサブネットの中は、NACLを通らない

ノード：同じサブネットにいるサーバーどうしの通信も、NACLで判定されるんですか？

博士：されない。NACLが見るのは、サブネットの境界を越えるパケットだけだ。SGは1台ずつの扉にいるので、同じサブネットの中の通信も判定する。

博士：たとえるなら、NACLは各フロアの入口にある関所、SGは各部屋の扉の門番だ。関所は人の顔を覚えないので、出ていくときにも改めて通行証を見せる必要がある。門番は、さっき入れた客の帰りは顔パスで通す。そして、同じフロアの部屋から部屋へ移るだけなら、関所は通らない。

### SGとNACLを並べてみる

博士：説明が終わったので、整理の表を置いておこう。

| | SG | NACL |
| --- | --- | --- |
| 第6章でいうと | ステートフルなファイアウォール | ステートレスなACL |
| 付ける場所 | インスタンス（のENI） | サブネット |
| 書けるルール | 許可だけ | 許可と拒否 |
| 評価のしかた | すべてのルールを見て、どれかに一致すれば許可 | 番号の小さい順に見て、最初に一致したもので決定 |
| どれにも一致しないと | 拒否 | 最後の `*` で拒否 |
| 帰りの通信 | 自動で許可 | 反対向きのルールで許可が必要 |
| 作った直後 | インバウンドなし、アウトバウンドはすべて許可 | デフォルトNACLはすべて許可、新しく作ったNACLはすべて拒否 |
| 同じサブネットの中の通信 | 判定する | 判定しない |

> **シミュレータ**
> NACLの設定欄では、ルール番号・方向（IN / OUT）・プロトコル・ポート・CIDR・allow / deny を入れて「追加」を押します。表の最後には、消せない `*` の deny が表示されます。

> **まとめ**
>
> - NACLはサブネットに関連付けるステートレスなフィルタ。番号の小さい順に見て、最初に一致したルールで許可か拒否が決まる
> - デフォルトNACLはすべて許可、新しく作ったNACLはすべて拒否の状態で始まる
> - ステートレスなので、帰りの通信（エフェメラルポート宛て）も反対向きのルールで許可する。範囲は 1024〜65535 が一般的
> - 細かい許可はSG、範囲をまとめて止めるのはNACL、と役割を分ける

## 1つの通信を、行きと帰りでたどる

### 通り道に並ぶ部品

博士：部品がそろったので、いよいよ1つの通信を最初から最後までたどろう。インターネットのクライアント `198.51.100.77` が、ブラウザで `http://203.0.113.10/` を開く。web へのHTTP、つまりTCPの80番への接続だ。public-a は、デフォルトNACL（すべて許可）を使っているとする。

ノード：これまでの部品の、どれを通るんですか？

博士：行きは「外側から内側へ」、帰りは「内側から外側へ」進む。

```text
行き  client --> IGW --> [NACL in] --> [SG in] --> web:80
帰り  client <-- IGW <-- [route table] <-- [NACL out] <-- [SG out] <-- web
```

ノード：行きと帰りで、通る部品が違うんですね。行きには、ルートテーブルがない？

博士：そこは後で説明する。まずは、パケットのヘッダが1か所ごとにどう変わるか、表で見よう。

### 行き：クライアントから web へ

博士：クライアントのOSは、送信元ポートにエフェメラルポートを1つ選ぶ。ここでは `50000` とする。

| # | 場所 | 送信元 | 宛先 | 判定・変化 |
| --- | --- | --- | --- | --- |
| 1 | インターネット | 198.51.100.77:50000 | 203.0.113.10:80 | クライアントが送る |
| 2 | IGW | 198.51.100.77:50000 | **10.0.1.10**:80 | 宛先を、パブリックIPからプライベートIPに変換 |
| 3 | public-a のNACL（インバウンド） | 同じ | 同じ | ルール100（All 0.0.0.0/0 ALLOW）に一致 → 許可 |
| 4 | web-sg（インバウンド） | 同じ | 同じ | 「TCP 80 送信元 0.0.0.0/0」に一致 → 許可し、接続を記録 |
| 5 | web のOS | 同じ | 同じ | 80番で待ち受けている → 受け付ける |

ノード：2番で、宛先が `203.0.113.10` から `10.0.1.10` に変わりました。IGWの1対1の変換ですね。

博士：うむ。そして、ここが「行きにルートテーブルがない」理由だ。IGWで宛先がVPCの中のアドレスに変わったら、あとはVPCの中だ。VPCルータは、local経路で public-a へ届ける。

ノード：じゃあ、行きの経路は気にしなくていい？

博士：VPCの外から入ってくる行きについては、そうだ。気にするべきは、帰りの経路だ。

ノード：3番がNACL、4番がSGの順なのは？

博士：外側から内側へ進むからだ。まずサブネットの境界（NACL）、次にインスタンスの扉（SG）。フロアの関所を通ってから、部屋の扉に着く。

### 帰り：web からクライアントへ

博士：web が、HTTPの返事を返す。送信元と宛先が入れ替わるぞ。

| # | 場所 | 送信元 | 宛先 | 判定・変化 |
| --- | --- | --- | --- | --- |
| 6 | web-sg（アウトバウンド） | 10.0.1.10:80 | 198.51.100.77:50000 | 記録にある接続の返事 → ルールを見ずに許可 |
| 7 | public-a のNACL（アウトバウンド） | 同じ | 同じ | ルール100に一致 → 許可（ステートレスなので、ここで改めて判定） |
| 8 | public-rt | 同じ | 同じ | `198.51.100.77` は `0.0.0.0/0` に一致 → ターゲット `igw-0a1b2c3d` |
| 9 | IGW | **203.0.113.10**:80 | 198.51.100.77:50000 | 送信元を、プライベートIPからパブリックIPに変換 |
| 10 | インターネット | 203.0.113.10:80 | 198.51.100.77:50000 | クライアントに届く |

ノード：6番と7番で、SGとNACLの扱いが分かれていますね。SGは覚えているから通して、NACLはもう一度ルールで見る。

博士：うむ。そして8番が、帰りの経路だ。返事の宛先はインターネットのアドレスなので、VPCルータは、public-a に関連付いた public-rt を見て、IGWへ送る。

ノード：もし、public-rt に `0.0.0.0/0 → igw` がなかったら？

博士：返事はIGWへ向かわないので、9番の変換が起きない。返事はどこにも出られないか、別の出口から、クライアントの知らない送信元で出ていく。どちらにしても、クライアントには届かない。行きと帰りで通り道が違うこういう状態を、非対称な経路と呼ぶ。第3章で学んだ「帰りの経路も要る」は、クラウドでも同じなのだ。

### 止まりやすい場所

博士：この表を上から順に疑えば、たいていの「つながらない」は見つかる。よくある止まり方を並べておこう。

| 止まる場所 | よくある原因 |
| --- | --- |
| 1〜2 | web にパブリックIPがない / VPCにIGWがアタッチされていない |
| 3 | NACLのインバウンドで、80番を許可していない |
| 4 | SGのインバウンドで、80番を許可していない |
| 5 | OSが80番で待ち受けていない（Connection refused） |
| 7 | NACLのアウトバウンドで、エフェメラルポートを許可していない |
| 8 | public-rt に `0.0.0.0/0 → igw` がない / サブネットに public-rt を関連付けていない |

ノード：毎回、これを手でたどるのは大変ッスね。

### Reachability Analyzer — 設定から、届くかを調べる

博士：AWSには、これを設定から自動でたどってくれる道具がある。**Reachability Analyzer** だ。

> **用語：Reachability Analyzer**（到達性アナライザー）
> 送信元と宛先を指定すると、ルートテーブル・NACL・SGなどの設定をたどって、通信が届くかどうかと、届かないならどの部品で止まるかを示すAWSの道具。実際にパケットは送らず、設定だけを調べる。

ノード：パケットを送らないで、わかるんですか？

博士：設定は、全部AWSが知っているからな。このシミュレータにも、同じ考え方の教育用の分析が付いている。送信元に Internet（`198.51.100.77`）、宛先に web、TCPの80番を指定すると、こう表示される。

```text
到達可能: 行き（往路）と帰り（復路）の両方で通信が成立します
往 Internet          198.51.100.77   インターネットのクライアント 198.51.100.77:50000 から接続します
往 Instance          web             パブリックIP 203.0.113.10 宛てに送ります
往 Internet Gateway  path-igw        VPCとインターネットの出入口です。…1対1で変換します
往 Network ACL       vpc-1-default-acl（public-a のインバウンド）
                     TCP 198.51.100.77:50000 → 10.0.1.10:80 は「ルール 100 ALLOW All 0.0.0.0/0」に一致するので許可します
往 Security Group    web-sg          インバウンドルール「TCP 80 from 0.0.0.0/0」に一致するので許可します
往 Instance          web             web は tcp/80 で待ち受けています
復 Security Group    sg-…            SGはステートフル（行きの通信を覚えている）なので、…通します
復 Network ACL       vpc-1-default-acl（public-a のアウトバウンド）
                     TCP 10.0.1.10:80 → 198.51.100.77:50000 は「ルール 100 ALLOW All 0.0.0.0/0」に一致するので許可します
復 Route Table       public-rt（public-a）  宛先 198.51.100.77 は経路 0.0.0.0/0 に一致 → ターゲット igw-… へ送ります
復 Internet Gateway  path-igw        戻りの通信も、…1対1で変換して通します
```

ノード：さっきの表と、順番がまったく同じだ！ 「往」が行き、「復」が帰りですね。

博士：うむ。届かない場合は、止まった行と、その理由が表示される。読み方は表と同じだ。

> **シミュレータ**
> 分析では、クライアントのエフェメラルポートを `50000` に固定しています。実際のAWSの Reachability Analyzer とは、表示の形や調べる範囲が異なります。また、インスタンスのOSのファイアウォール（第7章の iptables など）は考えません。

> **まとめ**
>
> - 行きは「IGW → NACL（イン）→ SG（イン）→ OSの待ち受け」、帰りは「SG（アウト）→ NACL（アウト）→ ルートテーブル → IGW」の順にたどる
> - 外から入る行きは、IGWで宛先がプライベートIPに変わり、local経路で届く。気にするべきは帰りの経路
> - 帰りでは、SGは記録で通し、NACLは改めてルールで判定する
> - Reachability Analyzer は、設定だけから、届くかどうかと止まる場所を示す

## プライベートサブネットに置き、SG参照で守る

### db は、外から届かないところに置く

博士：次は db だ。db は web だけが使うデータベースだから、インターネットから届く必要はない。どこに置く？

ノード：private-a です。プライベートサブネットで、パブリックIPも付けない。そうすれば、インターネットからは宛先に指定することすらできません。

博士：うむ。private-a はメインルートテーブル（local経路だけ）を使うので、プライベートサブネットだ。経路の上でもアドレスの上でも、外からは手が届かない。フィルタの設定を1つ間違えても、インターネットから直接は入れない。これが、プライベートサブネットに置く一番の理由だ。

### 役割ごとに区画を分ける：3層構成

博士：この章の例は web と db の2台だけだが、実務では、もう少し段を分けることが多い。

> **用語：3層構成**（three-tier architecture）
> システムを「外からの入口（Web）」「処理（アプリケーション）」「データ（DB）」の3つの層に分け、層ごとにサブネットとフィルタを分ける構成。外に近い層だけを公開し、奥の層ほど、届いてよい相手を絞る。

ノード：この章の web は、入口と処理を兼ねている、ってことですね。

博士：うむ。考え方は同じで、「奥の層には、1つ手前の層からしか届かない」ようにする。db に届いてよいのは、web からの5432番だけだ。これを、db に付けるSG（`db-sg` と呼ぶことにする）で表そう。

### db-sg に web のアドレスを書くと、困ること

ノード：db-sg のインバウンドに「TCP 5432 送信元 `10.0.1.10/32`」と書けばいいですね。`/32` で web の1台だけ。

博士：それでも動く。だが、web の調子が悪くて作り直したら、プライベートIPが `10.0.1.11` に変わるかもしれない。アクセスが増えて、web を3台に増やしたら？

ノード：そのたびに、db-sg のルールを書き直さないといけない…。忘れたら、新しい web から db に届かない。

博士：クラウドでは、サーバーを作ったり消したりするのが当たり前だからな。IPアドレスに頼ったルールは、すぐに古くなる。そこで、送信元にアドレスではなく、SGを書く。これを **SG参照** と呼ぶ。

> **用語：SG参照**（security group reference）
> SGのルールの送信元（や宛先）に、IPアドレスではなく別のSGを指定すること。「そのSGが付いているENIからの通信」を許可する意味になり、相手のIPアドレスが変わっても、ルールを直さずに済む。

```text
db-sg
インバウンド
  TCP  5432   送信元 web-sg        web-sg が付いたサーバーからの5432番だけ
アウトバウンド
  All  All    宛先   0.0.0.0/0     作ったときのまま（次のページで、OSの更新に使う）
```

ノード：「web-sg が付いているサーバーから」なら、web を何台に増やしても、web-sg を付けるだけで db に届くんですね。IPアドレスじゃなくて、役割で許可する。

博士：その通りだ。

### web から db へ、行きと帰りをたどる

博士：では、web から db への接続をたどろう。今度は、VPCの中から中への通信だ。

| # | 場所 | 送信元 | 宛先 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | web-sg（アウトバウンド） | 10.0.1.10:50000 | 10.0.2.10:5432 | 「All 0.0.0.0/0」に一致 → 許可 |
| 2 | public-a のNACL（アウトバウンド） | 同じ | 同じ | public-a から出るときに判定 |
| 3 | public-rt | 同じ | 同じ | `10.0.0.0/16` に一致 → local |
| 4 | private-a のNACL（インバウンド） | 同じ | 同じ | private-a に入るときに判定 |
| 5 | db-sg（インバウンド） | 同じ | 同じ | 送信元のENIに web-sg が付いている → 許可 |
| 6 | db のOS | 同じ | 同じ | 5432番で待ち受けている |
| 7 | db-sg（アウトバウンド） | 10.0.2.10:5432 | 10.0.1.10:50000 | 記録にある接続の返事 → 許可 |
| 8 | private-a のNACL（アウトバウンド） | 同じ | 同じ | private-a から出るときに判定 |
| 9 | メインルートテーブル | 同じ | 同じ | `10.0.0.0/16` に一致 → local |
| 10 | public-a のNACL（インバウンド） | 同じ | 同じ | public-a に入るときに判定 |
| 11 | web-sg（インバウンド） | 同じ | 同じ | 記録にある接続の返事 → 許可 |

ノード：NACLが4回！ サブネットをまたぐから、行きで2回（出る側と入る側）、帰りで2回。SGは、行きは両方がルールで判定して、帰りは両方とも記録で通す。

博士：うむ。private-a はメインルートテーブルを使うので、9番の帰りの経路は local だ。いまはどちらのサブネットもデフォルトNACL（すべて許可）なので、NACLは4回とも通る。

> **現場では**
> 3層構成では、SGを「インターネット → 入口のSG → アプリのSG → DBのSG」と、1つ手前の層のSGだけを送信元にして、順に参照させます。また、データベースは EC2 に自分で入れる代わりに、AWSが運用まで引き受けるデータベースのサービス（Amazon RDS）を使うことも多いですが、ネットワークの考え方（プライベートサブネットに置き、SG参照で絞る）は同じです。

> **まとめ**
>
> - 外から届く必要のないサーバーは、プライベートサブネットに置き、パブリックIPを付けない
> - 送信元にSGを書く「SG参照」なら、相手のIPアドレスが変わってもルールを直さずに済む
> - VPCの中の通信も、サブネットをまたげば、NACLを4回（行きで2回、帰りで2回）通る

## NAT Gatewayで外へ出し、NACLで守りを重ねる

```theory-visual
aws-nat-route
```

### でも、db からは外へ出たい

博士：前のページで、db を private-a に置いた。ところが、困ったことがある。db のOSには、ときどき更新（セキュリティの修正など）を入れたい。更新は、インターネットの更新サーバー `198.51.100.10` から、HTTPS（暗号化したWebの通信。TCPの443番）でダウンロードする。

ノード：あれ…。db はプライベートサブネットだから、インターネットに出られないんでしたよね。

博士：そうだ。どうする？

ノード：え〜っと、db にもパブリックIPを付けて、public-a に引っ越す…？

博士：それをすると、db をインターネットから宛先にできるようになる。SGで守っていても、設定ミス1つで外にさらされる。

ノード：うーん。「外へ出るのはいいけど、外から入られるのは困る」…。あ！ 第6章の **PAT**（たくさんの内側の端末で、1つの外側のアドレスを共有するNAT。ポート番号で通信を区別する）がまさにそれです。外から始まる通信には、変換の記録がないから通らない。

博士：見事だ。AWSで、そのPATをする部品が **NAT Gateway** だ。

> **用語：NAT Gateway**（NATゲートウェイ）
> プライベートサブネットのインスタンスが、インターネットへ出ていくための部品。送信元のアドレスを自分の Elastic IP に変換し（第6章のPAT）、その返事だけを元のインスタンスへ戻す。インターネット側から新しく始まる接続は通さない。

### NAT Gateway は、パブリックサブネットに置く

ノード：NAT Gateway は、守りたい private-a に置くんですか？

博士：いや、**パブリックサブネット** に置く。この章では public-a だ。そして、Elastic IP を付ける。ここでは `203.0.113.20` とする。

ノード：え、守りたいのは private-a なのに、public-a に置くんですか？

博士：NAT Gateway が変換したパケットは、その後どこへ行く？

ノード：インターネットへ…。あ、IGWを通らないといけない。だから、NAT Gateway自身が、IGWへの経路があるパブリックサブネットにいないといけないんだ。

博士：その通りだ。NAT Gateway も、インターネットへ出ていく側の1台だからな。そして、private-a から NAT Gateway へ送るための経路を、private-a のルートテーブルに入れる。メインルートテーブルではなく、private-a 用に `private-rt` を作って関連付けよう。

```text
private-rt（private-a に関連付け）
  10.0.0.0/16   local
  0.0.0.0/0     nat-4e5f6a7b      ← NAT Gateway nat-a のID

public-rt（public-a に関連付け。NAT Gateway もこれを使う）
  10.0.0.0/16   local
  0.0.0.0/0     igw-0a1b2c3d
```

ノード：private-rt の `0.0.0.0/0` は、IGWじゃなくて NAT Gateway を向いている。だから private-a は、プライベートサブネットのまま、外へは出られるんですね。

博士：うむ。ついでに確かめておこう。db から web への返事（宛先 `10.0.1.10`）は、private-rt でどこへ行く？

ノード：`0.0.0.0/0` にも一致しますけど、`10.0.0.0/16` のほうが長く一致するから、local です。NAT Gateway には行きません。

博士：正解だ。Longest Prefix Match のおかげで、VPCの中の通信はこれまでどおり local で届く。

### db から更新サーバーへ、行きと帰りをたどる

博士：では、db が更新サーバーへ接続するときのヘッダを、1か所ずつ見よう。

| # | 場所 | 送信元 | 宛先 | 判定・変化 |
| --- | --- | --- | --- | --- |
| 1 | db-sg（アウトバウンド） | 10.0.2.10:50000 | 198.51.100.10:443 | 「All 0.0.0.0/0」に一致 → 許可し、接続を記録 |
| 2 | private-a のNACL（アウトバウンド） | 同じ | 同じ | 許可 |
| 3 | private-rt | 同じ | 同じ | `0.0.0.0/0` に一致 → NAT Gateway へ |
| 4 | public-a のNACL（インバウンド） | 同じ | 同じ | 許可（NAT Gateway のいるサブネットに入る） |
| 5 | NAT Gateway | **203.0.113.20**:50000 | 198.51.100.10:443 | 送信元を Elastic IP に変換し、変換を記録 |
| 6 | public-a のNACL（アウトバウンド） | 同じ | 同じ | 許可 |
| 7 | public-rt → IGW | 同じ | 同じ | `0.0.0.0/0` に一致 → IGW → インターネットへ |

ノード：5番で、送信元が `10.0.2.10` から `203.0.113.20` に変わりました。更新サーバーから見ると、相手は NAT Gateway の Elastic IP なんですね。

博士：うむ。返事は、逆の順にたどる。

| # | 場所 | 送信元 | 宛先 | 判定・変化 |
| --- | --- | --- | --- | --- |
| 8 | IGW → public-a のNACL（インバウンド） | 198.51.100.10:443 | 203.0.113.20:50000 | 許可 |
| 9 | NAT Gateway | 同じ | **10.0.2.10**:50000 | 変換の記録を見て、宛先を元の db に戻す |
| 10 | public-a のNACL（アウトバウンド） | 同じ | 同じ | 許可 |
| 11 | private-a のNACL（インバウンド） | 同じ | 同じ | 許可（ステートレスなので、改めて判定） |
| 12 | db-sg（インバウンド） | 同じ | 同じ | 記録にある接続の返事 → 許可 |

ノード：NACLが何回も出てきますね。サブネットの境界をまたぐたびに、出る側と入る側で見られてる。

博士：その通りだ。NAT Gateway には、インスタンスのような扉の門番（SG）はないが、NAT Gateway のいるフロアの関所（NACL）は通る。

### 外から始まる通信は、通らない

ノード：逆に、インターネットの誰かが `203.0.113.20` の5432番に接続しようとしたら？

博士：NAT Gateway には、その通信の変換の記録がない。どのインスタンスに渡せばいいかわからないので、捨てる。第6章のPATと同じで、外から始まる通信は通らない。

ノード：だから db は、出られるけど、入られない。

> **注意**
> 「NAT Gateway は、守りたいプライベートサブネットに置く」は誤解です。NAT Gateway 自身がIGWを通ってインターネットへ出るので、パブリックサブネットに置き、Elastic IP を付けます。そのうえで、プライベートサブネットのルートテーブルで、`0.0.0.0/0` を NAT Gateway へ向けます。

> **発展**
> 厳密には、NAT Gateway はまず送信元を自分のプライベートIP（public-a の中のアドレス）に変え、そのパケットがIGWを通るときに、IGWが Elastic IP へ1対1で変換します。外から見た結果は同じなので、この章の表では1か所にまとめています。

> **現場では**
> NAT Gateway は、置いたAZの中では冗長化されています（壊れても別の機器が代わる）が、AZごと止まれば使えなくなります。1つの NAT Gateway を全AZで共有すると、そのAZの障害で、ほかのAZのサーバーも外へ出られなくなります。AZごとに NAT Gateway を作り、各AZのプライベートサブネットを同じAZの NAT Gateway へ向けます。料金は、時間と、処理したデータ量の両方にかかります。

> **シミュレータ**
> NAT Gateway での変換は、送信元ポートを `50000` のまま変えずに表示します。実際のPATは、ほかの通信とぶつからないように、ポート番号も変えることがあります（第6章）。

### db のサブネットに、もう1段の守りを足す

博士：これで db は、外へは出られるが、外からは入られない。最後に、db の守りをもう一段固めよう。

ノード：でも、db-sg の SG参照で、web からしか届かないようにしましたよね。もう十分じゃないですか？

博士：SGは、インスタンスごとの設定だ。誰かが private-a に新しいインスタンスを作って、うっかり「全部許可」のSGを付けたら？

ノード：そのインスタンスは、VPCの中のどこからでも届いちゃいますね。

博士：そこで、private-a の境界にも、NACLで「通ってよい通信」を決めておく。1つの守りが破られても、もう1つで止める。この考え方を **多層防御** と呼ぶ。

> **用語：多層防御**（defense in depth）
> 1つの守りに頼らず、性質の違う守りを重ねること。どれか1つの設定を間違えても、ほかの守りで止められるようにする。例: サブネットの境界のNACLと、インスタンスごとのSGを両方使う。

博士：private-a に関連付けるNACLを `db-acl` として、必要な通信を書き出そう。private-a を出入りする通信は何がある？

ノード：web から db への5432番と、db から更新サーバーへの443番の2つです。

博士：その2つについて、private-a の境界を、どの向きのパケットが通るかを考えたまえ。

ノード：え〜っと、web → db は、行きが private-a に入ってくる（インバウンド、宛先ポート5432、送信元は public-a）。帰りは private-a から出ていく（アウトバウンド、宛先は web のエフェメラルポート）。db → 更新サーバーは、行きが出ていく（アウトバウンド、宛先ポート443）、帰りが入ってくる（インバウンド、宛先は db のエフェメラルポート）。

博士：完璧だ。それを、そのままルールにする。

```text
db-acl（private-a に関連付け）
インバウンド
  100  TCP  5432         10.0.1.0/24  ALLOW   web → db の行き
  110  TCP  1024-65535   0.0.0.0/0    ALLOW   更新の帰り（NAT Gateway 経由）
  *    All  All          0.0.0.0/0    DENY
アウトバウンド
  100  TCP  1024-65535   10.0.1.0/24  ALLOW   web → db の帰り
  110  TCP  443          0.0.0.0/0    ALLOW   更新の行き
  *    All  All          0.0.0.0/0    DENY
```

ノード：NACLには SG参照が使えないから、送信元は public-a の範囲 `10.0.1.0/24` で書くんですね。

博士：そうだ。NACLに書けるのはCIDRだけだ。これで、たとえば web から db の22番（SSH）への接続は、db-acl のインバウンドのどのルールにも一致せず、`*` で拒否される。SGの設定を間違えても、ここで止まる。

ノード：でも、インバウンド110番の 1024〜65535 は、送信元が `0.0.0.0/0` だから、ずいぶん広い入口に見えます。

博士：いい目だ。それがステートレスなフィルタの限界で、帰りを通すために、広い範囲を開けざるをえない。だからこそ、SGと組み合わせて使うのだ。

> **注意**
> 新しく作ったNACLは、ルールが空の「すべて拒否」から始まります。ルールを書く前にサブネットに関連付けると、その瞬間に、サブネットの通信がすべて止まります。必要なルールを先に書いてから、最後に関連付けます。

> **現場では**
> NACLをここまで細かく書かず、デフォルトのまま使うか、大きな範囲の拒否だけに使う会社も多くあります。細かく書くほど、通信を1つ増やすたびに、行きと帰りのルールを両方の境界に足す手間が増えるからです。

> **まとめ**
>
> - 外へ出るときは NAT Gateway（第6章のPAT）を使う。外から始まる接続は通らない
> - NAT Gateway はパブリックサブネットに置いて Elastic IP を付け、プライベートサブネットのルートテーブルで `0.0.0.0/0` を向ける
> - NACLとSGを重ねる多層防御で、1つの設定ミスでは奥の層に届かないようにする
> - NACLのルールは、サブネットを出入りする通信ごとに「行き」と「帰り」の組で書き出す

## ロードバランサー — 複数のサーバーに振り分ける

```theory-visual
alb-health
```

### web が1台だけだと困ること

博士：ここまでで、この章の例は完成だ。だが、実務の目で見ると、まだ弱いところがある。web が1台しかないことだ。

ノード：web が壊れたら、サービスが止まります。AZの `1a` ごと止まっても、同じですね。

博士：アクセスが増えて、1台では処理しきれなくなることもある。そこで、web を2つのAZに1台ずつ置くとしよう。でも、クライアントは、どちらのアドレスに送ればいい？

ノード：2台のパブリックIPを両方教えて、選んでもらう…のは無理ですよね。

博士：そこで、入口を1つにまとめて、後ろの複数のサーバーに振り分ける部品を置く。**ロードバランサー** だ。

> **用語：ロードバランサー**（load balancer）
> 届いた通信を受け止めて、後ろにある複数のサーバーに振り分ける部品。壊れたサーバーには振り分けないので、1台が止まってもサービスを続けられる。

### ロードバランサーの言葉

博士：ロードバランサーでは、「どのプロトコルの、何番のポートで受けるか」の設定を **リスナー** と呼ぶ。

> **用語：リスナー**（listener）
> ロードバランサーが「どのプロトコルの、何番のポートで受け付けるか」の設定。例: HTTPS の443番で受けて、後ろのサーバーの80番へ渡す。

ノード：振り分ける先のサーバーは、何て呼ぶんですか？

博士：ルートテーブルで学んだ「ターゲット」を、ここでも使う。送り先という意味は同じで、ロードバランサーが通信を渡す先のサーバーのことだ。そのターゲットをまとめて登録したものを **ターゲットグループ** と呼ぶ。

> **用語：ターゲットグループ**（target group）
> ロードバランサーが振り分ける先（ターゲット）のサーバーを、まとめて登録したもの。リスナーごとに、どのターゲットグループへ渡すかを決める。

ノード：壊れたサーバーに振り分けないって、どうやって壊れたとわかるんですか？

博士：ロードバランサーが、ターゲットに定期的に問い合わせているのだ。これを **ヘルスチェック** と呼ぶ。

> **用語：ヘルスチェック**（health check）
> ロードバランサーが、ターゲットに定期的に問い合わせて、正常に応答するかを確かめること。応答しないターゲットには、新しい通信を振り分けない。

### ALB と NLB

博士：AWSのロードバランサーで、よく使うものは2種類ある。違いは、通信のどの層まで見て振り分けるかだ。第1章で、通信は層ごとに分業していると学んだな。HTTPのようなアプリケーションの層を「L7」、TCPやUDPの層を「L4」と、番号で呼ぶことがある。

ノード：L7はHTTPの中身まで見えて、L4はポート番号まで、ってことですか？

博士：そういうことだ。L7で振り分けるのが **ALB** だ。

> **用語：ALB**（Application Load Balancer）
> HTTPやHTTPSの中身（URLのパスや、`www.example.com` のようなホスト名）を見て振り分けるロードバランサー。アプリケーションの層（L7）で動く。

ノード：もう1つは？

博士：**NLB** だ。

> **用語：NLB**（Network Load Balancer）
> TCPやUDPのポート番号までを見て振り分けるロードバランサー。トランスポートの層（L4）で動き、通信の中身は見ない。非常に多くの接続を、速く処理できる。

博士：大事な違いは、ターゲットから見た「送信元のアドレス」だ。ALBは、クライアントとの接続をいったん自分で受け止め、ターゲットへは自分から新しい接続を張り直す。

```text
接続1   client 198.51.100.77:50000   -->  ALB:443
接続2   ALB のプライベートIP:別のポート  -->  web 10.0.1.10:80
```

ノード：じゃあ web から見ると、相手はALBで、クライアントの `198.51.100.77` は見えない？

博士：IPアドレスの上では見えない。そのためALBは、HTTPのヘッダに、元のクライアントのアドレスを書き足して渡す。それが **X-Forwarded-For** だ。

> **用語：X-Forwarded-For**
> ロードバランサーなどの中継役が、HTTPのヘッダに書き足す「元のクライアントのIPアドレス」。ALBの後ろのサーバーは、これを見て、本当のアクセス元を知る。例: `X-Forwarded-For: 198.51.100.77`

博士：一方のNLBは、ターゲットの種類や設定によっては、クライアントのアドレスを書き換えずに、そのままターゲットに届ける。そのときは、ターゲットのSGやNACLも、クライアントのアドレスを前提に許可しておく必要がある。

| | ALB | NLB |
| --- | --- | --- |
| 動く層 | L7（HTTP / HTTPS） | L4（TCP / UDP） |
| 振り分けの判断 | URLのパスやホスト名など | プロトコルとポート |
| ターゲットから見た送信元 | ALBのアドレス（元のアドレスは X-Forwarded-For） | 設定により、クライアントのアドレスのまま |

### ロードバランサーを入れると、SGはどう変わる？

ノード：ALBを入れたら、web-sg は「送信元 0.0.0.0/0」のままでいいんですか？

博士：いや。web に届くのは、もうALBからの通信だけだ。だから、ALBにもSGを付けて、SG参照でつなぐ。

```text
alb-sg   インバウンド  TCP 443   送信元 0.0.0.0/0    インターネットから
web-sg   インバウンド  TCP 80    送信元 alb-sg       ALB からだけ
db-sg    インバウンド  TCP 5432  送信元 web-sg       web からだけ
```

ノード：入口から奥へ、1つ手前の層のSGだけを許可していく。さっきの3層構成の形ですね。

博士：そうだ。しかも web は、ALBからしか届かなくてよいので、パブリックIPを外して、プライベートサブネットに移せる。インターネットに公開されるのは、ALBだけになる。

ノード：ALBは、どこに置くんですか？

博士：インターネットから受けるALB（internet-facing と呼ぶ）は、パブリックサブネットに置く。ALB自身も、IGWを通ってクライアントとやり取りするからだ。しかもALBは、2つ以上のAZのサブネットを指定して作る決まりになっている。片方のAZが止まっても、入口が残るようにな。

ノード：IGWを通るからパブリックサブネット。NAT Gateway と同じ理屈ですね。

博士：うむ。届くかを確かめるときは、「クライアント → ALB」と「ALB → web」の2つの接続に分けて、それぞれをこれまでの表と同じようにたどればよい。

> **シミュレータ**
> このシミュレータのロードバランサーは、リスナーのポートと転送先のポート、ターゲットだけを持ちます。URLのパスによる振り分けは再現しません。ヘルスチェックの代わりに、ターゲットまで往復で届くかどうかで、正常かどうかを判定します。

> **まとめ**
>
> - ロードバランサーは入口を1つにまとめ、ヘルスチェックで正常なターゲットだけに振り分ける
> - ALBはL7でHTTPの中身を見て振り分け、ターゲットへは自分から接続し直す。NLBはL4で、クライアントのアドレスを保つことがある
> - ALBを入れたら、web-sg の送信元を alb-sg にして、web をプライベートサブネットに移せる
> - インターネット向けのALBは、2つ以上のAZのパブリックサブネットに置く

## VPCの外とつなぐ — ピアリング・エンドポイント・VPN

### 別のVPCとつなぐ：VPCピアリング

博士：会社が大きくなると、VPCは1つでは済まなくなる。たとえば、社内の共通の機能（ログインの仕組みなど）を動かすサーバー `10.1.1.10` が、別のVPC `shared-vpc`（`10.1.0.0/16`）にあるとしよう。これを、path-vpc の web から呼び出したい。

ノード：VPCどうしは、切り離されているんでしたよね。

博士：うむ。2つのVPCを1対1でつなぐのが **VPCピアリング** だ。

> **用語：VPCピアリング**（VPC peering）
> 2つのVPCを1対1でつなぎ、お互いのプライベートIPで通信できるようにする接続。片方が申請し、もう片方が承認すると使えるようになる。IDは `pcx-` で始まる。

ノード：つないだら、もう通信できますか？

博士：ルートテーブルに経路が要る。しかも、両側にだ。

```text
path-vpc 10.0.0.0/16  ---- pcx-1a2b3c4d ----  shared-vpc 10.1.0.0/16

path-vpc 側（public-rt）       10.1.0.0/16  →  pcx-1a2b3c4d
shared-vpc 側のルートテーブル    10.0.0.0/16  →  pcx-1a2b3c4d
```

ノード：片側だけじゃダメなんですか？

博士：片側だけだと、行きは届いても、返事が戻れない。第3章の「帰りの経路も要る」と同じだ。それから、ピアリングできるのは、2つのVPCのCIDRが重なっていないときだけだ。

ノード：最初のページで言ってた「重ならない範囲を選ぶ」が、ここで効いてくるんですね。両方 `10.0.0.0/16` だったら、`10.0.1.10` がどっちのVPCかわからない。

### ピアリングは、乗り継げない

ノード：VPCがA、B、Cの3つあって、AとB、BとCをピアリングしたら、AからCにも届きますか？

博士：届かない。ピアリングで通信できるのは、直接つないだ2つのVPCの間だけだ。Bを経由してCへ、という **推移的ルーティング** はできない。

> **用語：推移的ルーティング**（transitive routing）
> 「AとBがつながり、BとCがつながっているので、Bを経由してAからCへ届く」という、間を乗り継ぐ経路。VPCピアリングでは、これができない。

ノード：Aのルートテーブルに「Cの範囲 → AとBのピアリング」と書いても？

博士：Bのところで捨てられる。同じ理由で、ピアリングの相手のVPCのIGWや NAT Gateway を借りて、インターネットへ出ることもできない。AからCへ届けたいなら、AとCも直接ピアリングするか、たくさんのVPCを中継できる別の部品（このページの最後で紹介する）を使う。

```theory-visual
aws-peering-transit
```

### AWSのサービスへ近道する：Gateway型エンドポイント

博士：次は、AWSのサービスへの通信だ。db のバックアップを、AWSのファイルの保存サービス **S3** に毎晩送るとしよう。

> **用語：S3**（Amazon Simple Storage Service）
> AWSの、ファイルを保存するサービス。容量を気にせずファイルを置け、バックアップの置き場所などに使う。VPCの外にあり、普段はインターネット向けの窓口から使う。

ノード：db はプライベートサブネットだから、NAT Gateway を通って、インターネット向けの窓口へ行くんですね。

博士：それでも届く。だが、NAT Gateway は、処理したデータ量でも料金がかかる。毎晩何十GBものバックアップを通したら？

ノード：お金がかかりそうです…。

博士：そこで、VPCから S3 へ、インターネットを通らずに届ける部品を使う。**Gateway型エンドポイント** だ。

> **用語：Gateway型エンドポイント**（gateway VPC endpoint）
> VPCから S3 や DynamoDB（AWSのデータベースのサービスの1つ）へ、インターネットや NAT Gateway を通らずに届けるための部品。ルートテーブルの経路のターゲットとして使い、利用料金はかからない。IDは `vpce-` で始まる。

ノード：これも、ルートテーブルで使うんですか？

博士：うむ。作るときに選んだルートテーブルに、次のような経路が自動で入る。

```text
private-rt
  10.0.0.0/16    local
  0.0.0.0/0      nat-4e5f6a7b
  pl-1a2b3c4d    vpce-2b3c4d5e     ← S3 宛ては、エンドポイントへ
```

ノード：宛先の `pl-1a2b3c4d` って、CIDRじゃないですよね？

博士：S3 が使うアドレスの範囲は広く、AWSの都合で変わることもある。だから、それを1つにまとめた名前で書く。それが **プレフィックスリスト** だ。

> **用語：プレフィックスリスト**（prefix list）
> 複数のCIDRに名前を付けて、1つにまとめたもの。IDは `pl-` で始まる。S3 などのサービスのアドレスの範囲はAWSが管理していて、ルートテーブルの宛先にそのまま書ける。

ノード：S3 宛てのパケットは、`0.0.0.0/0` にもプレフィックスリストにも一致しますけど…。

博士：プレフィックスリストの中身は具体的な範囲なので、`0.0.0.0/0` より長く一致する。だから S3 宛てはエンドポイントへ、それ以外は NAT Gateway へ行く。Longest Prefix Match は、ここでも同じだ。

### 会社のネットワークとつなぐ：VGW と Site-to-Site VPN

ノード：オンプレミスの会社のネットワーク（たとえば `192.168.10.0/24`）と、VPCをつなぐこともできますか？

博士：できる。よく使われるのが、インターネットの上に、暗号化した専用の通り道（トンネル）を作ってつなぐ方法だ。

> **用語：Site-to-Site VPN**
> 拠点のネットワークとVPCを、インターネットの上に作った暗号化のトンネルでつなぐ仕組み。トンネルの中身は、途中のインターネットからは読めない。しくみは第11章で詳しく扱う。

ノード：VPC側では、何がトンネルの出入口になるんですか？

博士：**VGW** という部品を、VPCにアタッチして使う。

> **用語：VGW**（Virtual Private Gateway、仮想プライベートゲートウェイ）
> Site-to-Site VPN のトンネルの、VPC側の出入口になる部品。VPCにアタッチし、ルートテーブルで拠点のアドレスの範囲をここへ向ける。IDは `vgw-` で始まる。

```text
private-rt
  192.168.10.0/24   vgw-5d6e7f8a      ← 会社のネットワーク宛ては、VPNへ
```

ノード：トンネルの中は、どうなっているんですか？

博士：それは次の第11章で、ネットワークのシミュレータを使ってじっくり見る。ここでは「ルートテーブルで、宛先を `vgw-` に向ける」とだけ覚えておけばよい。

### ルートテーブルのターゲットを、並べて整理する

博士：この章に出てきたターゲットを、IDの頭の文字で並べておこう。

| ターゲット | 部品 | 届く先 |
| --- | --- | --- |
| `local` | VPCルータ | VPCの中 |
| `igw-` | IGW | インターネット（1対1の変換） |
| `nat-` | NAT Gateway | インターネット（内側から始めた通信だけ） |
| `pcx-` | VPCピアリング | 直接つないだ相手のVPCだけ |
| `vpce-` | Gateway型エンドポイント | S3 / DynamoDB |
| `vgw-` | VGW | Site-to-Site VPN の先の拠点 |

ノード：どこへ行くにも、結局はルートテーブルを見ればいいんですね。

博士：そういうことだ。「つながらない」ときも、まずはルートテーブルの、行きと帰りの両方を見るのだ。

> **発展**
> 大きな構成では、ほかにも次のような部品を使います（このシミュレータでは扱いません）。
>
> - Transit Gateway: 多数のVPCやVPNを1か所に集める中継役（ハブ）。VPCピアリングと違い、ハブを経由した通信ができ、その経路は Transit Gateway 自身のルートテーブルで決める。
> - PrivateLink（Interface型エンドポイント）: サブネットの中に、プライベートIPを持つENIを作り、そこから AWS のサービスや、別のVPCで公開されたサービスへ、インターネットを通らずにつなぐ。
> - Route 53 のプライベートホストゾーン: AWSのDNSのサービス Route 53 で、関連付けたVPCの中だけで使える名前を定義する。VPCのDNSの設定（enableDnsSupport と enableDnsHostnames）を両方有効にしておく必要がある。

> **シミュレータ**
> このシミュレータでは、プレフィックスリストを `pl-s3` / `pl-dynamodb` という名前で表します。VGWは、VPN側から伝わってくる拠点の範囲を設定したうえで、ルートテーブルにも「拠点の範囲 → VGW」の経路を書いて使います。

> **まとめ**
>
> - VPCピアリングは2つのVPCを1対1でつなぐ。両側のルートテーブルに経路が要り、CIDRが重なるとつなげない
> - ピアリングは推移的ではない。Bを経由して、AからCへは届かない
> - Gateway型エンドポイントで、S3 / DynamoDB へ NAT Gateway を通らずに届けられる。宛先はプレフィックスリスト
> - 会社のネットワークへは、VGW を出入口にした Site-to-Site VPN でつなぐ（第11章）

## つながらないときの切り分けと、運用の勘所

### 「つながらない」と言われたら

博士：最後に、実務の話をしよう。「web が開けない」と言われたら、ノード君はどこから見る？

ノード：え〜っと…。行きと帰りの表を、上から順に、ですか？

博士：うむ。順番を決めておくと迷わない。

```text
1. 宛先      パブリックIP / Elastic IP があるか、DNSの名前がそのアドレスを指しているか
2. 出入口    IGWがアタッチされているか、NAT Gateway に Elastic IP があるか、ピアリングは承認済みか
3. 経路      行きと帰りの両方のルートテーブル（サブネットへの関連付けも含めて）
4. NACL      インバウンドとアウトバウンドの両方（帰りのエフェメラルポート）
5. SG        受ける側のインバウンド、始める側のアウトバウンド
6. OS        そのポートで待ち受けているか、OSのファイアウォール
```

ノード：AWSの部品を全部見てもダメなら、最後はOSなんですね。

博士：そうだ。第7章で、下の層から順に確かめたのと同じ考え方だ。1つずつ見る前に、まず Reachability Analyzer で、止まる場所の見当を付けるのが近道だ。

### よくある誤解を、もう一度

博士：この章で出てきた誤解を、ノード君の口から言ってみたまえ。

ノード：「サブネットの名前に public と付ければパブリックになる」。…違います。アタッチ済みのIGWへの経路があるルートテーブルを関連付けて、初めてパブリックです。

ノード：「SGで許可したから、NACLは関係ない」。…違います。サブネットをまたぐ通信は両方で判定されるし、NACLはステートレスだから、帰りのエフェメラルポートも許可が要ります。

ノード：「NAT Gateway はプライベートサブネットに置く」。…違います。NAT Gateway 自身がIGWへ出るから、パブリックサブネットです。

ノード：「AとB、BとCをピアリングすれば、AからCに届く」。…届きません。ピアリングは推移的じゃないです。

博士：全問正解だ。もう1つ付け加えると、「SGのルールを消せば、すぐに通信が止まる」も誤解だ。すでに記録されている接続は、すぐには切れないことがある。

### 実際に流れた通信を記録する：VPCフローログ

ノード：Reachability Analyzer は、設定から調べるんでしたよね。実際にどんな通信が来て、止められたかは、わからないんですか？

博士：それには **VPCフローログ** を使う。

> **用語：VPCフローログ**（VPC Flow Logs）
> VPCの中のENIを通った通信について、送信元・宛先・ポート・許可されたか（ACCEPT）拒否されたか（REJECT）などを記録する機能。通信の中身（データ）は記録しない。

博士：記録の1行は、こんな形だ。

```text
2 123456789012 eni-0a1b2c3d4e5f67890 192.0.2.5 10.0.1.10 51515 22 6 1 40 1700000000 1700000060 REJECT OK
```

ノード：え〜っと、`192.0.2.5` のポート `51515` から、`10.0.1.10` の22番へ。その次の `6` は…。

博士：第8章でパケットを読んだときの、IPヘッダのプロトコル番号だ。6はTCPを表す。その後ろはパケット数、バイト数、記録した時間の始まりと終わりで、`REJECT` が、SGかNACLで拒否されたことを示している。誰かが web のSSHを試して、止められたわけだ。

ノード：Reachability Analyzer で「設定の上で届くはずか」、フローログで「実際に届いたか、止められたか」。2つを合わせれば、推測じゃなくて証拠で説明できますね。

### 誰が設定を変えたか：CloudTrail

ノード：昨日まで動いていたのに、今日つながらない、ってこともありますよね。

博士：そういうときは、誰かが設定を変えた可能性が高い。AWSでは、設定の変更を操作の記録として残せる。それが **CloudTrail** だ。

> **用語：CloudTrail**（AWS CloudTrail）
> AWSに対する操作（SGのルールの追加・削除、ルートテーブルの変更など）を、いつ・誰が・何をしたかの形で記録するサービス。

ノード：フローログで「何時からREJECTが増えたか」を見て、CloudTrailで「その時刻に誰が何を変えたか」を見る。時刻で突き合わせるんですね。

### 変更と料金も、設計のうち

博士：SGやルートテーブルの変更は、保存した瞬間に効く。本番の画面で手作業で変えて、1行間違えたら？

ノード：その瞬間に、サービスが止まります…。

博士：だから、変更のしかたも決めておく。そして、もう1つ忘れがちなのが料金だ。NAT Gateway は通したデータ量でも料金がかかるし、パブリックIPにも料金がかかる。AZをまたぐ通信に料金がかかることもある。

ノード：S3 へのバックアップは Gateway型エンドポイントで、パブリックIPは公開する部品だけ、ですね。

> **現場では**
> SGやルートテーブルは、画面から手で変えるのではなく、構成をコードとして書いて管理する方法（IaC。第12章で扱う）で管理し、変更前に差分をレビューしてから適用することが多くあります。戻すときも、以前の版のコードを適用します。

> **まとめ**
>
> - 「つながらない」ときは、宛先 → 出入口 → 経路 → NACL → SG → OS の順に、行きと帰りの両方を確かめる
> - Reachability Analyzer で設定の上での到達性を、VPCフローログ（ACCEPT / REJECT）で実際の通信を確かめる
> - 設定の変更は CloudTrail に記録される。時刻で突き合わせて原因を探す
> - 変更は差分を見てから適用し、料金（NAT Gateway・パブリックIP）も設計に含める

#### ノード君の今日のポイント

- VPCは、リージョンの中に作る自分専用のネットワーク。CIDRは後から変えられないので、ほかと重ならない範囲を選ぶ
- サブネットは1つのAZに属し、5つのアドレスが予約される。大事なものは2つのAZに分けて置く
- ルートテーブルはサブネットに関連付ける経路表。パブリックかどうかは、名前ではなくIGWへの経路で決まる
- IGWは1対1の変換、NAT Gateway はPAT。NAT Gateway はパブリックサブネットに置く
- SGはインスタンスごとのステートフルな許可リスト、NACLはサブネットの境界のステートレスなフィルタ。NACLでは帰りのエフェメラルポートも許可する
- SG参照で、IPアドレスではなく役割で許可する
- 届くかどうかは、経路・NACL・SG・OSの待ち受けを、行きと帰りの両方でたどって確かめる
