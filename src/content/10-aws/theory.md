## AWS VPC — クラウドの中に、自分のネットワークを作る

博士：ノード君、新しいWebサービスをAWSで動かすことになって、「VPCとセキュリティグループの設定を見ておいて」と頼まれたとする。どうする？

ノード：え〜っと、とりあえず画面を開きます。…でも、見慣れない部品の名前がずらっと並んでいて、固まっちゃいそうです。

博士：焦るでない。名前は見慣れなくても、中身はこれまでに学んだサブネット、経路表、NAT、ファイアウォールなのだ。

ノード：えっ、クラウドでも同じなんですか？

博士：うむ。今回は、それぞれがAWSのどの部品にあたるかを対応づけて、1つの通信を行きと帰りでたどっていくぞ。

ノード：具体的には、どんな話をするんですか？

博士：まず、VPC、サブネット、Route Table、Internet Gateway、NAT Gateway、Security Group、Network ACLが、オンプレミスの何にあたるか。
次に、サブネットが「パブリック」になる条件だ。先に言っておくと、名前ではなく、経路で決まる。

ノード：名前じゃないんですか。気になりますね。

博士：それから、Security Group（ステートフル）とNetwork ACL（ステートレス）の違いと、戻りの通信の扱い。
インターネットからEC2までの通信を、行きと帰りで1つずつ確かめる方法。
最後に、別のVPCやS3など、VPCの外とつなぐ部品の違いだ。

ノード：盛りだくさんッスね。

### まず、言葉をそろえる

ノード：さっそくですけど、そもそもAWSって、Amazonのですよね？

博士：そうだ。AWSはAmazon Web Services。Amazonが提供するクラウドサービスだ。この章で出てくる言葉を、先にそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| AWS | Amazon Web Services。Amazonが提供するクラウドサービス |
| オンプレミス | 自社で機器を用意して、設置・管理する形。01〜09章の世界 |
| VPC（Virtual Private Cloud） | AWSの中に作る、自分専用の仮想ネットワーク |
| Region（リージョン） | 東京、大阪のような、AWSの地理的な地域 |
| AZ（Availability Zone） | Region内の、電源やネットワークが独立したデータセンター群 |
| EC2（Elastic Compute Cloud） | AWSの仮想サーバー。1台1台を**インスタンス**と呼ぶ |
| ENI（Elastic Network Interface） | インスタンスに付く仮想のネットワークカード。IPアドレスはここに付く |
| CIDR | `10.0.0.0/16` のように、アドレスの範囲を「先頭何ビットがネットワーク部か」で書く方法（02章） |

博士：**オンプレミス**は、自社で機器を用意して、設置・管理する形のことだ。01〜09章でやってきたのは、この世界だな。

ノード：それに対して**VPC**（Virtual Private Cloud）が、AWSの中に作る、自分専用の仮想ネットワークですね。

博士：その通り。

ノード：RegionとAZの違いが、よくわからないです。

博士：Regionは、東京、大阪のような、AWSの地理的な地域だ。AZ（Availability Zone）は、Region内の、電源やネットワークが独立したデータセンター群のことだ。あとで詳しくやる。

ノード：EC2（Elastic Compute Cloud）はAWSの仮想サーバーで、1台1台を**インスタンス**と呼ぶ、と。ENIって何ですか？

博士：Elastic Network Interface。インスタンスに付く仮想のネットワークカードだ。IPアドレスはここに付く。そこは覚えておきたまえ。

ノード：CIDRは02章でやりましたね。`10.0.0.0/16` のように、アドレスの範囲を「先頭何ビットがネットワーク部か」で書く方法です。

博士：うむ、よく覚えているな。

### オンプレミスの部品と、AWSの部品を対応づける

ノード：AWSにもルータやファイアウォールがあるんですよね？ データセンターのどこかに、僕専用の機械が置かれる感じですか？

博士：いや。AWSには、ルータやファイアウォールの「機器」はない。同じ役割を、設定で作る部品として提供しているのだ。

ノード：機械じゃなくて、設定なんですか。

博士：そうだ。これまでの章の部品と並べると、こうなる。

| オンプレミス（これまでの章） | AWSの部品 | 違うところ |
| --- | --- | --- |
| 社内のネットワーク全体 | VPC | 機器やケーブルは見えない。ブロードキャストは使えない |
| サブネット（02章） | サブネット | 必ず1つのAZに属する。5つのアドレスをAWSが予約する |
| ルータの経路表（03章） | Route Table（ルートテーブル） | サブネットに関連付ける。行き先は部品のID（`igw-…` など）で書く |
| 1対1のNAT（06章） | Internet Gateway（IGW） | サブネットに置く機器ではなく、VPCに1つ付ける出入口 |
| PAT（06章） | NAT Gateway | 内側から始めた通信の戻りだけを通す |
| ステートフルなファイアウォール（06章） | Security Group（SG） | インスタンスごとに付く。許可ルールしか書けない |
| ステートレスなACL（06章） | Network ACL（NACL） | サブネットの境界に付く |
| サーバー | EC2インスタンス | 待ち受けるポートを決めるのはOSとアプリ（01章と同じ） |

ノード：社内のネットワーク全体にあたるのがVPCですね。でも「機器やケーブルは見えない。ブロードキャストは使えない」って書いてあります。

博士：うむ。ブロードキャストが使えないことは、あとでアドレスの数え方にも出てくる。

ノード：サブネットは、AWSでもサブネットなんですね。

博士：名前は同じだが、必ず1つのAZに属する。そして、5つのアドレスをAWSが予約する。ここもあとで詳しく見るぞ。

ノード：ルータの経路表はRoute Table（ルートテーブル）。「行き先は部品のID（`igw-…` など）で書く」っていうのが新しいですね。

博士：そうだ。サブネットに関連付けるというのも、オンプレミスとの違いだな。

ノード：1対1のNATがInternet Gatewayで、PATがNAT Gateway…。名前がややこしいッスね。

博士：まあ待て。IGWは、サブネットに置く機器ではなく、VPCに1つ付ける出入口だ。NAT Gatewayは、内側から始めた通信の戻りだけを通す。どちらもあとで1つずつやる。

ノード：ファイアウォールは2種類あるんですね。ステートフルなファイアウォールにあたるのがSecurity Group（SG）で、インスタンスごとに付いて、許可ルールしか書けない。ステートレスなACLにあたるのがNetwork ACL（NACL）で、サブネットの境界に付く。

博士：その通り。最後の行も大事だ。サーバーはEC2インスタンスにあたるが、待ち受けるポートを決めるのはOSとアプリだ。01章と同じだな。

### Region と Availability Zone

ノード：さっきのRegionとAZ、もう少し詳しく教えてください。

博士：うむ。**Region**（東京、大阪など）の中には、複数の**AZ**がある。AZは、1つ以上のデータセンターの集まりだ。

ノード：AZどうしは、何が違うんですか？

博士：AZどうしは、電源やネットワークが独立している。

ノード：VPCは、どのAZに作るんですか？

博士：VPCは1つのRegionの中に作り、そのRegionのすべてのAZにまたがる。一方、サブネットは必ず1つのAZに属する。図にするとこうなる。

```text
Region: ap-northeast-1（東京）
└─ VPC 10.0.0.0/16（すべてのAZにまたがる）
   ├─ AZ ap-northeast-1a:  public-a 10.0.1.0/24   private-a 10.0.11.0/24
   └─ AZ ap-northeast-1c:  public-c 10.0.2.0/24   private-c 10.0.12.0/24
```

ノード：VPCは東京Region全体に広がっていて、public-aとprivate-aは1a、public-cとprivate-cは1cにある、ということですね。

博士：そうだ。

ノード：でも、なんでわざわざAZを分けるんですか？ 1か所にまとめたほうが楽そうです。

博士：1つのAZが障害で止まっても、別のAZのサーバーで動き続けるためだ。

ノード：なるほど、保険みたいなものですね。

博士：うむ。同じ役割のサブネットとサーバーは、2つ以上のAZに分けて置くのが基本だ。

### VPC と CIDR — 最初に決めるアドレスの範囲

ノード：VPCを作るときは、まず何を決めるんですか？

博士：IPv4のCIDRブロックを指定する。サイズは /16（65,536個）から /28（16個）までだ。

ノード：アドレスは何でもいいんですか？

博士：10.0.0.0/16のように、プライベートアドレスの範囲から選ぶのが一般的だな。

ノード：じゃあ、どのVPCも10.0.0.0/16にしておけば、迷わなくていいですね。

博士：そこが落とし穴だ。大事なのは、**ほかのネットワークと重ならない範囲を選ぶ**ことなのだ。

ノード：重なると、何が困るんですか？

博士：後で別のVPCや社内とつなぐとき、アドレスが重なると経路表で宛先を区別できない。CIDRが重なるVPCどうしは、VPC Peering（あとで話す）も作成できないぞ。

ノード：最初に決めるときに、先のことまで考えなきゃいけないんですね。

### サブネットと、使えない5つのアドレス

ノード：サブネットは、どうやって作るんですか？

博士：サブネットは、VPCのCIDRを分割したものだ。サイズは同じく /16〜/28 だ。

ノード：02章と同じなら、/24で256 − 2の254個使えますね。

博士：相変わらず気が早いな。各サブネットでは、先頭の4つと最後の1つ、計5つのアドレスをAWSが予約している。サーバーにはこれらを付けられない。10.0.1.0/24なら、次のとおりだ。

```text
10.0.1.0     ネットワークアドレス
10.0.1.1     VPCルータ用
10.0.1.2     AWSが予約（AmazonのDNSはVPCのCIDRの先頭+2）
10.0.1.3     将来の利用のため予約
10.0.1.255   ネットワークのブロードキャストアドレス（VPCはブロードキャスト非対応）
```

ノード：10.0.1.1がVPCルータ用で、10.0.1.2はAWSが予約。AmazonのDNSは、VPCのCIDRの先頭+2なんですね。

博士：そうだ。10.0.1.3は、将来の利用のため予約されている。

ノード：最後の10.0.1.255はブロードキャストアドレスですね。でも、VPCってブロードキャスト非対応でしたよね？

博士：うむ。それでも予約されているのだ。02章では、ネットワークアドレスとブロードキャストアドレスの2つを除いて数えた。AWSでは、さらに3つ減る。

```text
/24 … 256 − 5 = 251個
/28 …  16 − 5 =  11個
```

ノード：/24で251個、/28だとたった11個ですか。

博士：そうだ。AWSで数えるときは、5を引くのを忘れないことだ。

### Route Table — サブネットごとの経路表

ノード：次はRoute Tableですね。

博士：うむ。**Route Table**は、03章で学んだルータの経路表にあたる。まず例を見てもらおう。

```text
public-rt（public-a、public-c に関連付け）
Destination     Target
10.0.0.0/16     local
0.0.0.0/0       igw-0abc

private-rt（private-a に関連付け）
Destination     Target
10.0.0.0/16     local
0.0.0.0/0       nat-0def
```

ノード：public-rtとprivate-rtの2つがありますね。どっちも10.0.0.0/16はlocalで、0.0.0.0/0の行き先が違う。

博士：そうだ。public-aの10.0.1.10から送るパケットで考えてみよう。宛先が10.0.2.20だったら、どうなる？

ノード：え〜っと、public-aはpublic-rtですよね。10.0.2.20は、10.0.0.0/16にも0.0.0.0/0にも当てはまります…。

博士：そう、2つの行に一致する。そのときは、より長く一致する /16 が選ばれ、`local`（VPCの中）で届くのだ。

ノード：じゃあ宛先が8.8.8.8なら、`0.0.0.0/0` だけに一致するから、IGWへ送られる。

博士：その通り。経路の選び方は、03章と同じ**Longest Prefix Match**（いちばん長く一致する経路を選ぶ）だ。

ノード：`local` の行は、自分で書くんですか？

博士：**local**は、VPCのCIDR宛ての経路だ。自動で作られ、削除できない。VPC内のサブネットどうしは、この経路で通信できる。

ノード：「関連付け」っていうのは？

博士：各サブネットは、1つのルートテーブルに**関連付け**られる。逆に、1つのルートテーブルを、複数のサブネットで共有できる。

ノード：public-rtをpublic-aとpublic-cで共有しているのが、それですね。じゃあ、どこにも関連付けていないサブネットは、経路表なしですか？

博士：いや。明示的に関連付けていないサブネットは、**メインルートテーブル**を使う。

ノード：へぇ、デフォルトがあるんですね。

博士：ここは注意が要るぞ。メインに0.0.0.0/0 → IGWを入れると、新しいサブネットが意図せずパブリックになるのだ。

ノード：うわ、それは怖いですね。結局、オンプレミスの経路表といちばん違うのはどこですか？

博士：オンプレミスとの違いは、経路表を「ルータ」ではなく「サブネット」に関連付けることだ。そのサブネットから出ていくパケットの行き先を決める。

ノード：じゃあ、ルータはどこにいるんですか？

博士：ルータ本体（VPCルータ）は、画面に出てこないのだ。

ノード：見えないけど、ちゃんといるってことですね。

### パブリックかプライベートかは、経路で決まる

ノード：サブネットに「public」って名前を付ければ、パブリックサブネットになるんですよね？

博士：ならない。サブネットに「public」という名前を付けても、パブリックサブネットにはならないのだ。

ノード：えっ、じゃあ何で決まるんですか？

博士：**関連付けられたルートテーブルに、Internet Gatewayへ向かう経路（例：0.0.0.0/0 → igw-）があるサブネット**が、パブリックサブネットだ。ない場合は、プライベートサブネットだ。

ノード：つまり「パブリック」はサブネットの種類じゃなくて、経路の結果ってことですか。

博士：その通り。関連付けるルートテーブルを替えれば、同じサブネットがどちらにもなる。

ノード：なるほど。じゃあ経路さえあれば、インターネットに出られますね。

博士：焦るでない。経路があっても、IGWがVPCから**デタッチ**（切り離し）されていると、経路は「ブラックホール」（行き先のない経路）になり、通信できない。

ノード：経路だけ残って、行き先が消えちゃうんですね。

博士：うむ。さらに、インスタンスがインターネットと直接通信するには、次の2つが両方必要だ。

| 条件 | 何のためか |
| --- | --- |
| サブネットのルートテーブルに、アタッチ済みのIGWへの経路がある | パケットをIGWまで運ぶ |
| インスタンスに、パブリックIPv4アドレスかElastic IPがある | IGWで変換するときの、外側のアドレスになる |

ノード：経路でパケットをIGWまで運んで、IGWで変換するときの外側のアドレスとして、パブリックIPv4アドレスかElastic IPがいる、と。

博士：そうだ。パブリックサブネットに置いても、プライベートIPしかなければ直接は通信できない。

ノード：その2つがそろえば、もう大丈夫ですか？

博士：さらに、後で扱うSGとNACLの許可も必要だ。

### Internet Gateway と NAT Gateway — 外への出口は2種類

#### Internet Gateway（IGW）

ノード：IGWって、結局何なんですか？

博士：**IGW**は、VPCとインターネットの出入口だ。作成してVPCにアタッチ（取り付け）して、初めて使える。

ノード：いくつも付けられるんですか？

博士：1つのVPCにアタッチできるIGWは1つだ。

ノード：出入口ってことは、通すだけですか？

博士：いや、変換もする。IGWは、パブリックIPを持つインスタンスについて、プライベートIPとパブリックIPを1対1で変換する。06章の静的NAT（1対1のNAT）と同じ考え方だ。

ノード：じゃあIGWは、NATルータみたいにサブネットのどこかに置く機器なんですね。

博士：そこが違うところだ。IGWは、サブネットに置く機器ではない。

ノード：あ、そうでした。VPCに1つ付ける出入口でしたね。

博士：うむ。それに、インスタンスのOSから見えるのもプライベートIPだけだ。変換は、OSの外のIGWで行われる。

ノード：サーバーの中から見ると、自分はプライベートIPのままなんですね。

#### NAT Gateway

ノード：じゃあ、パブリックIPを持たないインスタンスは、外に出られないんですか？

博士：そこで**NAT Gateway**だ。プライベートサブネットのインスタンスが外へ出るための部品で、06章のPAT（多数の端末で1つのアドレスを共有するNAT）にあたる。流れを図にするとこうなる。

```text
app-a 10.0.11.10（private-a。パブリックIPなし）
  → private-rt: 0.0.0.0/0 → nat-0def
  → NAT Gateway（public-a にある。送信元を Elastic IP 203.0.113.10 に変換）
  → public-rt: 0.0.0.0/0 → igw-0abc
  → IGW → インターネット
```

ノード：app-aから出たパケットが、private-rtでNAT Gatewayへ行って、そこで送信元がElastic IPの203.0.113.10に変わって、今度はpublic-rtでIGWへ…。あれ、NAT Gatewayがpublic-aにありますね。

博士：よく気づいたな。インターネット向けのNAT Gatewayは、**パブリックサブネット**に作成してElastic IPを割り当てる。

ノード：守りたいのはプライベートサブネットなのに、パブリックに置くんですか？

博士：NAT Gateway自身も、変換したパケットをIGWへ送る必要があるからだ。

ノード：なるほど。NAT Gatewayも、インターネットに出ていく側なんですね。

博士：そうだ。そして、プライベートサブネットのルートテーブルでは、0.0.0.0/0をNAT Gatewayへ向ける。

ノード：外から入ってくることはできるんですか？

博士：内側から始めた通信の戻りは届くが、インターネット側から新しい接続は始められない。

ノード：料金はかかるんですか？

博士：かかる。時間単位と、処理したデータ量に応じてだ。

ノード：それと、NAT Gatewayが止まったら、みんな外に出られなくなりません？

博士：いい質問だ。AZを指定して作成するNAT Gatewayは、そのAZの中で冗長化されている。

ノード：じゃあ、1つで十分ですね。

博士：まあ待て。1つを全AZで共有すると、そのAZの障害で、ほかのAZのサーバーも外へ出られなくなる。

ノード：あ、AZごと止まったらダメなのか。

博士：うむ。AZごとにNAT Gatewayを作り、各AZのプライベートサブネットを同じAZのNAT Gatewayへ向けるのが推奨構成だ。

### Elastic IP と EC2

ノード：さっきから出てくるElastic IPって、何ですか？

博士：**Elastic IP**は、アカウントに確保して使い続けられる、固定のパブリックIPv4アドレスだ。インスタンスやNAT Gatewayに関連付ける。

ノード：自動で付くパブリックIPとは違うんですか？

博士：自動割り当てのパブリックIPは、停止・起動で変わることがある。Elastic IPは、解放するまで保持される。

ノード：使っていないときは、タダですよね？

博士：いや。パブリックIPv4アドレスには、使用中かどうかにかかわらず料金がかかる。そこは覚えておきたまえ。

ノード：気をつけます。EC2のほうは？

博士：**EC2**インスタンスは、サブネットの中でプライベートIPを持つ。注意したいのは、ネットワークが通信を届けても、OSやアプリケーションがそのポートで待ち受けていなければ、接続は成立しないということだ。

ノード：01章の「Connection refused」と同じですね。

博士：その通り。

### Security Group と Network ACL — 性質の違う2つのフィルタ

ノード：いよいよセキュリティグループですね。最初に頼まれたやつです。

博士：うむ。VPCのフィルタは2つある。インスタンスの手前の**Security Group（SG）**と、サブネットの境界の**Network ACL（NACL）**だ。

ノード：どっちか片方で許可すれば、通るんですか？

博士：いや。サブネットの外からの通信は、両方で許可されて初めて届く。違いを表にするとこうだ。

| | Security Group | Network ACL |
| --- | --- | --- |
| 近いもの（06章） | ステートフルなファイアウォール | ステートレスなACL |
| 付ける場所 | インスタンス（のENI） | サブネット |
| 戻りの通信 | ルールに関係なく自動で許可（ステートフル） | 逆方向のルールで明示的に許可が必要（ステートレス） |
| ルール | 許可のみ。拒否ルールは書けない | 許可と拒否 |
| 評価の仕方 | 順序はなく、すべてのルールを評価。どれかに一致すれば許可 | 小さい番号から評価し、最初に一致したルールで決まる |
| どれにも一致しないと | 拒否 | 最後の `*` ルールで拒否 |
| 作った直後 | インバウンドなし、アウトバウンドはすべて許可 | デフォルトNACLはすべて許可。新しく作ったカスタムNACLは、ルールを追加するまですべて拒否 |
| 送信元の指定 | CIDR、または別のSG（SG参照） | CIDRのみ |

ノード：え〜っと、SGはステートフルなファイアウォールに近くて、インスタンス（のENI）に付く。NACLはステートレスなACLに近くて、サブネットに付く。

博士：そうだ。戻りの通信の行を見るといい。

ノード：SGはルールに関係なく自動で許可。NACLは逆方向のルールで明示的に許可が必要…。これが06章のステートフルとステートレスの違いですね。

博士：うむ。ルールの書き方も違う。SGは許可のみで、拒否ルールは書けない。NACLは許可と拒否の両方を書ける。

ノード：評価の仕方も違いますね。SGは順序がなくて、すべてのルールを評価して、どれかに一致すれば許可。NACLは小さい番号から評価して、最初に一致したルールで決まる。

博士：では、どれにも一致しないときは？

ノード：SGは拒否。NACLは、最後の `*` ルールで拒否です。

博士：その通り。作った直後の状態も大事だ。SGは、インバウンドなし、アウトバウンドはすべて許可。

ノード：NACLは、デフォルトNACLはすべて許可。でも、新しく作ったカスタムNACLは、ルールを追加するまですべて拒否…。自分で作ると、最初は何も通らないんですね。

博士：そうだ。最後に送信元の指定。SGはCIDR、または別のSG（SG参照）を指定できる。NACLはCIDRのみだ。

ノード：06章のファイアウォールとは、どこが違うんですか？

博士：違いは置き場所だ。06章のファイアウォールは、境界に1台置いた。SGはインスタンスごとに付き、許可だけを並べる。

ノード：NACLは、サブネットの境界ですよね。

博士：うむ。NACLはサブネットの境界を越える通信だけを見るので、同じサブネット内のインスタンスどうしの通信は評価しない。

ノード：同じサブネットの中どうしなら、NACLの出番はないってことですね。

#### SG参照 — IPアドレスではなく「役割」で許可する

ノード：表にあった「SG参照」って、送信元に別のSGを書くってことですか？

博士：そうだ。送信元に別のSGを指定すると、「そのSGが付いたリソースからの通信」を許可できる。3層構成（Web・アプリ・DBを分ける構成）でよく使うぞ。

```text
alb-sg  インバウンド  TCP 443   送信元 0.0.0.0/0
app-sg  インバウンド  TCP 8080  送信元 alb-sg
db-sg   インバウンド  TCP 5432  送信元 app-sg
```

ノード：alb-sgは、TCP 443を送信元0.0.0.0/0から受ける。app-sgの送信元は、alb-sg…？

博士：app-sgの行は、「alb-sgが付いた相手からの8080だけを許可する」という意味だ。

ノード：で、db-sgはapp-sgからの5432だけ。Web、アプリ、DBの順番が、そのままルールになっているんですね。

博士：うむ。

ノード：でも、IPアドレスで書いても同じじゃないですか？

博士：クラウドでは、サーバーのIPアドレスがよく変わる。SG参照なら、ルールを直す必要がないのだ。

ノード：なるほど。IPアドレスじゃなくて、「役割」で許可するってことですね。

#### 戻りの通信と、エフェメラルポート

博士：さて、NACLでいちばんつまずきやすいのが、戻りの通信だ。

ノード：戻り…ですか。

博士：ALB（10.0.1.4）から、アプリ用サブネットのサーバー（10.0.11.10）の8080番へ接続する例で見よう。アプリ用サブネットには、次のカスタムNACLを付けたとする。

```text
app-acl
インバウンド
  100  ALLOW  TCP 8080         10.0.0.0/16
  *    DENY   すべて           0.0.0.0/0
アウトバウンド
  100  ALLOW  TCP 443          0.0.0.0/0
  *    DENY   すべて           0.0.0.0/0

行き  10.0.1.4:50000 → 10.0.11.10:8080   インバウンド 100 に一致 → 許可
帰り  10.0.11.10:8080 → 10.0.1.4:50000   アウトバウンド 100 は443だけ → * で拒否
```

ノード：インバウンドの100番で、10.0.0.0/16からの8080を許可していますね。行きはインバウンド100に一致して許可。…あれ、帰りが拒否されてます。

博士：帰りの行を、よく読んでみるといい。

ノード：10.0.11.10:8080から10.0.1.4:50000へ。アウトバウンド100は443だけだから、`*` で拒否…。この50000って何ですか？

博士：帰りの宛先ポート50000は、接続を始めたALBが選んだ**エフェメラルポート**（一時的に選ばれる送信元ポート。01章）だ。

ノード：行きを許可したんだから、帰りも通してくれればいいのに。

博士：NACLはステートレスなので、「行きを許可したから帰りも通す」とは考えないのだ。アウトバウンドに、次のような行が必要になる。

```text
  110  ALLOW  TCP 1024-65535   10.0.0.0/16
```

ノード：1024から65535まで、ずいぶん広いですね。50000だけじゃダメなんですか？

博士：エフェメラルポートの範囲は、OSやサービスで異なる。だから、戻りの通信を許可するNACLでは、1024〜65535を許可するのが一般的なのだ。

ノード：SGだったら、どうなんですか？

博士：SGなら、ステートフルなので、この行は要らない。

ノード：なるほど。ステートフルかどうかで、こんなに手間が違うんですね。

### ALB と NLB — 通信を複数のサーバーに振り分ける

ノード：さっきから出てくるALBって、何ですか？

博士：**ロードバランサー**の一種だ。ロードバランサーは、届いた通信を複数のサーバーに振り分ける部品だな。

ノード：覚えておく言葉はありますか？

博士：待ち受けるプロトコルとポートを**リスナー**、振り分け先のサーバー（**ターゲット**）の集まりを**ターゲットグループ**と呼ぶ。AWSのALBとNLBを比べると、こうだ。

| | ALB（Application Load Balancer） | NLB（Network Load Balancer） |
| --- | --- | --- |
| 扱う層 | L7（HTTP/HTTPS） | L4（TCP/UDP/TLS） |
| 振り分けの判断 | リスナーのルール（URLのパスやホスト名など） | リスナーのプロトコルとポート |
| ターゲットから見た送信元IP | ALBのIP。クライアントのIPはX-Forwarded-Forヘッダで伝わる | ターゲットの種類や設定により、クライアントのIPのまま（client IP preservation） |

ノード：ALBはL7（HTTP/HTTPS）、NLBはL4（TCP/UDP/TLS）を扱うんですね。

博士：うむ。振り分けの判断も、ALBはリスナーのルール（URLのパスやホスト名など）、NLBはリスナーのプロトコルとポートだ。

ノード：「ターゲットから見た送信元IP」が、ちょっとわからないです。

博士：ALBの場合、ターゲットから見える送信元はALBのIPだ。クライアントのIPは、X-Forwarded-Forヘッダで伝わる。NLBは、ターゲットの種類や設定により、クライアントのIPのまま届く。これをclient IP preservationという。

ノード：どうしてALBだと、送信元がALBになるんですか？

博士：ALBは、クライアントとのTCP接続をいったん受け止め、ターゲットへは自分から新しい接続を張るからだ。だから、ターゲットのSGでは「ALBからの通信」を許可する。

ノード：あ、さっきの送信元alb-sgですね！

博士：その通り。ちなみにALBは、作成時に少なくとも2つのAZのサブネットを指定する。

ノード：NLBで、クライアントのIPがそのまま届く場合は？

博士：その場合は、ターゲット側のSGやNACLも、クライアントのIPを前提に設定する。

ノード：ロードバランサーは、どのサブネットに置くんですか？

博士：インターネットから使うロードバランサー（internet-facing）は、パブリックサブネットに置く。ロードバランサー自身も、IGWを通ってクライアントとやり取りするからだ。

ノード：IGWを通るから、パブリック。NAT Gatewayと同じ理屈ですね。

### 到達性を、行きと帰りでたどる

博士：では、ここまでの部品を使って、1つの通信をたどってみよう。

ノード：待ってました。

博士：インターネットのクライアントから、パブリックサブネットのEC2のHTTPSへ接続する例だ。EC2のプライベートIPは10.0.1.10、Elastic IPは203.0.113.20とする。確かめる順番は、こうだ。

```text
行き  198.51.100.7:50000 → 203.0.113.20:443
  1. EC2にパブリックIP / Elastic IPがあるか
  2. VPCにIGWがアタッチされているか（宛先を10.0.1.10へ変換）
  3. サブネットのNACL インバウンド：TCP 443 を許可しているか
  4. SG インバウンド：TCP 443 を許可しているか
  5. EC2が443で待ち受けているか
帰り  10.0.1.10:443 → 198.51.100.7:50000
  6. SG：ステートフルなので戻りは許可
  7. NACL アウトバウンド：TCP 50000 宛てを許可しているか
  8. ルートテーブル：0.0.0.0/0 → IGW があるか
  9. IGWで送信元を203.0.113.20へ変換してクライアントへ
```

ノード：9ステップもあるんですね…。あれ、行きにはルートテーブルの確認がないですよ？

博士：行きは、IGWで宛先がVPC内のアドレスに変わる。あとはVPCの中（local）で届くからだ。

ノード：3と4は、NACLが先で、SGが後なんですね。

博士：そうだ。3〜4は、外側（サブネットの境界）から内側（インスタンス）への順になっている。

ノード：帰りの6と7は、同じフィルタなのに書き方が違いますね。

博士：うむ。6〜7で、SGとNACLの扱いが分かれる。SGは接続を覚えているので通し、NACLは改めてルールで判定する。

ノード：8は？

博士：8で帰りがIGWへ向かわないと、1対1の変換を通らず、クライアントに届かない。

ノード：よくある失敗って、ありますか？

博士：よくあるのは、7のNACLで戻りを許可していないこと、8で0.0.0.0/0がIGWを向いていないことだ。

ノード：ALBを挟んだら、どうなるんですか？

博士：ALBを挟む場合は、「クライアント → ALB」と「ALB → ターゲット」の2つの接続に分けて、同じように確かめる。

ノード：これを毎回、手でたどるのは大変ッスね。

博士：AWSには**Reachability Analyzer**というツールもある。パケットを送らずに、設定からこのような経路を分析してくれるのだ。

### VPCの外とつなぐ

#### VPC Peering — 2つのVPCを1対1でつなぐ

ノード：VPCが2つあるとき、つなぐ方法はありますか？

博士：**VPC Peering**だ。2つのVPCを1対1でつなぐ。

ノード：さっき、CIDRが重なると作れないって言ってましたね。

博士：うむ。CIDRが重複していると作成できない。それから、承認されて**active**になった後、**両側の**ルートテーブルに、相手のCIDR → pcx- の経路が必要だ。

```text
prod VPC 10.0.0.0/16  ── pcx-0aaa ──  shared VPC 10.1.0.0/16

prod のルートテーブル     10.1.0.0/16 → pcx-0aaa
shared のルートテーブル   10.0.0.0/16 → pcx-0aaa
```

ノード：prodには相手の10.1.0.0/16、sharedには相手の10.0.0.0/16を、どっちもpcx-0aaaへ向けていますね。片側だけじゃダメなんですか？

博士：片側だけだと、行きは届いても返事が戻らない。03章の「帰りの道も必要」と同じだ。

ノード：じゃあ、AとB、BとCをピアリングすれば、AからCにも届きますよね？

博士：届かない。Peeringは**推移的ではない**のだ。A–B、B–Cをつないでも、AからCへは通信できない。Bは、AとCの間を中継しないからだ。

ノード：VPCがたくさんあったら、大変ですね。

博士：多数のVPCをつなぐなら、Transit Gateway（あとの「発展」で紹介する）などを検討するといい。

#### Gateway型VPC Endpoint と VPN Gateway

ノード：S3みたいなAWSのサービスへは、どうやってつなぐんですか？

博士：**Gateway型VPC Endpoint**という部品がある。S3（ファイル保存サービス）とDynamoDB（データベースサービス）用だ。

ノード：どうやって使うんですか？

博士：ルートテーブルに、サービスの**プレフィックスリスト**宛てに、エンドポイントを向ける経路が追加される。プレフィックスリストは、`pl-` で始まる、AWSが管理するアドレス範囲のリストだ。

ノード：これも経路なんですね。何がうれしいんですか？

博士：インターネットやNAT Gatewayを経由せずに届くので、NAT Gatewayのデータ処理料金もかからない。

ノード：お得ですね。会社の拠点とVPCをつなぐときは、どうするんですか？

博士：**仮想プライベートゲートウェイ（VGW）**を使う。VPN Gatewayとも呼ぶ。Site-to-Site VPN（インターネット越しに拠点とVPCを、暗号化したトンネルでつなぐ仕組み）のAWS側の出入口だ。ルートテーブルで、拠点のアドレス範囲を `vgw-` へ向ける。

ノード：トンネルの中は、どうなっているんですか？

博士：トンネルの中の仕組みは、次章で扱う。

ノード：`igw-`、`nat-`、`pcx-`、`pl-`、`vgw-`…。どれもルートテーブルに出てくるんですね。

博士：うむ。VPCの外とつなぐときも、経路表を見るのが基本なのだ。

### 発展：大きな構成で使う部品

博士：ここからは発展だ。今は読み飛ばしてもかまわない。

ノード：一応、聞いておきます。

博士：うむ。大きな構成で使う部品を表にすると、こうだ。

| 部品 | 役割 |
| --- | --- |
| PrivateLink（Interface型エンドポイント） | サブネット内にプライベートIPを持つネットワークインターフェースを作り、AWSのサービスや他のVPCのサービスへプライベートに接続する |
| Transit Gateway | 多数のVPCやVPNを1か所に集めるハブ。Peeringと違ってハブを経由した通信ができ、その経路はTransit Gatewayのルートテーブルで制御する |
| Route 53 プライベートホストゾーン | VPCに関連付けると、VPC内だけで使える名前を定義できる。VPCのDNS属性 enableDnsSupport と enableDnsHostnames の両方を有効にする必要がある |

ノード：PrivateLinkは、サブネット内にプライベートIPを持つネットワークインターフェースを作って、AWSのサービスや他のVPCのサービスへプライベートに接続する…。

博士：そうだ。Interface型エンドポイントとも呼ぶ。

ノード：Transit Gatewayは、さっきのPeeringの話で出てきましたね。

博士：多数のVPCやVPNを1か所に集めるハブだ。Peeringと違って、ハブを経由した通信ができる。その経路は、Transit Gatewayのルートテーブルで制御する。

ノード：Route 53 プライベートホストゾーンは？

博士：Route 53は、AWSのDNSサービスだ。そのプライベートホストゾーンをVPCに関連付けると、VPC内だけで使える名前を定義できる。ただし、VPCのDNS属性 enableDnsSupport と enableDnsHostnames の両方を有効にする必要がある。

#### 用語メモ

- **VPC**［Virtual Private Cloud］：AWSの中に作る、自分専用の仮想ネットワーク。1つのRegionのすべてのAZにまたがる。
- **AZ**［Availability Zone］：Region内の、電源やネットワークが独立したデータセンター群。サブネットは必ず1つのAZに属する。
- **ルートテーブル**［Route Table］：サブネットに関連付ける経路表。行き先は部品のID（`igw-…` など）で書く。
- **インターネットゲートウェイ**［Internet Gateway］：VPCに1つ付ける、インターネットとの出入口。プライベートIPとパブリックIPを1対1で変換する。
- **NATゲートウェイ**［NAT Gateway］：プライベートサブネットのインスタンスが外へ出るための部品（PAT）。パブリックサブネットに置く。
- **Elastic IP**：アカウントに確保して使い続けられる、固定のパブリックIPv4アドレス。
- **セキュリティグループ**［Security Group］：インスタンス（のENI）ごとに付く、ステートフルな許可リスト。
- **ネットワークACL**［Network ACL］：サブネットの境界に付く、ステートレスなフィルタ。小さい番号から評価する。
- **エフェメラルポート**［ephemeral port］：接続を始めた側が一時的に選ぶ送信元ポート。NACLでは戻りの通信のために許可が必要。
- **VPCピアリング**［VPC Peering］：2つのVPCを1対1でつなぐ。推移的ではない。

#### ノード君の今日のポイント

- VPCは、AWSの中に作る自分専用のネットワーク。サブネットは1つのAZに属し、5つのアドレスが予約される。
- パブリックかどうかは、名前ではなく経路で決まる。アタッチ済みIGWへの経路があるサブネットがパブリック。
- プライベートサブネットから外へ出るには、パブリックサブネットに置いたNAT Gatewayへ経路を向ける。
- SGはインスタンスごとのステートフルな許可リスト、NACLはサブネット境界のステートレスなフィルタ。
- 到達性は、経路・NACL・SG・待ち受けを、行きと帰りの両方で確かめる。
