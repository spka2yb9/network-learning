## パケットは「次に渡す相手」を決めながら進む

博士：ノード君、浮かない顔だな。どうした？

ノード：本社のPCから支店のサーバーへpingしたのに、返事が来ないんです。先輩に相談したら「経路が足りないんじゃない？」って言われて…。

博士：うむ、よくある場面だ。ノード君は、ルータがネットワーク全体の地図を見てパケットを送っていると思っていないか？

ノード：え、違うんですか？ てっきり全部の道を知ってるものだと思ってました。

博士：違う。ルータが見ているのは「この宛先なら、次はあの機器へ」という一覧だけだ。これを**経路表**という。今回は、経路表の読み方と作り方を話すぞ。

ノード：経路表ですか。具体的にはどんなことをやるんです？

博士：まず、ルータが経路表を引いて「次に渡す相手」を決める流れ。次に、Connected Route・Static Route・Default Routeの違いだ。

ノード：ふむふむ。

博士：それから、候補が複数あるときの選び方。Longest Prefix Match → AD → Metric の順に比べる。

ノード：なんだか呪文みたいッスね。

博士：心配はいらん、順に説明する。さらに、pingが「行きは届くのに返ってこない」理由と、ループしたときに起きること。最後に、動的ルーティング（OSPF）が経路を自動で計算する仕組みだ。

ノード：盛りだくさんですね。がんばります。

### まず、言葉をそろえる

博士：話を始める前に、言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| ルータ | 複数のネットワークをつなぎ、宛先IPを見てパケットを次へ転送する機器 |
| ルーティングテーブル（経路表） | 「この宛先なら、次はここへ」を並べた一覧。1行を「経路（ルート）」と呼ぶ |
| Next Hop | 次にパケットを渡す相手（隣のルータなど）のIPアドレス |
| インターフェース | ルータの口。`g0/0` は GigabitEthernet 0/0 の略 |
| Default Gateway | PCが、別のネットワーク宛てのパケットを預けるルータ |

ノード：ルータは、複数のネットワークをつないで、宛先IPを見てパケットを次へ転送する機器。経路表の1行を「経路（ルート）」って呼ぶんですね。

博士：そうだ。Next Hopは、次にパケットを渡す相手、たとえば隣のルータのIPアドレスだ。

ノード：`g0/0` っていうのは何ですか？

博士：ルータの口、つまりインターフェースの名前だ。GigabitEthernet 0/0 の略だな。

ノード：Default Gatewayは、PCが別のネットワーク宛てのパケットを預けるルータ、と。

博士：その通り。では今回の構成だ。192.168.1.0/24 と 192.168.2.0/24 を、R1・R2でつなぐ。図にするとこうなる。

```text
PC1 192.168.1.10  (GW 192.168.1.1)
 │
R1  g0/0 192.168.1.1   g0/1 10.0.0.1
 │         10.0.0.0/30
R2  g0/0 10.0.0.2      g0/1 192.168.2.1
 │
PC2 192.168.2.10  (GW 192.168.2.1)
```

ノード：ルータとルータの間の 10.0.0.0/30 っていうのは何ですか？

博士：使えるアドレスが2つのサブネットだ。R1の 10.0.0.1 と R2の 10.0.0.2 で、ちょうど2つだな。

### ルータは「次の1台」だけを決める

ノード：PC1からPC2へ送ると、パケットはどう進むんですか？

博士：次の順に進む。

```text
1. PC1  宛先 192.168.2.10 は自分のネットワークの外 → Default Gateway（R1）へ
2. R1   経路表を引く：「192.168.2.0/24 は 10.0.0.2 へ」 → R2 へ渡す
3. R2   経路表を引く：「192.168.2.0/24 は g0/1 に直結」 → PC2 のMACをARPで調べて届ける
```

ノード：え〜っと、PC1は宛先 192.168.2.10 が自分のネットワークの外だから、Default GatewayのR1へ渡す。

博士：うむ。

ノード：R1は経路表を引いて「192.168.2.0/24 は 10.0.0.2 へ」だからR2へ。R2は「g0/1 に直結」だから、PC2のMACをARPで調べて届ける…。

博士：その通り。ここで大事なのは、どのルータも全体の道筋は知らない、ということだ。自分の経路表で「次の1台」を決めるだけなのだ。

ノード：それで困らないんですか？

博士：困らない。むしろ、そのおかげで各ルータは自分の周りの情報だけを持てばよい。だからネットワークが大きくなっても成り立つのだ。

ノード：なるほど。道路の案内標識みたいですね。交差点の標識には「◯◯方面はこちら」としか書いてないですし。

博士：いい例えだ。ただし標識と違う点がある。ルータは、経路表が間違っていても、そのとおりに機械的に送り続けるのだ。

ノード：うわ、融通が利かないッスね。

博士：機械だからな。経路表の各行が持つのは3つだ。「宛先プレフィックス」「Next Hop または出力インターフェース」「どうやって知った経路か」。

ノード：もし、一致する経路が1つもなかったら？

博士：ルータはパケットを捨てる。このとき送信元へ、ICMPのDestination Unreachableを返すのが一般的だ。

ノード：ICMPって、第1章で出てきた「IPの連絡係」ですよね？

博士：そうだ。Destination Unreachableは「宛先に届けられません」という知らせだな。

ノード：ところで、PC1はPC2のMACアドレスもARPで調べるんですか？

博士：いや。PC1がARP、つまりIPアドレスからMACアドレスを調べる仕組みで調べるのは、同じリンクにいるNext Hop（R1）だけだ。PC2のMACアドレスを知る必要はない。

ノード：隣のR1に渡せればいいから、ですね。

博士：そうだ。

### 直結していないネットワークは、教えてあげる

ノード：ルータの経路表って、最初はどうやってできるんですか？

博士：IPを設定してUpになったインターフェースから、**Connected Route**（directly connected）が自動でできる。

ノード：自動なんですね。じゃあリンクがDownになったら？

博士：その経路は消える。

ノード：じゃあR1は、PC2側のLANも最初から知ってるんですか？

博士：知らない。直結していないからな。そこで**Static Route**を使って、宛先ネットワークとNext Hopを手で指定するのだ。

```text
R1# configure terminal
R1(config)# ip route 192.168.2.0/24 10.0.0.2
R1(config)# end
R1# show ip route
C     10.0.0.0/30        is directly connected, g0/1
C     192.168.1.0/24     is directly connected, g0/0
S     192.168.2.0/24     [1/0] via 10.0.0.2
```

ノード：`ip route 192.168.2.0/24 10.0.0.2` が、「192.168.2.0/24 は 10.0.0.2 へ」って意味ですね。表示の頭の C とか S は？

博士：C は Connected、S は Static だ。

ノード：`configure terminal` と `end` は？

博士：`configure terminal` で設定モードに入り、`end` で抜ける。その前に `enable` で特権モードに入っておくのだ。

ノード：`[1/0]` っていう数字も気になります。

博士：それは [Administrative Distance / Metric] だ。後で説明するから、今は覚えておくだけでいい。

ノード：あれ、でもR1は、Next Hopの 10.0.0.2 にどうやって届けるんですか？

博士：いいところに気づいたな。もう一度経路表を引いて決めるのだ。10.0.0.0/30 → g0/1、とな。これを**再帰検索**（recursive lookup）と呼ぶ。

ノード：じゃあ、Next Hopに届く経路がなかったら…。

博士：そのStatic Routeは使えない。そこは覚えておきたまえ。

### Default Route：「その他すべて」の行き先

博士：次は 0.0.0.0/0 だ。ノード君、これはどんな宛先に一致すると思う？

ノード：え〜っと、プレフィックス長が0だから…。

博士：1ビットも比べない、ということだ。だから、どの宛先にも一致する最も短いプレフィックスなのだ。

ノード：何でも一致しちゃうなら、いつもそれが使われちゃいませんか？

博士：いや、より具体的な経路がないときだけ使われる。だから**Default Route**（Gateway of last resort）と呼ぶのだ。

ノード：Default…あれ、PCのDefault Gatewayと似てますね。

博士：その通り。PCのDefault Gatewayの設定も、中身はDefault Routeだ。「自分のサブネット以外は、全部このルータへ」という1行なのだ。

ノード：便利ですね。じゃあ全部これでいいんじゃ？

博士：相変わらず気が早いな。便利な反面、知らない宛先を何でも送ってしまう。**ルータどうしが互いにDefault Routeを向け合うと、ループの原因になる。**

ノード：ループ？

博士：どこにも存在しない宛先のパケットが、2台の間を行ったり来たりするのだ。

ノード：うわぁ、ピンポンみたいですね。

### 候補が複数あるとき：選ぶ順番

ノード：1つの宛先に、一致する経路が2つ以上あったらどうなるんですか？

博士：よくあることだ。ルータは次の順に比べる。表にするとこうだ。

| 順番 | 比べるもの | 選ぶ経路 |
| --- | --- | --- |
| 1 | プレフィックスの長さ | 最も長く一致するもの（Longest Prefix Match） |
| 2 | Administrative Distance（AD） | プレフィックスが同じなら、ADが小さいもの |
| 3 | Metric | 同じプロトコルどうしなら、Metricが小さいもの |
| 4 | （すべて同じ） | 複数の経路を同時に使う（ECMP。あとで説明します） |

ノード：まずプレフィックスの長さ、次にAD、最後にMetric、ですね。

博士：うむ。1つずつ見ていこう。

#### 1. Longest Prefix Match：最も具体的な経路を選ぶ

博士：宛先が 192.168.2.10 のとき、経路表がこうだったとする。

```text
宛先 192.168.2.10
  0.0.0.0/0         一致（何でも一致）
  192.168.0.0/16    一致（先頭16ビットが同じ）
  192.168.2.0/24    一致（先頭24ビットが同じ）  ← 最も長いので、これを使う
  192.168.3.0/24    不一致
```

ノード：0.0.0.0/0 は何でも一致、192.168.0.0/16 は先頭16ビットが同じ、192.168.2.0/24 は先頭24ビットが同じ。192.168.3.0/24 は不一致…。

博士：そうだ。一致した中で最も長い 192.168.2.0/24 を使う。

ノード：どうして長いほうなんですか？

博士：プレフィックスが長いほど範囲が狭く、情報が具体的だからだ。そして大事なことを言っておく。**どの方法で知った経路かより、プレフィックスの長さが先だ。**

ノード：はい、メモしておきます。

#### 2. AD：情報源の信頼度

ノード：じゃあ、プレフィックスがまったく同じ経路が2つあったら？

博士：同じプレフィックスを複数の方法で知った場合は、**AD**（Administrative Distance：情報源の信頼度）で選ぶ。小さいほど優先だ。Ciscoの既定値はこうなる。

```text
Connected 0 / Static 1 / eBGP 20 / OSPF 110 / iBGP 200
```

ノード：Connectedが0で一番信頼されてて、Staticが1…。eBGPとかiBGPっていうのは？

博士：BGPは、組織の間で経路を交換するプロトコルだ。第11章で扱うから、今は名前だけでいい。

ノード：この値って、どのルータでも同じなんですか？

博士：いや、値はベンダーごとに異なる。これはあくまでCiscoの既定値だ。

ノード：なるほど。

博士：では、同じ 192.168.2.0/24 をStatic（AD 1）とOSPF（AD 110）の両方で知っていたら？

ノード：ADが小さいStaticが使われる、ですね。

博士：正解だ。

#### 3. Metric：同じプロトコルの中での近さ

ノード：最後のMetricは？

博士：同じプロトコル内の候補は、**Metric**の小さいものを選ぶ。Metricは経路の「遠さ」で、OSPFならコストだ。

ノード：じゃあ、StaticとOSPFのMetricを比べたりも…。

博士：しない。プロトコルが違うとMetricの単位が違うから、比べないのだ。

ノード：センチとインチをそのまま比べないのと同じですね。

博士：そういうことだ。ひとつ実用的な技を教えておこう。Static RouteのADをわざと大きくすると、予備の経路にできる。

ノード：え、どういうことですか？

博士：たとえば `ip route 192.168.2.0/24 10.0.1.2 200` と書く。最後の200がADだ。

ノード：OSPFは110だから…OSPFの経路のほうが優先される？

博士：そうだ。このStatic Routeは、OSPF（110）の経路が消えたときだけ使われるのだ。

ノード：普段はベンチで控えてる選手ってことですね。

### 行きだけでなく、帰りの道も必要

博士：さて、ノード君の最初の悩みに戻ろう。pingが成功するのはどんなときだ？

ノード：え〜っと、相手に届いたら？

博士：惜しい。pingは、ICMPのEcho Requestを送り、Echo Replyが送信元に戻ったら成功だ。つまり**往復の経路**が必要なのだ。

ノード：あ、帰り道もいるんですね。

博士：そうだ。R1だけに経路を設定すると、こうなる。

```text
行き：PC1 → R1 → R2 → PC2    Echo Request は届く
帰り：PC2 → R2 → ？          R2 は 192.168.1.0/24 を知らず、Reply を捨てる
```

ノード：行きはPC2まで届いてるのに、帰りはR2で止まってる…。R2が 192.168.1.0/24 を知らないから、Replyを捨てちゃうんですね。

博士：その通り。だからR2にも `ip route 192.168.1.0/24 10.0.0.1` が必要だ。

ノード：R2の経路があれば、もう大丈夫ですか？

博士：まだある。PC2のDefault Gatewayが間違っている、たとえば存在しないアドレスになっている場合も、PC2はReplyをルータに渡せない。

ノード：どうしてですか？

博士：ARPで調べても、誰も答えないからだ。

ノード：つまり、宛先まで届いたからって、通信できてるとは限らないってことですよね。

博士：うむ。**「宛先まで届いた」と「通信が成立した」は同じではない。** Packet DebuggerでReplyの経路も追うといい。

### TTLとループ：パケットは永遠には回らない

博士：第1章で見たことを思い出してほしい。ルータを越えるたびに、MACアドレスとIPアドレスはどうなる？

ノード：MACアドレスは付け替えられて、IPアドレスは通常そのまま、でしたよね。

博士：そうだ。そしてTTL（Time To Live：残りの転送回数）は1ずつ減る。今回の構成では、送信時64がPC2では62になる。

ノード：R1とR2の2台を越えるから、2減るんですね。

博士：その通り。では、経路が互いを向いてループしたらどうなると思う？

ノード：永遠にぐるぐる回り続ける…？

博士：いや、無限には回らない。TTLが尽きたところで捨てられ、ICMPのTime Exceeded（時間切れ）が返るのだ。

ノード：あ、そうでした。TTLはそのためにあるんでしたね。ループしてるかどうかは、どうやって調べるんですか？

博士：tracerouteを使う。TTLを1から増やしながら調査用のパケット（probe）を送り、返ってくるICMPから途中のルータを調べるのだ。

ノード：probeって、pingと同じICMPですか？

博士：Linuxの既定はUDPのprobeだ。`-I` でICMP、`-T` でTCPを使う。

ノード：なるほど、選べるんですね。

博士：ループしていると、同じルータが交互に出てくる。こんな具合だ。

```text
 1  R1 のアドレス
 2  R2 のアドレス
 3  R1 のアドレス   ← また R1 に戻っている
 4  R2 のアドレス
```

ノード：3番目で、またR1に戻ってますね。

博士：同じアドレスが繰り返し表示されたら、ループを疑うといい。

ノード：どこでループしてるかは、どうやって見つけるんですか？

博士：各ルータで `show ip route <宛先>` を実行し、Next Hopを順にたどる。すると、折り返している場所がわかるのだ。

### 動的ルーティングが必要になる理由

ノード：Static Routeって、全部のルータに手で書くんですよね。ルータがたくさんあったら大変じゃないですか？

博士：そうだ。ルータが数台ならStatic Routeで足りる。だが台数が増えると、次の違いが効いてくる。

| | Static Route | 動的ルーティング |
| --- | --- | --- |
| 設定 | 宛先ごとに人が書く | ルータどうしが経路情報を交換する |
| 障害時 | 人が書き換えるまで切り替わらない | 自動で迂回路に切り替わる |
| 向いている場面 | ルータが数台の小さな構成 | ルータが多い構成、冗長な構成 |

ノード：動的ルーティングだと、ルータどうしが経路情報を交換してくれるんですね。障害のときも、自動で迂回路に切り替わる。

博士：うむ。Static Routeは、人が書き換えるまで切り替わらない。

ノード：小さな構成ならStatic Route、ルータが多い構成や冗長な構成なら動的ルーティング、と。

博士：その通り。ちなみに、障害のあと全ルータの経路表が新しい状態で落ち着くことを**収束**と呼ぶ。

ノード：動的ルーティングにも種類があるんですか？

博士：組織内ではOSPFなどの**IGP**（Interior Gateway Protocol：組織内用の経路プロトコル）を使う。組織の間ではBGPだ。

ノード：組織の間…？

博士：ここでいう組織はAS（Autonomous System）だ。1つの組織が管理するネットワークのまとまりのことだな。

### OSPF：地図を共有して、各自で最短経路を計算する

ノード：OSPFって、どういう仕組みなんですか？

博士：**OSPF**（Open Shortest Path First）は、リンクステート型のプロトコルだ。3つの段階で考えるといい。

ノード：はい。

博士：まず、各ルータは「どのリンクで、誰と、どのコストでつながっているか」を**LSA**（Link State Advertisement）として広告する。

ノード：自己紹介カードを配るみたいな感じですね。

博士：次に、受け取ったLSAを集めて、**LSDB**（リンクステートデータベース）を作る。これがネットワークの地図にあたる。同じエリアのルータは同じLSDBを持つのだ。

ノード：みんな同じ地図を持ってるんですね。

博士：そうだ。最後に、各ルータは自分を根として**SPF**（Shortest Path First：Dijkstraの最短経路計算）を行い、各宛先へのコスト最小の経路を求める。

ノード：つまり、みんなで同じ地図を持って、各自がカーナビみたいに自分からの最短ルートを計算するってことですよね。

博士：まさにそういうイメージだ。例を見てみよう。

```text
R1 ─10─ R2 ─10─ R4
 └──50── R3 ─10──┘
```

ノード：数字がコストですね。R1からR4へは、R2経由だと10＋10で20、R3経由だと50＋10で60…。R2経由を選ぶ！

博士：正解だ。では、R1–R2が切れたら？

ノード：R3経由しか残らないから…R3経由に切り替わる？

博士：うむ。LSDBが更新されて、R3経由に切り替わるのだ。OSPFの用語も表にしておこう。

| 用語 | 意味 |
| --- | --- |
| Neighbor（隣接） | 同じリンクのOSPFルータとHello（挨拶）を交換して作る関係。サブネットやエリア番号が一致しないと隣接にならない |
| Area（エリア） | LSDBを共有する範囲の単位。Area 0 がバックボーン（中心） |
| Cost（コスト） | リンクの「遠さ」。小さいほど優先。`ip ospf cost` で変えられる |

ノード：Neighborは、同じリンクのOSPFルータとHello、つまり挨拶を交換して作る関係。サブネットやエリア番号が一致しないと隣接にならない…。

博士：Areaは、LSDBを共有する範囲の単位だ。Area 0 がバックボーン、つまり中心になる。

ノード：Costはリンクの「遠さ」で、小さいほど優先。`ip ospf cost` で変えられる、と。

博士：ここで大事なことを言うぞ。**隣接しなければ、経路は交換されない。**

ノード：え、OSPFを設定すれば勝手に経路が来るんじゃないんですか？

博士：隣接してこそだ。たとえば片方のルータのインターフェースだけがArea 1だと、Area 0の相手とは隣接しない。

ノード：じゃあ「OSPFを設定したのに経路が来ない」ときは…。

博士：まず `show ip ospf neighbor` で隣接を確認するといい。状態が FULL（隣接が完成した状態）になっているかを見るのだ。

ノード：わかりました。設定はどう書くんですか？

博士：こんな感じだ。

```text
R1(config)# router ospf 1
R1(config-router)# network 10.0.0.0/16 area 0
R1(config-router)# network 192.168.1.0/24 area 0
R1(config-router)# passive-interface g0/2
R1(config)# interface g0/1
R1(config-if)# ip ospf cost 50
```

ノード：`network` っていうのは、広告するネットワークを書いてるんですか？

博士：どのインターフェースでOSPFを動かすかを選ぶものだ。その結果、一致したインターフェースのサブネットが広告される。

ノード：`passive-interface` は？

博士：そのインターフェースではHelloを送らず、つまり隣接を作らず、サブネットの広告だけを続ける。PCしかいないLAN側に使うのだ。

ノード：LANのサブネットは広告したいけど、隣接する相手はいない、ってことですね。

### ECMP：同じコストの経路を、同時に使う

ノード：さっきの選ぶ順番で、プレフィックスもADもMetricも全部同じだったら、どうなるんですか？

博士：よいところに気づいた。そのとき、ルータは1本に決めず、**複数の経路を同時に使う**ことができる。これを**ECMP**（Equal-Cost Multi-Path）という。

ノード：同時に、ですか？

博士：例で見よう。

```text
        R2
       /  \
PC -- R1   R4 -- Server（10.20.0.0/24）
       \  /
        R3
```

博士：R1から見ると、R2経由とR3経由は、段数もコストも同じだ。経路表はこうなる。

```text
R1# show ip route
S     10.20.0.0/24   [1/0] via 10.0.12.2
                     [1/0] via 10.0.13.3
```

ノード：同じ宛先の下に、Next Hopが2行ある！

博士：うむ。ここまでは「1つの宛先には、選ばれた経路が1本」という**単一経路**（single-path）で考えてきた。ECMPでは、同じ宛先に複数のNext Hopを持つ。

ノード：静的ルートでもできるんですか？

博士：同じ宛先・同じADで、Next Hopの違う静的ルートを2本書けばよい。OSPFなら、コストの同じ経路が見つかれば自動でECMPになる。

ノード：2本あるなら、パケットを交互に送るんですか？

博士：そうする方式もある。**per-packet**（パケットごと）の振り分けだ。だが、2つの経路の速さが少しでも違うと、パケットの到着順が入れ替わる。TCPは順番の入れ替わりに弱いので、性能が落ちてしまう。

ノード：じゃあ、どうするんですか？

博士：多くの機器は、**per-flow**（フローごと）に振り分ける。パケットの**5-tuple**、つまり送信元IP・宛先IP・プロトコル・送信元ポート・宛先ポートからハッシュを計算して、経路を1つ選ぶのだ。ハッシュとは、いくつかの値から決まった計算をして、番号を1つ取り出すことだ。

ノード：同じフローなら値が同じだから、いつも同じ経路…。

博士：そうだ。これを**フローの固定**（flow stickiness）という。別のフローは、別の経路になることがある。

```text
Flow A（PC:49152 → Server:443） → R2経由
Flow B（PC:49153 → Server:443） → R3経由
Flow C（PC:49154 → Server:443） → R2経由
```

ノード：じゃあ、1本のTCP接続は…片方の経路しか使わない？

博士：その通り。1つのフローの上限は、1経路分の速さだ。ECMPで増えるのは、たくさんのフローを合わせた合計の容量だ。

ノード：たくさんのフローがあってこそ、ってことですね。

博士：うむ。次の章で出てくるLink Aggregation（LAG：複数のリンクを1本に束ねる技術）も、似た考え方で振り分ける。そのとき、違いを比べてみるとよい。

ノード：経路が1本壊れたら、どうなりますか？

博士：壊れた経路は候補から外れ、残りの経路にフローが移る。R1の隣のリンク（R1–R2）が切れれば、R1は自分で気づいて、その経路を消す。

ノード：隣じゃなくて、R2–R4 が切れたら？

博士：そこが落とし穴だ。静的ルートは、Next Hop（R2）に届くかしか見ない。R1–R2が正常なら、R1はR2経由を候補に残したままだ。

ノード：じゃあ、ハッシュでR2経由を選んだフローだけ、R2で行き場がなくなる…。

博士：そうだ。「つながったり、つながらなかったり」という分かりにくい症状になる。OSPFなら、R2–R4の故障がLSAで伝わり、SPFの計算し直しでR2経由が消える。さっき話した**収束**（reconvergence）だな。

ノード：経路を見つけるのがOSPFで、同じコストの経路を使い分けるのがECMP、という分担なんですね。

博士：うむ。ルーティングプロトコルとECMPは別の概念だ。何本まで同時に使うかは、機器や設定で決まる。

```text
R1(config)# router ospf 1
R1(config-router)# maximum-paths 1     ← 等コストでも1本だけ使う（単一経路）
```

ノード：どのフローがどっちへ行くか、確かめる方法はありますか？

博士：Cisco機器なら `show ip cef exact-route <送信元> <宛先>` で、そのフローの行き先がわかる。PCからは、ポートの変わらない `traceroute -I`（ICMP）が向いている。

ノード：UDPのtracerouteだとダメなんですか？

博士：既定のUDPのtracerouteは、プローブごとに宛先ポートを変える。つまり毎回別のフローなので、ホップごとに違う経路を通り、結果が混ざることがあるのだ。

ノード：tracerouteにも、そんな落とし穴が…。

> シミュレータでの簡略化: ECMPは、同じプレフィックス・同じAD・同じメトリックで、Next Hopを解決できる経路をすべて候補にし、Next Hopの順に並べて、5-tupleのハッシュで1つを選びます（ICMPはポートがないので、送信元・宛先が同じなら同じフロー）。ハッシュは教育用の関数です。OSPFの `maximum-paths` は1〜16（既定4）。BGPのmultipathはなく、ベストパス1本だけを使います。障害の検出と収束は瞬時で、実機のようなタイマーの待ち時間はありません。

### 発展：OSPFのもう少し細かい話

博士：ここからは発展だ。今は読み飛ばしてもかまわんぞ。

ノード：せっかくなので聞きます！

博士：よろしい。まず**隣接の条件**。実機では、サブネットとエリアIDのほか、Hello/Dead間隔なども一致しないと隣接にならない。

ノード：Hello/Dead間隔？

博士：挨拶の間隔と、相手が消えたと判断するまでの時間だ。

ノード：なるほど。次は？

博士：**FULLにならない相手**の話だ。実機では、Ethernetのように多数のルータがつながるリンクでDR/BDRを選ぶ。Designated Router / Backup Designated Router、つまり代表ルータとその予備だな。

ノード：代表を決めるんですね。

博士：そうだ。そしてDR/BDR以外のルータどうしは、2-WAY（互いの存在を確認しただけの状態）のままで正常なのだ。

ノード：え、FULLにならなくてもいい場合があるんですか。

博士：そういうことだ。それから**複数エリア**。Area 0 以外のエリアは、ABR（Area Border Router：エリア境界ルータ）を介してArea 0につながる。

ノード：Area 0 がバックボーンだから、ですね。

博士：そうだ。**コストの既定値**にも注意だ。Ciscoの既定は「参照帯域100Mbit/s ÷ インターフェース帯域」で、最小1だ。

ノード：1Gbit/sだと、100 ÷ 1000 で0.1…あ、最小1だから1ですね。100Mbit/sは100 ÷ 100で1。

博士：そうだ。1Gbit/sも100Mbit/sもコスト1になる。そこは注意するといい。

ノード：速さが違うのに同じコストなんですね。気をつけます。

博士：最後に**network の書き方**。実機のCisco IOSでは、`network 10.0.0.0 0.0.255.255 area 0` のようにワイルドカードマスクで書く。

ノード：ワイルドカードマスク？

博士：マスクの0と1を反転したものだ。

ノード：/16 のマスク 255.255.0.0 を反転すると 0.0.255.255、ですね。

#### 用語メモ

- **経路表**［routing table］：「この宛先なら、次はここへ」を並べた一覧。1行を経路（ルート）と呼ぶ。
- **Next Hop**：次にパケットを渡す相手（隣のルータなど）のIPアドレス。
- **Connected Route**：IPを設定してUpになったインターフェースから自動でできる経路。
- **Static Route**：宛先ネットワークとNext Hopを人が手で指定する経路。
- **Default Route**：0.0.0.0/0。より具体的な経路がないときに使う「その他すべて」の行き先。
- **最長一致**［Longest Prefix Match］：一致する経路のうち、プレフィックスが最も長いものを選ぶ規則。
- **AD**［Administrative Distance］：情報源の信頼度。小さいほど優先。
- **TTL**［Time To Live］：残りの転送回数。ルータを越えるたびに1減り、0になると捨てられる。
- **OSPF**［Open Shortest Path First］：地図（LSDB）を共有し、各ルータがSPFで最短経路を計算するリンクステート型プロトコル。
- **収束**［convergence］：障害のあと、全ルータの経路表が新しい状態で落ち着くこと。
- **ECMP**［Equal-Cost Multi-Path］：同じ宛先への、同じAD・同じコストの複数の経路を同時に使うこと。
- **フロー / 5-tuple**：同じ送信元・宛先IP、プロトコル、送信元・宛先ポートを持つひと続きの通信／その5つの値の組。ECMPやLAGのハッシュの入力に使われる。

#### ノード君の今日のポイント

- ルータは経路表を引いて「次の1台」だけを決める。一致する経路がなければ捨てる。
- 直結のネットワークはConnected Route、それ以外はStatic Routeや動的ルーティングで教える。0.0.0.0/0 は「その他すべて」。
- 候補が複数あれば、①プレフィックスの長さ ②AD ③Metric の順で選ぶ。
- 通信には行きと帰りの両方の経路が必要。ループしてもTTLが尽きれば捨てられる。
- OSPFは地図（LSDB）を共有し、各ルータが最短経路を計算する。隣接しなければ経路は交換されない。
- 同じ宛先に同じコストの経路が複数あれば、ECMPで同時に使う。振り分けはフローごと（5-tupleのハッシュ）で、1つのフローは1経路分の速さまで。
- ECMPの経路が壊れたとき、気づけるのは「隣の故障」か「ルーティングプロトコルが伝えた故障」だけ。静的ルートは離れた区間の故障を知らない。
