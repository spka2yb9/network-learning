## ネットワークを組み立て、パケットを1ホップずつ追う

博士：ノード君、もし小さな営業所のネットワークづくりを任されたら、まず何をする？

ノード：え〜っと、ルータとスイッチを買ってきて、並べて、ケーブルを挿します！

博士：相変わらず気が早いな。機器を並べてケーブルを挿すだけでは、通信はできないのだ。

ノード：えっ、そうなんですか？

博士：うむ。誰が誰と通信するかを決め、アドレスを割り当て、経路を設定する。そして最後に、本当にその通りに流れるかを確かめる。

ノード：なるほど。けっこう手順があるんですね。

博士：今回は、これまでの章で学んだことを1つの構成にまとめるぞ。まずは、機器を並べる前に要件とIPアドレス計画を書く理由。それから、機器ごとの役割と、ポート単位で配線を考えることだ。

ノード：ふむふむ。

博士：さらに、VLAN・ルーティング・DNS・NAT・Firewallを、構成の中でどう組み合わせるか。パケットが1ホップ進むごとに、何が変わり、何が変わらないか。最後に、物理構成図と論理構成図の違いだ。

ノード：盛りだくさんッスね。総まとめって感じです。

博士：その通り。

### まず、言葉をそろえる

博士：本題に入る前に、今回使う言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| ホップ | パケットが次の機器へ渡る、1回ぶんの移動。経路の話では、通過するルータの数を数えることが多い |
| セグメント | ルータで区切られた、1つのネットワークの範囲 |
| IPアドレス計画 | どのネットワークに、どのアドレス範囲とGatewayを割り当てるかを書いた表 |
| Default Gateway | 自分のネットワークの外へ送るときに、パケットを渡すルータのアドレス |
| アクセスポート / トランクポート | 1つのVLANだけを運ぶポート / 複数のVLANを運ぶポート |
| 物理構成図 / 論理構成図 | 機器と配線を描いた図 / ネットワークの区切りと経路を描いた図 |

ノード：ホップって、よく聞きますけど、パケットが次の機器へ渡る1回ぶんの移動のことなんですね。

博士：そうだ。経路の話では、通過するルータの数を数えることが多い。

ノード：セグメントは、ルータで区切られた1つのネットワークの範囲。Default Gatewayは、自分のネットワークの外へ送るときにパケットを渡すルータのアドレス、と。

博士：うむ。IPアドレス計画、アクセスポートとトランクポート、物理構成図と論理構成図は、このあと順番に詳しく話すぞ。

### 作る前に、決めておくこと

博士：さて、ノード君。いきなり機器を並べる前に、やることがある。何だと思う？

ノード：え〜っと…IPアドレスを決める、とかですか？

博士：それも大事だが、その前に**要件**を言葉にするのだ。次の問いに答えると、それぞれが設計の根拠になる。

| 問い | 決まる設計 |
| --- | --- |
| 誰が誰と通信するのか | ルーティング、フィルタ（ACL/Firewall） |
| どのセグメントを分けるのか | VLAN、IPアドレス計画 |
| インターネットへ出るのはどこか | Default Route、NAT |
| 外から入れるのはどのサーバーか | 宛先NAT、Firewallの許可ルール |

ノード：「誰が誰と通信するのか」が決まれば、ルーティングやフィルタ（ACL/Firewall）が決まるんですね。

博士：そうだ。どのセグメントを分けるのかでVLANとIPアドレス計画が、インターネットへ出るのはどこかでDefault RouteとNATが決まる。

ノード：外から入れるサーバーを決めれば、宛先NATとFirewallの許可ルールが決まる、と。

博士：その通り。

ノード：でも、わざわざ書かなくても、動けばいいんじゃないですか？

博士：まあ待て。要件が書いてあれば、「この設定は正しいか」を判断する基準になる。書いていないと、動いているのか、たまたま通っているだけなのか、区別できないのだ。

ノード：たまたま通っている…。それはちょっと怖いですね。

### IPアドレス計画を先に書く

博士：では、例を使おう。今回は、営業LANのPC1から、R1とR2を通って、サーバーLANのPC2へ届く小さな構成を例にする。図にするとこうなる。

```text
PC1 --- SW1 === R1 --- R2 --- SW2 --- PC2
（=== はトランク。R1とR2の間は 10.0.12.0/30）
```

ノード：PC1からスイッチ、ルータ2台、スイッチを通ってPC2ですね。`===` はトランクで、R1とR2の間は 10.0.12.0/30、と。

博士：うむ。この構成のIPアドレス計画を書くと、こうだ。

```text
用途           VLAN  ネットワーク        Gateway
営業LAN        10    192.168.1.0/24      192.168.1.1
サーバーLAN    20    192.168.2.0/24      192.168.2.1
R1-R2間        -     10.0.12.0/30        (.1 と .2)
管理用         99    192.168.99.0/24     192.168.99.1
```

ノード：営業LANがVLAN 10、サーバーLANがVLAN 20…。R1-R2間の /30 って、ずいぶん小さいですね。

博士：よく気づいたな。**/30**は、アドレスが4つだけの小さなネットワークだ。第2章で出てきたな。

ノード：え〜っと、先頭と末尾は使えないから…。

博士：そうだ。先頭と末尾を除くと、使えるのは.1と.2の2つ。ルータ2台をつなぐのにちょうどよい大きさなのだ。

ノード：なるほど、無駄がないですね。じゃあ、管理用のVLAN 99は何ですか？

博士：機器にログインして設定するための通信を、利用者の通信と分けるためのものだ。

ノード：へぇ、管理のための通信は別にしておくんですね。

博士：うむ。計画には、ゲートウェイや機器管理用のアドレス、将来の増設分も含めておく。

ノード：表にしておくと、何かいいことがあるんですか？

博士：アドレスの重複や設定ミスを、レビューで見つけやすくなるのだ。

### 機器を置き、ポート同士をつなぐ

博士：計画ができたら、いよいよ機器を置いてつなぐ。ノード君、ケーブルは何と何をつなぐものだと思う？

ノード：それは簡単です。機器と機器ですよね。

博士：惜しい。「機器と機器」ではなく「ポートとポート」をつなぐと考えるのだ。たとえば「R1のg0/0とSW1のg0/1」のようにな。

ノード：g0/0って何ですか？

博士：ポートの名前だ。GigabitEthernet 0/0の略だな。

ノード：どうしてそこまで細かく考えるんですか？

博士：VLANやIPアドレスの設定が、ポートごとだからだ。どの口に何がつながっているかがずれると、設定が正しくても通信できない。

ノード：設定が正しいのに通信できないなんて、原因を探すのが大変そうですね。

博士：うむ。だからこそ、この対応が大事なのだ。あとで設定と図を突き合わせるときの基準になる。

ノード：置く機器には、どんな種類があるんですか？

博士：主なものを表にするとこうだ。

| 機器 | 役割 | 主に設定するもの |
| --- | --- | --- |
| PC / Server | 通信の起点と終点 | IPアドレス、プレフィックス長、Default Gateway、DNSサーバー |
| L2 Switch | MACアドレスを学習し、同じVLAN内でフレームを転送する。IPの経路は判断しない | VLAN、アクセス/トランク |
| Router | 異なるネットワーク間を、IPの経路表で転送する | インターフェースのIP、経路 |
| L3 Switch | スイッチの機能に加え、VLAN間ルーティングをスイッチ内で行える | VLAN、VLANごとの仮想インターフェースのIP |
| Firewall | 通信を許可・拒否し、境界を作る | ルール |
| Internet（ISP） | 外部ネットワークへの出口 | — |

ノード：L2 Switchは同じVLAN内でフレームを転送するだけで、IPの経路は判断しないんですね。

博士：そうだ。異なるネットワーク間を、IPの経路表で転送するのはRouterの仕事だ。

ノード：L3 Switchは、スイッチの機能に加えて、VLAN間ルーティングもスイッチの中でできる、と。いいとこ取りッスね。

博士：L3 Switchで設定するのは、VLANと、VLANごとの仮想インターフェースのIPだ。Firewallは通信を許可・拒否して境界を作り、Internet（ISP）は外部ネットワークへの出口だな。

### VLAN：1台のスイッチを論理的に分ける

博士：次はVLANだ。1台のスイッチを論理的に分ける仕組みだったな。

ノード：はい。アクセスポートとトランクポートがあるんでしたよね。

博士：うむ。アクセスポートは1つのVLANに属し、端末とはタグなしのフレームをやり取りする。

ノード：トランクポートは？

博士：トランクポートは複数のVLANを運ぶ。だから、フレームに**802.1Qタグ**を付けるのだ。VLAN IDを含む4バイトだ。

ノード：どのVLANのフレームか、見分けるための札みたいなものですね。タグはいつ付くんですか？

博士：スイッチは、アクセスポートから受けたフレームをトランクへ送るときに、タグを付ける。逆に、トランクからアクセスポートへ送るときに、タグを外す。

ノード：つまり、トランクの上では必ずタグが付いてるってことですよね。

博士：そこは例外がある。トランク上でも、**ネイティブVLAN**のフレームはタグなしで流れるのだ。ネイティブVLANとは、タグを付けずに運ぶと決めたVLANのことだ。

ノード：へぇ、例外があるんですね。

博士：そこは覚えておきたまえ。もう1つ大事なことがある。VLANが違えば、同じスイッチにつながっていても別のネットワークだ。

ノード：同じスイッチなのに、直接は話せないんですか？

博士：そうだ。VLAN間の通信には、ルータやL3スイッチによるルーティングが必要になる。

ノード：第4章で出てきた、Router on a Stickもその1つですか？

博士：その通り。ルータの1つのポートをトランクにつなぎ、複数のVLANを受け持つ構成だ。この構成では、VLAN間の通信は同じトランクを往復する。

ノード：同じケーブルを行って帰ってくるんですか。タグはどうなるんですか？

博士：VLAN 10からVLAN 20へ送ると、上りのフレームにはタグ10、ルータが送り返すフレームにはタグ20が付く。

ノード：なるほど、行きと帰りでタグが違うんですね。

### ルーティング：静的か、動的か

博士：では、ルーティングだ。例の構成で、R1はPC2側の192.168.2.0/24を知っていると思うか？

ノード：え〜っと、R1から見るとPC2側はR2の向こうだから…知らないですね。

博士：うむ。同じように、R2もPC1側の192.168.1.0/24を知らない。小さな構成では、**Static Route**で宛先と次のルータを指定するのだ。

```text
R1(config)# ip route 192.168.2.0/24 10.0.12.2
R2(config)# ip route 192.168.1.0/24 10.0.12.1
```

ノード：R1には「192.168.2.0/24は10.0.12.2へ」、R2には「192.168.1.0/24は10.0.12.1へ」ですね。でも、R1のほうだけ設定すれば、PC2には届くんじゃないですか？

博士：焦るでない。R2の設定を忘れると、行きは届いても、帰りのパケットが戻れないのだ。第3章でやったな。

ノード：あっ、そうでした。帰り道も要るんでした。

博士：なお、ルータが1台だけなら、両側のLANが直結、つまり**Connected Route**なので、Static Routeは不要だ。

ノード：ルータが2台になったから、お互いの向こう側を教えてあげる必要があるんですね。

博士：その通り。ここで、シミュレータの注意書きも見ておこう。

> シミュレータでの簡略化: `ip route` はCIDR表記でもマスク表記でも書けます。実機のCisco IOSでは `ip route 192.168.2.0 255.255.255.0 10.0.12.2` のようにマスクで書きます。

ノード：シミュレータならCIDR表記でもいいけど、実機のCisco IOSではマスクで書く、と。

博士：そうだ。さて、ルータや経路が増えると、どうなると思う？

ノード：Static Routeを全部に書くのは…大変そうです。

博士：うむ。すべてのStatic Routeの整合性を保つのが難しくなる。そこで**OSPF**のような**動的ルーティング**の出番だ。ルータ同士が経路情報を交換するのだ。

ノード：自動で教え合うんですね。

博士：しかも、リンクに障害が起きると、別の経路へ自動で切り替わる。設定は、たとえば次のようになる。例の構成とは別のアドレスだから注意したまえ。

```text
router ospf 1
 network 10.0.0.0/16 area 0
 passive-interface g0/0
```

ノード：`network 10.0.0.0/16 area 0` は、どういう意味ですか？

博士：この範囲のIPを持つインターフェースで、OSPFを動かす、という意味だ。area 0は、OSPFの基本となるエリアだ。

ノード：じゃあ `passive-interface g0/0` は？

博士：そのインターフェースのネットワークは広告しつつ、OSPFの隣接関係は作らない、という設定だ。端末しかいないLAN側に使う。

ノード：どうして隣接関係を作らないんですか？

博士：そこにはOSPFの相手がいないからだ。相手がいないのに、やり取りを流す必要はないだろう？

ノード：なるほど。誰もいない部屋に話しかけても仕方ないですもんね。

博士：うまいことを言う。それから、経路の選ばれやすさ、つまり**コスト**は、インターフェースごとに `ip ospf cost` で調整できるぞ。

### DNS・NAT・ACL/Firewall

博士：ルーティングができても、まだ足りないものがある。DNS、NAT、ACL/Firewallだ。構成の中での役割と、抜けたときにどう見えるかを表にするとこうなる。

| 仕組み | 構成の中での役割 | 抜けると、どう見えるか |
| --- | --- | --- |
| DNS | 端末は名前をDNSサーバーに問い合わせ、IPアドレスを得てから通信する | 経路が正しくても「つながらない」ように見える |
| 送信元NAT（PAT/NAPT） | 境界の機器が、内側の送信元IPとポートを外側のアドレスとポートに書き換える。変換表を使って、戻りのパケットを元に戻す | 内側のアドレスのまま外へ出て、戻りが届かない |
| 宛先NAT（ポートフォワード） | 外から内側のサーバーへ入れるようにする | 外から公開サーバーに届かない |
| ACL / Firewall | 通信を許可・拒否する | 必要な通信が止まる、不要な通信が通る |

ノード：DNSが抜けると、経路が正しくても「つながらない」ように見えるんですね。

博士：そうだ。端末は名前をDNSサーバーに問い合わせ、IPアドレスを得てから通信するからな。

ノード：送信元NATは、境界の機器が、内側の送信元IPとポートを外側のアドレスとポートに書き換える…。

博士：そして、変換表を使って、戻りのパケットを元に戻す。これが抜けると、内側のアドレスのまま外へ出て、戻りが届かない。

ノード：宛先NATがないと、外から公開サーバーに届かない。ACL/Firewallがおかしいと、必要な通信が止まったり、不要な通信が通ったりする、と。

博士：その通り。ACLとFirewallのルールには、第6章でやった性質がある。もう一度確認しておこう。

ノード：はい、お願いします。

博士：ACLは上から順に評価され、最初に一致したルールが適用される。多くの実装では、最後に**暗黙の拒否**がある。第6章で見た、末尾の見えない「すべて拒否」のことだ。

ノード：どのルールにも一致しなかったら、最後に拒否される、ってことですね。

博士：うむ。それから、**ステートフル**なファイアウォールは、許可した通信の戻りを自動で通す。

ノード：じゃあ、**ステートレス**なACLだと？

博士：戻りの通信も、明示的に許可する必要がある。

ノード：ステートレスだと、帰り道の許可も忘れずに書かないといけないんですね。

### Simulation Mode：パケットを1ホップずつ追う

博士：さて、いよいよ本番だ。組み立てた構成で、パケットが本当にその通りに流れるか、1ホップずつ追ってみよう。

ノード：待ってました！

博士：例の構成で、PC1（192.168.1.10）からPC2（192.168.2.10）へpingを送る。経路はPC1 → SW1 → R1 → R2 → SW2 → PC2で、SW1とR1の間はVLAN 10を運ぶトランクだ。

ノード：リンクごとに、ヘッダを見ていくんですね。

博士：そうだ。表にするとこうなる。表の「R1 g0/0」は、R1のg0/0ポートのMACアドレスを表しているぞ。

```text
Link       Src MAC   Dst MAC   VLAN  Src IP        Dst IP        TTL
PC1->SW1   PC1       R1 g0/0   -     192.168.1.10  192.168.2.10  64
SW1->R1    PC1       R1 g0/0   10    192.168.1.10  192.168.2.10  64
R1->R2     R1 g0/1   R2 g0/0   -     192.168.1.10  192.168.2.10  63
R2->SW2    R2 g0/1   PC2       -     192.168.1.10  192.168.2.10  62
SW2->PC2   R2 g0/1   PC2       -     192.168.1.10  192.168.2.10  62
```

ノード：うわ、いろいろ変わってますね…。え〜っと、PC1が送るとき、宛先MACがPC2じゃなくて「R1 g0/0」になってます。

博士：いいところに気づいた。**MACはルータを越えるたびに変わる**のだ。宛先MACは「最終的な宛先」ではなく、「このリンクで次に受け取る機器」だ。

ノード：だからPC1は、PC2じゃなくてR1のMACを宛先にするんですね。

博士：うむ。PC1は、ゲートウェイであるR1のMACを、ARPで調べる。ARPはIPからMACを調べる仕組みだったな。

ノード：次に、PC1->SW1とSW1->R1を比べると…MACもIPもTTLも同じで、VLANの欄だけ「-」から「10」になってます。

博士：その通り。**スイッチはMACもIPもTTLも変えない**。変わるのは、トランクでのVLANタグの有無だけだ。

ノード：Src IPとDst IPは、最初から最後までずっと192.168.1.10と192.168.2.10ですね。

博士：そうだ。**IPの送信元・宛先は変わらない**。変わるのは、NATを通ったときだ。

ノード：TTLは64、63、62と減ってます。R1で1減って、R2でまた1減ってますね。

博士：うむ。**TTLはルータが転送するたびに1減る**。IPv4では、それに合わせてヘッダチェックサムも計算し直される。

ノード：つまり、ルータを越えるとMACが付け替えられてTTLが減る。スイッチではVLANタグの有無だけが変わって、IPアドレスはNATがなければそのまま、ってことですよね。

博士：その通り。よくまとめたな。

ノード：行きがわかったら、これで終わりですか？

博士：いや、帰りのEcho Replyも、同じように1ホップずつ追うといい。行きと帰りが同じ経路とは限らないからな。

ノード：帰りは別の道を通るかもしれないんですね。

### 帯域を設計する：どこが詰まるか

博士：通信できる構成が組めたら、次は「十分な速さが出るか」だ。第4章で、1つの転送の上限は何で決まると言ったかな？

ノード：通る道の、一番遅いリンクです。ボトルネックでした。

博士：うむ。設計では、まず通り道の各リンクの速度を並べて、ボトルネックを探す。測るときは `iperf3` のようなツールを使う。

```text
PC1 ─10G─ SW1 ═(10G×2のLAG)═ SW2 ─1G─ R1 ─10G─ R2 ─10G─ SRV
                                   ↑ ここが1本の転送の上限
```

ノード：LAGが20 Gbps分あっても、その先の1Gで決まっちゃうんですね。

博士：そうだ。しかも、使われていないリンクを速くしても意味がない。まず traceroute で、実際に通る道を確かめるのだ。

ノード：はい。たくさんの人が同時に使うときは、どう考えるんですか？

博士：**オーバーサブスクリプション**（oversubscription）という考え方がある。たとえば、1 Gbpsの端末用ポートが48個あるスイッチの上りが、10 Gbps×2本だとする。

```text
下り（端末側）の合計: 1 Gbps × 48 = 48 Gbps
上り（アップリンク）:  10 Gbps × 2 = 20 Gbps
比率: 48 : 20 = 2.4 : 1
```

ノード：全員が同時に全力で送ったら、上りが足りない…。

博士：うむ。だが、全員が同時に全力で送ることはまずないので、ある程度の比率は普通に許容する。大事なのは、バックアップのように大量に流れる通信がどこを通るかを知っておくことだ。

ノード：「経路がある」と「速さが足りる」は、別々に確かめるんですね。

> シミュレータでの簡略化: iperf3 の値は、リンク速度だけから求めた理論上限です。同じリンクを使う複数のストリームには、公平になるように分けます（max-min公平）。TCPの輻輳制御・キュー・パケットロス・プロトコルのオーバーヘッドは再現しません。

### 冗長化を設計する：単一障害点を探す

博士：次は、壊れたときのことだ。ノード君、この構成で、何が壊れたら通信が止まる？

```text
PC ── SW1 ── R1 ── Server
```

ノード：え〜っと、SW1が壊れたら止まります。R1も。それと、間のケーブルのどれか1本でも…。

博士：その通り。1か所壊れるだけで全体が止まる箇所を、**単一障害点**（SPOF：Single Point of Failure）という。この1本道の構成は、SPOFだらけだ。

ノード：今ちゃんと通信できていても、ですか？

博士：今動いていることと、壊れにくいことは別の話だ。止まらずに使える度合いを**可用性**（availability）、予備を用意して可用性を上げることを**冗長化**（redundancy）という。

ノード：何を予備にするんですか？

博士：3つに分けて考えるといい。

| 冗長化 | 例 | 必要な仕組み |
| --- | --- | --- |
| リンクの冗長化 | 同じ2台の間にケーブルを2本 | STP（片方を待機）、LACP（束ねる） |
| 機器の冗長化 | ルータを2台にする | 経路の切り替え（ルーティング） |
| 経路の冗長化 | 別々の機器を通る2つの道 | 動的ルーティング、ECMP |

ノード：壊れたとき、予備に切り替わることは何ていうんですか？

博士：**フェイルオーバー**（failover）だ。それから、1つの障害が影響する範囲を**障害ドメイン**（failure domain）という。VLANを分けるとブロードキャストストームの影響範囲が分かれるように、障害ドメインを小さく分けることも設計の一部だ。

### 線を増やしても、冗長になるとは限らない

ノード：じゃあ、スイッチを2台にして、線をたくさんつなげば安心ですね！

博士：またそれか。たとえばこうつないだとする。

```text
       SW1
      /   \
PC --       -- R1
      \   /
       SW2
```

博士：PCのNICが1つなら、PCはSW1かSW2のどちらか一方にしかつながらない。PCがつながる側のスイッチは、SPOFのままだ。

ノード：あ…。線を増やしても、その機器が1台しかつながってなければ同じなんですね。

博士：それだけではない。スイッチの間に2本目のケーブルを足すと、L2ではループになる。STPがなければ、ブロードキャストストームで全体が止まる。冗長化のつもりが、逆効果だ。

ノード：怖い…。

博士：ルータを2台にしても、経路を設定しなければ2台目は使われない。静的ルートだけだと、離れた区間の故障に気づけない。

ノード：線や機器を増やすだけじゃなくて、切り替える仕組みも必要なんですね。

博士：うむ。L2の並列リンクには**STPやLACP**、L3の複数経路には**ルーティング（動的ルーティング・ECMP）**だ。それぞれ違う仕組みが必要になる。

### 帯域と冗長化は、別の目標

ノード：2本にすれば、速くもなって、壊れにくくもなる。ですよね？

博士：そこが混同しやすいところだ。**帯域を増やすことと、可用性を高めることは同じではない**。同じ2本のリンクでも、使い方で意味が変わる。

| 2本の使い方 | 例 | 容量 | 障害への備え |
| --- | --- | --- | --- |
| Active / Standby（片方は待機） | STPのブロック、ADの大きい予備の静的ルート | 1本分のまま | あり |
| LAG（束ねて両方使う） | LACP | 2本分 | あり（同じ相手との間だけ） |
| ECMP（両方の経路を使う） | 等コストの静的ルート・OSPF | 2本分 | あり（障害を検出できれば） |

ノード：待機させる方式だと、速くはならないんですね。

博士：そうだ。だから設計では、必ずこう問う。**「この2本のリンクは何のために存在するのか？」** 容量を増やすためか、障害に備えるためか、両方か。

ノード：両方のつもりなら、LAGかECMPで両方使えばいいんですね。

博士：ただし、気をつけることがある。2本とも使って容量を出している状態で1本壊れたら、どうなる？

ノード：残りの1本分に…容量が半分になります。

博士：うむ。これが**縮退**（degraded）だ。「2本分の容量がないと業務が回らない」なら、1本壊れた時点で実質的に止まる。必要な容量を、1本壊れても確保できるように見積もるのが設計だ。

ノード：容量の見積もりにも、壊れたときのことを考えるんですね。

### LACPとECMPの違い

ノード：LACPとECMP、どっちもフローをハッシュで分けるので、こんがらがってきました…。

博士：初心者が一番混同するところだ。図で比べよう。

```text
LACP（Link Aggregation）              ECMP

SW1                                       R2
 |\                                      /  \
 | \     → 束ねると →   SW1          R1        R4
 |  \                    ║                \  /
 |   \                   ║ po1             R3
SW2                     SW2
```

博士：LACPは、**同じ相手（SW2）との間の、複数の物理リンク**を、1つの論理リンクにする。ECMPは、**異なるNext Hop（R2とR3）を通る、複数のL3経路**を同時に使う。

ノード：束ねる相手が「同じ1台」か「別々の機器」か、ですね。

博士：その通り。パケットの通り道で見ると、もっとはっきりする。LAGのどのメンバーを通っても、届く先は同じSW2で、MACアドレスもTTLも変わらない。ECMPでは、選んだルータ宛てにMACが付け替わり、TTLが1減る。

ノード：経路表の見え方も違いますか？

博士：LAGは経路表やSTPから見ると、po1という1本のインターフェースだ。ECMPは、経路表の同じ宛先に、複数のNext Hopが並ぶ。

ノード：R2とR3をLACPで束ねることはできないんですか？

博士：別々の機器なのでできない（複数の筐体を1台に見せる技術もあるが、ここでは扱わない）。別々の機器への複数の道は、ECMPで使うのだ。

ノード：「同じ相手との並列リンクはLACP、別の機器を通る経路はECMP」。覚え方じゃなくて、通り道で考えればいいんですね。

博士：うむ。シミュレータのVisualステップで、同じフローがSW1ではメンバーを、R1ではNext Hopを選ぶ様子を確かめるとよい。

### 図とドキュメント

博士：最後に、図とドキュメントの話だ。構成図には、**物理構成図**と**論理構成図**の2種類がある。

ノード：違いは何ですか？

博士：表にするとこうだ。

| | 物理構成図 | 論理構成図 |
| --- | --- | --- |
| 答える問い | どこに何が刺さっているか | パケットがどう流れるか |
| 書くもの | 機器、ポート、ケーブル、設置場所 | サブネット、VLAN、Gateway、ルーティングの範囲、主要なIPアドレス |

ノード：物理構成図は「どこに何が刺さっているか」、論理構成図は「パケットがどう流れるか」に答えるんですね。どっちか1枚あれば十分じゃないですか？

博士：どちらか一方では足りないのだ。配線の障害は物理構成図で、経路の問題は論理構成図で追うからな。

ノード：なるほど。じゃあ、両方をきちんと描いておけば安心ですね。

博士：まあ待て。図は、作った時点から古くなり始めるのだ。

ノード：えっ、そうなんですか？

博士：設定を変えるたびに、図、IP計画、インターフェースの説明（description）を更新する。そういう運用とセットで考えるといい。

ノード：描いて終わり、じゃないんですね。

### よくある誤解

博士：では、よくある誤解を確認しておこう。ノード君、スイッチを通るとTTLはどうなる？

ノード：スイッチを通るとTTLが1減る…んですよね？

博士：違うぞ。TTLを減らすのは、IPを転送するルータだ。L2スイッチはIPヘッダを変えない。

ノード：あっ、さっきの表でも、スイッチの前後でTTLは同じでした。

博士：その通り。では、宛先MACは何のMACだ？

ノード：最終的な宛先のMACです！

博士：それも誤解だ。宛先MACは、そのリンクで次に受け取る機器のMACだ。LANの外へ送るなら、まずゲートウェイのMACになる。

ノード：そうでした…。じゃあ、行きの経路を設定すれば、pingは通りますよね？

博士：それでは足りない。Echo Replyが戻る経路も必要だ。

ノード：帰り道、また忘れてました。物理構成図があれば、論理構成図はいらないですよね？

博士：いや、サブネットやVLAN、経路の関係は、物理構成図だけではわからないのだ。

ノード：うっ。でも、ケーブルを2本にすれば、速さも2倍で壊れにくさも2倍ですよね？

博士：STPで待機させれば容量は1本分のままだし、STPがなければループだ。両方使うにはLAGやECMPが要る。それに、2本使っていて1本壊れれば、容量は半分になる。

ノード：最後に…pingが通っているなら、単一障害点はないですよね？

博士：今通っていることと、1か所壊れても通り続けることは別だ。1つずつ壊したと考えて、確かめるのだ。

ノード：全部ひっかかっちゃいました…。

博士：ひっかかったところこそ、よく覚えられるものだ。

### 確認してみよう

博士：では、問題を出すぞ。

1. PC1 → SW1 → R1 → R2 → SW2 → PC2と進むとき（NATなし）、IPの送信元・宛先はどうなりますか？
2. L2スイッチを通過したとき、TTLはどうなりますか？
3. トランク上でも802.1Qタグが付かないのは、どのVLANのフレームですか？
4. R1から別々のルータR2・R3を通る2つの経路を同時に使いたいとき、LACPとECMPのどちらを使いますか？

ノード：え〜っと、1はNATがないから、IPの送信元・宛先は変わらない。変わるのはリンクごとのMACアドレスです。

博士：正解だ。

ノード：2は、L2スイッチはIPヘッダを変えないので、TTLも変わらない。

博士：うむ、正解。

ノード：3は…ネイティブVLANです！

博士：正解だ。4は？

ノード：ECMPです。LACPは同じ相手との並列リンクを束ねる仕組みで、R2とR3は別の機器だからです。

博士：全問正解だ。答えは、1. 変わらない（変わるのはリンクごとのMACアドレス）。2. 変わらない。3. ネイティブVLAN。4. ECMP。

### このシミュレータで試せること

博士：このシミュレータでは、次のようなことを試せるぞ。

- パレットからPC、Server、Router、L2 Switch、L3 Switch、Firewall、Internet（ISP）をドラッグ&ドロップで配置し、ポート同士をケーブルでつなぐ。
- プロパティパネルでIP、VLAN、経路、サービスを編集する。機器ごとのCLIでも設定・確認する。
- 送信バーから `ping`、`traceroute`、`curl`、`dig` を実行する。
- Packet Debugger（右パネルの「Debugger」タブ）で、記録されたイベントを1つずつ進める。「Hop」表示で、リンクごとのMAC・VLAN・IP・TTLを比較する。
- ケーブルをダブルクリックしてリンクをDown/Upし、Connected Routeが消えることや、OSPFで経路が切り替わる様子を確かめる。
- テンプレート（ルーティング、VLAN、L3スイッチ、STP、OSPF、DNS、NAT、Firewall/DMZ、BGP、VPN、社内LAN）から始めて、壊して直す。
- ラボ「ゼロからネットワークを組む」で空の状態から構成を作り、「Simulation Mode: 1ホップずつ追う」でヘッダの変化を確かめる。
- **LACPとECMPの通り道**・**単一障害点を探す**（Visualステップ）：同じフローがLAGのメンバーとECMPのNext Hopをどう選ぶか、構成ごとに1か所ずつ壊したときに何が止まるかと、合計の容量を確かめられます。
- テンプレート「Link Aggregation」「ECMP」「冗長化と帯域」。PC1で `iperf3 -c <宛先> -P 4`（ECMP・冗長化と帯域は 10.20.0.10、Link Aggregationは 192.168.10.13）を実行し、ボトルネックと合計の速さを測る。ケーブルの速度は、ケーブルを選んで変えるか `speed` で変える。
- ラボ：Challenge「どこが遅いのかを見つけて、1本だけ増強する」「単一障害点をなくす」、Mastery「容量と冗長性を両立させる」。Capstone 1 でも、冗長な2本のケーブルの使い方を自分で決めます。

ノード：ラボ「ゼロからネットワークを組む」で、今日の構成を自分で作ってみたいです。

博士：それがいい。ただし、シミュレータならではの簡略化もある。目を通しておくといい。

> シミュレータでの簡略化:
> - Packet Debuggerは記録済みのイベントを再生するもので、稼働中のネットワークを一時停止しているわけではありません。
> - OSPFは単一のSPF計算による簡略版で、DR/BDRの選出やHello・LSAのやり取りは再現しません。`network` はCIDR表記でも書けますが、Cisco IOSでは `network 10.0.0.0 0.0.255.255 area 0` のようにワイルドカードマスクで書きます。
> - ルータに直結したリンクをDownにすると、そのルータのConnected Routeは即座に消えます。実機では、検知までに時間がかかることがあります。
> - ルータどうしの間にスイッチが入っていると、スイッチの先で起きた障害は、ルータからはリンクDownとして見えません（これは実機もシミュレータも同じです）。そのため、動的ルーティングでは隣接の生存確認が重要になります。

ノード：ルータどうしの間にスイッチがあると、スイッチの先で起きた障害は、ルータからはリンクDownに見えない…。

博士：うむ。これは実機も同じだ。だから、動的ルーティングでは隣接の生存確認が重要になるのだ。

博士：さて、次回は「AWS VPC」だ。今回組み立てたような構成を、クラウドの上で見ていくぞ。

ノード：クラウドですか。今日の総まとめが役に立ちそうッスね。

博士：うむ。その前に、今日の構成を一度自分の手で組んでみるといい。

#### 用語メモ

- **ホップ**［hop］：パケットが次の機器へ渡る、1回ぶんの移動。経路の話では、通過するルータの数を数えることが多い。
- **セグメント**［segment］：ルータで区切られた、1つのネットワークの範囲。
- **IPアドレス計画**［IP address plan］：どのネットワークに、どのアドレス範囲とGatewayを割り当てるかを書いた表。
- **Default Gateway**：自分のネットワークの外へ送るときに、パケットを渡すルータのアドレス。
- **802.1Qタグ**［802.1Q tag］：トランクでフレームに付ける、VLAN IDを含む4バイトのタグ。
- **ネイティブVLAN**［native VLAN］：トランク上でも、タグを付けずに運ぶと決めたVLAN。
- **Static Route**：宛先ネットワークと次のルータを、手で指定する経路。
- **passive-interface**：そのインターフェースのネットワークは広告しつつ、OSPFの隣接関係は作らない設定。
- **物理構成図 / 論理構成図**［physical / logical diagram］：機器と配線を描いた図 / ネットワークの区切りと経路を描いた図。
- **単一障害点**［SPOF：Single Point of Failure］：そこが1か所壊れるだけで、全体の通信が止まる箇所。
- **可用性・冗長化**［availability / redundancy］：止まらずに使える度合い／予備を用意して可用性を上げること。リンク・機器・経路の冗長化がある。
- **フェイルオーバー・縮退**［failover / degraded］：故障時に予備へ切り替わること／動いているが能力が落ちた状態。
- **障害ドメイン**［failure domain］：1つの障害が影響する範囲。
- **オーバーサブスクリプション**［oversubscription］：下り側の合計帯域が、上り側の帯域より大きいこと。その比率。

#### ノード君の今日のポイント

- 機器を並べる前に、要件とIPアドレス計画を書く。それが設計とレビューの基準になる。
- ケーブルはポートとポートをつなぐ。どの口に何がつながるかを記録する。
- VLANが違えば別のネットワーク。VLAN間の通信にはルーティングが必要で、帰りの経路も要る。
- ルータを越えるたびにMACは付け替えられ、TTLは1減る。スイッチはどちらも変えず、IPアドレスは（NATがなければ）変わらない。
- 物理構成図と論理構成図の両方を持ち、変更のたびに更新する。
- 「経路がある」と「十分な速さが出る」は別。ボトルネックは、実際に通る道の一番遅いリンク。
- 1か所ずつ壊したと考えて、単一障害点を探す。線や機器を増やすだけでは冗長にならず、L2はSTP・LACP、L3はルーティング・ECMPの仕組みが要る。
- 帯域を増やすことと可用性を高めることは別。「この2本は何のため？」を問い、1本壊れたとき（縮退）の容量まで見積もる。
- 同じ相手との並列リンクはLACP、別の機器を通る複数の経路はECMP。
