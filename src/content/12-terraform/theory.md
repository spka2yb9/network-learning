## ネットワークを、コードとして持つ

博士：ノード君、AWS VPCの章で作ったネットワークを覚えているかね？

ノード：はい。VPC、サブネット、ルートテーブル、Internet Gatewayを1つずつ作って、関連付けていきました。

博士：うむ。では、ある日こう頼まれたとしよう。「ステージング環境にも同じ構成を作って」。

ノード：え〜っと、画面の操作を、最初からもう一度全部やる…ってことですか？

博士：手作業で作ったなら、そうなるな。もう1つ、「先月から何が変わった？」と聞かれたらどうする？

ノード：うっ。それは…覚えてないッス。

博士：手作業で作った環境では、どちらも答えにくい問いなのだ。そこで今回は、インフラをコードで管理するツール、**Terraform**の話をするぞ。

ノード：インフラを、コードで管理するんですか。

博士：そうだ。目標は、変更の影響を**実行する前に**読めるようになることだ。まず、IaC（Infrastructure as Code）とTerraformが、どんな困りごとを解決するか。それから、HCLの基本の書き方と、resource・variable・output・moduleなどの構成要素だ。

ノード：ふむふむ。

博士：さらに、作成の順番が「参照」から決まる仕組みと、count・cidrsubnetによる繰り返し。state（Terraformの記憶）の役割と、drift・import・ロック。最後に、planの記号を読み、applyの前に変更の影響を説明する方法だ。

ノード：盛りだくさんですね。

博士：焦るでない。1つずつ行くぞ。

### まず、言葉をそろえる

博士：最初に、この章で使う言葉をそろえておこう。表にするとこうだ。

| 用語 | 意味 |
| --- | --- |
| IaC（Infrastructure as Code） | インフラのあるべき状態をコードに書き、レビュー・バージョン管理・再現を可能にする考え方 |
| Terraform | IaCの代表的なツール。HCLで書いたコードをもとに、クラウドのリソースを作る |
| HCL（HashiCorp Configuration Language） | Terraformのコードを書くための、宣言的な言語 |
| 宣言的 | 「手順」ではなく、「最終的にこうなっているべき」を書くやり方 |
| API | プログラムからサービスを操作するための窓口 |
| リソース | Terraformが管理する1つ1つのもの（VPC、サブネットなど） |
| state | Terraformが、コード上のリソースと実物の対応を記録したもの |
| plan / apply | 何が起きるかの予告 / その実行 |

ノード：「宣言的」っていうのが、ちょっとピンとこないです。

博士：「手順」ではなく、「最終的にこうなっているべき」を書くやり方だ。あとでコードを見れば、実感できるはずだ。

ノード：plan と apply は、予告と実行…。いきなり実行しないで、先に予告があるんですね。

博士：その通り。この予告を読めるようになるのが、今回のゴールなのだ。

### なぜ、コードにするのか

ノード：でも、そもそもなんでコードにするんですか？画面で操作するほうが、わかりやすい気もします。

博士：さっきの問いを思い出すといい。手作業とコードで比べると、こうなる。

| 問い | 手作業の場合 | コードの場合 |
| --- | --- | --- |
| 同じ構成をもう1つ | 画面の操作を、もう一度くり返す | 同じコードを、別の変数で実行する |
| 先月から何が変わった？ | 画面を見比べるしかない | Gitの差分で見られる |
| 誰が、なぜ変えた？ | 記録が残りにくい | レビューとコミットの記録が残る |

ノード：同じ構成をもう1つ作るなら、同じコードを別の変数で実行するだけ…。楽ですね。

博士：うむ。そして「先月から何が変わった？」には、Git（ファイルの変更履歴を管理するツール）の差分で答えられる。

ノード：「誰が、なぜ変えた？」も、レビューとコミットの記録が残るんですね。手作業だと、記録が残りにくい。

博士：そういうことだ。インフラのあるべき状態をコードに書くから、レビューもバージョン管理も再現もできる。それがIaCなのだ。

### HCLの基本と、構成要素

博士：では、実際のコードを見てみよう。VPCを1つ作るコードだ。

```hcl
provider "aws" {
  region = var.region
}

resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr
  tags = {
    Name = "${var.project}-vpc"
  }
}

output "vpc_id" {
  value = aws_vpc.main.id
}
```

ノード：え〜っと、`resource "aws_vpc" "main"` っていうのは…？

博士：「aws_vpc という種類のリソースを、main という名前で作る」という意味だ。

ノード：種類と名前の、2つを書くんですね。

博士：そうだ。この組がTerraform内の住所、つまり**アドレス**になる。書き方は `aws_vpc.main` だ。

ノード：`"${var.project}-vpc"` の、この `${…}` は何ですか？

博士：文字列の中に値を埋め込む書き方だ。`var.project` が `shop` なら、`shop-vpc` になる。

ノード：なるほど。じゃあ、最後の `aws_vpc.main.id` は？

博士：作ったVPCのIDを参照している。

ノード：このコードって、上から順番に実行されるんですよね？provider、resource、outputの順に。

博士：そこが手順書との違いだ。Terraformは、ディレクトリ内の `.tf` ファイルをまとめて読む。書いた順番は関係なく、「こうなっているべき」という宣言として扱うのだ。

ノード：あ、それがさっきの「宣言的」ですか。

博士：うむ。手順書ではなく、完成図を渡すイメージだな。

ノード：でも、完成図だけ渡されても、どれから作ればいいか困りませんか？

博士：いい質問だ。完成図から作る順番を組み立てるのは、Terraformの仕事だ。その手がかりが、次の節で話す「参照」なのだ。

ノード：あとで出てくるんですね。了解です。

博士：その前に、HCLのブロックの種類を見ておこう。表にするとこうだ。

| ブロック | 役割 | 参照の書き方 |
| --- | --- | --- |
| provider | AWSなどのAPIと話すプラグイン。`terraform init` で取得する | — |
| resource | Terraformが作成・変更・削除を管理するもの | `aws_vpc.main.id` |
| data | 既存の情報を読むだけのもの（例：`data "aws_availability_zones" "available" {}`） | `data.aws_availability_zones.available.names` |
| variable | 外から与える入力値。`terraform.tfvars` などで渡す | `var.vpc_cidr` |
| locals | モジュール内で使う名前付きの値 | `local.azs` |
| output | 結果を外へ見せる値。`terraform output` で表示でき、親モジュールからも参照できる | — |
| module | リソースをまとめた再利用の単位。`source = "./modules/network"` のように呼び出す | 子のoutputを `module.network.vpc_id` |

ノード：いっぱいありますね…。provider は、AWSなどのAPIと話すプラグインで、`terraform init` で取得する、と。

博士：そうだ。resource は、Terraformが作成・変更・削除を管理するもの。data は、既存の情報を読むだけのものだ。

ノード：data の参照は `data.aws_availability_zones.available.names` …。頭に `data.` が付くんですね。

博士：うむ。variable は外から与える入力値で、`terraform.tfvars` などで渡す。参照は `var.vpc_cidr` のように書く。

ノード：さっきのコードの `var.region` や `var.project` も、それですね。

博士：その通り。locals はモジュール内で使う名前付きの値で、`local.azs` のように参照する。output は結果を外へ見せる値だ。`terraform output` で表示でき、親モジュールからも参照できる。

ノード：親モジュール…。module っていうのは何ですか？

博士：リソースをまとめた再利用の単位だ。`source = "./modules/network"` のように呼び出す。子のoutputは、`module.network.vpc_id` のように参照するのだ。

ノード：じゃあ、モジュールの中のリソースのアドレスはどうなるんですか？

博士：`module.network.aws_vpc.this` のようなアドレスになる。

ノード：なるほど。住所の頭に「どのモジュールか」が付くんですね。

### 依存関係は、参照から決まる

博士：では、さっきの「作る順番」の話だ。サブネットを2つ作り、ルートテーブルに関連付けるコードを見てみよう。

```hcl
resource "aws_subnet" "public" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index + 1)
  availability_zone = data.aws_availability_zones.available.names[count.index]
}

resource "aws_route_table_association" "public" {
  count          = 2
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}
```

ノード：サブネットの中に、`vpc_id = aws_vpc.main.id` がありますね。

博士：そこだ。サブネットは `aws_vpc.main.id` を参照している。VPCのIDは、VPCを作るまでわからないだろう？

ノード：あ、そうか。VPCを先に作らないと、IDが入れられない。

博士：うむ。だからTerraformは「VPCが先」と判断する。これが**暗黙の依存関係**だ。

ノード：わざわざ「VPCが先」って書かなくても、参照を見ればわかるってことですね。

博士：その通り。Terraformは参照をたどって依存グラフを作り、その順に処理する。依存のないものは並行して処理するのだ。図にするとこうなる。

```text
aws_vpc.main
 ├─ aws_subnet.public[0], [1]
 ├─ aws_internet_gateway.main
 └─ aws_route_table.public（IGWも参照）
      └─ aws_route_table_association.public[0], [1]（サブネットも参照）
```

ノード：VPCの下に、サブネットとIGWとルートテーブルがぶら下がって…。ルートテーブルは、IGWも参照しているんですね。

博士：そうだ。そして関連付けはルートテーブルの下にあって、サブネットも参照している。

ノード：サブネットとIGWはお互いを参照していないから、並行して作れる、と。

博士：うむ。それが「依存のないものは並行して処理する」ということだ。

ノード：じゃあ、参照さえ書いておけば、順番は全部おまかせでいいんですか？

博士：ほとんどはな。だが、参照に表れない依存もある。そういうときは、`depends_on = [aws_internet_gateway.main]` のように**明示的な依存関係**を書くのだ。

ノード：参照に表れない依存って、たとえば？

博士：代表例は、NAT GatewayとInternet Gatewayだ。NAT Gatewayのコードには、IGWへの参照が出てこない。

ノード：でも、10章で見たとおり、IGWがないとNAT Gatewayは外へ出られない…ですよね。

博士：その通り。コードには表れないが、依存はあるわけだ。こういうときに、NAT Gatewayのブロックへ `depends_on` を書いておくのだ。

ノード：便利ですね。迷ったら、全部 `depends_on` を書いておけば安心かも。

博士：まあ待て。`depends_on` は、公式ドキュメントでも最後の手段とされている。まず、参照で表せないかを考えるといい。

ノード：はい。まずは参照、ですね。

#### count と cidrsubnet — 繰り返しを1つのブロックで書く

ノード：さっきのコードの `count = 2` は何ですか？

博士：同じリソースを2つ作る、という指定だ。`aws_subnet.public[0]`、`[1]` のように番号で区別する。

ノード：`count.index` が、その番号ですか？

博士：うむ。`count.index` は0から始まる。そこは覚えておきたまえ。それから、`aws_subnet.public[*].id` と書くと、全部のIDをリストで得られる。

ノード：`cidrsubnet(var.vpc_cidr, 8, count.index + 1)` っていうのも気になります。

博士：`cidrsubnet(プレフィックス, 延ばすビット数, 番号)` は、サブネットのアドレスを計算する関数だ。

ノード：え〜っと、たとえば `cidrsubnet("10.0.0.0/16", 8, 1)` だと…？

博士：/16を8ビット延ばして/24にし、その番号1の範囲だ。番号は0から数える。つまり `10.0.1.0/24` だな。

ノード：あ、これ02章でやったサブネット計算ですね！

博士：その通り。02章のサブネット計算が、そのまま関数になっているのだ。上のコードでは、次のように計算される。AZの名前は例だぞ。

```text
count.index   cidr_block（netnum = count.index + 1）   availability_zone
0             10.0.1.0/24                              names[0]  ap-northeast-1a
1             10.0.2.0/24                              names[1]  ap-northeast-1c
```

ノード：番号が `count.index + 1` だから、0番目のサブネットが `10.0.1.0/24`、1番目が `10.0.2.0/24` なんですね。AZも `names[0]` と `names[1]` で分かれてる。

博士：うむ。繰り返しを、1つのブロックで書けるわけだ。

### state — Terraformの記憶

ノード：ところで、Terraformは、自分が作ったVPCをどうやって覚えているんですか？

博士：いいところに気づいたな。Terraformは、コード上のアドレスと、実際のクラウドのオブジェクトの対応を**state**に記録している。既定のファイル名は `terraform.tfstate` だ。

ノード：中身は、どんな感じですか？

博士：イメージとしてはこうだ。

```text
aws_vpc.main           = vpc-0abc...
aws_subnet.public[0]   = subnet-0123...
```

ノード：アドレスと、実物のIDの対応表みたいですね。

博士：うむ。この記録がないと、Terraformはどの実物が自分の管理するものか、わからないのだ。

ノード：plan は、このstateとコードを比べるんですか？

博士：もう1つある。planは、コード、state、そして実環境を読み直した結果を比べて差分を出すのだ。

ノード：3つを比べるんですね。

博士：それから、注意が1つ。stateには属性値がそのまま入る。秘密情報が平文で含まれることもあるのだ。

ノード：えっ、それはまずいですね。

博士：だから、stateはGitにコミットしない。手で編集もしない。

ノード：コードはGitに入れるけど、stateは入れない。覚えておきます。

#### チームで使うときは、stateを共有してロックする

ノード：でも、stateをGitに入れないなら、チームではどうするんですか？各自のパソコンにバラバラにあったら困りますよね。

博士：うむ。チームでは、stateをS3などの**リモートバックエンド**に置いて共有する。stateを置く共有の保存先のことだ。

ノード：みんなで同じstateを使うんですね。でも、2人が同時にapplyしたら…？

博士：stateが壊れる。

ノード：やっぱり。

博士：そのため、実行中はstateを**ロック**して、ほかの人が同時に実行できないようにするのだ。

ノード：S3だと、どうやってロックするんですか？

博士：S3バックエンドでは、従来DynamoDBのテーブルでロックしていた。新しいバージョンでは、S3上のロックファイル（`use_lockfile = true`）も使える。

ノード：へぇ、ロックの置き場所も選べるんですね。

#### drift — コードの外で、実物が変わったとき

ノード：もし誰かが、Terraformを使わずに、コンソール（AWSの管理画面）で設定を変えちゃったら？

博士：コンソールでの手作業などで、実環境がstateとずれることを**drift**と呼ぶ。例で見てみよう。

```text
コード   app-sg のインバウンド: 443 のみ
state    app-sg のインバウンド: 443 のみ（前回のapplyの記録）
実物     app-sg のインバウンド: 443 と 22（誰かがコンソールで追加）
```

ノード：コードとstateは443のみなのに、実物だけ22番が増えてますね。

博士：うむ。driftは、planの前のrefreshで検出される。refreshというのは、実物を読み直す処理だ。そのとき「Objects have changed outside of Terraform」と表示される。

ノード：「Terraformの外で変わりましたよ」と教えてくれるんですね。そのあとは？

博士：コードで管理している属性なら、planはコードの状態へ戻す変更を提案する。この例なら、22番のルールを削除する変更だ。

ノード：つまり、コードのほうに合わせるってことですよね。勝手に足した22番は消される、と。

博士：その通り。

#### import — 既存のリソースを管理下に入れる

ノード：逆に、手作業で作ってある既存のリソースを、Terraformで管理したいときは？

博士：**import**を使う。`terraform import aws_vpc.main vpc-0abc123` のようなコマンドや、Terraform 1.5以降の `import` ブロックだ。

ノード：importしたら、コードも自動でできあがるんですか？

博士：`terraform import` コマンドは、stateに対応を書き込むだけだ。コードは作らない。

ノード：え、じゃあコードはどうするんですか？

博士：先にresourceブロックを書いておく。そして、取り込んだ後のplanに差分が出ないよう、コードを実物に合わせるのだ。

ノード：planに差分が出なくなったら、取り込み完了ってことですね。

### 基本のワークフロー

博士：ここで、Terraformの基本のワークフローをまとめておこう。

```text
terraform init      プロバイダ・モジュールの取得、バックエンドの初期化
terraform fmt       書式を標準の形に整える
terraform validate  構文と参照の整合性を確認（クラウドには問い合わせない）
terraform plan      何が起きるかを表示
terraform apply     planを表示し、yes の入力で実行
terraform destroy   管理しているリソースを削除
```

ノード：initでプロバイダやモジュールを取ってきて、バックエンドを初期化。fmtで書式を整えて、validateで確認…。

博士：うむ。validateは構文と参照の整合性を確認するが、クラウドには問い合わせない。

ノード：そしてplanで何が起きるかを見て、applyで実行。applyもplanを表示して、yes を入力したら実行されるんですね。

博士：そうだ。destroyは、管理しているリソースを削除する。

ノード：この中で、いちばん大事なのはどれですか？

博士：大事なのは、applyの前に必ずplanを読むことだ。

ノード：予告を読まずに実行しない、ですね。

博士：その通り。では、その読み方を練習しよう。

### planを読む — 1行ずつ

博士：まず、planの記号だ。

| 記号 | 意味 |
| --- | --- |
| `+` | 作成 |
| `~` | その場で変更 |
| `-` | 削除 |
| `-/+` | 削除してから作り直す（置き換え） |

ノード：`~` と `-/+` は、どっちも「変更」っぽいですけど…。

博士：`~` はその場で変更。`-/+` は削除してから作り直す、つまり置き換えだ。ここは大きな違いだぞ。

ノード：はい。

博士：では、実際のplanを読んでみよう。`count` を使わずに1つだけ作ったパブリックサブネットで、`cidr_block` を `10.0.1.0/24` から `10.0.10.0/24` に変えたときのplanだ。一部の行は省略してある。

```text
  # aws_subnet.public must be replaced
-/+ resource "aws_subnet" "public" {
      ~ cidr_block = "10.0.1.0/24" -> "10.0.10.0/24" # forces replacement
      ~ id         = "subnet-0abc" -> (known after apply)
    }

  # aws_route_table_association.public must be replaced
-/+ resource "aws_route_table_association" "public" {
      ~ id        = "rtbassoc-0def" -> (known after apply)
      ~ subnet_id = "subnet-0abc" -> (known after apply) # forces replacement
    }

Plan: 2 to add, 0 to change, 2 to destroy.
```

ノード：うわ、なんだか長いですね…。

博士：焦るでない。上から1行ずつ読むのだ。まず、`# aws_subnet.public must be replaced`。

ノード：どのアドレスに、何が起きるか…ですか？

博士：うむ。ここでは置き換えだ。次の `-/+` は？

ノード：いったん削除して、作り直す、ですね。

博士：そうだ。では、なぜ作り直しになるのか。それを示すのが `cidr_block … # forces replacement` だ。

ノード：この属性の変更が、作り直しの原因ってことですか？

博士：その通り。サブネットのCIDRは、作った後にその場で変更できないからだ。

ノード：なるほど。次の `id … (known after apply)` は？

博士：新しいIDは、作るまで決まらない。だから「applyの後でわかる」と書いてあるのだ。

ノード：作り直すから、IDも新しくなるんですね。

博士：うむ。そして、下のほうを見るといい。関連付けの `subnet_id` も `(known after apply)` になり、こちらも作り直しだ。

ノード：あっ、関連付けはサブネットを参照してるから…。サブネットのIDが変わると、関連付けも巻き込まれるんですね。

博士：その通り。1つの変更が、参照している側に波及しているのだ。

ノード：最後の `Plan: 2 to add, 0 to change, 2 to destroy.` は合計ですね。でも、2つ作って2つ消す？置き換えは2つなのに？

博士：置き換えは、addとdestroyの両方に数えられるのだ。サブネットと関連付けで、2つずつだな。

ノード：CIDRを1か所変えただけなのに、けっこう大ごとですね。

博士：うむ。サブネットを作り直すと、そこに置いたインスタンスなど、依存するリソースも作り直しになることがある。ネットワークの変更では、特に注意するのだ。

### lifecycle — 作り直しと削除を制御する

ノード：大事なリソースを、うっかり作り直したり消したりしないようにする方法はありますか？

博士：ある。resourceブロックの中に `lifecycle { prevent_destroy = true }` のように書くと、作り直しや削除の扱いを変えられる。

ノード：prevent_destroy…「削除を防ぐ」ですか。

博士：うむ。**prevent_destroy** は、このリソースを削除するplanをエラーにする。

ノード：これを付けておけば、もう絶対に消えないですね！

博士：相変わらず気が早いな。resourceブロックごとコードから消すと、保護も消える。そこは覚えておきたまえ。

ノード：保護の設定ごと消えちゃうんですね…。ほかにもありますか？

博士：**create_before_destroy** は、作り直しの際、新しいものを先に作ってから古いものを消す。

ノード：`-/+` の「削除してから作り直す」とは、逆の順番なんですね。

博士：そうだ。ただし、名前など、一意の値が衝突しないか注意するといい。

ノード：古いのと新しいのが同時にある間は、同じ名前だとぶつかるかもしれないんですね。

博士：その通り。最後の **ignore_changes** は、指定した属性の差分を無視する。Terraformの外で管理するタグなどに使うのだ。

ノード：外で管理しているものまで、コードの状態に戻されたら困りますもんね。

### セキュリティグループのegressに注意

博士：もう1つ、つまずきやすいところを話しておこう。10章で、AWSで新しく作ったSGには、何が既定で付くと学んだかね？

ノード：え〜っと、全宛先へのアウトバウンドを許可するルールです。

博士：うむ。アウトバウンドのルールを、Terraformでは **egress** と書く。しかしTerraformの `aws_security_group` は、作成時にこの既定のegressルールを削除するのだ。

ノード：えっ、じゃあegressを書かなかったら…？

博士：インスタンス側から始める通信は許可されない。

ノード：通信が全部ダメになっちゃうんですか？

博士：ダメなのは、インスタンス側から始める通信だ。許可した着信への応答は、ステートフルなので返る。

ノード：そっか、SGはステートフルでしたね。

博士：外向きの通信が必要なら、egressブロックを明示的に書く。こうだ。

```hcl
egress {
  from_port   = 0
  to_port     = 0
  protocol    = "-1"
  cidr_blocks = ["0.0.0.0/0"]
}
```

ノード：`protocol = "-1"` って、マイナス1ですか？

博士：「すべてのプロトコル」という意味だ。このとき、ポートの指定は0〜0にする。

ノード：なるほど。from_port も to_port も 0 なのは、そういうことなんですね。

### 発展：アドレスを変えると、作り直しになる

博士：ここは発展の話だ。今は読み飛ばしてもかまわない。

ノード：せっかくなので、聞きたいです！

博士：うむ、その意気だ。`aws_vpc.main` をモジュールへ移して `module.network.aws_vpc.this` にするなど、アドレスだけを変えることがある。

ノード：中身は同じで、住所だけ変わるんですね。それなら何も起きないですよね？

博士：ところが、Terraformはこれを「古いアドレスを削除し、新しいアドレスを作成する」と解釈するのだ。

ノード：えぇっ、VPCが作り直しに…。

博士：実物を作り直さずにアドレスだけを変えるには、`moved` ブロック（Terraform 1.1以降）や `terraform state mv` を使う。

ノード：住所変更の届けを出すようなものですね。

博士：うまいことを言うな。ただし、このシミュレータでは次のとおりだ。

> シミュレータでの簡略化: `moved` ブロック・`import` ブロック・`terraform state mv` には対応していません。アドレスを変えると作り直しになります。既存リソースの取り込みには `terraform import` コマンドを使います。

ノード：シミュレータでは、アドレスを変えると作り直しになる。既存リソースの取り込みは、`terraform import` コマンドを使うんですね。

### よくある誤解

博士：さて、よくある誤解を確認しておこう。ノード君、Terraformのリソースは、どんな順番で作られる？

ノード：ファイルに書いた順番に作られる、ですよね？

博士：おっと、それがよくある誤解だ。順番は参照、つまり依存関係で決まる。依存のないものは並行して作られるのだ。

ノード：あ、そうでした。書いた順番は関係ないんでした。

博士：では、planの `~` と `-/+` は？

ノード：どっちも同じ「変更」…じゃないんですよね。

博士：うむ。`-/+` は削除して作り直す。IDが変わり、参照している側にも波及する。

ノード：あと、`terraform import` すれば、コードもできあがる…。

博士：それも誤解だ。stateに対応を書き込むだけだ。resourceブロックは自分で書き、実物に合わせるのだ。

ノード：はい。気をつけます。

### 確認してみよう

博士：では、確認の問題だ。

1. planで `(known after apply)` と表示されるのは、どんな値ですか？
2. `# forces replacement` が付いた変更をapplyすると、何が起きますか？
3. リモートのstateをロックするのは、何を防ぐためですか？

ノード：1は、IDなど、リソースを作成するまで決まらない値です。

博士：正解だ。2は？

ノード：リソースを削除して作り直します。planでいう `-/+` です。

博士：うむ。では3は？

ノード：同時に2人がapplyして、stateが壊れることを防ぐため、です。

博士：全問正解だ。よく聞いていたな。

### このシミュレータで試せること

博士：このシミュレータで試せることは、次のとおりだ。

- `terraform init` → `fmt` → `validate` → `plan` → `apply`（yesで承認）→ `destroy` の流れ。`state list` / `state show` / `state rm`、`output`、`show`、`graph`、`import`、`force-unlock` も使えます。
- aws_vpc、aws_subnet、aws_internet_gateway、aws_nat_gateway、aws_route_table、aws_security_group、aws_instance、aws_lb などを書いてapplyすると、結果がVPC図に描かれ、到達性アナライザで通信経路を確認できます。
- `cidr_block` を変えて `-/+` と `# forces replacement` を観察する。`prevent_destroy` を付けて `destroy` がエラーになることを確かめる。
- driftやstateのロック、VPCの範囲外のCIDRを指定したサブネットによるAPIエラーを体験する。APIエラーではapplyが途中で止まり、作成済みのリソースはstateに残ります。

ノード：applyすると、VPC図に描かれて、到達性アナライザで通信経路まで確認できるんですね。

博士：うむ。APIエラーのときは、applyが途中で止まり、作成済みのリソースはstateに残る。そこも自分の目で確かめるといい。簡略化している点は、次のとおりだ。

> シミュレータでの簡略化:
> - 実際のTerraform CLIやAWSプロバイダではなく、ブラウザ内の教育用エンジンです。AWSの認証情報は不要で、実際のAWSには何も作られません。
> - HCLはサブセットです。for式、ヒアドキュメント、dynamicブロック、for_each、レジストリのモジュールは使えません（ローカルモジュールは使えます）。
> - driftやロックの競合、AWS APIのエラーは、シミュレートされたクラウドで再現しています。
> - EC2の `Role` / `Listen` タグは、インスタンスが何を待ち受けるかを伝えるシミュレータ独自の約束です。実際のAWSでは単なるタグです。

ノード：実際のAWSには何も作られないし、認証情報もいらないんですね。for_each などは使えないけど、ローカルモジュールは使える、と。

博士：そうだ。それから、EC2の `Role` / `Listen` タグはシミュレータ独自の約束で、実際のAWSでは単なるタグだ。そこは混同しないようにな。

#### 用語メモ

- **IaC**［Infrastructure as Code］：インフラのあるべき状態をコードに書き、レビュー・バージョン管理・再現を可能にする考え方。
- **HCL**［HashiCorp Configuration Language］：Terraformのコードを書くための、宣言的な言語。
- **アドレス**［address］：`aws_vpc.main` のような、Terraform内でリソースを指す住所。
- **暗黙の依存関係**［implicit dependency］：参照から決まる作成の順番。参照に表れない依存は `depends_on` で明示する。
- **state**：Terraformが、コード上のアドレスと実物の対応を記録したもの。既定のファイル名は `terraform.tfstate`。
- **リモートバックエンド**［remote backend］：S3など、stateを置く共有の保存先。
- **drift**：コンソールでの手作業などで、実環境がstateとずれること。
- **import**：既存のリソースを、Terraformの管理下に入れること。
- **置き換え**［replacement］：リソースを削除してから作り直す変更。planでは `-/+` で表される。

#### ノード君の今日のポイント

- IaCは、インフラのあるべき状態をコードに書き、レビュー・差分・再現を可能にする。
- Terraformは書いた順ではなく、参照から依存グラフを作って順番を決める。
- stateは、コードと実物の対応の記録。チームではリモートに置き、ロックする。
- コードの外での変更はdriftとして検出され、planはコードの状態へ戻す変更を提案する。
- applyの前にplanを読み、`-/+` と `# forces replacement` があれば、波及する範囲を確かめる。
