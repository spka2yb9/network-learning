# 教材の書き方（Theory と Simulation）

各章は **Theory（しくみを読む）→ Simulation（自分で組み立てて確かめる）** の2つのタブだけでできています。

- Theory: `src/content/<NN-章>/theory.md`。`## ` 見出しごとに1ページずつ表示します（`lessons/theory.ts`）。
- Simulation: `src/labs/simulations/<章>.ts`。ワークスペース（ネットワーク / AWS / Terraform）を埋め込み、ステップごとに状態を自動判定します（`labs/simulation.ts`、`components/Lab/SimulationSteps.tsx`）。

読者は **ジュニアエンジニア**（ネットワークは業務で触り始めたばかり）です。ここがこのサイトの肝なので、量よりも「わからない言葉が一つも残らない」ことを優先します。

---

## 1. Theory の構成

```text
## この章で学ぶこと        ← 1ページ目（固定の見出し）
## （本題のセクション）     ← 8〜14ページ
## （本題のセクション）
...
## この章のまとめ          ← 最終ページ（固定の見出し）
```

- 1ページ（`## ` から次の `## ` まで）は **4〜12分** で読める長さ（およそ2,000〜6,000字）。15分（7,500字）を超えるとテストで失敗します。長くなったら分けます。
- ページの中は `### ` で小見出しを付けます（右の目次から飛べます）。`####` は小見出しの中の補足にだけ使います。
- 章全体の目安は 30,000〜45,000字（以前の約2〜2.5倍）。
- **この章で学ぶこと**: この章が答える問い、読み終えるとできること（3〜5個）、前提（どの章の何を使うか）、この章でずっと使う「例のネットワーク」の図。Simulation で同じものを組み立てることも予告します。
- **本題の各セクションの最後**: `> **まとめ**` のコールアウト（2〜4項目の箇条書き）。テストで必須です。
- **この章のまとめ**: 章全体の振り返り（会話）、締めのあいさつ `path. ネットワーク講座でした〜♪`（1行・単独）、`#### ノード君の今日のポイント`（5〜8項目の箇条書き）、次の章の予告。用語集は用語カードから自動で作るので、手で書きません。

## 2. 会話の書き方

本文は **パス博士** と **ノード君** の会話です。段落の先頭に `博士：` / `ノード：`（全角コロン）を付けると吹き出しになります。

- 1段落に話者は1人。話者が変わるたびに空行を入れます。箇条書きの中に話者は置けません。
- 博士: 落ち着いた先生役。「〜だ」「〜なのだ」「うむ」「〜たまえ」「焦るでない」「いいところに気づいたな」。
- ノード君: 素直なジュニア。「〜ですか？」「え〜っと」「なるほど！」「〜ッスね」（ときどき）。
- 図・表・コマンド・コールアウトは会話の間に地の文として置けます（話者の接頭辞なし）。

### ノード君の役割（いちばん大事）

ノード君は **読者の代わりに質問する人** です。読者が引っかかるところで、必ず立ち止まって聞きます。

- 「〇〇って何ですか？」「なぜ〇〇が必要なんですか？」「〇〇と△△は何が違うんですか？」「それって、さっきの〇〇とどうつながるんですか？」
- ありがちな勘違いを口にして、博士に正してもらう（直後に `> **注意**` で整理するとよい）。
- 理解したことを **自分の言葉で言い換える**（具体例に当てはめてみる）。

やってはいけないこと:

- 表の行を順番に読み上げるだけの往復（「〇〇は△△で…」「その通り。□□は…」）。表は、説明が終わった後の **整理** として置きます。
- 「なるほど」「すごい」だけの相づちを続けること。

## 3. 解像度を上げるためのルール

**未定義語ゼロ。** 専門用語を使う前に、読者がそれを知っている状態にします。初めて出す言葉は、次のどれかです。

1. その場で説明し、**用語カード** を置く（下の書式）。
2. 前の章で学んだ言葉なら、最初に使うときに短く思い出させる: 「第1章で学んだ**MACアドレス**（NICごとに付いた番号）を思い出してほしい」。ホバーのヒントも自動で付きますが、本文だけで読めるようにします。
3. 後の章で扱う言葉なら、一言の平易な説明と行き先を書く: 「**NAT**（アドレスを書き換える仕組み。第6章で詳しく扱う）」。

**1つの吹き出しで新しい言葉は1つまで。** 新しい言葉を並べた表から始めない。

**概念は、この順で積み上げます。**

1. 困りごと（なぜ必要か。これがないと何が起きるか）
2. ひとことで言うと（定義）→ 用語カード
3. 具体例（実際の値: IPアドレス・ポート番号・MACアドレス・コマンドと出力）
4. しくみ（手順を1つずつ。図で）
5. たとえ（必要なら。たとえだけで終わらせず、どこまで当てはまるかも言う）
6. よくある誤解（`> **注意**`）

**例のネットワークを通しで使う。** 章の最初に決めた構成（機器名・アドレス）を最後まで使い、Simulation でも同じ構成を組み立てます。値は文書用のアドレス（`192.168.x.x`、`10.x.x.x`、`203.0.113.x`、`198.51.100.x`、`example.com` など）を使います。

**見せる。** パケットの流れは ` ```text ` の図で、ヘッダの値が1ホップごとにどう変わるかを表で。コマンドは実際の出力例（このシミュレータのCLIの表示に近いもの）と一緒に、どこを読むかを説明します。

**「なぜ」を書く。** 規則だけでなく、その規則がある理由と、守らないと何が起きるかを書きます。

**正確に。** 実機・標準と違う簡略化をしているところは `> **シミュレータ**` で明記します（`docs/simulation-scope.md` が根拠）。

## 4. コールアウトと用語カード

Markdown の引用（`>`）の1行目を太字のラベルで始めると、色付きの枠になります。使えるラベルはこれだけです（テストで確認）。

```markdown
> **用語：MACアドレス**（Media Access Control address）
> ネットワークの差し込み口（NIC）ごとに付けられた48ビットの番号。同じLANの中で「誰宛てか」を表す。例: `02:00:00:00:00:01`

> **ポイント**
> いちばん大事なこと。1〜3文。

> **注意**
> よくある誤解と、正しい理解。

> **現場では**
> 実務での使われ方・設計や運用の勘所。

> **発展**
> 読み飛ばしてもよい、一歩進んだ話。

> **シミュレータ**
> このシミュレータで簡略化していること。

> **まとめ**
>
> - 箇条書きで2〜4項目
```

用語カードのきまり:

- `> **用語：<用語>**` の後ろに、読み・英語の正式名を `（ ）` で書けます（省略可）。2行目以降の `>` 行が定義です。定義は **1〜3文**、その言葉を知らない人が読んでわかる言葉だけで書きます。例があれば付けます。
- `<用語>` は本文で実際に使う表記と同じにします（その表記で本文中を探してホバーのヒントを付けます）。`ARP` と `ARP要求` のように別の言葉として使うなら別のカードにします。
- 同じ章で同じ用語のカードは1枚。章で12枚以上（多くの章では25〜50枚）。前の章のカードと同じ用語を、その章の文脈で改めて説明したいときはカードを置いてかまいません。ヒントは、その章とそれより前の章のカードだけを使い、同じ用語ならその章のカードが優先です（例: DNSの章の「TTL」はキャッシュの有効期間。後の章の言葉は、前の章ではヒントになりません）。
- カードは、その言葉を会話で初めて説明した直後に置きます。

### 操作できる図解

Theoryには、全12章で計48個の図解があります。本文の対応する位置に、次のコードフェンスで埋め込みます。

````markdown
```theory-visual
encapsulation
```
````

- ID・タイトル・各ステップの説明は `src/components/TheoryVisual/visuals.ts` に定義します。追加例は `moreVisuals.ts` から同じ一覧へまとめています。未登録IDと使われていない図解は `src/lessons/visuals.test.ts` で検出します。
- 通信の順序にはシーケンス図、接続や経路にはSVGの構成図、カプセル化には入れ子の箱、サブネットにはビット・範囲表示を使います。図の値は本文の例と合わせ、別の簡略例を使うときは図の説明に明記します。
- 図にはタイトル、読み方、各ステップの説明を付けます。色だけで意味を伝えず、文字でも「採用」「不一致」などの判定を表示します。
- 状態の違いは `compare`（列見出しとステップごとの表）、帯域やMTUは `bars`（共通の尺度と内訳）で比較できます。棒の長さは値に比例させ、上限を超える場合は破線と文字で示します。グラフの障害箇所は `blockedNodes` / `blockedEdges` で明示します。
- 共通プレイヤーが再生・一時停止・前後移動・リセットと、説明を一覧で読む表示を提供します。自動再生はせず、画面外や別タブでは停止し、`prefers-reduced-motion` ではパケット移動を省きます。
- 各章の冒頭には、埋め込んだ図解のセクションへのリンクが自動で表示されます。セクション番号を別途管理する必要はありません。
- 検証は `npm test`、`npm run build`、`npx playwright test tests/e2e/theory-visuals.spec.ts`。ブラウザテストでは各ステップ、再生制御、計算結果と、対応最小幅1024pxでの表示を確認します。

## 5. Simulation の書き方

1章に1つ。`src/labs/simulations/<章>.ts` に書き、`src/labs/simulations/index.ts` の配列に章の順で加えます。手本は `routing.ts`（第3章）です。

```ts
export const xxxSimulation = networkSimulation({   // awsSimulation / terraformSimulation
  id: 'sim-<章id>', chapter: '<章id>', minutes: 30,
  title: '…（何を組み立てるか）',
  mission: '…（1文のゴール）',
  brief: '…（Markdown。開始時の状態と、完成形の図。Theoryのどの流れに沿うか）',
  build: () => …,            // 開始時の状態（毎回新しく作る）
  sim: [ { title, body, check?, solve?, quiz?, hints? }, … ],
  debrief: '…（完成後のひとこと。何ができるようになったか）',
});
```

- **ステップは6〜12個**。Theory で説明した順に、小さな変更を1つずつ積み上げます。各ステップのタイトルは「〜する」で終わる短い動作（例: 「R1に、LAN1側のアドレスを付ける」）。
- **body**（Markdown）: 何をするか → なぜか（Theory のどの話か）→ やり方（GUI と CLI の両方。CLIはコードブロック）→ 何が見えれば正しいか。会話文は使わず、短く。
- **check**: いまの状態がそのステップの完成形になっているか。判定はコマンド履歴ではなく **最終状態** です。毎回、状態の独立したコピーに対して呼ばれるので、`ping` などを実行してかまいません。
  - ネットワーク: 引数は `NetworkSimulator`。`net` ヘルパー（`labs/simulation.ts`）を使います。学習者は配線でポートを選ぶので、「eth0 が g0/0 につながっているか」ではなく `net.linked(n, 'PC1', 'R1')`・`net.address(n, 'R1', 'PC1')`（R1 の、PC1 側のポートのアドレス）のように **ポートに依存しない** 書き方にします。
  - 機器名: パレットから追加した機器は種類ごとに空いている最小の番号になります（PC1, PC2, R1, R2, SW1 …）。
  - AWS: 引数は `AwsModel` のコピー。Terraform: 引数は `TerraformWorkspace` のコピー（コードの編集だけでは再判定されず、validate / plan / apply などのコマンドを実行したときに再判定されます。body にそう書きます）。
- **solve**: そのステップの模範解答（`check` があるステップには必須）。前のステップの solve を適用した後の状態に適用されます。全ステップの solve が「完成形（解答例）」になります。
- **quiz**: 状態では判定できない「観察」（Debugger で何が見えたか、コマンドの出力のどこが変わったか）は、選択肢の問いにします（`{ question, options, answer, explanation }`）。`check` と併用すると、check を満たした後に問いが表示されます。
- **hints**: 詰まったときの段階的なヒント（任意）。

テスト（`npm test`、`src/labs/labs.test.ts`）が保証すること:

- 開始状態では、各ステップの check は **そのステップの solve を適用するまで成り立たない**（＝どのステップにも学習者の作業が要る）。前のステップの作業だけで次の check が通ってしまうなら、ステップを統合するか、観察（quiz）にします。
- solve を順に適用すると、それまでのステップの check はすべて成り立ち続ける。
- check のあるステップには solve がある。各ステップに check か quiz がある。

使える機能は、既存のラボ（`src/labs/*.ts`）・シナリオ（`src/simulator/scenarios/*.ts`）・CLI（`src/cli/ios.ts`、`src/cli/linux.ts`）・GUI（`src/components/TopologyEditor/properties/*.tsx`）が実際に対応しているものだけです。body に書くコマンドは、CLI が受け付けることを確かめてください。

## 7. 見本（1ページの一部）

````markdown
## 宛先が2種類あるのはなぜ？

博士：ノード君、PC1から隣の部屋のPC2にデータを送るとしよう。PC1は、どうやって「PC2宛てだ」と伝えると思う？

ノード：え〜っと、宛先を書くんですよね。住所みたいなものを。

博士：そうだ。ところがネットワークには、宛先の書き方が2種類ある。今日はまず、近い相手に使うほうから話そう。

### 同じLANの中の宛先：MACアドレス

博士：PCの裏には、LANケーブルを挿す口があるだろう。あの口の正体は **NIC** という部品だ。

> **用語：NIC**（Network Interface Card）
> 機器をネットワークにつなぐための部品。LANケーブルの差し込み口やWi-Fiの電波を扱う。ノートPCでは本体に組み込まれていることが多い。

ノード：NICって、カードなんですか？ 僕のノートPCには、カードなんて挿さってないですよ。

博士：昔は拡張カードとして後から挿していたので、その名前が残っているのだ。今は本体に組み込まれていることが多い。名前は気にしなくていい。「ネットワークの差し込み口」と覚えておきたまえ。

博士：そして、NICには一つひとつ、製造時に番号が付けられている。これが **MACアドレス** だ。

> **用語：MACアドレス**（Media Access Control address）
> NICごとに付けられた48ビットの番号。同じLANの中で「どの機器宛てか」を表す。16進数2桁を6つ並べて書く。例: `02:00:00:00:00:01`

ノード：48ビットって、どのくらいの大きさなんですか？

博士：2の48乗、およそ281兆通りだ。世界中のNICに別々の番号を配れる大きさだな。
````

ポイント:

- 新しい言葉（NIC → MACアドレス）を1つずつ、困りごと → 定義 → 具体例の順に出している。
- ノード君の質問は、読者が実際に引っかかるところ（「カード？」「48ビットってどのくらい？」）。
- 用語カードは、会話で初めて説明した直後に置いている。
